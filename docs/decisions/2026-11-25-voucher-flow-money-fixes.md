## 근거 (실측: 로컬 시험 환경 = 실제 라우트·cron + 라이브 구조 DB + 가짜 카드사·가짜 KT)
라이브 실측(2026-11-25): 교환권 발송 기록(`voucher_orders`) 0행, 승인 매장 13곳 중 계좌 등록 0곳, 수수료 구분을 스스로 바꾼 매장 0곳. **실제로 잘못 나간 돈은 0원.**
1. **발송된 교환권(기프티콘)이 환불됐다.** 손님이 딜로 교환권을 사면 KT 가 바로 문자로 보낸다. 그 뒤 ① '구매 취소' 를 누르면 딜이 전액 돌아왔고(시험: 4,500딜 환불 200) ② 유효기간이 지나면 만료 환불 cron 이 다시 딜로 돌려줬다. 기프티콘은 이미 손님 폰에 있다. 유어딜은 KT 에 원가를 내고 손님에게 값을 돌려주는 셈.
   뿌리 둘: 환불 경로가 "발송됐는가" 를 안 봤다. 그리고 발송 성공 때 주문 연결 키(`external_order_id = u{주문번호}-…`)를 KT 주문번호로 덮어써서 볼 방법도 없었다.
2. **사장님이 자기 수수료를 반으로 내릴 수 있었다.** `POST /api/seller/stores/:id/channel` 은 소유자 확인만 하고 값을 저장했다. 직접 입점(10%) 매장이 `brokered` 로 바꾸면 그 뒤 주문이 5%. 화면은 이 길을 안 부르지만 API 는 열려 있었다(시험: 200).
3. **사장님이 정산 계좌를 넣을 수 없었다.** 계좌 변경은 보안 PIN 이 필요한데, PIN 만들기가 "현재 비밀번호" 를 요구한다. `/store/new` 로 만든 매장은 비밀번호가 없다(카카오로 들어온다). 맞출 비밀번호가 없어 PIN 을 못 만들고, 계좌를 못 넣고, 지급이 막힌다. 라이브 승인 매장 13곳 중 12곳이 이 상태다.

시험 생략 판단: 실결제(staging)는 하지 않았다. 별도 시험 서버가 없고 카드 결제·실제 KT 발송은 세션이 할 수 없다. 대신 실제 코드를 라이브 구조 DB 위에서 끝까지 돌렸다(`voucher-full-flow-2026-11-25.test.ts` 39항목 · 되돌려-검증 8건 중 단일 되돌림 7건 + 이중 잠금 1건 빨강 확인). 진짜 KT 응답은 `S-VOUCHERLOCAL` 에 남겼다.

못 막는 것: KT 가 "발송 성공" 을 줬는데 문자가 실제로 안 간 경우(통신사 실패)는 이제 손님이 스스로 환불받지 못한다. 그 건은 어드민이 KT 취소(`cancelCoupon`) 뒤 처리한다. KT 잔액은 2026-11-25 기준 8,380원이라 발송 자체가 거의 일어나지 않는다.
