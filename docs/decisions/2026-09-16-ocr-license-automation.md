# 서류 심사를 OCR 로 자동화할 것인가 — 그리고 어느 서류부터인가?

상태: approved
등급: C
역할: ops
올린 날: 2026-09-16
기한: 2026-09-23

## 질문

사업자등록증·영업신고증을 **OCR 로 읽어** 심사를 자동화할 것인가. 한다면 **어느 엔진**으로,
그리고 **어디까지 기계에 맡길 것인가**(추출만 / 자동 승인 / 자동 반려).

> 대표: *"영업신고증도 받고 OCR 하면 비용이 어떻게 나간다고 했지? AI 없이도 가능한 부분인가?"*
> → *"그래서? OCR 쓰는게 아무래도 운영 자동화에는 도움이 될 것 같은데? 사업자등록증 말고도
> 영업신고증도 말이야."*

## 🩸 먼저 정정 — 세션이 "기계로 불가능"이라고 보고했던 것

2026-09-16 오전 결재(`2026-09-16-store-fraud-defense-order.md` §🔴)에서 세션이
*"②(등록증과 대조)는 기계로는 불가능하다"* 고 적었다. **그 문장은 국세청 API 기준에서만 맞다.**
API 가 상호·주소를 안 준다는 실측은 사실이지만, 거기서 *"기계로 불가능"* 으로 넓힌 것이 오류다 —
**종이를 읽으면 된다.** 당근이 보내 준 화면(상호·주소가 이미 채워진 "정보를 확인해 주세요")이
정확히 그 OCR 결과다.

## 근거 (실측 2026-09-16)

### 🔑 두 서류는 성격이 완전히 다르다 — **대조할 원장이 있느냐**

| | 대조할 공개 원장 | OCR 뒤 가능한 것 |
|---|---|---|
| 사업자등록증 | **없다** (국세청은 `valid`·`b_stt` 둘만 준다) | 사람 눈을 돕는 **보조** |
| **영업신고증** | **있다 — 우리 DB 에 269,708건** | 추출값 ↔ 원장 **기계 대조 = 자동 판정** |

`localdata-collect.ts`(지방행정 인허가정보, 2026-07-22 배선)가 **일반음식점·휴게음식점·미용업·
숙박업** 넷을 매일 받아 `store_prospects` 에 쌓는다. 실측: **269,708행(영업 중 269,581)**,
키는 `opnSvcId + opnSfTeamCode + mgtNo`, 필드는 상호(`bplcnm`)·지번/도로명 주소·영업상태
(`trdstategbn`)·인허가일.

⇒ **영업신고증 OCR 은 위조까지 잡는다.** 사진에서 뽑은 상호·주소·관리번호가 공개 원장에
실재하고 *영업 중* 이어야 하기 때문이다. 이것이 오전 결재가 지목한 구멍
(사기꾼이 **자기 진짜 등록증** + 남의 가게 이름)을 정면으로 막는 유일한 무료 수단이다.

### 코드는 이미 있고 — **한 번도 돈 적이 없다**

- `src/worker/utils/ocr-business-registration.ts` + `POST /api/seller/business-registration/ocr-verify`
  (2026-05-27 작성). Cloudflare Workers AI 비전 모델(`@cf/meta/llama-3.2-11b-vision-instruct`) 호출.
- 그런데 실측: `wrangler.toml` 에 `[[ai]]` 바인딩 **없음** · `Env` 타입에 `AI` **없음** ·
  **부르는 화면 0개**. 전형적인 *"코드에 있다 ≠ 살아 있다"*.

### 공공데이터로 사업자등록증을 대신할 수 있나 — **없다** (재 봤다)

- 사업자번호를 가진 수집분 **359,066건은 전부 통신판매업 신고**(온라인 판매업자).
  이름에 식당·돈까스·국밥·카페가 든 것은 **723건(0.2%)** — 동네 매장 대조엔 못 쓴다.
- 상가정보(34,193)·지역(16,746)은 상호·주소는 있으나 **사업자번호가 0건**이라
  "이 번호의 주인이 이 가게" 를 못 잇는다. 게다가 키워드로 모은 영업 리드라 전수도 아니다.

### 비용

건당 1회, 가입 1건당 2장(등록증 + 영업신고증). 하루 10건이면 **20콜**.
⚠️ **단가는 이 환경에서 확인 못 했다** — Cloudflare·네이버 요금 페이지가 프록시에 막혀 있다(403).
기억으로 적으면 틀리므로 비워 둔다. 다만 규모가 이 수준이면 **사람 심사 1건의 시간**과
비교가 안 된다는 것이 판단의 실질이다.

## 선택지

1. **Workers AI 로 먼저 실측 (권고)** — 키 발급 불필요, 대시보드 바인딩 1스텝, 무료 한도 안.
   등록증·신고증 10장씩 돌려 **필드별 정확도**를 잰 뒤 다음을 정한다.
   단점: 한글 서류 정확도 미검증(그래서 재는 것이다).
2. **네이버 클로바 OCR 바로 도입** — 사업자등록증 **전용 템플릿**이 있어 정확도 최상.
   단점: 키 + 과금 + 계약이 먼저 필요하고, 정확도가 문제가 아닐 수도 있는데 값부터 치른다.
3. **안 한다** — 어드민이 계속 눈으로 대조. 단점: 승인 대기열이 사람 손에 묶이고,
   위조 사진은 **원장 대조 없이는 영영 못 잡는다**.

## 기본안 (답이 없을 때 권하는 것 — 자동 실행되지 않는다)

안 1. 비용 0 · 되돌리기 1스텝 · 교체 비용 낮음(호출부가 `ocrBusinessRegistration` 한 함수).

## 🚧 양보하지 않는 안전 레일 둘

1. **자동 승인은 게이트 뒤**(기본 OFF). `fee-resolver`·쇼핑 원장과 같은 **그림자 → 권위 2단**:
   1단계는 추출값을 어드민 화면에 **입력값과 나란히** 띄우기만 한다(사람이 1초에 대조).
2. **자동 반려는 하지 않는다.** 틀린 반려는 정상 사장님을 쫓아내고 되돌릴 방법이 없다.
   사유 **제안**까지만 하고 버튼은 사람이 누른다.

## 🩸 이 결재의 근거 하나가 실측에서 뒤집혔다 (착수하며 발견 — 정정)

문서 §근거가 *"영업신고증을 대조할 공개 원장이 우리 DB 에 269,708건"* 이라고 적었다.
**틀렸다.** 라이브(`ads-leads` D1)를 재 보니 그 숫자의 대부분이 인허가 원장이 아니다:

| `opn_svc_id` | 건수 | 정체 |
|---|---|---|
| `neis_academy` | 139,477 | 학원 — 유어딜 업종 아님 |
| **`kakao_place`** | **96,832** | **카카오 플레이스 스크랩** — `mgt_no` 가 장소 ID, 인허가일 없음 |
| `hira_hospital` | 26,809 | 병원(심평원) |
| **`general_restaurants` + `rest_cafes`** | **6,590** | ← **진짜 인허가 원장(localdata)** |

그 6,590건은 품질이 완벽하다(`mgt_no` = `3000000-101-2026-00229` · 인허가일 100% · 영업상태 100%).
다만 **하루 300건씩 신규 인허가만** 들어와 전국 음식점 대비 1% 미만이다.

⇒ **원장 대조는 "걸리면 강한 양성, 안 걸리면 무신호"** 다. 주력이 될 수 없고,
문서가 약속한 *"영업신고증 OCR 은 위조까지 잡는다"* 는 **오늘 그대로는 성립하지 않는다.**

### 그래서 주력을 바꿨다 — 원장이 필요 없는 대조

**서류에 박힌 소재지 ↔ 사장님이 카카오맵에서 고른 매장 주소.**
매장 주소는 이미 우리가 갖고 있고 **커버리지 100%** 다. 결재가 지목한 구멍
(*"사기꾼이 자기 진짜 등록증 + 남의 가게 이름"*)은 서류 소재지가 등록한 가게와 다른 순간 드러난다.
원장 대조는 **보너스**로 남긴다(걸리면 싣고, 없으면 "이상 신호가 아님"이라고 화면이 분명히 말한다).

**실측 뒷받침**: 원장 주소 500건에 파서를 돌려 시군구·도로명·건물번호 **500/500(100%) 해독**.
⚠️ 이건 원장·카카오맵 쪽 주소의 해독률이다 — **OCR 이 사진에서 뽑은 주소**가 얼마나 지저분할지는
실제 사진을 돌려 봐야 한다(배포 후 판정 항목).

## 🚨 착수하며 발견한 것 — 죽은 코드가 안전 레일을 어기고 있었다

`seller-profile.routes.ts` 의 `ocr-verify` 는 추출값이 맞으면 **게이트 없이**
`UPDATE sellers SET business_registration_status='verified'` 를 때렸다(2026-05-27 작성).
AI 바인딩이 없어 한 번도 안 돌았을 뿐, **바인딩이 켜진 2026-09-16 그 순간부터 살아난다.**
게다가 그 비교는 대조 대상이 *사장님이 직접 타이핑한 값* 이라 남의 가게 이름 위조를 못 잡는다.
⇒ `isOcrAutoVerifyEnabled`(`platform_settings.ocr_auto_verify_enabled`, **기본 OFF**) 뒤로 넣었다.
