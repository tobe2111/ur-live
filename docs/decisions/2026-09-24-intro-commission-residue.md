## 1. 영입 커미션 — ✅ 코드 정리 완료

### 🩸 먼저 정정: 내가 "켜져 있다"고 보고한 것이 틀렸다

대표에게 *"`influencer_store_intro_pct` 2 → 0 으로 끄면 됩니다"* 라고 보고했다. **이미 꺼져 있었다.**

| 실측 | |
|---|---|
| `creditInfluencerStoreIntroCommission` 호출부 | **0개** |
| `CommissionAxis` 에 `store_intro` | 없음(2026-08-31 제거) |
| 라이브 `influencer_attributions` | 0건 |

나는 `platform_settings` 값이 `'2'` 인 것만 보고 단정했다. **그리고 같은 오판이 2026-09-15 에도
있었다** — `store-intro-abolished-2026-09-16.test.ts` 머리말이 그 사건을 기록해 뒀고,
대표가 그때도 *"그런거 없어"* 로 바로잡아야 했다. 나는 그 기록을 읽지 않은 채 같은 실수를 반복했다.

🧭 **교훈: 머니 경로의 "켜져 있나"는 설정값이 아니라 호출부로 판정한다.** 설정은 아무도 안 읽으면
그냥 남은 문자열이다. `grep` 한 줄이면 됐다.

### 그래도 고칠 것이 있었다 — 잔재가 사람을 속이고 있었다

오판의 원인은 사람이 아니라 남아 있던 잔재다. 09-16 정리는 React 화면 셋(`EarnLadder`·인플루언서
약관·정산 페이지)만 고쳤고 **아래 셋을 놓쳤다**:

| 잔재 | 무엇이 문제였나 | 처치 |
|---|---|---|
| `COMMISSION_DEFAULTS.INFLUENCER_STORE_INTRO_PCT = 2.0` | 어드민 화면·자동 생성 운영백서가 이 상수를 읽어 **"2.0"을 표시** — 두 세션이 이걸 보고 오판했다 | **0** |
| 셀러 가이드 시드 | *"매출의 2% 를 1년간 드립니다"* 를 그대로 약속. **가이드는 재시드로만 바뀌므로** 시드를 안 고치면 라이브가 영영 옛 약속을 한다 | 중단 안내로 교체 + `GUIDE_SEED_VERSION` 34 → 35 |
| 어드민 운영백서 | *"매출의 2%, 1년"* | 중단 표기 |
| `getStoreIntroPct` 의 `pct > 0` | 0(= 끔)을 넣어도 폴백으로 되돌아감 — 끄는 스위치가 안 듣는다 | `pct >= 0` |

### 🔴 `platform_settings.influencer_store_intro_pct` 는 **일부러 안 건드린다**

09-16 결정을 승계한다 — 지우면 어드민 저장 payload 가 흔들리고, **값이 무엇이든 부를 코드가 없다.**
0 으로 바꾸는 것도 안 한다: 다음 사람이 "0이니까 2로 올리면 켜지겠네" 로 오해할 여지만 만든다.

## 2. 정산 레일 단일화 — ⏳ 대표 실행 대기

### 🔴 상황이 코드 주석과 다르다 (라이브 실측 2026-09-24)

`auto-settlement.ts` 주석은 2026-08-02 실측으로 *"`restaurant_settlements` 테이블 없음 ⇒ Rail A 는
단 한 행도 만든 적이 없다"* 고 적었다. **지금은 테이블이 있다.**

| | 2026-08-02 주석 | 2026-09-24 실측 |
|---|---|---|
| `restaurant_settlements` 테이블 | 없음 | **있음** |
| `vouchers.settlement_id` | 없음 | **있음** |
| Rail A 행 / 정산된 voucher | — | 0 / 0 |
| 원장 `voucher_used` / `payouts` | — | 0 / 0 |
| `settlement_skip_ledgered` | — | **키 없음(=OFF)** |

⇒ 누군가 어드민 정산 화면을 열어 `ensureSettlementTables()` 가 발동했다. 그 파일이 경고한
*"Rail A 는 화면 한 번으로 깨어난다"* 가 이미 일어났다. **cron 이 매일 03:00 KST 에 정상 진입한다.**

아직 사고는 없다(양쪽 0건). 하지만 **구조는 무장돼 있다** — 이용권이 처음 사용되는 순간부터
같은 매출이 두 레일에 쌓이고, 두 레일은 서로의 멱등 마커를 안 본다.

### 처방과 근거

`platform_settings.settlement_skip_ledgered = 'true'`

- Rail B(원장)는 **게이트 없이 상시 기록**한다(`recordVoucherUsedLedger`, voucher 사용 직후 waitUntil).
  즉 지급의 진실은 원장이고, Rail A 는 원장에 없는 것만 다루면 된다.
- **지금 켜면 즉시 변화 0** — skip 대상(원장 `voucher_used`)이 0건이다.
- 원장 기록이 실패한 voucher(merchant_id 0 등)는 skip 되지 않아 **Rail A 가 폴백**으로 남는다.
- ⚠️ 어드민 스위치 목록의 `turn_on_when` 은 *"그전엔 켜면 정산이 통째로 빠진다"* 고 경고하는데,
  그 전제(Rail A 가 유일한 지급 경로)는 **지금 사실이 아니다** — 지급은 Rail B 가 한다.

### 왜 내가 못 했나

세션 권한(auto mode)이 **프로덕션 공유 자원 쓰기**를 막았다. 우회하지 않았다.
⇒ 어드민 `/admin/platform-settings` → 머니 스위치 **⑨ 자동정산에서 원장 기록분 제외** → `true`.

## 3. 부가세 별도 — 설명 (대표 질문 *"3번은 무슨 말이야"*)

별도 파일: 이 문서 §3 은 채팅 설명으로 대체. 요약은 아래.

지금 수수료 5% 는 **부가세가 포함된 값**이다. 10,000원 매출에서 500원을 떼면 그 안에 부가세가
들어 있어 유어딜 실수입은 `500 ÷ 1.1 = 454원`. 대표가 말한 *"5% + VAT, 부가세 별도"* 는
**공급가액이 5%** 여야 한다는 뜻이고, 그러려면 `500 + 50 = 550원` 을 떼야 한다.

코드는 "매출 × 요율" 만 하므로 **요율을 1.1 배 하면 결과가 같다**: 5 → 5.5 · 10 → 11.
코드 변경 0, 설정 세 값(`platform_fee_pct_brokered` · `platform_fee_pct_direct` ·
`commission_rate_meal_voucher`)만 바꾸면 된다. ⚠️ 약관 문구와 **같은 시점에** 바꿔야 한다 —
요율만 올리면 약관이 "5%" 인 채 5.5% 를 떼는 게 되고, 문구만 고치면 반대가 된다.

**대기**: 세무사 질의 3건(Q3) 결과 — 우리가 부가세 과세사업자로서 수수료에 VAT 를 별도 청구하는
구조가 맞는지, 세금계산서 발행 주체·시점이 어떻게 되는지 확인 후 진행.
