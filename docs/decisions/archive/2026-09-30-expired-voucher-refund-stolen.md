## 근거 (실측 2026-09-30)

**두 cron 이 같은 행을 다투고, 이기는 쪽이 환불을 안 한다.**

| | 무엇을 하나 | 언제 도나 |
|---|---|---|
| 🅰️ `handleExpiredVoucherRefunds`<br>(`cron/auto-settlement.ts:281`) | `status='unused' AND expires_at < now` 를 찾아 → `expired` 로 바꾸고 → **환불 + 알림 + 커미션 회수** | **하루 1회** `0 18 * * *` |
| 🅱️ `scheduled-cleanup.ts:252` | 같은 조건을 **일괄 UPDATE** 로 `expired` 로 바꾸기만 한다. 환불·알림·회수 **없음** | **매시 :10**<br>(`scheduled.ts:220` `slotOpen({minute:10})`) |

🅱️ 가 매시간 돌고 🅰️ 는 하루 한 번이라, **만료된 이용권은 최대 23시간 먼저 🅱️ 에게 잡힌다.**
그 뒤 🅰️ 의 `WHERE status='unused'` 는 아무것도 못 찾는다 ⇒ 환불 0.

**에러가 안 난다.** 🅰️ 는 "이번엔 만료된 게 없었다"로 판단해 정상 종료하고,
하트비트도 `ok:true` 다(`cron_hb:expired-voucher-refund` = `2026-09-29T18:00:01Z ok:true`).
⇒ 실패가 아니라 **조용한 부재**다.

**라이브 증거 — 실제로 일어났다:**

| 항목 | 값 |
|---|---|
| 이용권 id=1 (`UR-UR66-YDAZ`, 주문 85) | `status='expired'` · `expires_at=2026-08-22T02:55Z` |
| 결제수단 / 금액 | `deal_points` / 1,800원 |
| `refund_status` | **null** |
| `orders.refunded_amount` | **0** |
| user 3 포인트 환불 내역 | **0건** (가장 최근 기록이 2026-09-17, 무관한 건) |
| 만료 알림 | **0건** |

🅱️ 의 hourly 티어가 `03:10Z` 에 잡았고 🅰️ 는 `18:00Z` 에 빈손이었다 — 시각이 정확히 맞는다.

**소비자에게 한 약속과 어긋난다.** 이용권 상세 화면이 *"토스로 3초 안전결제 · 미사용 시 100% 자동환불"*
이라고 적고 있다. 지금 구조로는 그 환불이 **구조적으로 불가능**하다.

**만료 표시를 하는 자리가 실은 셋이다** — 착수 시 함께 볼 것:
🅰️(환불함) · 🅱️(환불 안 함, 매시간) · 그리고 **사용 시도 경로**
(`group-buy-voucher.routes.ts:54`·`333` — 손님이 만료된 코드를 찍으면 그 자리에서 `expired` 로 바꾼다).
세 번째는 손님이 화면 앞에 있을 때만 도니까 이번 사고의 원인은 아니지만, 이 역시 환불을 안 한다.
⇒ "만료 표시는 환불하는 쪽만 한다" 를 택하면 세 번째도 🅰️ 로 위임해야 앞뒤가 맞는다.

**같이 죽는 것 두 개** — 🅰️ 안에 있어서 함께 못 돈다:
- 미수령 차감 정책(`pickup_unclaimed_policy_enabled`)의 `unclaimed_forfeit` 원장 기록
- 만료 이용권의 커미션 회수(`clawbackVoucherCommission`)

## 지금 손해는 0이지만 다음 손님부터는 아니다

만료된 이용권은 **1장**이고 그 주인은 user 3(대표 테스트 계정)이다. 즉 **실제 손님이 잃은 돈은 아직 없다.**
다만 이건 확률이 아니라 **구조**라서, 이용권을 산 손님이 안 쓰고 넘기는 **첫 사례에서 100% 재현된다.**

## 선택지

1. **🅱️ 에서 vouchers 만료 UPDATE 를 제거한다** — 만료 표시를 🅰️ 하나가 독점.
   장점: 한 줄 삭제, 가장 작다. 🅰️ 는 이미 CAS(`AND status='unused'`)로 이중환불을 막고 있다.
   단점: 만료 표시가 하루 1회로 늦어진다 — 만료된 이용권이 최대 24시간 `unused` 로 보인다.
   ✅ **돈이 새지는 않는다(확인됨)**: 사용 경로는 `status` 가 아니라 `expires_at` 자체를 본다
   (`group-buy-voucher.routes.ts:68` — `AND (expires_at IS NULL OR expires_at > datetime('now'))`).
   즉 표시가 늦어도 만료된 이용권은 **쓸 수 없다.**
   머니 접촉: **있음**(환불이 비로소 돈다 = 의도한 변화).
2. **🅱️ 를 그대로 두고 🅰️ 의 선택 조건을 넓힌다** — `status IN ('unused','expired') AND refund_status IS NULL`.
   장점: 만료 표시는 매시간 유지. **이미 놓친 과거분도 회수된다.**
   단점: 조건이 두 곳에 걸쳐 있어 다음 세션이 다시 어긋내기 쉽다. `refund_status` 가 환불 완료를
   실제로 기록하는지 먼저 확인해야 한다(지금 null 이라 미검증).
   머니 접촉: **있음** + **과거분 소급 환불**이 딸려 온다(1건, 1,800딜 · 대표 계정).
3. **아무것도 안 한다** — 첫 실손님 만료 때 수동 환불.
   단점: 사람이 알아채야 한다. 알림도 안 가므로 **알아챌 신호가 없다.**

### 날짜가 붙은 결과 — 2026-10-02 03:00 KST 에 1건이 실제로 환불된다

2번에는 결재문이 적어 둔 대로 **과거분 소급 환불**이 딸려 온다. 라이브 D1 실측(2026-10-01 01:38 UTC):

| id | code | status | refund_status | 만료 | 금액 | 주인 |
|---|---|---|---|---|---|---|
| 1 | `UR-UR66-YDAZ` | `expired` | **null** | 2026-08-22 | 1,800원 | user 3 (대표 테스트 계정) |
| 2 | `UR-LUBA-RCP5` | `unused` | null | **무기한** | 1,000원 | — (만료 없음 → 이 cron 대상 아님) |

환불 cron 은 `0 18 * * *`(= 03:00 KST)이고 배포가 09-30 19:14 UTC 였으므로 **첫 발화는
2026-10-01 18:00 UTC = 10-02 03:00 KST** 다. 그때 id=1 이 잡혀 1,800딜이 user 3 에게 들어간다.
**실손님 돈이 아니라 손해 0**이고, 오히려 *"미사용 시 100% 자동환불"* 약속이 처음으로 지켜지는 건이다.

### E4 판정 (10-02 03:00 KST 이후 — 다음 세션이 이걸 확인한다)

```sql
SELECT id, status, refund_status FROM vouchers WHERE id = 1;
-- 기대: status='expired', refund_status='refunded'
SELECT COUNT(*) FROM point_transactions WHERE user_id = 3 AND type = 'refund'
  AND created_at > '2026-10-01T18:00:00Z';       -- 기대: 1
SELECT COUNT(*) FROM notifications WHERE user_id = 3 AND type = 'refund'
  AND created_at > '2026-10-01T18:00:00Z';       -- 기대: 1
```
하트비트 `cron_hb:expired-voucher-refund` 가 `ok:true` 인 것만으로는 **판정이 안 된다** —
이 사고가 정확히 "초록 하트비트 + 환불 0" 이었다. 위 세 줄을 **값으로** 봐야 한다.

⚠️ `refund_status='failed'` 로 남으면 토스 취소 거부이고 `toss-refund-retry` cron 이 맡는다.
`refund_status='claimed'` 로 남아 있으면 **처리 중에 예외가 터져 결과를 못 적은 것**이므로
그때는 사람이 봐야 한다(아래 동반 수리 참조).

### 동반 수리 (같은 결정으로 함께 간다 — 머니 PR 에 묶는다)

선점(`claimed`)과 결과 기록 사이의 `await` 는 전부 try/catch 가 감싸고 있지만, **순수 함수
(`parsePickup`·`unclaimedRefundAmount`)가 던지면 결과 기록 줄에 도달하지 못한다.** 그 행은

조용한 부재**다. ⇒ 루프 몸통을 감싸 던져도 결과를 `failed` 로 남기고 크게 로그한다(금액 계산 불변).
