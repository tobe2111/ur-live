## 질문

## 근거 (실측)
- 점검 전문: `docs/handoff/2026-11-17-traffic-surge-readiness.md`
- 요금제 유료, D1 쓴 줄 하루 약 120만(월 포함분의 ~72%), 메인 DB 57.6MB.

## 선택지
1. **정산 이중 지급 위험 수리** (머니 · 정산) — `src/worker/cron/auto-settlement.ts` 가 한 가게의 이용권 100장 이상을
   한 번에 정산하면 `UPDATE … WHERE id IN (…)` 이 D1 바인딩 한도(100)를 넘어 실패한다. 정산행은 이미 만들어졌는데
   이용권엔 "정산됨" 표시가 안 붙어 **다음 날 같은 이용권이 또 정산**된다. 지금 이용권 전체 5장이라 피해 0.
   수리: 90개 묶음 + `DB.batch`(한 덩어리) + 실패 시 정산행 삭제. 단독 세션 + staging 확인.
2. **로그인 손님도 공용 캐시를 쓰게** (잠금 파일 `edge-cache.ts`) — 지금은 로그인 쿠키만 있으면 에지 캐시를 통째로
   비켜 유어샵(`/api/curator/:handle`, 10~12쿼리)·홈 숏폼·배너가 매번 DB 로 간다. 수리: 누구에게나 같은 응답은
   `publicCache` 로, 유어샵은 익명 응답을 캐시하고 주인만 DB. ⚠️ 잘못하면 개인 응답이 남에게 보인다 — 신중히.
3. **성능 표본 쓰기 줄이기** — 페이지 한 번에 측정 신호 ~10개, 그중 25% 를 KV 에 읽고-쓰기(뷰당 ~5쓰기).
   하루 10만 뷰면 KV 쓰기 ~55만/일, 같은 키에 몰려 초당 1회 한도로 유실. 수리: 세션 단위 표본(브라우저에서 5%) +
   한 번에 묶어 보내기, 또는 Workers Analytics Engine 으로. (9/2 대표 승인 25% 를 바꾸는 일이라 여쭙는다.)
4. **요청 제한 장치를 DB 밖으로** — `rate-limit.ts` 가 걸린 요청마다 미국 원본에 쓰기 1 + 읽기 1(지도 장소 검색·
   지역 판정·카카오 로그인 등 42개 GET 포함). 몰리면 그만큼 느려지고 쓰기 포함분을 먹는다. 수리: 이미 바인딩된
   `RATE_LIMITER` Durable Object 로 이전(로그인은 지금처럼 실패 시 차단 유지).
5. **알림 일괄 발송을 줄 세우기** — 공구 달성·팔로워 알림이 요청 안에서 사람마다 4~5번 외부 호출. 사람이 많으면
   뒤쪽 사람은 조용히 못 받는다. 수리: `notification_jobs` 표에 넣고 cron 이 나눠 보냄(대량 메일이 이미 이 방식).
