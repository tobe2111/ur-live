## 근거 (실측 — 로컬 시험 환경: 실제 라우트·cron + 라이브 구조 DB + 가짜 카드사)
라이브 숙박 예약 0건 · 숙소에 묶인 이용권 0장 → **실제로 잘못 나간 돈은 0원.** 아래는 전부 시험에서 재현했다.
1. **먼저 판매 숙박권은 살 수 없었다.** 예약 표(`stay_bookings`)의 `check_in_date` 가 라이브에서 NOT NULL 인데 코드가 NULL 을 넣어 예약 만들기가 500. 결제 전에 멈춘다(주문 행만 PENDING 으로 남는다). 2026-05 부터 있던 결함이고, 2026-11-24 에 먼저 판매를 기본으로 바꿨다.
2. **기한 지난 숙박권이 환불되지 않았다.** 숙소 결제 확정이 주문에 결제 수단(`orders.payment_method`)을 안 적어, 만료 환불 cron 이 카드·딜 어느 쪽으로도 못 보내고 '처리 없음' 으로 닫았다(다시 잡히지도 않는다). 2026-11-25 새벽 보고의 "이미 자동 환불된다" 는 코드만 읽고 한 말이었다.
3. **숙소 주문을 일반 주문 취소로 돌릴 수 있었다.** `POST /api/orders/:id/cancel` 은 숙소 주문을 안 가렸다 → ① 확정된 날짜 예약을 취소 규정 없이 전액 환불(예약은 확정인 채, 방도 잡힌 채) ② 50% 환불받은 예약의 나머지 50% 요청 ③ 전액 환불된 주문에 다시 전액 취소 요청. `POST /api/orders/refund` 한 곳만 2026-11-18 에 막혀 있었다.
4. **숙소 취소 환불액이 주문 장부에 안 적혔다**(`orders.refunded_amount` 0 · 주문 PAID 그대로) — 3번이 가능했던 뿌리. 그리고 기한이 지난 숙박권을 손님이 취소하면 환불 0원으로 닫히고 이용권이 '환불됨' 으로 바뀌어 만료 환불도 못 받았다.
5. **에이전시가 숙박을 올리면 반쪽 상품이 남았다.** 에이전시 좌석으로 상품은 만들어지는데 숙소 정보·객실 저장이 막혀(권한 목록에 숙박 경로가 없었다) 손님 화면에 "객실 없음".
