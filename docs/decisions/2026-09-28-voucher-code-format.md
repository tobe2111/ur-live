# 이용권 코드를 6자리 숫자로 바꿀까

상태: approved
등급: C
역할: dev
올린 날: 2026-09-28
기한: 2026-10-05

## 질문

계산대에서 읽고 치기 어려운 `UR-XXXX-XXXX`(8자 영숫자)를 **6자리 숫자**로 바꿀까?

## 근거 (실측)

대표: *"지금 코드 형태가 너무 복잡해 `39AW-7K9A` 이런식인데 4~6자리 숫자로만 되도록 해줘."*

- 지금: `generateVoucherCode()`(`features/group-buy/api/helpers.ts:280`) = `UR-` + 8자,
  알파벳 32종(`ABCDEFGHJKLMNPQRSTUVWXYZ23456789` — 혼동 문자 `I`·`O`·`0`·`1` 제외) → **32^8 ≈ 1.1조**
- 소각 경로: `POST /api/group-buy/:code/use-by-seller`
  (`group-buy-voucher.routes.ts:317`) · `rateLimit({ max: 30, windowSec: 60 })`
- **코드 자체가 소각의 열쇠다** — 셀러 토큰(또는 `X-Scan-Device-Key`)만 있으면 코드로 바로 소각된다

### ⚠️ 길이를 줄이면 생기는 것 (계산)

| | 경우의 수 | 30회/분 기준 |
|---|---:|---|
| 현재 8자 영숫자 | 1.1조 | 사실상 불가 |
| **6자리 숫자** | 100만 | 미사용 이용권 1,000장이면 **약 30분**에 한 건 적중 |
| 4자리 숫자 | 1만 | **약 6시간**에 전수 탐색 |

🔴 단순 오입력 사고가 아니다. `payout_requires_voucher_use` 게이트가 있어서
**안 온 손님의 이용권을 태워 정산을 청구**하는 경로가 된다(머니 경로).

## 선택지

1. A — 영구 코드는 QR 에 두고, 지갑에 60~180초마다 바뀌는 6자리를 띄운다(추측이 무의미해진다)
2. B — 영구 코드를 6자리 숫자로. 요청 그대로, 위 위험 감수
3. C — 4자리 숫자
4. 안 함

## 기본안 (답이 없을 때 권하는 것 — 자동 실행되지 않는다)

1(A). 원하는 UX(짧은 숫자)를 그대로 주면서 추측 경로가 안 생긴다.

## 결정 (대표가 한 말 그대로)

> **"B로 해야지, 사장, 알바 등 헷갈린다. 저 영구 6자리는 변경 가능하게끔 하고."**

⇒ **B 채택.** A(회전 코드)를 기각한 이유는 보안이 아니라 **계산대 사람**이다 — 사장과 알바가
같은 이용권을 두고 서로 다른 숫자를 보면 "왜 아까랑 달라?" 가 된다. 매일 수십 번 쓰는 동작에서
그 혼란은 추측 위험보다 확실한 비용이다.

**추가 지시: 그 영구 6자리는 변경 가능해야 한다.** 유출·오남용이 의심되면 코드를 갈아 끼울 수 있어야
한다 — 영구 코드를 고른 대신 붙는 안전판이다.

### 그래서 구현이 반드시 함께 가져가야 하는 것 (B 를 안전하게 만드는 부분)

1. **코드 재발급** — 위 지시. 갈아 끼우면 옛 코드는 즉시 무효
2. **실패 시도 제한** — 지금 `max: 30/분` 은 *성공·실패 구분이 없다*. 100만 공간에서 이 값은
   위 표의 "30분" 을 만든다. 실패 연속 N회면 잠그는 방향이 함께 가야 한다
3. **가게 스코프 유지** — 지금도 좌석 토큰이 대상을 정한다(불변)

⚠️ **머니 경로다** — `CLAUDE.md` 룰대로 **단독 세션 + staging 실결제**로 진행한다.
기존 발급분 마이그레이션(옛 코드 유지 vs 일괄 재발급)도 그 세션에서 함께 정한다.

## 롤백

`generateVoucherCode()` 를 8자 영숫자로 환원. 단, **이미 6자리로 발급된 이용권은 그대로 남으므로**
검증 정규식은 둘 다 받아야 한다(환원해도 옛 발급분이 깨지지 않게).
