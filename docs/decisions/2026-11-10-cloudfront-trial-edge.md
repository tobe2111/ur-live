# 한국 손님의 첫 응답 1~3초(회선 몫 91%)를 줄이기 위해 CloudFront 시험 주소를 하나 열어 볼까?

상태: open
등급: C
역할: dev
올린 날: 2026-11-10
기한: 2026-11-17

## 질문
`urdeal.kr` 앞에 AWS CloudFront(서울 엣지)를 시험용 별도 주소로 하나 두고 한국 폰에서 첫 응답을 2주 비교해 볼까? (실서비스 도메인은 건드리지 않는다)

## 근거 (실측)
- 실사용 표본(어드민 `analytics/summary`, 2026-11-09, 표본 2~6건): 홈 첫 응답(TTFB) p50 **1,220ms** · p75 **1,545ms** 중 서버 몫(SRV) p50 68 · p75 112ms — **8~9%**. 앱 브라우저 준비(PRE) p50 3ms(1건만 347) · DNS 0~21ms · **연결(TCP) p75 1,774ms** · `/pass` 연결 **2,972ms**(서버 15ms).
- Cloudflare 가 한국 손님을 LAX(미국 서부)로 보낸다(`TTFB:colo:LAX` p50 1,325 · p75 2,758 · p95 9,257ms). 연결 왕복(TCP+TLS 2~3회)과 응답 거리 모두 그 경로 비용이다.
- 2026-11-09 결재(`2026-11-04-korea-icn-routing.md`): 대표 *"무료 유지 + 다듬기"* — Cloudflare 유료는 보류. 코드 쪽은 서버 몫 0.1초라 더 줄일 것이 거의 없다.
- CloudFront 는 서울(ICN) 엣지가 있고 무료 구간(월 1TB 전송·1천만 요청)이 있다. 다만 워커(API·서버 첫 화면)는 Cloudflare 에 남으므로 **정적 자원과 HTML 만** 앞단에서 받는 구조라, 동적 HTML 은 여전히 Cloudflare 를 거친다 — 효과는 캐시된 HTML·JS·CSS 에 한정된다.

## 추가 근거 (2026-11-11, 대표 *"지금도 문제가 있는 것 같은데 로딩이 느린듯 처음에"*)
- 실사용 표본(한국 IP만, `analytics/summary` 2026-11-11): 첫 응답 **홍콩(HKG) 연결 p50 166ms · p75 704ms (7건)** vs **LA(LAX) 연결 p50 1,625ms · p75 2,652ms (6건)**. 같은 날 같은 화면인데 연결된 데이터센터만으로 **10배** 차이다. 표본의 약 절반이 LAX 로 갔다.
- 같은 날 홈의 서버 몫(SRV) p50 213ms — 나머지는 회선이다.
- Cloudflare 무료 플랜에서 켤 수 있는 연결 단축 설정은 **이미 전부 켜져 있다**(API 읽기 실측: `0rtt` on · `http3` on · `tls_1_3` zrt · `early_hints` on · `brotli` on). 설정으로 더 줄일 곳이 없다.
- 재방문은 별개 처방이 있다: 앱 껍데기 캐시(shell-sw, 11/16 까지 관찰 중)가 켜진 화면은 두 번째 방문부터 HTML 왕복을 건너뛴다. **첫 방문**은 경로를 바꾸는 것 말고 방법이 없다.

## 선택지
1. **시험 주소(예: `edge-test.urdeal.kr`)만 CloudFront → `urdeal.kr` 원본으로 2주 측정.** 실서비스 무변경. 머니 접촉: AWS 계정 필요(무료 구간 안이면 0원, 초과 시 소액).
2. **하지 않는다** — Cloudflare 가 한국 경로를 고칠 때까지 대기. 머니 접촉 없음.
3. Cloudflare Enterprise 문의(기존 결재 선택지 2) — 월 수백만 원대.

## 기본안 (답이 없을 때 권하는 것 — 자동 실행되지 않는다)
2. 동적 HTML 은 어차피 Cloudflare 를 거쳐 효과가 정적 자원에 한정되고, 측정 표본이 아직 하루 2~6건이라 비교 자체가 어렵다. 월요일 RUM 표본이 쌓인 뒤 다시 본다.

## 롤백
시험 주소 DNS 삭제 + CloudFront 배포 삭제. 실서비스는 처음부터 무접촉.
