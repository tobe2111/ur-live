# 첫 정산 전에 토스 정산 설정 3건을 지금 손볼 것인가

상태: approved
등급: C
역할: finance
올린 날: 2026-09-21
기한: 2026-09-30

## 질문
대표가 보내 준 토스 정산 설정 화면에서, **첫 실매출이 나기 전에** 손봐야 하는 것이 셋이다.
Q1(한도 상향 신청) · Q2(가상계좌·계좌이체 차단) · Q3(정산계좌 명의 확인) 각각 진행할까?

## 근거 (실측 2026-09-21, 라이브 D1 + platform_settings)
- **payouts 0건** — 우리 쪽 정산이 한 번도 실행된 적 없다. 지금이 고칠 수 있는 마지막 시점.
- **매장 7곳 전부 `bank_account = NULL`** (실매장 홍대돈까스 id=14 포함) → payout 이 생겨도 보낼 계좌가 없다.
- 원장 잔액: `seller:14` 1,000원(fee 50) · `seller:null` 1,800원(오염 행) · `supplier:3` 10,000원.
  전부 최소출금액 10,000원 미만 → 아직 payout 미생성이 **정상 동작**.
- 게이트: `fee_channel_rates_enabled=true`(직접 10%/중개 5%) · `payout_requires_voucher_use=true`(사용 게이트 ON)
  · `settlement_skip_ledgered` 기본 OFF(이중레일 미수렴 — Rail A `restaurant_settlements` 현재 0건이라 아직 무해).
- **Q1** 토스 화면 `월 정산한도 10,000,000원`. 이용권 객단가 1~3만원 → **월 300~1,000건에서 천장**.
  한도 상향은 매출 실적 심사라 도달한 뒤 신청하면 그 달 초과분이 묶인다.
- **Q2** 화면상 가상계좌·계좌이체가 **에스크로 '사용'**, 정산 기준이 `구매확정일로부터 3일 후`.
  그런데 우리 코드에 **토스 에스크로 API 호출 0건**(`grep escrow src/worker/utils/toss-gateway.ts`),
  우리 '구매확정'은 **배송 주문 전용**(`orders.routes.ts:212` — 배송중 상태에서만 / 14일 자동확정).
  이용권·교환권은 배송이 없다 ⇒ 그 수단으로 팔리면 구매확정 신호를 줄 방법이 없다.
- **Q3** 화면 예금주 `정지원(리스터코퍼레…)`, 카카오뱅크 `3333-…`. 고객 결제대금이 들어오는 계좌다.
  2026-12-17 시행 개정 전금법은 **정산자금 전액 외부관리**를 요구한다(`docs/design/pg-cost-and-settlement-legal-2026.md` §4).

## 선택지
1. **셋 다 진행** — Q1 토스에 한도 상향 문의 / Q2 콘솔에서 가상계좌·계좌이체 OFF(카드·간편결제만) / Q3 계좌 명의 확인.
   머니 접촉: **없음**(우리 코드 무수정, 토스 콘솔 설정 + 확인 작업).
2. **Q2 만 진행** — 에스크로 구멍만 막고 한도는 도달하면 대응. 머니 접촉 없음.
3. **아무것도 안 함** — 첫 실매출에서 한도·에스크로 둘 중 하나를 현장에서 맞는다.

## 기본안 (답이 없을 때 권하는 것 — 자동 실행되지 않는다)
안 1. 셋 다 우리 코드를 안 건드리고, 지금 하면 10분이며, 나중에 하면 이미 판 돈이 묶인 뒤다.

## 롤백
Q1 신청 철회 · Q2 콘솔에서 두 수단 다시 ON · Q3 계좌 변경신청. 전부 토스 콘솔에서 즉시 되돌아간다.

## 함께 처리할 것 (대표 판단 불필요 — 실무)
- 매장 정산계좌 수집(현재 0곳). 이게 없으면 payout 이 만들어져도 `account_number=NULL` 이다.
- `seller:null` 오염 원장 1건 정리(`ledger.ts sellerLedgerAccount` 가 이미 재발은 막고 있다).

## 결정 (대표가 한 말 그대로)

**2026-09-24 대표:** *"지급대행으로 가지 않을거야. 지금은. 나중엔 변경할 수 있어. 나머지는 다 해줘."*

⇒ **안 1(셋 다 진행) 승인.** 지급대행 보류는 **별건**(`2026-09-21-settlement-structure-payouts.md` Q1)이고,
이 결재의 Q1~Q3 는 그것과 무관하게 전부 유효하다 — 오히려 **지급대행을 안 가기로 했으니 더 중요해진다**:
돈이 계속 우리 계좌를 거치므로 한도(Q1)에 우리가 직접 부딪히고, 에스크로 수단(Q2)의 구매확정 신호도
우리가 직접 맞아야 한다.

### ⚠️ 셋 다 **세션이 할 수 없는 일**이다 — 대표가 토스 콘솔에서 직접 누른다
세션에는 토스 상점관리자 접근이 없고(자격 없음), 있더라도 CLAUDE.md 는 플랫폼 쓰기를 세션 일이 아니라고
못 박는다. 그래서 이 결재의 실행은 **대표의 10분**이고, 세션이 한 일은 아래 절차를 클릭 단위로 적어 둔 것이다.
다음 세션이 이 파일을 열면 *"코드로 뭘 만들어야 하나"* 를 찾지 말 것 — **코드는 무수정이 정답이다.**

| | 어디서 | 무엇을 | 확인 |
|---|---|---|---|
| **Q1** | 토스페이먼츠 상점관리자 → 문의하기 | 월 정산한도 10,000,000원 **상향 신청**(사유: 이용권 객단가 1~3만원, 월 300~1,000건에서 천장) | 회신에 적힌 심사 조건·상향 한도 |
| **Q2** | 상점관리자 → 결제 → 결제수단 | **가상계좌·계좌이체 OFF**(카드·간편결제만 남긴다) | 결제창에 두 수단이 안 보이는지 |
| **Q3** | 상점관리자 → 정산 → 정산계좌 | 예금주가 **사업자 명의**인지 확인(화면상 `정지원(리스터코퍼레…)`) | 개인 명의면 사업자 명의로 변경신청 |

🔴 **Q2 를 못/안 끄기로 바뀌면 그건 새 결재다** — 그 수단으로 이용권이 팔리면 우리가 토스에 줄
'구매확정' 신호가 없다(에스크로 정산 기준이 `구매확정일 +3일`, 우리 구매확정은 배송 주문 전용).
코드로 막는 길(결제수단 제한)은 **잠금표 파일**(`TossPaymentWidget`·`TossWidgetPayPage`)을 건드리고
머니 경로라, 콘솔에서 끄는 것보다 비싸고 위험하다. 순서를 뒤집지 말 것.

### 함께 처리할 것의 상태 (2026-09-24 실측)
- **매장 정산계좌 수집** — 수집 **UI·API 는 이미 있다**(`seller-business-info/BankInfoSection.tsx` +
  `PATCH seller-profile.routes.ts`, 변경 시 알림까지). 비어 있는 것은 **데이터**이고 코드가 아니다
  ⇒ 개발 항목이 아니라 **운영 항목**(매장에 입력 요청). 지급대행을 안 가기로 한 지금 이게 **정산의 임계
  경로**다 — 계좌가 없으면 payout 이 생겨도 보낼 곳이 없다.
- `seller:null` 오염 원장 1건 — 재발은 `ledger.ts sellerLedgerAccount` 가 이미 막고 있다. 정리는
  일회성 SQL 이 아니라 코드 경로로(CLAUDE.md D1 읽기전용 룰).
