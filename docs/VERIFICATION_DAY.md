# 🧪 검증 데이 실행서 (반나절)

> 2026-08-12 작성. 대표가 **이 문서 하나만 열고** 반나절에 끝낼 수 있게 만든 실행 절차다.
> 절차의 근거·배경은 [`STAGING_CHECKLIST.md`](./STAGING_CHECKLIST.md) 에 있고, 이 문서는 **실행**만 담는다.
>
> **왜 필요한가**: 게이트 6개와 코드 경로 11건이 만들어진 지 한 달 넘게 **한 건도 검증되지 않았다**
> (완료 기록표가 비어 있다). 그래서 커미션 예산 아비터·쇼핑 원장·부분환불·미수령 정책이
> **전부 꺼진 채** 잠들어 있다. 실결제 없이는 켤 수 없고, 실결제는 대표만 할 수 있다.

## ⚠️ 먼저 알아야 할 것 — **staging 은 없다. 프로덕션에서 한다**

`STAGING_CHECKLIST` 는 "staging 배포 후 검증" 을 전제하고 `npm run deploy:staging` 스크립트도
있지만, **그 스크립트가 배포하려는 `ur-live-staging` Pages 프로젝트가 실재하지 않는다**
(2026-08-12 실측 — 계정의 Pages 프로젝트 7개 중 없음).

⇒ **검증은 프로덕션 실결제로 한다.** 그래서 이 실행서는 다음을 전제로 쓰였다:

- **결제한 것은 그 자리에서 환불**한다(P10 만 예외 — 다음날까지 둔다)
- **게이트는 켠 뒤 반드시 되돌린다.** 프로덕션 게이트는 라이브 사용자에게도 즉시 적용된다.
  현재 실주문이 88건뿐이라 위험은 낮지만, **켠 채로 잊으면 그게 곧 배포다.**
- 실패하면 **끄면 즉시 현행 복귀** — 되돌릴 수 없는 변경은 없다(전 게이트 공통 설계)

> 🔧 staging 을 진짜로 만들 생각이면 그건 별건이다(대표 판단). 없다고 검증을 미루면
> 게이트는 계속 잠들어 있는다 — 지금까지 한 달 넘게 그랬다.

## 🎛️ 게이트는 **어디서** 켜는가 (2026-08-12 신설 — 이전엔 켤 화면이 아예 없었다)

**`/admin/platform-settings` → `💸 커미션 예산 아비터 (INV-CB)` 섹션.** 드롭다운으로 ON/OFF 를 고르고
저장하면 끝이다. Cloudflare 대시보드를 만질 필요 **없다**.

| 검증 | 게이트 | 화면 라벨 |
|---|---|---|
| **P10** 미수령 | `pickup_unclaimed_policy_enabled` | ⑤ 미수령 환불 정책 (보관구분별) |
| **P11** 부분환불 | `partial_refund_enabled` | ⑥ 부분환불 금액 지정 |

> 🕳️ **왜 이 안내가 새로 생겼나**: 2026-08-12 실측에서 **그 토글이 어디에도 없었다.**
> `pickup_unclaimed_policy_enabled` 는 이 화면에 *"시스템 모니터링에서 켜라"* 는 **안내문만** 있었는데
> 그 화면은 **조회 전용**(쓰기 API 없음)이고, `partial_refund_enabled` 는 **어느 화면에도 없었다**.
> ⇒ 게이트가 한 달 넘게 꺼져 있던 이유의 일부는 "검증을 안 해서"가 아니라 **켤 방법이 없어서**였다.

⚠️ **P10 은 비율을 먼저 채워야 한다.** 같은 페이지의 **"운영 정책"** 섹션에서:
`냉장·냉동 미수령 환불(%)` = **0** · `실온 미수령 유예(일)` = **3** (2026-08-02 대표 확정값).
**비우면 100%(전액 환불)로 동작**해서 게이트를 켜도 아무것도 판정되지 않는다.

🛟 **되돌리기**: 같은 드롭다운을 OFF 로 바꾸고 저장하면 **즉시** 현행(전액 환불)으로 복귀한다.

### 🚨 사고가 나면 — 공구가 청구 킬스위치

같은 섹션에 **🚨 공구가 청구 킬스위치** 가 있다(기본 ON = 정상). 잘못된 공구가로 **과소청구**가
발생하면 이걸 **OFF** 로 내리면 즉시 상시가 청구로 되돌아간다. 되돌리면 곧바로 복구되니
사고 시 주저하지 말 것.

> 🕳️ 이 손잡이도 2026-08-12 에야 생겼다 — **그전에는 킬스위치가 코드에만 있고 당길 화면이 없었다.**

## 1. 준비물 — 테스트 상품 4개

**전부 셀러 화면 한 곳에서 만든다: `/seller/products/quick` (⚡ 빠른 공구 등록)**

이 화면 하나가 공구가·마감·픽업일·보관구분을 **함께** 받는다. 상품 등록 → 공구 열기를
따로 할 필요가 없다.

> 🔎 **왜 이 안내가 중요한가**: `STAGING_CHECKLIST` 의 준비물 표는 `pickup_storage=room`,
> `공구가` 를 **products 컬럼처럼** 적어 놨는데, 실제로는 **`product_supply_meta` 사이드테이블의
> K-V**(`pickup_storage` · `gb_price`)다(products 는 컬럼 예산제라 새 컬럼을 못 만든다).
> DB 를 직접 고치려 들면 막힌다 — **화면에서 넣으면 서버가 알아서 저장한다.**

| 상품 | 어떻게 만드나 | 무엇에 쓰나 |
|---|---|---|
| **A** | 공구가만 설정(픽업 비움) | P9 ① 공구 특가가 원장에 5%로 잡히는지 |
| **B** | 공구가 설정 + 기존 tiers 가 있는 상품에 | P9 ② **이중할인 안 나는지**(공구가 그대로여야 한다. 더 싸면 실패) |
| **C** | 공구가 + **픽업일** + **보관구분 `실온(room)`** + 상품의 `voucher_expiry` 를 **오늘**로 | P10 미수령 환불 |
| **D** | 아무 소액 상품 | P11 부분환불(반품용) |

⚠️ **C 의 만료일**: 만료를 기다릴 수 없으니 상품에서 **오늘로 당긴다.** 그래야 그날 밤
스윕이 그 건을 집는다.
⚠️ 서버가 강제하는 두 규칙이 있다 — **공구가 < 상시가**, **픽업일 ≥ 공구 마감**. 어기면 저장이 거부된다.

## 2. 한 번의 결제 방문에 하는 것 (결제 4건)

> 순서를 지켜라. P10 은 **결제만** 하고 판정은 다음날이다.

### ① P9 — 공구 특가 (A·B)

1. A 결제 → 즉시 **전액 환불**
2. B 결제 → 즉시 **전액 환불**

**판정**: 원장의 플랫폼 몫이 **결제액의 5%** 인가(상시가의 5% 가 아니다).
B 는 **공구가 그대로** 결제됐는가(tiers 가 얹혀 더 싸지면 이중할인 = 실패).

### ② P11 — 부분환불 (D)

**먼저 게이트를 켠다** → `/admin/platform-settings` → 커미션 예산 아비터 → **⑥ 부분환불 금액 지정 = ON** (위 §게이트 참조)

1. D 결제
2. 반품 신청 → 승인 → 검수 통과
3. **환불 금액을 결제액보다 작게** 저장
4. 환불 실행

**판정 4가지**
- Toss 취소액 = 내가 저장한 금액
- 딜이 섞여 있었다면 **비례** 복원
- 결제액보다 **큰 금액**을 넣으면 서버가 잘라낸다(안내가 뜬다)
- 환불 실행 **후엔** 금액 변경 시도가 400

⚠️ 게이트가 OFF 면 금액 설정 API 가 **403** 이다 — 그게 정상(현행 = 전액 환불).

### ③ P10 — 미수령 (C) · **결제까지만**

**먼저 게이트를 켠다** → `/admin/platform-settings` → **⑤ 미수령 환불 정책 = ON**.
⚠️ 같은 페이지 "운영 정책"의 비율(냉장 0 · 실온 유예 3)을 **먼저** 채울 것 — 비우면 전액 환불로 동작해 판정이 안 된다.

C 를 결제하고 **그날은 끝**. 찾아가지 않는다.

### ④ 이용권 공구 결제 수정 4건 — **게이트 없음. ①의 결제로 같이 판정된다**

2026-08-12 에 머지된 결제 경로 수정분이다(`docs/handoff/2026-08-12-urdeal-groupbuy-money-fixes.md`).
**셋 다 "에러가 아니라 부재"** 라 몇 달간 아무도 몰랐다 — 그래서 눈으로 확인하는 수밖에 없다.

| 무엇 | 어떻게 | 통과 기준 |
|---|---|---|
| **주문번호 일치** | ①의 카드 결제 후 | `orders.order_number` 가 **토스 콘솔의 주문번호와 문자열로 동일**. 지금까진 밀리초만 달라 **눈으로 구분이 안 됐고**, 그래서 토스 웹훅이 이 주문을 영영 못 찾았다 |
| **가상계좌 차단** | 가상계좌로 결제 시도 1회 | 이용권 **미발급** + `VIRTUAL_ACCOUNT_UNSUPPORTED` 안내 + 토스 콘솔에서 그 가상계좌가 **취소**됨. 취소 실패 시 어드민 벨 |
| **셀러 자기 공구 구매** | 셀러 본인 계정으로 자기 공구 구매 시도 | **403** `SELF_PARTICIPATION_BLOCKED`. 지금까진 **통과**했다 |
| **미달성 환불** | 미용/숙소 이용권 공구를 마감·미달성 상태로 | 셀러 환불 버튼이 **404 대신 동작** |

⚠️ 가상계좌는 **돈이 안 나가지만 계좌가 발급**된다 — 취소까지 확인해야 끝이다.

## 5. 같이 보면 좋은 것 — 로그인 후 화면

이번 AB 스윕(2026-08-11)은 **카카오 OAuth 를 자동화가 못 뚫어서 비로그인 화면만** 봤다.
"결함 9건 수정"은 **로그인 안 한 사람이 보는 화면 기준**이고, 그 뒤는 아직 아무도 안 봤다.

검증 데이엔 어차피 로그인 상태이니, 결제 사이사이에 **한 번씩만 열어 보면** 된다:

- **마이 / 주문내역 / 내 이용권** — 방금 산 것이 제대로 보이는가
- **장바구니 → 결제 진입** — 금액이 맞는가
- **링크샵 소유자 뷰**(`/u/{내 핸들}`) — ⚠️ **"내 가게인데 방문자로 보인다"가 반복 재발한 자리다**
  (편집 버튼이 안 보이면 그 사고의 재발)

이상한 게 보이면 **화면을 캡처만** 해 두면 된다. 원인은 다음 세션이 판다.
