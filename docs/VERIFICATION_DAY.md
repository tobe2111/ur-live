> `공구가` 를 **products 컬럼처럼** 적어 놨는데, 실제로는 **`product_supply_meta` 사이드테이블의
> K-V**(`pickup_storage` · `gb_price`)다(products 는 컬럼 예산제라 새 컬럼을 못 만든다).
> DB 를 직접 고치려 들면 막힌다 — **화면에서 넣으면 서버가 알아서 저장한다.**

| 상품 | 어떻게 만드나 | 무엇에 쓰나 |
|---|---|---|
| **A** | 공구가만 설정(픽업 비움) | P9 ① 공구 특가가 원장에 5%로 잡히는지 |
| **B** | 공구가 설정 + 기존 tiers 가 있는 상품에 | P9 ② **이중할인 안 나는지**(공구가 그대로여야 한다. 더 싸면 실패) |
| **C** | 공구가 + **픽업일** + **보관구분 `실온(room)`** + 상품의 `voucher_expiry` 를 **오늘**로 | P10 미수령 환불 |
| **D** | 아무 소액 상품 | P11 부분환불(반품용) |

⚠️ **C 의 만료일**: 만료를 기다릴 수 없으니 상품에서 **오늘로 당긴다.** 그래야 그날 밤
스윕이 그 건을 집는다.
⚠️ 서버가 강제하는 두 규칙이 있다 — **공구가 < 상시가**, **픽업일 ≥ 공구 마감**. 어기면 저장이 거부된다.

### B-2. 결제 4건

> 순서를 지켜라. P10 은 **결제만** 하고 판정은 다음날이다.

#### ① P9 — 공구 특가 (A·B)

1. A 결제 → 즉시 **전액 환불**
2. B 결제 → 즉시 **전액 환불**

**판정**: 원장의 플랫폼 몫이 **결제액의 5%** 인가(상시가의 5% 가 아니다).
B 는 **공구가 그대로** 결제됐는가(tiers 가 얹혀 더 싸지면 이중할인 = 실패).

#### ② P11 — 부분환불 (D)

**먼저 게이트를 켠다** → `/admin/platform-settings` → 커미션 예산 아비터 → **⑥ 부분환불 금액 지정 = ON** (위 §게이트 참조)

1. D 결제
2. 반품 신청 → 승인 → 검수 통과
3. **환불 금액을 결제액보다 작게** 저장
4. 환불 실행

**판정 4가지**
- Toss 취소액 = 내가 저장한 금액
- 딜이 섞여 있었다면 **비례** 복원
- 결제액보다 **큰 금액**을 넣으면 서버가 잘라낸다(안내가 뜬다)
- 환불 실행 **후엔** 금액 변경 시도가 400

⚠️ 게이트가 OFF 면 금액 설정 API 가 **403** 이다 — 그게 정상(현행 = 전액 환불).

#### ③ P10 — 미수령 (C) · **결제까지만**

**먼저 게이트를 켠다** → `/admin/platform-settings` → **⑤ 미수령 환불 정책 = ON**.
⚠️ 같은 페이지 "운영 정책"의 비율(냉장 0 · 실온 유예 3)을 **먼저** 채울 것 — 비우면 전액 환불로 동작해 판정이 안 된다.

C 를 결제하고 **그날은 끝**. 찾아가지 않는다.


### B-3. 다음날 아침 — 조회만

미수령 스윕은 **하루 한 번, 새벽 3시(KST)** 에 돈다.

**판정 5가지**
- 환불액이 설정한 비율인가(전액이 아니라)
- `ledger_entries` 에 `unclaimed_forfeit` **1행**
- 보관구분을 **안 정한 상품은 전액** 환불됐는가 (모르면 안 깎는다)
- cron 이 두 번 돌아도 **이중 환불 0**
- 🔴 **유어딜 5% 불변** — 플랫폼 몫이 그대로인가

⚠️ 게이트를 **꺼 두면** 전액 환불이 정상 동작이라 아무것도 판정되지 않는다. 켠 채로 밤을 넘겨야 한다.
