# 2026-08-29 — 유어애즈가 유어딜에 피해를 못 주게 하는 경계(가드) + D1 읽기 수리 판정

대표 지시: **"유어애즈 때문에 유어딜이 부정적인 영향을 받는 일이 없도록 해."**

## 1) 먼저 잰 것 — 실제 피해 경로가 어디인가

추측하지 않고 전부 실측했다. 결론부터: **오늘의 실제 피해는 작다. 문제는 그걸 지키는 장치가 없다는 것이었다.**

| 경로 | 실측 | 판정 |
|---|---|---|
| 유어애즈가 유어딜 **업무 테이블**(orders·products·sellers·users·payments)에 쓰기 | **0곳** | 안전 |
| 유어딜 DB 안에 남은 유어애즈 테이블 | 34개 / **565행** | 무시 가능 |
| `platform_settings` 부기 | 366행 중 **174행이 유어애즈** | 작음 |
| 유어딜 DB 쓰기 기여 | 정각마다 +290행 ≈ **2만행/일** (한도 10만) | 여유 |
| 유어딜 워커 cron 의 유어애즈 작업 | 1건 `outreach-email-drain`, 하트비트 **0ms**(큐 0건) | 지금은 무해 |
| 워커 요청 수 | ur-ads 443 · ur-live 416 /일 (계정 한도 10만) | 경쟁 없음 |
| 리드 읽기 | 별도 DB(ADS_DB·ADS_COMPANY_DB) | 분리됨 |

⚠️ **`src/features/supply/api/` 를 유어애즈로 착각하지 말 것.** 처음 스캔에 그 폴더를 넣었더니
`wholesale_orders`·`suppliers`·`distributor_grades` 가 "유어애즈가 유어딜 테이블에 쓴다"로 잡혔다.
그건 **도매몰(유통스타트)** 이고 유어애즈가 아니다. 유어애즈 = `src/features/marketing/api/**` + `src/worker-ads/**`.

## 2) 만든 것 — `check-ads-urdeal-isolation.mjs` (불변식 92번째)

**왜 문서가 아니라 가드인가**: 이 경계는 **이미 한 번 무너졌다.** 유어애즈 리드가 유어딜의 주문·결제와
같은 D1 파일에 쌓여 494 MB / 한도 500 MB(**99%**)까지 갔고, 그 의미는 *"한도에 닿으면 유어애즈만
멈추는 게 아니라 주문·결제 쓰기가 같이 죽는다 — 유어딜은 원인이 아니라 인질이었다"* 였다
(`leads-db.ts` 헤더). 2026-08-19 에 테이블은 옮겼지만 **지키는 장치는 없었다.**

- **R1** 유어애즈 코드가 유어딜 업무 테이블에 **쓰기 금지**(읽기는 허용 — 광고슬롯↔`sellers` 는 정당).
- **R2** 유어딜 DB 에 유어애즈 테이블을 **새로 만들지 않는다**(36개 동결, `ads-urdeal-shared-tables.json`).
- **R3** 유어애즈 작업을 **유어딜 워커 cron 에 새로 얹지 않는다**(1건 동결).

세 규칙 모두 **손으로 주입해 빨간불을 확인**했고, 주입 매니페스트 3건 등록(총 529) + 자체 테스트
`ads-urdeal-isolation.test.ts` 8건(그중 2건은 실제로 baseline 을 깨뜨려 실행 결과가 빨간불인지 본다).

### ⚠️ 이번에 가드 자체에서 틀린 것 (같은 함정 반복 방지)
`safeCron('bulk-email-drain', …); safeCron('outreach-email-drain', () => drainOutreachEmails(env))` 가
**한 줄에 나란히** 있어서, 함수명 주변 고정 창(200자)으로 이름을 붙였더니 **앞 작업의 이름을 뒤 함수에
붙였다** — 유어딜 작업인 `bulk-email-drain` 이 유어애즈 것으로 잡혔다. 각 `safeCron` 의 몸통을
**다음 `safeCron` 시작점까지**로 잘라 해결(`CRON_SPANS`). 테스트가 이 성질을 고정한다.

## 3) 남은 결합과 판단

- **부기(`platform_settings` ads_* 174행)가 아직 유어딜 DB 에 있다.** 옮기려면 테이블이 아니라
  **키 프리픽스로 라우팅**해야 해서(같은 테이블을 양쪽이 쓴다) `adsLeadsDb` 에 지연 라우팅이 필요하다.
  쓰기 사이트가 127곳이고, 커서를 잘못 라우팅하면 레인이 조용히 처음부터 다시 돌거나 두 번 처리한다.
  **지금 여유(2만/10만)를 보면 급하지 않다** → 별건. 늘어나는지는 `rowsWritten` 으로 본다.
- `outreach-email-drain` 은 큐가 비어 0ms 다. **커지면 ur-ads 로 옮길 것**(R3 이 그때 알려 준다).
