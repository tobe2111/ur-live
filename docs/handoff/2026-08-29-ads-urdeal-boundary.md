# 후속 (2026-08-30) — 대표 "3,4까지 해줘"

## ③-a 카카오 전화 스윕 재작성 — **완료**

`ROW_NUMBER() OVER (PARTITION BY source …)` 는 60건 뽑으려고 **전 대상의 등수를 다 매긴다**
(회당 1,654,670행 = 하루 3,970만). 인덱스로는 안 준다 — 창은 어차피 전량을 재료로 쓴다
(로컬 실측: 800ms → **453ms**, 여전히 전량 정렬).

⇒ **[소스별 상위 N] + [코드 인터리브]** 로 바꿨다. 등수는 배열 인덱스 그 자체라 계산이 필요 없다.
```
로컬 동일 분포:  800ms → 0.6ms   ·   뽑히는 60행이 **순서까지 동일**
라이브 대상 소스: commerce 309,988 · storeinfo 26,997 · local 368  (3개뿐)
```
- 대상 집합(`KAKAO_SWEEP_WHERE`)과 안쪽 정렬(`KAKAO_SWEEP_INNER_ORDER`)은 **한 글자도 안 건드렸다** — 세 번의 수리에서 계속 그렇다.
- **소스 목록을 코드에 박지 않았다**(`SELECT DISTINCT source`). 박으면 새 수집기의 소스가 영원히 굶는다 — 이 파일이 두 번 고친 사고가 정확히 그 모양이다. 인덱스 선두가 `source` 라 이 조회는 0.0ms.
- 서브리퀘스트가 1 → (1+소스수)=4 로 늘어난다. **호출부가 먼저 예산에서 뺀다** — 안 빼면 크롤 몫을 조용히 잠식한다.
- 소스 목록 조회 실패는 **빈 목록이 아니라 중단**이다(빈 목록으로 진행하면 "대상 없음"으로 조용히 기록된다).

**가드**: 유닛이 `node:sqlite` 로 **예전 창 함수와 새 방식의 결과를 직접 대조**한다(id 순서까지).
문자열이 아니라 동작을 본다 — 이 파일에서 문자열 가드는 두 번 다 사고를 못 막았다.
주입 3건 추가(총 539), 전부 되돌려-검증.

### ⚠️ 스윕 재작성이 남의 가드 3개를 낡게 만들었다 (CI 가 잡음)

이름 하나(`KAKAO_SWEEP_SQL`)를 없앴더니 **그 이름을 앵커로 쓰던 가드 3개가 조용히 "지키는 척"** 이 됐다.

| 어디 | 낡은 앵커 | 옮긴 곳 |
|---|---|---|
| `ads-cpu-work-cap-callsites` | `DB.prepare(KAKAO_SWEEP_SQL)` · `.bind(rowCap)` | 소스별 SELECT · `.bind(src, rowCap)` |
| 주입 `소스별 인터리브가 사라져…` | `ROW_NUMBER() OVER (PARTITION BY source` | `interleaveBySource` 의 등수 묶기 |
| 주입 `…다시 tier 순만 보고` | 여러 줄 SQL 정렬 키 | `KAKAO_SWEEP_INNER_ORDER` 상수 |

**세 건 다 계약은 그대로 두고 앵커만 옮겼다**(완화 0). 다만 두 가지를 배웠다:

1. **내 실수**: 바꾼 파일의 테스트만 돌리고 전체를 안 돌렸다. 이 가드들은 `company-collect.ts` 를
   *읽는 다른 파일*에 있어서 그 방식으로는 안 보인다. → **전체 vitest 를 돌려라**(520파일 6,609건).
2. **주입이 무력했던 것**: 인터리브를 `perSource.flat()` 으로 바꿔 심었는데 **뒤따르는
   `tie.sort(tier→id)` 가 작은 소스를 id 로 앞자리에 되돌려 놔** 테스트가 통과했다.
   `perSource[rank]`(소스 단위 통째)로 바꿔야 진짜로 인터리브가 사라진다.
   ⇒ *"결함을 심었다"가 아니라 "심은 결함이 관측 가능한가"를 확인해야 한다.*

**재사용할 기법** — 이름을 바꾸거나 지웠으면 매니페스트 전체 앵커를 한 번에 훑어라(전수 30분 대신 수 초):

→ 낡은 지도를 즉시 찾는다. 이번에 3건 중 1건은 이 스캔으로만 발견했다.
