## 1. 다음 세션의 첫 액션 — **조절기가 실제로 도는가**

```sql
SELECT value FROM platform_settings WHERE key = 'ads_cpu_quanta';
```

| 관측 | 뜻 |
|---|---|
| **행 없음** | 아직 CPU 사망이 없었거나 **감지가 안 걸렸다.** 하트비트에 `Worker exceeded CPU time limit` 이 있는데도 이 행이 없으면 → 감지 실패다(문구 변화 의심, `isCpuDeath` 확인) |
| `{"ads:collect-hira":{"q":0.5,"c":0}}` | ✅ 걸렸다. 그 레인이 죽어서 절반으로 줄었다 |
| `q` 가 `0.2`(바닥)에 붙어 있음 | ⚠️ **줄여도 계속 죽는다** = 근본 원인이 따로 있다. 기계는 여기까지다 — **사람이 그 레인을 봐야 한다** |
| 행이 사라짐 | ✅ 완전 회복(깨끗한 회차가 쌓여 1.0 복귀). 정상이다 |

⚠️ **대표께 보고할 판정은 이것 하나**: *"손으로 하던 조정이 자동으로 되기 시작했는가."*

## 2. 왜 만들었나 — 이미 있는 조절기에 이 신호만 안 물려 있었다

이 워커에는 자기교정 루프가 **둘** 있다: 서브리퀘스트 상한(`nextSubreqCap`)과 회차당 레인 수(`lane-aimd`).
**그런데 `Worker exceeded CPU time limit` 은 어느 쪽에도 안 들어간다.** 실행 기록에 문장 그대로
남는데 아무도 읽지 않았다. 그래서 08-04 에 사람이 손으로 줄였고(#1054·#1059), **그 손작업의 효과가
라이브로 확인됐다**(`ms=1,316` 사망 → `ms=5,681` 완주 · `run_ms 31,376 → 12,981`).
**효과가 확인된 손작업은 자동화 후보다.**

### 디스코드는 안 거친다
디스코드는 **내보내기 전용**이다(받으려면 봇이 필요). 그리고 **원본은 이미 D1 에 있다** —
08-04 의 모든 판정은 디스코드가 아니라 `cron_hb:*` 직독이었다. 복사본을 되받으려고 우회로를
만들 이유가 없다.

## 3. 무엇을 만들었나

```
레인이 CPU 로 죽음  →  그 레인의 작업량 배수 q 를 ×0.5   (바닥 0.2)
깨끗한 회차 3번     →  q += 0.1  (가산 — 배율이면 백오프와 맞물려 2주기 진동)
q 가 1.0 도달       →  표에서 제거 (표가 무한히 자라지 않게)
```

- **순수 로직**: `src/features/marketing/api/cpu-quantum.ts`
- **감지**: `beat-batch.ts` `learnCpuQuanta` — 하트비트를 **쓴 뒤에** 학습(fail-soft)
- **소비**: `reclassifyWorkPlan(env, DB)` — 학습값만큼 상한을 더 줄인다(바닥 50행/100행)
- **저장**: 단일 행 `ads_cpu_quanta`(`ads_lanes_learned` 와 같은 방식 — 레인마다 행을 만들지 않는다)

### 왜 감지가 저 한 곳인가
**CPU 로 죽은 레인은 자기 하트비트를 못 쓴다**(죽었으니까). 그 사망은 **항상 부모가** 기록하고,
부모 기록은 전부 `makeBeatWriter` 를 지난다. 감지 지점이 하나로 떨어진다.

### 💸 비용
평시(전부 성공, 표 비어 있음) **읽기 1 · 쓰기 0**. 표에는 **줄어든 레인만** 담고 `changed` 일 때만 쓴다.

## 4. ⚠️ 경계 — 값 조정만, 코드 수정은 아니다

08-04 의 수리 세 건은 전부 판단이 필요했다(상한을 어디에 걸지 · 커버리지가 보존되는지 · 어느 루프를
묶을지). 그리고 같은 날 **가드가 정상 코드에 네 번 빨간불**을 냈다 — 그때마다 *"이건 검사 범위
문제지 결함이 아니다"* 라는 판단이 필요했다. 자동이었다면 멀쩡한 코드를 고치려 들었을 것이다.

⇒ **이 모듈이 만지는 것은 이미 존재하는 상한의 배수 하나**이고, 바닥·천장이 있어 되돌릴 수 있다.

## 5. 이번에 잡은 무음 고장 (기록)

**`result` 는 문자열이 아니라 객체였다.** 첫 판을 `String(result)` 로 썼는데, `adsBeat` 은 실패를
`{ err, detail }` 객체로 싣는다 → `"[object Object]"` 와 비교하게 되어 **영영 아무것도 감지 못 하면서
에러도 안 나는** 상태가 될 뻔했다. **호출부를 읽고서야** 알았다(타입이 `unknown` 이라 컴파일러도 안 잡는다).

> 🧭 교훈: 새 감지기를 붙일 때 **신호의 실제 모양을 호출부에서 확인**하라. 문서·이름·타입이 아니라
> 값을 싣는 코드를 봐야 한다. 이 레포가 반복해 만난 "조용한 no-op" 의 가장 흔한 입구다.
