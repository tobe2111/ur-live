## 🐌 2026-09-17 후속 — 셀러 홈 "내 이용권" 이 늦게 뜨던 것 (PR 별건)

대표 *"내 이용권이 너무 늦게 떠. 로딩이 느려."*

### 실측이 뒤집은 것
처음엔 SQL 을 의심했는데 **DB 는 빠르다.** 라이브 D1 실행계획: `idx_products_seller_id` 를 타고
`order_items` 는 **79행**뿐이다. 대표 매장(seller 14)은 상품 1개다.

진짜 원인은 **데이터를 읽기 전에** 도는 스키마 보정이었다:

| | 왕복 | 라이브에서 |
|---|---|---|
| `ensureTables`(group-buy helpers) | ALTER **20** + 인덱스/테이블 6 | **20개 전부 이미 존재 → 전부 실패** |
| `ensureSupplyVisibilitySchema` | PRAGMA 1 + 조건부 ALTER + 7 | 이미 게이트가 있어 ALTER 0 |

`PRAGMA table_info(products)` 로 확인: **47개 ALTER 대상 컬럼이 전부 이미 있다.**
`ensureTables` 만 게이트가 없어 20개를 매번 직렬로 던지고 있었다. 에러가 없어 아무도 못 봤다.

⚠️ 메모이즈(`WeakSet` + 모듈 전역)는 **isolate 안에서만** 통한다. 저트래픽 대시보드는 거의 매번 콜드다.

### 고친 것
1. `ensureTables` — **같은 레포가 이미 쓰는 처방**(`supply-visibility.ts`)을 가져왔다: 컬럼 목록을
   한 번 읽고 **없는 것만** ALTER. 라이브 왕복 20 → 2.
   ⚠️ PRAGMA 실패·테이블 부재 시 **빈 집합 → 전부 시도**(종전 동작) — self-heal 이 약해지지 않는다.
2. 라우트가 두 보정을 **`Promise.all` 로 동시에 시작** — 왕복이 더해지던 것이 최댓값이 된다.

### 🩸 이번에도 로컬 `--changed` 가 잡았다
내 `Promise.all` 이 기존 가드 둘의 앵커를 옮겼다(`voucher-restore` 시험 1건 + 주입 1건).
**어제 배운 것을 바로 써서 푸시 전에 잡았다** — `--only` 로만 돌렸으면 또 CI 한 바퀴였다.
둘 다 **재조준**했다(불변식은 그대로 — 시험은 이제 *형태*가 아니라 *순서*를 본다).
