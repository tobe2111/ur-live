# CI 러너를 ubuntu-24.04 로 고정 — 내일(10-19) Ubuntu 26 이전이 필수 체크를 깨뜨린다 (2026-10-18)

## 무엇이 문제였나

GitHub Actions 주석(모든 잡에 붙는다): *"The ubuntu-latest label will migrate to Ubuntu 26 beginning
October 19, 2026."* 이 레포는 **잡 31개 전부** `ubuntu-latest` 였다.

설치된 Playwright **1.58.2** 는 Ubuntu 26 을 모른다 — 추론이 아니라 코드 경로로 확인했다:

```
lib/server/utils/hostPlatform.js   major >= 26 → hostPlatform = "ubuntu26.04-x64"
lib/server/registry/index.js       DOWNLOAD_PATHS.chromium["ubuntu26.04-x64"] → 없음
                                   DOWNLOAD_PATHS.chromium["<unknown>"]       → void 0
                                   → throw "ERROR: Playwright does not support chromium on ubuntu26.04-x64"
```

그 `npx playwright install --with-deps chromium` 이 **`verify.yml`(main 머지의 유일한 필수 체크)** 안에 있다.
브라우저를 까는 워크플로가 9개(그중 PR 게이트 7개).

🔴 **더 나쁜 점 — 점진 이전이다.** 26 에 떨어진 잡만 터지므로 같은 커밋이 어떤 날은 초록, 어떤 날은
빨강인 *"플레이크"* 로 보였을 것이다. 이 레포가 가장 오래 헤맨 모양이다.

## 바꾼 것

- `.github/workflows/*.yml` 30파일 31잡: `runs-on: ubuntu-latest` → **`ubuntu-24.04`**
  (= 오늘 `ubuntu-latest` 가 실제로 가리키는 이미지 ⇒ **오늘 동작 변화 0**). `macos-14` 1개는 무관.
- 가드 `src/tests/unit/ci-runner-pin-2026-10-18.test.ts` 4건 + 주입 3건(전부 빨간불 확인):
  지키는 것은 *"`-latest` 금지"* 와 **"브라우저 워크플로의 이미지 = 설치된 Playwright 가 Chromium 을
  받을 수 있는 이미지"** 다. 지원 목록은 손으로 적지 않고 **`playwright-core` 의 `DOWNLOAD_PATHS` 를
  읽어서** 만든다(`chromium` ∩ `chromium-headless-shell`). 그래서 26.04 로 올리는 날 Playwright 가 아직
  모르면 **Verify 가 아니라 이 시험이 먼저** 빨간불을 낸다.

## 이번에 틀렸던 판단

- 🩸 가드의 첫 판이 파일의 **첫 번째** `"chromium": {` 를 잡았는데 그건 **실행 파일 경로 표**(line 79)였고
  다운로드 표는 `const DOWNLOAD_PATHS` 아래(line 158)다 → 지원 목록 **0**. 바로 옆 *"비었으면 고장"* 단언이
  즉시 잡았다. **그 단언이 없었으면 이 가드는 영원히 빨간불이거나(지금) 영원히 헛돌았을 것이다.**

## 🔎 같은 조사에서 나온 별건 — SNS 마케팅 봇(#1866)은 기억을 저장할 수 없다 (대표 판단 필요)

`SNS comment replies` 가 **3번 돌아 3번 다 실패**(한 번도 성공 못 함). 봇 자체(`Run`)는 통과하고
**`Commit data` 단계만** 죽는다.

**원인**: 봇은 상태(`marketing-bot/data/posts.json` · `comments.json`)를 **main 에 직접 push** 해서 저장한다
(#1866 본문 *"게시 기록은 data/posts.json 등에 자동 커밋"*). 그런데 main 룰셋(`23392011`)이
`Verify` 필수 체크를 요구하고 **bypass 가 0** 이며, 봇 커밋은 `[skip ci]` 라 Verify 가 붙을 수도 없다
⇒ **그 push 는 원리상 한 번도 성공할 수 없다.** main 에 봇 데이터 커밋은 0건이다.

**지금 영향(실측)**: `posts.json` 이 `[]` 라 댓글 봇은 볼 게시물이 없어 **실제 답글 0**(실패 이유는
`comments.json` 을 예쁘게 다시 써서 diff 가 생긴 것뿐). 매일 게시는 오늘 슬롯이 **19:30 KST** 라
그때 **첫 실제 게시**가 나가고 — 그 기록이 저장되지 못한다.

**결과**:
1. 댓글 답글 기능이 **처음부터 죽어 있다**(게시물 목록을 못 받는다)
2. 주간 리뷰가 배울 데이터가 없어 "최적 시간대" 가 영영 안 정해진다(2주 순환 실험이 무의미)
3. 같은 날 중복 게시 방지(`postedToday`)가 없다 — cron 지연(오늘 09:00 cron 이 **2시간 늦게** 돌았다)으로
   두 회차가 같은 창에 들면 두 번 올라간다
4. 🔴 **함정**: 누가 `posts.json` 만 살리면(예: 손으로 커밋) 댓글 봇이 게시물은 보는데 `comments.json` 은
   여전히 못 저장 → **같은 고객 댓글에 2시간마다 다시 답글**. 지금 안 터지는 건 둘 다 죽어 있어서다.

**제안**(대표 결정 대기 — 다른 세션 소유 · 발행 표면):
- 상태를 **main 밖** 전용 브랜치(룰셋은 기본 브랜치만 대상)에 저장 — 단, 브랜치 push 마다 Cloudflare
  Pages 미리보기 빌드가 2개씩 돈다(하루 최대 24회 → 무료 한도 500/월 초과 위험). 대시보드에서 그 브랜치를
  제외해야 한다(대표만 가능).
- 또는 **저장소 없이 실물로 중복 판정**: 답글 전에 그 댓글의 답글 목록에 `urdeal_official` 이 있는지
  API 로 확인, 게시 전에 오늘 내 게시물이 있는지 API 로 확인. 저장이 깨져도 중복이 안 난다(가장 튼튼).
