## ③ 계산대 코드 직접 입력 — 답: **필요하다. 그런데 반쪽으로 동작하고 있었다**

### 왜 필요한가
카메라가 실패하는 경로가 셋이다 — 권한 거부 · 기기 카메라 없음(데스크톱 POS) ·
`BarcodeDetector`/`qr-scanner` 둘 다 실패. 손님 화면 파손·저조도도 있다.
그때 이 입력칸이 **유일한 통로**다. 손님 화면엔 QR 아래에 코드 글자(`UR-XXXX-XXXX`)가
그대로 보이므로(`QRModal.tsx:244`) 받아 칠 수 있다.

### 위험하지 않은가 — 아니다 (실측)
| | |
|---|---|
| 코드 엔트로피 | `UR-XXXX-XXXX`, crypto 난수, 32⁸ ≈ 1.1조 |
| 속도 제한 | `voucher_use_seller` 30회/분 |
| 소유권 | 본인 매장 바우처가 아니면 403 |
| 이중사용 | 원자 CAS (`WHERE status='unused'`) |

### 🩸 그런데 손으로 친 코드는 거의 항상 실패했다
- 발급 알파벳(`generateVoucherCode`)이 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` — **전부 대문자**.
- 서버 조회는 `WHERE code = ?` — SQLite 기본 BINARY 대조라 **대소문자를 가린다**.
- 입력칸엔 `autoCapitalize` 가 없어 **폰 키보드가 소문자로 시작**한다.

**라이브 D1 실측**: `vouchers` 전량 대문자(`upper_only = total`) · 같은 코드를 소문자로 조회 → **0건**.
⇒ 유효한 바우처인데 `404 "바우처를 찾을 수 없습니다"`. 카메라가 안 될 때 쓰라고 만든 폴백이,
정작 그 상황에서 절반은 실패하고 있었다. 그리고 **에러가 아니라 "없는 바우처"로 보이니**
사장님은 손님을 의심하게 된다.

**수정(클라이언트만)**: `extractCode` 가 공백 제거 + 대문자 정규화(QR 경로에도 무해·idempotent),
입력칸에 `autoCapitalize="characters"` / `autoCorrect="off"` / `spellCheck={false}`,
안내 문구에 형식 노출 — **6개 언어 전부**(로케일 값이 `defaultValue` 를 이긴다, CLAUDE.md 가 기록한 함정).
서버는 안 건드렸다 — 입력 정규화는 입력을 받는 쪽 몫이고, 서버 대조 규칙을 바꾸면
`/:code/use` 등 다른 경로까지 조용히 달라진다.
