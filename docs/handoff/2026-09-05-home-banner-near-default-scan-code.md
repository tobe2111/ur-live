## ① 상단 띠 배너 — 시안 안 2(가로 카드) 확정

시안 3안: https://claude.ai/code/artifact/615187f0-4699-4f9c-8d6f-4b4f214b9efc
(390px 폰 화면 실제 크기 · 안 1 한 줄 띠 40px / **안 2 가로 카드 76px** / 안 3 스와이프 96px+도트)

새 배너 자리 `strip` 을 SSOT(`home-showcase.ts`)에 추가하고 두 홈의 **첫 섹션 위**에 배선했다.
왼쪽 56×56 사진 + 제목 + 부제 + 화살표, 흰 카드에 `shadow-lift` — 아래 딜 카드와 같은 표면 언어다.
잉크 색면 띠(안 1)는 흰 카드가 이어지는 그 자리에서 이물감이 있었다.

- **PC 홈에도 넣었다.** 두 홈이 같은 섹션·같은 배너 자리를 쓰는데 한쪽만 반영하면
  이 레포가 이미 겪은 "한쪽만 개선되는" 상태가 된다(더보기 링크가 정확히 그랬다).
- **등록된 배너가 0장이면 아무것도 안 그린다** — 기존 규칙 그대로. 지금 라이브 배너는
  `banner_slot = NULL` 인 옛 배너 1장뿐이라 **배포 직후엔 화면이 지금과 똑같다.**

## 🩸 함께 드러난 결함 — 배너 규격 SSOT 두 개가 뒤바뀌어 있었다

`BANNER_SLOT_SPECS` 의 `inline`(3열)과 `wide`(가로 전체) **몸통이 서로 바뀐 채** 있었고,
렌더가 이름을 **엇갈려** 참조해(`inline` 렌더가 `SPECS.wide` 를) **사진 크기는 맞았다.**
그래서 몇 달간 증상이 없었다 — 대신 **어드민 안내 문구만 반대로** 나갔다:

| 자리 | 안내가 말하던 것 | 사실 |
|---|---|---|
| 중간 배너(3열) | "가로 전체 · 104px · 1600px 권장" | 3열 · 96px · 800px |
| 와이드(가로 전체) | "3열 그리드 · 96px · 800px 권장" | 가로 전체 · 104px · **1600px** |

가로 전체 배너를 올리는 사람은 "800 × 400 권장"을 보고 그대로 올렸고, 실제 필요 폭은 1,600px 이라
**그만큼 흐려졌다.** 이 상수 파일이 애초에 막으려던 사고(*"안내가 틀리면 사진 올리는 사람이 헛수고"*)가
이 파일 안에서 났다. 몸통을 제자리로 돌리고 렌더도 같은 이름을 참조하게 했다.

## ② 아래 딜 목록 기본 정렬 = 가까운 순

두 홈 모두 `readCachedLoc() && !readHomeRegion().regionKey ? 'near' : 'popular'`.

- **위치를 새로 묻지 않는다.** 지도 홈·위치바가 저장해 둔 마지막 측위(`ur_last_loc_v1`)만 읽는다.
  홈 진입에 권한 팝업을 띄우는 건 과하고, 거부하면 어차피 기존 동작으로 돌아온다.
  ⇒ 위치를 한 번이라도 잡은 사람은 **재방문부터** 첫 페인트가 '가까운 순', 아니면 지금과 동일.
- **지역을 직접 고른 사람은 제외.** 지역 필터와 거리순이 겹치면 무엇을 기준으로 걸러진 목록인지
  화면이 말할 수 없다(지도의 `useNearMeAuto` 와 같은 가드).
- **더보기는 인기순이 이긴다** — 라이브 `homepage_sections.more_href` 는 이미 `/?sort=popular` 였고,
  `useHomeQuerySync` 가 기본값 위를 덮는다. 이쪽은 **손댈 게 없었다**(실측으로 확인).

## ③ 계산대 코드 직접 입력 — 답: **필요하다. 그런데 반쪽으로 동작하고 있었다**

### 왜 필요한가
카메라가 실패하는 경로가 셋이다 — 권한 거부 · 기기 카메라 없음(데스크톱 POS) ·
`BarcodeDetector`/`qr-scanner` 둘 다 실패. 손님 화면 파손·저조도도 있다.
그때 이 입력칸이 **유일한 통로**다. 손님 화면엔 QR 아래에 코드 글자(`UR-XXXX-XXXX`)가
그대로 보이므로(`QRModal.tsx:244`) 받아 칠 수 있다.

### 위험하지 않은가 — 아니다 (실측)
| | |
|---|---|
| 코드 엔트로피 | `UR-XXXX-XXXX`, crypto 난수, 32⁸ ≈ 1.1조 |
| 속도 제한 | `voucher_use_seller` 30회/분 |
| 소유권 | 본인 매장 바우처가 아니면 403 |
| 이중사용 | 원자 CAS (`WHERE status='unused'`) |

### 🩸 그런데 손으로 친 코드는 거의 항상 실패했다
- 발급 알파벳(`generateVoucherCode`)이 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` — **전부 대문자**.
- 서버 조회는 `WHERE code = ?` — SQLite 기본 BINARY 대조라 **대소문자를 가린다**.
- 입력칸엔 `autoCapitalize` 가 없어 **폰 키보드가 소문자로 시작**한다.

**라이브 D1 실측**: `vouchers` 전량 대문자(`upper_only = total`) · 같은 코드를 소문자로 조회 → **0건**.
⇒ 유효한 바우처인데 `404 "바우처를 찾을 수 없습니다"`. 카메라가 안 될 때 쓰라고 만든 폴백이,
정작 그 상황에서 절반은 실패하고 있었다. 그리고 **에러가 아니라 "없는 바우처"로 보이니**
사장님은 손님을 의심하게 된다.

**수정(클라이언트만)**: `extractCode` 가 공백 제거 + 대문자 정규화(QR 경로에도 무해·idempotent),
입력칸에 `autoCapitalize="characters"` / `autoCorrect="off"` / `spellCheck={false}`,
안내 문구에 형식 노출 — **6개 언어 전부**(로케일 값이 `defaultValue` 를 이긴다, CLAUDE.md 가 기록한 함정).
서버는 안 건드렸다 — 입력 정규화는 입력을 받는 쪽 몫이고, 서버 대조 규칙을 바꾸면
`/:code/use` 등 다른 경로까지 조용히 달라진다.
