## 대표 지시 두 건이 "머지됐는데 실행된 적이 없었다" — 재추출 단계의 굶주림

> 대표 지시: *"카페 회원수는 반영이 안되고 있음(카운팅이 안됨)"* · *"정보 최대 수집"* ·
> *"응 계속해서 완료까지 해줘"*

### ❗ 이번에 배운 것 (먼저 읽어라)

**코드가 머지됐다 ≠ 그 코드가 돈 적 있다.** 07-29·08-01 에 지역 백필과 카페 회원수를
`reextract` 정비 단계에 배선하고 "완료"로 표시했는데, 라이브에서 **한 번도 실행된 적이 없었다.**

판정법(새 배포 없이): 어드민 `/api/admin/tools/settings` 의 `ads_maintenance_last` 를 본다.
`region`·`cafemembers` **키 자체가 없으면** 그 코드는 도달한 적이 없는 것이다.
(하트비트는 `err=Error` 만 말할 뿐 *어디까지 갔는지*는 말하지 않는다.)

### 🔎 원인 — 커서 저장 한 줄

```ts
.bind(CURSOR_KEY, String(done ? 0 : cursor))   // 다 훑으면 0 으로 되돌림
```
전수를 끝내면 커서가 0 이 되어 **매 회차가 36,880행을 처음부터 다시** 훑었다
(라이브 `scanned: 36,880 · filled: 0` — 저장 시점에 이미 추출하므로 재수확이 구조적으로 0).
그 CPU 로 인보케이션이 끝났고, **같은 단계에서 뒤에 서 있던** 지역·카페는 시작조차 못 했다.

`poolScanShouldStop` 은 이 함수 안에서만 멈출 뿐, **이미 쓴 CPU 를 되돌려주지 않는다** —
"상한이 있으니 괜찮다"는 잘못된 안심이었다.

### ✅ 수리 셋 (하나만으론 부족했다)

| # | 수리 | 왜 이것만으론 부족한가 |
|---|---|---|
| ① | 다 훑으면 커서를 **그 자리에 주차**(전수 재스캔은 `REEXTRACT_RULES_VERSION` bump 로만) | 순서가 그대로면 여전히 앞에서 예산을 다 쓴다 |
| ② | 지역·카페를 재추출 **앞**으로 | 지역 스윕이 `budget.left` 바닥까지 도는 구조라 **뒤가 또 굶는다** |
| ③ | `sweepRegions(…, reserve)` 로 카페 몫 예약 | — (예약은 **하한이지 상한이 아니다**: 지역이 끝나면 남은 예산이 통째로 카페로) |

②를 하고 나서야 ③의 필요를 발견했다. **"순서를 바꿨다"로 끝냈으면 병이 자리만 옮겼을 것이다.**

💱 지역을 앞에 둔 근거는 취향이 아니라 환산이다 — **ops 당 산출 83배**
(지역 500행/6 ops vs 카페 1행/1 op).

### 📅 배정표 재배분 — 주석이 예고한 그대로

`MAINT_SCHEDULE` 주석은 *"handle 이 done:true 로 끝나면 그 슬롯을 남는 일 쪽으로 옮겨야 한다"*
고 적어 뒀다. 라이브에서 그 조건이 성립했다: `handle → { scanned: 34, fixed: 0, unfixable: 34, done: true }`.
⇒ `handle` 3 → 1 · `reextract` 1 → 3.

🕘 **자리가 결과를 바꾼다**: 인덱스 7 은 hour 19(야간 재보정 양보)에 걸려 **하루 1회**다.
1슬롯 단계를 거기 두면 간격이 조용히 24h 로 벌어져 경보 창(12h)을 깬다 —
`maxScheduleGapHours(MAINT_SCHEDULE)` 를 양보 없이 재면 12 가 나와 **통과해 버린다.**
첫 판이 실제로 `handle` 을 인덱스 7 에 둘 뻔했고, 그래서 별도 검사를 신설했다.

### 🧪 유닛이 *정당한 변경*을 막은 사례 — 사실을 테스트가 소유하면 안 된다

이전 배정표 유닛은 `busy = ['reclassify','handle']` / `idle = ['reextract','merge']` 로
**07-29 그날의 라이브 사실을 박아** 뒀다. 그 사실이 뒤집히자 유닛이 빨간불을 냈다.
⇒ 사실은 코드 옆(`MAINT_SLOT_INTENT.why`)에 두고, 테스트는 **선언표와 배정표의 일치**만 본다.
배정표를 고치면 근거 한 줄을 같이 고치게 되어 **둘이 같이 늙는다.**

### 🩸 같은 세션에서 낸 회귀 하나 — 수동 버튼이 0건을 처리하게 됐다

#930 에서 버튼을 드라이버(팬아웃)로 돌렸더니 버튼이 **더 많이가 아니라 아무것도** 안 하게 됐다.

```
킥 → {"success":true,"fanout":4}   (즉시 반환)
30초 후 nb_unmeasured 변화 = 0      ← 직전 단발 경로는 한 번에 22 감소
```

원인은 **이 레포가 이미 적어 둔 규칙**이다(`dispatchRoundChain` docblock, 07-29):
*"서비스 바인딩 피호출자는 호출자보다 오래 살 수 없다."*
cron 은 부모 scheduled 가 다른 레인을 kick 하느라 살아 있지만, **어드민 버튼은 응답을 받는 순간
메인 워커 요청이 끝나** ur-ads 의 `waitUntil` 자식이 통째로 취소된다.

> 🔑 **교훈**: 같은 코드가 **호출자에 따라 다르게 죽는다.** cron 에서 depth 3 을 확인했다고
> 버튼도 된다고 볼 수 없었다 — 나는 그렇게 봤고, 그래서 하루치 수동 드레인을 날릴 뻔했다.

⇒ 수동 경로는 `sync=1` 로 자식 K개를 **`await`** 한다(버튼 1회 = K라운드). 자식에게도 `sync` 를
물려 어차피 취소될 릴레이를 안 낳게 했다. cron 경로는 동작 불변.
