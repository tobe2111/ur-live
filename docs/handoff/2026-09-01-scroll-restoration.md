# 뒤로가기 스크롤 복원 — "어떠한 페이지든 무조건" (2026-09-01)

대표: *"메인에서 스크롤 내려 이용권에 들어갔다 뒤로 오면 메인 맨 위로 나옴. 스크롤했던 위치로
나와야 함. 이건 어떠한 페이지든 마찬가지임. 무조건."*

## 실측

| | 홈(모바일) | 홈(PC) | 숙소 목록 |
|---|---|---|---|
| 수정 전(라이브) | ❌ 1100→0 | ❌ 1100→0 | ❌ 1100→0 |
| 수정 후(로컬 빌드) | ✅ 1100→1100 | ✅ 1100→1100 | ✅ 1100→1100 |

## 원인 — 복원 코드는 **있었는데** 저장이 0 으로 덮어써졌다

`ScrollToTop` 에는 2026-07-02 부터 POP 복원 로직이 있었다. 그런데 떠나는 순간, 그 페이지의
scroll 리스너가 **아직 붙어 있는 채로** 0 을 받아 적었다 — 라우터 상태가 바뀌고 DOM 이 교체되는
사이에 옛 키(`/`)로 `set('/', 0)`. 복귀 시 `saved > 0` 이 거짓이 되어 **"저장된 자리 없음" 폴백**
(맨 위로)을 탔다. 에러가 없고, 코드를 읽으면 복원이 되는 것처럼 보인다.

## 고친 것은 **한 줄**이다 (귀속 검증함)

`currentKeyRef` 를 **렌더 중에** 갱신하고, 리스너가 자기 키와 다르면 쓰지 않는다.
렌더는 DOM 교체보다 먼저라 떠난 뒤 도착한 이벤트가 전부 걸러진다.

⚠️ 함께 넣은 셋은 **각각 되돌려도 3/3 통과**했다 — 이번 사고의 원인이 **아니다**(정합성·내구성
보강일 뿐). 다음 세션이 "이게 그 수리"라고 오해하지 말 것:
- cleanup 저장 제거(있어도 키 검사가 막는다) · `sessionStorage` 영속 · 복원 예산 1.2s→3s

## 🕳️ 두 번 오진할 뻔했다 — 하네스 함정 (가장 값진 교훈)

첫 재현 스크립트가 **화면 밖 카드**를 클릭했다. 그러면 **Playwright 가 먼저 스크롤해서** 요소를
보이게 만든다. 즉 앱이 아니라 **테스트가** 위치를 0 으로 바꿔 놓았고, 나는 그 0 을 앱의 증상으로
읽어 *"문서 높이 붕괴 → clamp"* 라는 그럴듯한 기전을 확신하고 파일 주석까지 그렇게 써 뒀다.
계측 로그가 `docH=8332`(문서 멀쩡) · `URL=/`(아직 이동 전) 을 보여주고 나서야 하네스를 의심했다.

⇒ **재현은 뷰포트 안의 링크를 눌러야 한다.** 그리고 "원인을 찾았다" 뒤에는 **귀속 검증**
(하나씩 되돌려 무엇이 실제로 고쳤는지)을 반드시 붙일 것 — 이번에도 그게 아니었으면 틀린 기전이
주석으로 굳을 뻔했다.

## 가드

`src/tests/unit/scroll-restoration.test.ts` 4건 — 렌더 중 키 갱신 / 리스너 키 검사 / 높이 성장
재시도 / 사용자 스크롤 시 중단. 되돌려-검증 4건 전부 빨강 확인, 핵심 1건은 주입 매니페스트 등록.

**못 막는 것**: 실제 브라우저 동작(소스가 맞아도 렌더 순서가 바뀌면 깨진다) · 내부 컨테이너
(`overflow-y-auto`)로 스크롤하는 화면. 소비자 주요 표면이 전부 문서 스크롤인 것은 실측 확인했다.

## 후속 — "다른 페이지들도 다 되나?" (대표 질문, 2026-09-05)

배포 후 소비자 표면 10개 × 2뷰포트를 라이브에서 훑었다.

**판정 가능한 것은 전부 통과**(홈 모바일/PC · 숙소 목록 · 블로그). 나머지는 판정 불가였고 사유가 다르다:
- 문서가 짧아 스크롤 여지 없음(동네공구·체험단·쇼핑) — 복원할 것이 없다
- 뷰포트 안 링크를 못 찾음(교환권·검색·상세) — 하네스 한계이지 앱 문제 아님
- **`/map` 은 진짜 구멍이었다** — 목록이 문서가 아니라 컨테이너(`flex-1 min-h-0 overflow-y-auto`)에서
  스크롤돼 문서 스크롤만 다루던 복원이 닿지 않았다.

### 그래서 일반화했다 — `data-scroll-restore="<이름>"`
컨테이너에 이 표시만 달면 문서 스크롤과 **똑같이** 저장·복원된다. 새 화면도 한 줄이면 되고,
안 단 화면은 아무 일도 안 일어난다(옵트인 — 모달·캐러셀·가로 스크롤을 잘못 건드릴 위험 없음).

⚠️ **`window` 리스너로는 안 된다** — scroll 이벤트는 **버블하지 않아서** `capture: true` 로 들어야
컨테이너 스크롤이 잡힌다. 이게 빠지면 저장이 조용히 0건이 되고 화면은 그대로라 아무도 모른다
(주입 매니페스트에 등록).

### ✅ `/map` 왕복 실측 완료 (2026-09-05)
앞선 판에 *"저장까지만 쟀고 복원 왕복은 남은 항목"* 이라고 적었는데, **그 왕복을 이제 쟀다.**
하네스가 막혔던 이유는 앱이 아니라 도구였다 — 카드가 `<a>` 가 아니라 `<button onClick>` 이라
Playwright 의 좌표 클릭·tap 이 전부 헛돌았다. `page.evaluate` 안에서 **DOM `.click()`** 을 부르면
하네스 자동 스크롤도 없고(그 함정이 이 파일의 원래 오진 원인이다) 핸들러는 정상 발화한다.

로컬 빌드(dist) + 라이브 API 프록시로 대표님 시나리오 그대로:
```
목록 컨테이너 scrollTop 620  →  sessionStorage {"p:/map#map-list":620}
카드 탭 → peek 카드 탭 → /group-buy/2872  →  뒤로
AFTER {"url":"/map","paneTop":620}                      ✅ PASS
```
**되돌려-검증**: 런타임에 `data-scroll-restore` 속성만 떼고 같은 절차 → `ss: null` · `paneTop: 0` → ❌ FAIL.
즉 이 하네스는 **앱을 재고 있다**(자기 자신이 아니라).

⚠️ 지도는 카드를 한 번 누르면 **목록 컨테이너가 언마운트**되고 peek 카드로 바뀐다. 그래도 복원되는
이유는 저장이 *떠나기 전 scroll 이벤트*에서 이미 끝나 있고, 뒤로 왔을 때 목록이 다시 마운트되면
POP 복원 루프가 rAF 로 따라잡기 때문이다. **언마운트가 저장을 지우지 않는다**는 게 이 설계의 핵심이다.
