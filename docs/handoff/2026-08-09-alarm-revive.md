# 자가치유가 자기가 고쳐야 할 상태를 "건강"으로 읽었다 — 알람 되살리기

**2026-08-09 · 유어애즈 레인 알람** · 대표 지시 *"응 계속 영구적이어야 해"*

## 사고 (라이브 실측)

측정 샤딩 2배(#1101) 배포 당일, **샤드 0 이 오후 4시부터 6시간 죽어 있었다.**

```
KST    측정   샤드0(짝)  샤드1(홀)
15시   519     261       258     ← 정상
16시   347      92       255     ← 붕괴
17시   256       0       256
19시   240       0       240     ← 계속 0
```

원인: `/start` 가 `getAlarm()` 이 non-null 이면 *"이미 걸려 있다"* 며 넘어갔는데,
**예약 시각이 3.5시간 과거인데 안 깨어난** 인스턴스가 정확히 그 상태였다.

```
enrich-influencer     마지막 실행 16:24 · alarmAt 3.5h 과거
lane-alarm-boot:…     ok=true  started=false        ← 화면은 계속 초록
```

`lane-alarm-boot.ts` 헤더는 *"알람 체인이 어떤 이유로든 끊겨도 다음 정각이 되살린다"* 고
약속했지만 **매 정각 확인하면서 매 정각 못 살리고 있었다.** 값은 있는데 체인은 죽었고,
자가치유가 그걸 건강으로 읽었다 — 이 레포의 *"침묵이 성공처럼 보인다"* 알람 계층 판.

## 수리

| 항목 | 파일 |
|---|---|
| `alarmReviveKind()` — `none`/`stale`/`alive` 판정(순수) + `ALARM_DEAD_AFTER_MS = 30분` | `lane-alarm-policy.ts` |
| `/start` 가 그 판정을 사용 · `revived` 를 응답에 남김 | `lane-alarm.ts` |

- ⚠️ **`none` 과 `stale` 을 구분해 남긴다** — 뭉개면 "원래 없었다"와 "죽어서 되살렸다"를 못 가른다.
  이번 사고가 6시간 안 보인 이유가 정확히 그것이다. 하트비트에 `revived: true` 로 뜬다.
- ⚠️ **여유(30분)가 간격(5분)보다 넉넉한 이유**: 런타임 알람 발화는 정확하지 않다(수십 초~수 분 지연이
  정상). 짧게 잡으면 정상 지연을 죽음으로 오판해 알람을 계속 덮어써 **회차를 잃는다** — 부호만 반대인
  같은 고장이라 유닛으로 같이 고정했다.

## 못 고친 것 (과신 금지)

- **왜 알람이 안 깨어났는지는 여전히 모른다.** 이 수리는 *깨어나지 않았을 때 되살아나게* 만든 것이고
  근본 원인(런타임 유실·CPU 사망 등)은 미확정이다. `revived: true` 가 자주 뜨면 그게 빈도 지표가 된다.
- `enrich-influencer-driver` / `-fanout` 은 여전히 죽어 있다(cron 게이트 뒤). 샤딩이 역할을 대체하므로
  무해하지만 정리(삭제 또는 알람 편입)는 안 했다.
