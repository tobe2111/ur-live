# 2026-08-04 — 카카오 전화 스윕이 뒷줄 15,582건을 굶기고 있었다

> 대표 지시 맥락: *"보강 처리량부터 올려줘"* → 확인해 보니 **처리량만이 병목이 아니었다.**
> 이미 가진 행에서 연락처를 못 꺼내고 있었다. 새 수집 0건으로 얻을 수 있는 것부터 처리했다.

## 1. 무엇이 고장이었나 (라이브 실측)

```
스윕 적격            148,297
  tier1     96 · tier2 933 · tier3 2,637 · tier4 129,049 · tier5 15,582
storeinfo         17,979건 — 주소 보유 100%, 카카오 조회를 받은 것 **0건**
실적              회차당 tried 50 · found 10 · 하루 360조회 · limit_hit true
```

`runKakaoPhoneSweep` 의 정렬이 `ORDER BY (tier IS NULL) ASC, tier ASC, id ASC` 뿐이었다.
tier4(통신판매, 12.9만)가 앞을 통째로 막아 **tier5 storeinfo 는 하루 360조회로 358일 뒤에나** 차례가 온다.

그런데 더 나쁜 건 그 뒤다 — 이 스윕은 **커서가 없다.** 대상 선택이
`kakao_checked_at IS NULL OR kakao_checked_at < now-30days` 인데, **쿨다운 30일 < 한 바퀴 411일**이라
앞줄이 만료돼 계속 재적격된다. 즉 358일이 아니라 **영영 안 온다.**

⚠️ 파일 헤더에는 *"✅ 여기는 기아 걱정이 없다"* 고 적혀 있었다(2026-07-28). 도장이 시도한 행에만
찍힌다는 부분은 맞지만, **쿨다운이 한 바퀴보다 짧다는 전제 붕괴를 아무도 안 봤다.** 그 주석을 믿고
"스윕은 멀쩡하다"고 넘어가면 이 15,582건은 계속 안 보인다 → 주석을 반증과 함께 고쳐 놨다.

## 2. 무엇을 했나

정렬에 **축 두 개를 앞에 붙였다**(대상 집합·tier 정의는 불변):

```sql
ORDER BY (kakao_checked_at IS NOT NULL) ASC,          -- ① 한 번도 안 본 것 먼저 (기아 수리)
         (email IS NOT NULL AND email <> '') ASC,     -- ② 연락처가 아예 없는 것 먼저
         (tier IS NULL) ASC, tier ASC, id ASC         -- ③ 기존 접촉 가치 순 (그대로)
```

- ①이 기아를 **구조적으로** 없앤다. 미조회 행이 남아 있는 한 앞줄 재적격이 끼어들 수 없다.
- ②는 목적함수 정합 — tier4 12.9만 중 **17,921건은 이미 이메일이 있다.** 이미 부를 수 있는 사람에게
  희소한 조회를 쓰는 건 손해다. 목표는 조회 수가 아니라 **부를 수 있는 사람 수**(대표 확정).

**기대값**: storeinfo 17,979건 × 현재 스윕 적중률(found/tried ≈ 20%) ≈ **약 3,500 전화**
= 현재 B2B 연락처의 +12.7%. **새 수집 0건, API 키 0개, 대표 액션 0건.**
