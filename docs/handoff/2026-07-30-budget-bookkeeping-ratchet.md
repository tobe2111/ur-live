## 그리고 self-beat 이 곧바로 새 사실을 보여줬다

**통신판매**: 하트비트 `00:00:45`(= 완주) ↔ 자기 스탬프 `전날 14:00:40`.
**완주했는데 자기 기록만 못 썼다.** 이 구분은 self-beat 이 없었으면 불가능했다(둘 다 "멈춤"으로 보였다).

원인은 카카오 스윕과 **같은 클래스**였다:

```
루프:  for (... ; budget.left > 0 ; ...)      ← 예산을 0까지 소진
뒤:    커서 쓰기 ×2  +  persist(스냅샷) ×1     ← 예산 밖 → 던짐 → .catch(() => null) 이 삼킴
```

그래서 우리가 하루 종일 기다린 `diag.error` 원문이 **매 회차 유실**됐다. 원인 규명이 하루 늦어진 이유다.

## 고친 것

- 통신판매 루프: `budget.left > services.length + 1`(커서 N + 스냅샷 1).
- **가드 신설** `check-budget-bookkeeping`(래칫, strict) — 예산 루프가 `budget.left > 0` 까지 소진하면서
  뒤에 D1 쓰기가 있으면 차단. 기존 2건(`franchise-collect:91` · `influencer-performance:157`)은 **동결**
  (후자는 다른 세션이 작업 중인 파일이라 건드리지 않았다 — 정리하면 `--rebaseline`).

⚠️ **가드가 못 잡는 것**: 형태만 본다. 예약 숫자가 실제 뒤따르는 쓰기 수보다 **작아도 통과**한다.
그 정합은 레인별 단위 시험이 맡는다(`ads-sweep-bookkeeping.test.ts` 가 실제 쓰기 수를 센다).
플랫폼 한도를 진짜로 친 회차는 예약으로도 못 살린다.
