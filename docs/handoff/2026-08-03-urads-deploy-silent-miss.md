## 무슨 일이 있었나

`#969`(회차당 레인 수 학습기)를 머지했는데 **ur-ads 워커에 안 올라갔다.** `deploy-ads` 실패 원문:

```
A request to the Cloudflare API (/accounts/***/workers/services/ur-ads) failed.
Rate limited. Please wait and consider throttling your request speed [code: 10429]
```

재시도는 있었다 — 그런데 `sleep $((i*10))` = 10s·20s 라 **3회가 40초 안에 전부 소진**됐다
(15:03:29Z → 15:03:51Z). 레이트 리밋은 초 단위로 안 풀린다. 즉 **재시도가 있으나 마나**였다.

🔴 **대가가 조용하다.** 라이브 화면은 멀쩡하고 ur-ads 는 낡은 코드로 계속 돈다. 실패는 Actions 탭
안에만 있다. 실제로 그날 머지 **2건**(`#971`·`#969`)의 ur-ads 코드가 배포되지 않은 채였고 아무도 몰랐다.
이 워크플로 주석이 이미 경고했던 클래스(*"배포가 아예 안 돌아 ur-ads 가 조용히 낡은 코드로 계속 돌았다"*)의
**재발**이다 — 그때는 경로 필터가 원인이었고 이번엔 백오프였다.

### 왜 리밋에 걸렸나 — 우리가 스스로 만든 부하

이 워크플로의 경로 필터가 넓어서(`src/worker/**` 포함) **거의 모든 머지가 ur-ads 를 재배포**한다.
세션이 여러 개 병렬로 도는 이 레포에선 머지가 잦다(실측: 20분에 11회). 즉 리밋은 예외가 아니라 **일상**이다.

### 더 나쁜 것 — 수리를 검증할 방법이 없었다

`paths:` 에 **이 워크플로 자신이 없었다.** 그래서 이 파일을 고쳐도 배포가 안 돈다 —
깨진 배포 경로를 고쳤는데 그 고침이 적용되는지 확인하려면 무관한 코드 변경을 기다려야 했다.

## 아직 못 막는 것 (정직하게)

**"ur-ads 가 낡은 코드로 돌고 있다"에 대한 자동 경보가 없다.** 신호는 이미 있다 —
`ads:scheduled` 하트비트의 `build_age_min` — 그런데 그걸 읽고 알려 주는 것이 아무것도 없다.
지금은 사람이 위 ① 명령을 쳐야 안다. 배포 재시도를 고쳤으니 빈도는 줄겠지만 **클래스가 사라진 건 아니다.**
자동화하려면 어드민 인증이 필요한 값이라 `live-contracts`(무인증 URL 두드리기) 방식으로는 안 되고,
별도 인증 경로나 무인증 노출이 필요하다 — 그건 새 표면이라 대표 판단 사항으로 남긴다.
