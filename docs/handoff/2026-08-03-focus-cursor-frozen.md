# 대행사 축이 얇던 진짜 이유 — 커서가 얼어 있었다 (그리고 필터는 무죄였다)

> 대표 지시: *"db로 유어딜에 활동할 인플루언서 및 대행사에게 제휴 제안을 보낼거야"* ·
> *"계속 끝까지 해"*

## ❗ 이번에 배운 것 (먼저 읽어라)

**증상에서 원인을 추측하면 정확히 반대쪽을 고친다.**

마케팅대행사 리드가 283명뿐이고 키워드 성과가 `found 2,070 → saved 10`(0.5%) 이었다.
읽자마자 떠오른 가설은 **저장 필터**였다 — `MIN_YT_SUBSCRIBERS = 1000` 과 브랜드 컷이
"대행사는 개인이 아니라 회사"라서 걸러내는 것 아니냐. 그럴듯했고, 고칠 코드도 바로 보였다.

**라이브를 먼저 봤더니 필터는 무죄였다.** 저 세 키워드는 오히려 **정상 작동한 유일한 셋**이고,
0.5% 는 나머지가 이미 풀에 있어서(중복)다. 진짜 원인은 전혀 다른 자리에 있었다:

```
활성 대행사 키워드 18개 중 16개가  found_total = 0 · last_run_at = null
                                   = 한 번도 검색된 적이 없다
```

필터를 손댔으면 멀쩡한 것을 망가뜨리고 원인은 그대로 남았을 것이다.

## 🔎 원인 — 커서 한 줄이 아니라, 커서 **두 줄**

집중 축 슬롯(#930)은 배치의 1/4을 대행사 키워드에 떼어 준다. 배정은 정상이었다(`focus_n: 4`).
커서만 한 번도 안 움직였고, 그 이유가 **둘 다 "조용한 부재"** 였다:

```ts
// ① 읽기 — 이 키가 readSettings 목록(SETTING_KEYS)에 없다
settings['ads_autocollect_cursor_focus']   // → 에러가 아니라 undefined → parseInt('0') → 0

// ② 쓰기 — 계산해서 통계 JSON 에만 넣고 platform_settings 엔 안 쓴다
const nextFocusCursor = ...                 // stats.focus_cursor 로만 나감
```

라이브 D1 이 그대로 보여줬다:

```
ads_autocollect_cursor_pri  = 158
ads_autocollect_cursor      = 6
ads_autocollect_cursor_focus  ← 행 자체가 없음
```

⇒ 매 회차 `focusPool[0..3]` 만 뽑는다. 그리고 예산은 픽 4개를 다 못 돌아 실제로는 앞 3개만
돌았다. 4번째부터 끝까지가 통째로 사각지대:

```
56459 마케팅 대행사  found 2,070   56462 디지털 마케팅   found 0 · null
56460 광고 대행사    found 1,150   …
56461 온라인 마케팅  found    58   56476 지역 광고       found 0 · null
```

빠진 것들이 하필 **대행사를 가장 잘 찾을 키워드**다 — "체험단 대행" · "체험단 모집" ·
"인플루언서 섭외" · "인플루언서 마케팅" · "소상공인 마케팅" · "자영업 마케팅".

## 왜 아무도 몰랐나

통계는 **정상으로 보였다**. `focus_n: 4` 가 매 회차 찍혔고, 대행사 키워드도 셋은 돌았다.
"집중 축이 도는가?" 에 대한 답은 계속 예였다. 틀린 질문이었던 것이다 —
**"집중 축의 *어느* 키워드가 도는가"** 를 물었어야 했다.

## ✅ 수리 (PR #990)

| 수리 | 왜 |
|---|---|
| 키를 `FOCUS_CURSOR_KEY` 상수로 묶고 `SETTING_KEYS` 에 추가 | 읽기·쓰기가 같은 문자열을 보게 |
| `writeSettings` 배치에 커서 저장 1줄 | pri·gen 과 대칭 — 통계 blob 은 다음 회차가 안 읽는다 |
| 전진량 `nFocus` → `prefixDone(focusPicks)` | 예산이 4개를 다 못 돈다. 계획한 수만큼 밀면 **한 바퀴에 한 번도 안 걸리는 자리**가 생긴다(pri·gen 이 `prefixDone` 을 쓰는 이유와 같은 leapfrog) |

## 🛡️ 가드 — 특정 키가 아니라 **규칙**을 고정했다

`src/tests/unit/ads-keyword-focus-split.test.ts` 에 셋. 전부 일부러 깨뜨려 빨간불 확인 후 복원,
`check-guard-mutations.mjs` 매니페스트에 등재(73개 주입 전부 red).

1. **`settings[X]` 로 읽는 키는 전부 `SETTING_KEYS` 에 있어야 한다** — 이 키 하나가 아니라
   앞으로 추가되는 키에도 자동 적용된다. `readSettings` 호출부는 레포에 이 파일 하나뿐이라
   (grep 확인) 이 가드가 클래스 전체를 덮는다.
2. `const next*Cursor` 로 계산한 값은 전부 `writeSettings` 에 있어야 한다.
3. 집중 축 커서도 `prefixDone` 을 쓴다.

⚠️ **가드는 주석을 걷어낸 본문을 읽는다.** 첫 구현이 자기 설명 주석 속 `settings[...]` 예시를
실제 접근으로 세어 빨간불을 냈다 — 이 레포가 여러 번 겪은 *"주석에만 남아도 통과"* 의
정확한 반대편이다. 문자열 스캔 가드를 쓸 땐 **무엇을 읽고 있는지** 먼저 정할 것.

## ▶️ 다음 세션의 첫 액션 — 배포 후 판정

배포(머지) 후 **다음 정각 회차**에:

```bash
bash scratchpad/d1.sh "SELECT key, value FROM platform_settings WHERE key='ads_autocollect_cursor_focus'"
```
- **행이 생기고 값이 회차마다 늘면 성공.** 여전히 행이 없으면 쓰기가 안 닿은 것(다른 원인).

하루 뒤 최종 확인:
```bash
bash scratchpad/d1.sh "SELECT COUNT(*) never_run FROM ad_discovery_keywords
  WHERE category='마케팅대행사' AND active=1 AND last_run_at IS NULL"
```
- **배포 전 baseline = 16** (활성 18개 중). 이 수가 줄면 잠들어 있던 키워드가 깨어난 것이다.
- 대행사 리드 baseline: **287명 · 이메일 69**.

## 🪪 이어서 나온 두 번째 결함 — 목록의 16%가 대행사가 아니었다 (PR #992)

커서를 고쳐 키워드가 돌기 시작하면 **모인 목록이 맞는지**가 다음 질문이다. 확인해 봤더니 틀렸다.

`/api/admin/ads/influencer-pool?category=마케팅대행사&hasEmail=1&platform=naver_blog` 로 실물을 열자
호캉스 후기 · 비트코인 · 제주 맛집 · 경주 숙소 블로거가 줄줄이 나왔다. 라이브 분류기(`classify-debug`)에
물으니 **"콘텐츠 신호=마케팅대행사(현재와 동일)"** — 키워드 상속이 아니라 **분류기 본인의 판정**이었다.

정규식 어느 갈래가 물었는지 실제 문자열에 돌려서 찾았다:

```
▶ 매치 '마케터'   "…년 경력 일본 여행사 마케팅 담당자 → 현재 여행 인플루언서 & 일본 전문 마케터 와그잡!"
```

규칙 주석은 함정 넷(`마케팅`·`바이럴`·`대행`·`퍼포먼스`)에 *"업 신호를 요구한다"* 고 적어 놓고
**마지막 토큰 `마케터` 만 맨몸**이었다. 대행사 273명 중 **45명(16%)** 이 이 단어 하나로 들어와 있었고,
원래 자리는 맛집 10 · 외식창업 8 · IT/재테크 5 · 카페 5 · 숙소 4 · 여행 2 · 패션 1 · 미분류 10 —
**이용권 본체 축에서 훔쳐오고 있었다.**

갈림은 이름/소개글로 깨끗했다: **이름 14건은 전부 자기 선언**(싱어송마케터·QR마케터·로컬마케터즈),
**소개글 31건은 전부 지나온 경력**. ⇒ `nameRe`(이름 전용 신호) 도입.

### 💡 방법론 — 라이브 데이터에 진짜 코드를 돌려서 검증했다

npm 이 막힌 세션이었지만 `influencer-classify.ts` 는 **import 0 인 순수 모듈**이라 전역 tsc 로 단독
컴파일해 D1 실물 287행에 돌릴 수 있었다. 정규식을 손으로 옮겨 적었으면 못 믿을 결과였다.

```
대행사 유지 241 · 다른 축으로 27 · 비워서 재도전 19 · 그대로 굳음 0
검산: 228(다른 신호로도 대행사) + 14(이름) − 1(마케터 지망생) = 241 ✓
```

⚠️ **`shouldClearCategory` 를 같이 건드려야 했다.** 규칙을 좁히면 어느 규칙에도 안 걸리는 10건이
`null` 이 되는데 재분류는 null 이면 **그대로 둔다** → 옛 값이 영구히 굳는다. 그 함수 docblock 이
입주 시공업체 27명 실측으로 이미 경고한 형태다. 좁게(대행사 한정) 열었다 — 일반화하면 키워드 상속으로
정당하게 붙은 분류까지 날아간다.

### ⏱️ 라이브 반영 시점
