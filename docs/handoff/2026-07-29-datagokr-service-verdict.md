# 인허가 500 판정 — **우리 코드 문제가 아니다** (2026-07-29, 대표 지시로 수동 실행)

## 결론 먼저

`apis.data.go.kr/1741000`(지방행정인허가)이 **우리 계정에 대해 HTTP 500** 을 낸다.
키는 유효하고, 요청 형태도 문제가 아니다. **대표가 포털에서 확인해야 풀린다.**

## 근거 3개 (전부 라이브 실측)

**① 요청 형태 5종 전부 실패** — 프로브가 이미 다 시도했다(13:00:53 실행분, `diag.probe_last`):

```
v1 현행(pageIndex/pageSize=500)      → HTTP 500
v2 pageSize 100                      → HTTP 500
v3 형식 파라미터 중복 제거            → HTTP 500
v4 pageNo/numOfRows                  → HTTP 500
v5 변동일 필터 제거                   → HTTP 500
```

**② 같은 키로 다른 서비스는 된다**(대조군) — 한 계정의 serviceKey 를 공유하는데 서비스별로 갈린다:

| 서비스 | 경로 | 상태 |
|---|---|---|
| 상가정보(소상공인) | `B553077` | ✅ 정상 — 누적 12,999건 |
| 인허가(LOCALDATA) | `1741000` | ❌ HTTP 500 |
| 병원(심평원) | `B551182` | ❌ 25초 타임아웃(100행에서도) |
| 통신판매(공정위) | `1130000` | ❌ 비JSON — **02:00 엔 24,469건 성공**, 이후 깨짐 |
| 가맹사업(공정위) | `1130000` | ❌ HTTP 404 |
| 나라장터 | `1230000` | ❌ HTTP 404 |
| 학원(NEIS) | `open.neis.go.kr` (**별도 키**) | ✅ 정상 — 36,390건 |

⇒ 게이트웨이 전체 장애도, 키 무효도 아니다. **서비스별 상태**의 문제다.

**③ 일일 쿼터도 아니다** — data.go.kr 한도는 00:00 KST 에 리셋된다. 수동 실행을 **01:47 KST(리셋 후)** 에
했는데 그대로 500 이었다. 쿼터였다면 회복됐어야 한다.

## 대표가 확인할 것 (이 환경에선 불가 — 프록시가 data.go.kr CONNECT 403)

data.go.kr 마이페이지 → 활용신청 현황에서 **`1741000` 지방행정인허가데이터**:
1. 승인 상태인가 / **활용기간이 만료**되지 않았나(개발계정은 기간 만료가 흔하다)
2. 포털의 **미리보기 호출**이 성공하는가 — 성공하면 우리 요청으로 좁혀지고, 실패하면 제공자 장애다

같은 화면에서 `B551182`(심평원) · `1130000`(공정위)도 함께 보면 세 축이 한 번에 갈린다.

## 왜 이게 중요한가

매장 후보 40,741건 중 **학원이 36,390(98.7%)**, 음식점·카페·미용실·숙박은 **0건**이다.
그 16개 업종이 전부 `1741000` 하나에 걸려 있다. 이게 풀리기 전엔 공동구매용 매장 DB 는 안 늘어난다.
(학원만 쌓이는 이유도 이 표가 설명한다 — NEIS 만 다른 키·다른 호스트다.)

## 이번에 확인된 수정 효과 하나

`pending_days: 0 → 1`. 백필이 500 을 만난 날짜를 **'완료'로 소모하지 않고 미완으로 남긴다**(#891).
이 수정 전이었다면 방금 수동 실행도 하루치를 그냥 태웠을 것이다.

## 다음 세션이 하지 말 것

- **요청 형태를 더 바꾸지 마라.** 5종을 이미 다 시도했고 전부 같은 500 이다.
- **진단을 더 파지 마라.** `describePublicDataFailure` 가 이미 본문을 읽고 있고, 본문이 문자 그대로
  `Unexpected errors`(코드 없는 제공자 일반 오류)다. 우리 쪽에서 더 알아낼 것이 없다.
- 대표 답변 전까지 이 축은 **대기**다. 그 시간에는 권한이 필요 없는 다른 축을 볼 것.

## 곁다리 — 파트너풀 카테고리화는 값이 낮다(실측)

`온라인판매` 표본 300건의 상호를 봤다: "주식회사이제이네트웍스 · 옴니웍스 · 주식회사꾼 · (주)제이에스지"…
**법인명 위주라 업종 추론이 대부분 불가능**하다(신호 있는 건 타이어가게·별푸드 정도로 소수).
게다가 통신판매업 신고자는 유어딜의 이용권 공급 대상(오프라인 매장)이 아니다.
⇒ 이름 기반 업종 분류는 **투입 대비 값이 낮다.** 하려면 원부의 취급품목(`trtmntPrdlstNm`)이 필요한데,
그건 통신판매 레인이 살아나야 들어온다.

## 곁다리 2 — 전화 스윕이 **자기 기록을 쓸 예산을 안 남겼다**

`ads_kakao_sweep_stats.last_run` 이 13:01 에 멈춰 있었다. 같은 게이트 블록의 `reclassify` 는 매시간
갱신되는데(둘 다 매시간 디스패치) 이쪽만 멈춘 것 — 차이는 **그쪽은 예산을 안 쓴다**는 것뿐이다.

원인은 산수다. 루프는 `left <= 2` 에서 멈추는데 **루프 뒤 D1 접근이 5회**다:
전화 저장 · 시도 도장 · 학습 상한 갱신 · 직전 통계 조회 · **자기 스탬프**.
D1 도 서브리퀘스트라 예산을 넘으면 던지고, 전부 `.catch(() => null)` 이라 조용히 사라진다.
그리고 하필 **마지막이 자기 스탬프**다 ⇒ 돌았는데 "안 돈 것"처럼 보인다.

⇒ 예약을 `SWEEP_BOOKKEEPING_RESERVE = 6` 으로. 테스트가 **실제 쓰기 횟수를 세어** 예약과 비교하므로,
쓰기를 추가하고 상수를 안 올리면 빨간불이 뜬다(또 마지막부터 조용히 잘리는 일이 없게).

⚠️ 이걸로도 못 막는 것: **플랫폼 한도를 실제로 친 회차**(`limitHit`)는 이후 어떤 서브리퀘스트도 못 쓴다.
예약으로 해결되지 않는다 — 그건 학습 상한이 낮추는 방식으로만 줄어든다.

⚠️ 아직 안 본 것: 이 레인의 **수확률**이 0 이다(`tried:50 · found:0`, 누적 `total_found:81`).
기록이 살아난 뒤 출처/카테고리별 적중률을 보고, 수율 0 인 부류에 50회/시간을 계속 쓸지 판단할 것.
