# 검색이 조용히 틀린 결과를 주던 것 — 바인드 순서 (2026-09-30)

**[E2]** 작성·검증됨(tsc 0 · 유닛 67건 · 주입 5건 되돌려-검증 빨간불). 배포 전.

대표 지시: *"검색기능도 지금 완벽한지 확인해줘"* (#1583 머지 뒤 E4 라이브 판정 중 발견).

---

## 1. 무엇이 틀렸나

`buildSearchClause`(검색 SSOT)가 바인드 값을 **한 배열**(`params = [...where, ...rank]`)로 돌려줬는데,
호출부 `ProductRepository.searchByText` 는 랭킹 식을 **SELECT 에** 놓는다:

```sql
SELECT …, (CASE WHEN name = ? … END) AS _rank   ← rank 의 ? 가 먼저
FROM products p WHERE (name LIKE ? OR …) AND …  ← where 의 ? 는 그다음
```

SQLite 는 **SQL 텍스트 등장 순서**로 바인딩한다. 두 묶음이 통째로 **5칸 어긋나 있었다.**

🔴 **개수가 맞아 예외가 안 났고**, 어긋난 값도 전부 `%…%` LIKE 패턴이라 **에러도 로그도 없었다.**
결과만 조용히 틀렸다.

## 3. 왜 기존 가드가 못 잡았나

`search-engine-rebuild.test.ts` 는 **SQL 문자열과 배열 내용**만 본다 — 그 파일 머리말이
*"⚠️ 이 파일이 못 잡는 것: 실제 D1 실행 결과"* 라고 **스스로 적어 뒀다.**
이 결함은 문자열도 배열 내용도 전부 맞고 **순서만** 틀렸다 ⇒ 눈먼 자리에 정확히 들어앉았다.

🧭 **교훈: "못 잡는 것" 이라고 적어 둔 자리가 실제로 결함이 사는 자리다.**
적어 두는 것으로 끝내지 말고, 값이 크면 그 자리를 덮는 가드를 만들어야 한다.

## 4. 수정

1. **`SearchClause` 를 `{ where, rank, whereParams, rankParams }` 로 쪼갰다** — 합쳐진 `params` 를
   없앴다. 합쳐서 주면 **어느 자리에 넣어야 하는지 아는 사람이 아무도 없다.** 그게 원인이었다.
   (타입이 바뀌므로 모든 호출부가 다시 결정하게 된다 — 그게 이 모양의 요점이다.)
2. `searchByText` 가 `params.push(...rankParams, ...whereParams)` — SQL 텍스트 순서대로.

## 6. 다음 세션의 첫 액션 — 배포 후 라이브 판정 (E4)

```bash
UA='Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/126.0.0.0 Safari/537.36'
q(){ python3 -c "import urllib.parse,sys;print(urllib.parse.quote(sys.argv[1]))" "$1"; }
for t in "홍대" "홍대 홍대" "홍대 돈가스 버크셔 프리미엄 세트" "홍대 돈가스 버크셔 프리미엄 돈가스" "zzzqqq없는것"; do
  printf '%-40s ' "$t"
  curl -sS "https://urdeal.kr/api/search?q=$(q "$t")&limit=3" -H "User-Agent: $UA" \
   | python3 -c "import sys,json;d=json.load(sys.stdin);print(('OK '+str(len(d.get('data') or []))) if d.get('success') else 'ERROR')"
done
```

판정 기준:
- `홍대` 와 `홍대 홍대` 가 **같은 건수** (지금은 21 vs 0)
- `…프리미엄 세트` **≥1건** (지금 0)
- `…프리미엄 돈가스` **ERROR 아님** — ⚠️ **이 오류의 기제는 아직 규명 못 했다.**
  로컬 재현(`node:sqlite`)에선 그 쿼리가 1건을 정상 반환한다. 바인드 어긋남의 부수효과로
  보이지만 **확증은 없다.** 배포 후에도 ERROR 면 그것만 따로 판다(워커 로그는 이 컨테이너에서
  wss 가 막혀 못 본다 → D1 조회 + 응답 이분탐색이 유일한 길).
- `zzzqqq없는것` **0건** (대조군 — 0 이 아니면 측정이 죽은 것)

## 7. 이번에 틀렸던 판단

1. **PR #1583 본문의 "🔒 눌러서 0건이 나오면 안 된다"** — 컬럼 목록만 보는 가드를 실행 보장처럼
   적었다. 위 §2 참조.
2. **E4 측정 자체가 한 번 헛돌았다** — 처음에 `/api/group-buy/products?search=` 로 "0건 없음"을
   쟀는데 그 엔드포인트는 `search` 를 **무시**한다(대조군까지 50건). 대조군(`zzzqqq없는것` → 0)을
   넣고서야 측정이 살아났다. **대조군 없는 측정은 측정이 아니다.**
3. **원인을 "토큰 5개 상한"으로 먼저 의심했다** — 상한은 토큰을 *잘라* 조건을 느슨하게 만들므로
   결과를 줄일 수 없다. 방향을 따져 봤으면 바로 기각했을 가설이다.

## 9. 추가 실측 (커밋 이후, 라이브 · 읽기 전용)

**① 영향 범위를 숫자로 쟀다** — 라이브에서 활성 상품 **301개**를 받아(공개 API) `node:sqlite` 에
넣고 *상품이 자기 이름으로 자신을 찾는지* 전수 확인했다:

```
고친 순서 :  301개 중 못 찾음  0건   · 매장명으로 못 찾음 0/301
틀린 순서 :  301개 중 못 찾음 31건(10.3%)   예) 홍대 돈가스 버크셔 프리미엄 돈가스 1인 세트
                                              한우 육회 + 등심 구이 세트
                                              평일 1박 숙박권 (프리미엄 리버뷰 스위트)
```

**② 여러 낱말 검색이 사실상 "통짜 문자열" 검색으로 강등돼 있었다** — 라이브에서 `홍대 세트` 가
**0건**이다(그 낱말 둘을 **다 가진** 상품이 실재하는데도). 어긋난 바인딩이 **마지막 토큰 묶음에
랭킹용 패턴(`%검색어 전체%`)을 밀어 넣어**, AND 매칭이 "전체 문자열이 연속으로 들어있는가" 로
바뀌기 때문이다. 고친 순서로는 1건이 나온다(로컬 301행 재현).
⇒ **증상이 "가끔 0건" 이 아니라 "여러 낱말 검색의 의미 자체가 바뀜" 이었다.**

## 10. 🔴 별건 결함 — 검색어가 **49바이트 이상이면 HTTP 500** (이번 PR 범위 밖, 미규명)

`GET /api/products` · `/api/search`, 파라미터 `q`/`search` 무관, **결정적**:

```
'z'×48  → 200        'z'×49  → 500 {"success":false,…,"_tag":"[products]"}
한글 46바이트 → 200   한글 49바이트 → 500
```

- 경계는 **디코딩된 검색어의 UTF-8 48바이트**다(문자 수·토큰 수·토큰 길이·결과 행 수와 무관).
  13개 표본이 전부 이 하나로 설명된다.
- **캐시 키 길이가 아니다** — `category`/`brand` 를 300자로 늘려 키만 키우면 200 이다.
- **SQL 도 아니다** — `'z'×49` 는 `MAX_TOKEN_LEN=40` 으로 잘려 `'z'×40` 과 **완전히 같은 SQL·바인드**를
  만드는데, 40 은 200 이고 49 는 500 이다.
- 같은 길이로 `/api/search/suggestions` 와 `/api/products/count` 는 **200** — 이 핸들러 고유다.
- 🩸 **도달 가능하다**: 활성 상품 301개 중 **이름이 49바이트 이상인 것이 17개(5%)**. 검색 제안을
  누르면 상품명 전체가 그대로 검색어가 되므로 그 17개는 **500** 이 된다.

**아직 원인을 못 밝혔다.** 핸들러 안에서 생 검색어를 쓰는 곳(캐시 키·`logSearch`·오타 보정
`findClosestKeyword`)은 전부 try/catch 안이라 던질 수 없고, SQL 은 위와 같이 동일하다.
워커 로그(wss)가 이 컨테이너에서 막혀 예외 원문을 못 본다.
⇒ **다음 세션**: ① 이 PR 배포 후 재측정(바인드 수정의 부수효과였는지) ② 여전하면 `safeError` 가
`_debug` 를 붙이는 조건을 임시로 넓히거나, 핸들러 안 단계별 계측을 한 번 배포해 예외 원문을 잡는다.
