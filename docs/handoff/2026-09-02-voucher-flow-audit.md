# 🎟️ 이용권 등록 플로우 전수조사 (2026-09-02)

## 🔴 다음 세션의 첫 액션

**배포 후 실제 등록 1회가 유일한 판정이다.** 순서:

1. 셀러 대시보드 → 이용권 등록 → 1단계에서 **매장 칩이 보이는지**(대표 계정은 매장 14 운영자 · 개인 좌석 5)
2. 칩을 눌러 좌석이 바뀌는지 → 2·3단계 진행 → **등록 성공**
3. 매장을 하나 더 등록 → **"매장 등록 중 오류" 가 안 나는지**(이게 이번 최대 건)
4. 확인 쿼리:
```sql
-- 매장이 늘었는가 (이전엔 영원히 1행이었다)
SELECT id, username, email, status FROM sellers WHERE seller_type='store_owner';
-- 마감이 KST 로 맞는가 (저장은 UTC — 9시간 차이가 나면 실패)
SELECT id, name, group_buy_deadline, datetime(group_buy_deadline,'+9 hours') AS kst
  FROM products WHERE seller_id IS NOT NULL AND group_buy_deadline IS NOT NULL ORDER BY id DESC LIMIT 3;
```

## ⚠️ 이번에 틀렸던 판단 (제일 값진 부분)

1. **③ 을 고치다가 더 나쁜 걸 만들 뻔했다.** `listOperableStores().length` 로 게이트를 열면 승인 대기
   매장까지 세어져, 게이트는 열리고 좌석은 안 바뀌어 **이용권이 개인 좌석으로 등록**된다. 게이트를 넓힐
   때는 *"열린 다음에 실제로 할 수 있는가"* 를 같이 봐야 한다(③-c 로 교정).
2. **④ 는 컴포넌트 버그가 아니었다.** 처음엔 `KakaoMapPicker` 의 `dark:text-white` 를 지우려 했는데,
   그건 소비자 화면에서도 쓰이는 **정상 코드**다. 고칠 자리는 컴포넌트가 아니라 **대시보드가 `dark:` 를
   끄지 않는다는 사실**이었다(tailwind variant 한 줄). 같은 증상이 다른 공용 컴포넌트로 계속 번졌을 것이다.
3. **가드가 계약 대신 문자열을 못박고 있었다.** `home-panel-light-island.test.ts` 가 darkMode variant
   **전체**를 정규식으로 고정해, 같은 자리에 형제를 *추가*하자 — 그 섬의 계약은 그대로인데 — 빨간불이
   났다. 계약만 검사하도록 고쳤다. **가드는 "지금 값"이 아니라 "지켜야 할 성질"을 검사해야 한다.**
4. `--only` 는 정규식이 아니라 **부분일치**다. `"a|b"` 로 부르면 0건을 돌고 실패한다(가드가 그걸 잡아 준다).

## 🕳️ 같은 커밋에 든 별건 — cf-image 되돌림

같은 날 내가 넣은 "미지 호스트도 cdn-cgi 로" 를 **되돌렸다.** 근거였던
*"`onerror=redirect` 가 실패 시 원본으로 302"* 가 **라이브 실측에서 반증**됐다:
`HTTP/2 403 · cf-resized: err=9408` (검증 호스트의 없는 경로로 시험해도 동일 — URL 이 아니라 폴백 자체가
안 돈다). 그리고 `digitaloceanspaces.com` 을 **실측 없이 승격**해 403 을 만들었다(이 파일의 원래 규율은
`cf-resized: internal=ok` 실측 후 승격이고, 내가 그걸 안 지켰다). `cloudfront.net` 은 실측했으므로 유지.

## 🩸 ①-b 후속 — 행이 만들어진 뒤의 실패 (같은 날 3번째 커밋)

①의 UNIQUE 버그를 고치고 나서 핸들러를 다시 읽다 발견. `setSellerMeta` 와 `grantOperator` 가

그런데 `sellers` 행은 **이미 만들어져 있다.**

⇒ 사용자는 실패로 알고 다시 누른다. **①을 고친 뒤에는 그 재시도가 실제로 성공해서
같은 가게가 두 번 등록된다** — 즉 이 갭은 ① 수정이 배포되는 순간부터 진짜 문제가 된다.

무게가 달라서 다르게 다뤘다:
- **메타**(채널·좌표·플레이스) — 없어도 매장은 매장이다(프로필 수정으로 채워진다) → fail-soft.
- **권한**(`grantOperator`) — 실패하면 **방금 만든 매장에 아무도 못 들어간다**
  (`linked_user_id` 는 설계상 비워 두므로 접근 경로가 `seller_operators` 하나뿐).
  → 1회 재시도, 그래도 실패하면 **"실패" 라고 말하지 않는다**(매장은 존재하니까).
  재시도를 부추기지 않는 문구 + 매장 번호를 돌려줘 운영이 손으로 붙일 수 있게 한다.

## 🔭 별건 — Sentry 429 (대표 콘솔, 이번 수정 범위 밖)

`ingest.us.sentry.io/.../envelope/` 가 **429** 를 반복한다 = **할당량 초과로 에러 리포트가 버려지는 중**.
즉 **지금 우리는 라이브 에러를 못 보고 있고**, 대표가 콘솔을 직접 보여줘야만 알 수 있는 상태다
(이 세션의 발견 상당수가 실제로 그렇게 나왔다).

- `src/lib/sentry.ts`: `tracesSampleRate: 0.01`(2026-05-01 에 같은 429 로 이미 한 번 낮춤).
  **에러 `sampleRate` 는 미설정 = 100%.**
- 두 레버: ⓐ 이 PR 이 고치는 깨진 엔드포인트들이 에러 발생량 자체를 줄인다 ⓑ 에러 `sampleRate` 상한.
- ⚠️ ⓑ 는 **관측 가시성을 깎는 결정**이라 세션이 임의로 하지 않는다 — 대표 판단 사항.

### ⚠️ 내 검증 표에 허점이 있었다 (정정)

`support-contact` 의 **비로그인 401 은 판정 근거가 못 된다.** 그 라우트 그룹은 `requireSeller` 가
라우트 매칭보다 **먼저** 401 을 내므로, 그림자가 있든 없든 비로그인은 401 이다. 수정 전에 내가 기록한
400 은 **로그인 상태**의 값이었고, 배포 후 표에는 그 구분을 안 적어 뒀다.
⇒ **이 항목의 최종 확인은 셀러로 로그인한 브라우저에서 해야 한다**(콘솔에 400 이 안 뜨는지).
다른 두 개는 인증 미들웨어가 라우트 뒤에 있어 400/404 → 401 전이가 그대로 증거다.
