## 0. 다음 세션의 첫 액션

**배포된 뒤** 어드민 토큰을 잡고 아래를 그대로 실행한다. 이것이 "백업이 실제로 되는가"의 유일한 판정이다.

```bash
# 한 회차 수동 실행 — cron 을 기다리지 않는다
curl -sS -X POST "https://live.ur-team.com/api/admin/tools/backup-chunk" \
  -H "Authorization: Bearer $TOK" -H "User-Agent: $UA" \
  -H 'Content-Type: application/json' --data '{"maxReads":12}'
# 진행 상황(커서)
curl -sS "https://live.ur-team.com/api/admin/tools/backup-chunk" -H "Authorization: Bearer $TOK" -H "User-Agent: $UA"
```

읽는 법:
- `reason:"reads"` + `partsWritten>0` → **정상**. 계속 호출하면 스냅샷이 완성된다(반복 호출로 밀 수 있다).
- `reason:"error"` → `error` 필드에 **원문**이 있다. 이제 조용히 실패하지 않는다.
- `reason:"complete"` → 그 라벨(ads/main)의 스냅샷 1벌 완료. `manifest.json` 의 `counts`(테이블별 [파트,행])로
  잘림 여부를 판별할 수 있다.
- 502/CPU 로 끊기면 `maxReads` 를 6~8 로 낮춘다(무료 플랜 수동 경로의 알려진 벽).

## 2. 🩸 이번에 틀렸던 판단 (제일 값진 항목)

1. **"본진 DB 쓰기가 막혔다"고 대표에게 보고했다가 정정했다.** 근거로 삼은 것이 `cron_hb:%` 키의
   `MAX(updated_at)` 이었는데, **그건 하트비트만 멈춘 것**이고 `platform_settings` 전체로 보면 같은 시각에
   쓰기가 멀쩡히 들어가고 있었다(`ads_neis_cursor` 14:00, `group_buy_feed_cache` 14:55).
   ⇒ **부분집합의 침묵을 전체의 침묵으로 읽지 말 것.**
2. **"매장 78%가 폐업"으로 셀 뻔했다.** `trd_state_nm NOT LIKE '%영업%'` 으로 셌는데 실제 값은
   `개원`(138,839) · `운영(요양기관 현황)`(24,394) 이었다 — 전부 **영업 중**이다. 진짜 폐업은 **68건**.
   ⇒ 분류값은 **GROUP BY 로 먼저 눈으로 보고** 조건을 만든다.
3. **"용량이 부족하다"는 전제 자체가 틀렸다.** 무료 플랜은 **DB 10개 · 각 500MB · 총 5GB** 인데
   계정은 **7개 · 913MB(18%)** 만 쓰고 있다. 꽉 찬 건 **한 DB**(본진 100%)이지 계정이 아니다.
   그래서 "저품질 리드를 지워 공간을 만든다"는 계획을 짜고 있었는데, **대표 원칙은 "절대 삭제 금지"** 였다.
   ⇒ 정답은 삭제가 아니라 **DB 를 종류별로 나누는 것**이고, 남은 슬롯 3개가 필요한 수와 정확히 같다.
4. **`guard-mutations` 를 `audit-gate` 와 동시에 돌려 워킹트리를 오염시켰다.** 둘 다 소스를 잠깐 고쳤다
   되돌리는데, 겹치면 서로의 복원을 덮어써 **엉뚱한 파일 5개가 수정된 채로 남았다**(커밋했으면 사고).
   ⇒ **주입 검증은 반드시 단독으로.** 그리고 `pkill -f` 는 자기 셸까지 죽인다 — PID 로 죽일 것.
5. 서버측 D1 export 는 **또 실패했다**(이번엔 "Uploaded part 27", 이전엔 21). **두 번째 데이터 포인트라
   이 길은 확실히 막혔다** — 다음 세션은 이걸 다시 시도하지 말 것.

## 3. 남은 결정 (대표 판단 대기)

1. **cron 트리거 1칸을 백업에 줄 것인가.**
   지금 백업은 5분 cron 의 **다른 작업 10여 개와 같은 인보케이션**을 써서 서브리퀘스트 예산(무료 50)을
   나눠 쓴다. 죽은 주간 백업(`0 20 * * SUN`, 08-02 이후 매주 실패)을 `*/10 * * * *` 로 **교체**하면
   백업이 자기 인보케이션을 갖는다. 트리거 수는 그대로(4/5).
   ⚠️ **스케줄 PUT 은 원자적 전체 교체**라, 과거에 표현식 하나가 거부돼 **전체 cron 이 등록조차 안 된**
   사고가 있었다. 그래서 세션이 단독으로 하지 않는다 — 대표 승인 후, 배포 직후 `schedules` API 로 확인.
2. **본진의 유어애즈 중복분(726,417행) 정리** — 삭제가 아니라 *이사 끝난 짐 빼기*(같은 데이터가 유어애즈
   DB 에 있고 전수 대조 완료). **백업 1벌이 확인된 뒤**에만.
3. **유어애즈 DB 종류별 분리**(인플루언서/업체/매장) — 라우터(`adsLeadsDb`)에 줄 추가 + D1 3개 생성.
   **D1 생성은 대표가 대시보드에서** (플랫폼 쓰기는 세션이 하지 않는다).
