# 관측을 고치자 예산이 통제할 대상이 0 개가 됐다 — `gapMin` 이 두 뜻으로 겹쳐 쓰임

> 2026-08-03 세션. 오늘 **세 번째** 같은 형태다: 한 값을 두 함수가 다르게 읽는다.
> (①`0`=미설정↔쉬어라(#1007) ②시트 커서 스냅샷(#998) ③이번 `gapMin`.)

## 1) 다음 세션의 첫 액션

배포 후 **한 회차**면 판정된다. D1 읽기 전용:

```sql
SELECT value FROM platform_settings WHERE key='ads_dispatch_last';
```

* **고쳐졌다** = 도메인별 `deferred` 가 **다시 채워진다**(12:00 KST 실측은 네 도메인 전부 0).
  총 레인이 14 → `per_tick`(현재 2) 근처로 내려온다.
* **아직이다** = `deferred` 가 여전히 전부 0. 그러면 `periodMin` 이 실제로 실렸는지부터 볼 것
  (배포 번들에 들어갔는지 — 옛 코드 잔존 의심).

이어서 연쇄:
`ads_tick_history` 에 매시간 항목이 생기는가(부모가 꼬리까지 감) → `ads_sheets_cursor.off < total`
(#998 이 비로소 실행) → `ads_lanes_learned.cap` 이 바닥 2 에서 상승.

## 2) 무엇이 고장나 있었나 (실측)

12:00 KST 회차 — **14개 전부 `always`, `deferred` 전부 0**:

| domain | budget | always | run | deferred |
|---|---:|---:|---:|---:|
| influencer | 1 | 3 | 3 | 0 |
| company | 0 | 5 | 5 | 0 |
| prospect | 0 | 5 | 5 | 0 |
| wholesale | 1 | 1 | 1 | 0 |

11:00 KST 에는 `prospect` 가 `deferred 4` 였다(collect-hira·collect-neis·collect-store-kakao·enrich-prospects).
그 넷이 12:00 엔 전부 `run` 이다. 사이에 들어온 것은 **#1006**(11:23 KST 머지):

```ts
gapMin: opts?.gap            →   gapMin: opts?.gap ?? hourlyGapMinutes()
hourlyGapMinutes() = staleGapMinutes(60) = 60 × 2 + 30 = 150
isDeferrable(lane): return gap <= 60        // 150 > 60 → false = always
```

`gapMin` 이 **두 뜻으로 겹쳐 쓰인다**:
① 침묵 판정 임계(하트비트 `g` — 늦은 레인을 오탐하지 않으려 일부러 부풀린 값)
② 디스패치에서 미룰 수 있는지

#1006 은 ①을 채우려 값을 넣었고, 그 순간 ②가 매시간 레인 전부를 재분류했다.
**의도와 정반대다** — 매시간 레인은 다음 시간에 또 오니 가장 미루기 쉬운데, 그 주기를 *기록했다는
이유로* 가장 미룰 수 없는 레인이 됐다.

⇒ 예산·AIMD 학습기는 **미룰 수 있는 레인에만** 작용한다. 통제 대상이 0 개가 되어,
같은 날 배포한 **#1007(예산 0 구속)이 옳고도 무력**해졌다. 그리고 부모가 14개를 띄우다 죽어
꼬리의 `writeTickSummary`·`sheets-sync` 가 계속 안 돈다 = **#998 도 아직 한 번도 실행 못 함.**

## 3) 수리

`src/worker-ads/dispatch-budget.ts` + `index.ts` + `lane-cadence.ts` — 필드 분리.

* `LaneCandidate.periodMin` 신설(**실제 주기**) · `KickOpts.period` 신설. `isDeferrable` 은 `periodMin`
  을 먼저 본다. `gapMin` 폴백은 **남긴다**.
* `kick()` 은 **명시 `gap` 이 없을 때만** `periodMin: 60` 을 싣는다.
  ⚠️ 이 조건이 핵심이다 — 게이트 레인(일 1회·N시간·스케줄)에까지 60 을 실으면 **반대 사고**가 난다:
  미룰 수 있게 되고, 조 차례가 지정 시각이 아닌 때 걸리는 순간 **영영 안 돈다**(침묵이 아니라 부재라
  경보에도 안 잡힌다). 그래서 게이트 레인은 `gapMin` 폴백으로 종전과 **byte 동등**하게 `always` 로 남는다.

⚠️ **#1006 을 되돌리는 게 아니다** — 침묵 판정은 그 값이 있어야 돈다. 두 소비자를 끊는 것뿐이다.
⚠️ **부풀린 값에서 주기를 역산하지 말 것**(`(gap−30)/2`). 공식이 바뀌는 순간 조용히 깨진다 — 테스트로 고정했다.

검증: 유닛 46 pass · 주입 3종 전부 빨강(periodMin 분기 제거 / 게이트에도 60 / 역산) · 매니페스트 등재 2건.

## 4) 이번에 틀렸던 판단

**"1차(예산 0 구속)가 풀리면 2차가 순서대로 살아난다"** 고 보고했는데, 그 인과는 **#1006 이전 기준**이었다.
1차는 실제로 통과했는데(`budget=0 → run == always`) 2차는 하나도 안 왔다 — 예산이 닿는 레인이
사라졌기 때문이다. **결정값(`cap`)이 아니라 결과값(`ads_dispatch_last` 의 `run`/`deferred`)을 봐야 한다**는
교훈을 세운 직후에, 같은 자리에서 인과를 한 번 더 헛짚었다.

⇒ 다음 수리의 판정 지표도 결과값으로 잡았다: **`deferred` 가 채워지는가**.
