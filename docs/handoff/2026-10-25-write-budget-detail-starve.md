## 2. 이번에 고친 것

### ① `PROSPECT_VERIFY_STAMP_DAYS = 7` (`store-prospects.ts`)

도장 창을 1일 → 7일. **그 컬럼을 읽는 곳은 이 조건 하나뿐**(전수 확인 — 필터·정렬·판정·화면 0건)이라
비용은 "마지막 확인 시각" 해상도가 하루 → 7일로 거칠어지는 것뿐이고, 재방문 ~5.6회 중 1회만
쓰므로 **도장 쓰기 약 −82%** 가 기대값이다.

🩸 **같이 정정한 오기**: 2026-10-24 docblock 이 *"`is_new_open` 이 날짜 기준이라 하루 1회가 필요"*
라고 적어 뒀는데 **틀렸다** — 그 값이 뒤집히면 자기 OR 절이 직접 참이 된다. 그 오기를 믿으면
다음 세션이 창을 못 넓힌다(이 PR 이 막힐 수 있었다).

### ② 레코드 상한을 **서비스별 몫**으로 (`commerce-notify-collect.ts`)

`recordsPerService = floor(MAX_RECORDS_PER_RUN / services.length)` + 서비스별 누적 변수.
**전역 상한은 그대로 둔다**(그게 CPU 천장 — 몫만 두면 `N×(몫+페이지)` 로 넘친다. 둘이 짝이다).

🧮 **CPU 총량 불변**: 상한은 페이지를 *받기 전에* 보므로 양수 몫이면 각 서비스가 정확히 1페이지(500행).
종전 status 2장 + detail 0장 = 1,000행 → 이후 status 1장 + detail 1장 = **1,000행**.
⇒ `status` 수확 절반을 `detail` 이 받는 교환이고 파싱량은 안 는다.

⚠️ **서비스를 3개로 늘리면 전역 상한이 셋째를 또 굶긴다**(500+500 > 700). 그때는 상한·마감선을
**재측정**하고 올릴 것 — 몫만 늘리면 2026-08 의 CPU 사망으로 돌아간다. 가드 ①이 그 부등식을 센다.

`description` 이 `대표 심** · 정상영업 · 취급 06 · 판매 02` 모양인데, 취급 구간만 떼지 않고
`'취급 ' 뒤 전부`에서 `% 02 %` 를 찾았다 — **모든 행에 `판매 02` 가 붙어 있어** 코드 `02` 검사가
언제나 참이 됐다(어제 세션이 식품 정규식 `주\b` 가 `주식회사` 에 걸려 같은 종류로 틀렸고, 그 문서가
그걸 정정해 뒀다. **같은 작업 줄기에서 두 번째다**). ⇒ 같은 문자열에 여러 코드 필드가 섞여 있으면
**세그먼트를 먼저 자르고** 세라, 그리고 **100% 에 가까운 수치는 먼저 의심할 것**(분포가 그걸 뒷받침하지
않았다 — `02` 단독이 145건인데 99.8% 가 나올 수 없다).

### 그래도 coverage 는 **공짜로** 확인한다 — 16:00 회차가 저절로 만든다

텍스트 형제 가설은 확률이 낮아졌을 뿐 **0 이 아니고**, 확인 비용이 0 이다(코드 변경·요청 없이 ②의

(어제 문서가 그걸 범인으로 특정했다) 그 문서의 19키 목록은 이 질문에 답하지 못한다.

**판정 도구**: `ads_commerce_stats.diag.by_service.detail.coverage`

(status 쪽은 그렇게 18개 필드가 전부 보인다: `brno`·`bzmnNm`·`operSttusCdNm`·…).

⚠️ **`commerceProbe.goods.detail.kind` 로 판정하지 말 것** — 그 함수는 `GOODS_FIELD_ALIASES`
**여섯 개만** 보므로 "안 보는 텍스트 필드" 를 **구조적으로 못 본다**(그 파일 docblock 에 ⚠️②로 박아 뒀다).

**분기**:
- coverage 에 텍스트 품목 필드가 **있다**(확률 낮음) → 그 이름을 `g()` **뒤에 덧붙인다**(순서를 바꾸면

## 6. ✅ ① 도장 창 — **E4 통과(회차 단위)** · 누적은 내일 (2026-10-25 15:00 KST)

배포 후 **첫 회차**에서 바로 효과가 나왔다.

```
15:00 회차(06:00Z)  found=1747  saved=20     ← n < f   (hb at 06:00:22.896Z · rw=1834)
14:00 회차(05:00Z)  found=3693  saved=3693   ← 스킵 0%  (rw=18469)   ← 배포 전
```
`ads_lane_runs:collect-neis` 의 12회차가 **전부 `n == f`** 였던 것이 **처음으로 깨졌다**.

### 🔢 쓰기 비용은 **행당**으로 재야 한다 — 원시 `rw` 는 과장한다

| | 14:00(배포 전) | 15:00(배포 후) |
|---|---|---|
| `rw / found` | 18,469 / 3,693 = **5.00** | 1,834 / 1,747 = **1.05** |
| | | **−79%** |

**원시 `rw` 로 비교하면 18,469 → 1,834 = −90% 로 과장된다** — 이 레인은 회차마다 다른 지역을
돌고(`office=세종(I10)` ← 작은 지역) `found` 가 1,747~8,000 으로 흔들린다. ⇒ **분모를 맞추지 않은
감소율을 보고하지 말 것.** 행당 −79% 는 §2 docblock 의 추정치(−82%)와 거의 일치한다.

📌 행당 5.00 → 1.05 의 해석: 조건부 UPDATE 가 억제되면 **행 1 + 인덱스 4** 가 아니라 INSERT 시도
회계분(~1)만 남는다. 즉 수리가 노린 그 비용이 정확히 빠졌다.

### ⚠️ 첫 날 값을 정상 상태로 말하지 말 것

스킵률 **98.9%**(1,727/1,747)는 **첫 날 효과**다 — 그 행들은 전부 24시간 안에 도장이 찍혀 있어
7일 창 안쪽이라 **거의 전부** 건너뛴다. 정상 상태는 재방문 주기 ~35h ÷ 창 168h ⇒ **스킵 ~79%** 로
내려온다(한 행이 4.8회 방문 중 1회 도장). 그래도 "0%" 에서의 개선은 그대로다.

### ⚠️ 누적 예산값은 **아직 올랐다** — 그게 정상이다

`cron_hb:ads:read-budget` 의 `top=collect-neis` 가 **88,784 → 109,087**.
그 값은 **하루 누적**이라 리셋(09:00 KST) 전까지 계속 오른다 — 14:00 회차의 3,693 쓰기가 그 안에 있다.
⇒ **하락 판정은 10-26 오후**다(전용 체크인 예약됨). `written` 도 315,146 → 360,676 으로 같은 이유.

🧭 **그래서 ①의 판정 지표는 둘로 나뉜다**: *회차 단위*(`n < f`, `rw/found`)는 **한 회차로 즉시** 나오고,
*누적 단위*(`top`, `written`)는 **하루**가 필요하다. §3-1 의 교훈("집계가 느리다고 판정이 느린 건
아니다")이 그대로 적용된 자리다.
