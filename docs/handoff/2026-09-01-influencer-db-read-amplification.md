## 2026-09-01 (오후) — 인플루언서 DB: 한 달 전 수리가 왜 안 먹었나 (#1287)

### 판정 먼저 — #1257·#1284 는 먹었다

```
원부 전화 매칭   22,735,932행/58회  →  9,029행/153회      2,518배
업체 DB 12시간   44,149,063 → 14,595,363                  −67%
```

### 그리고 인플루언서 DB 를 팠다 (하루 1억 1,800만 행 — 업체 DB 의 4배)

**1위(4,111만 행/일)는 이미 2026-08-27 에 고쳐진 걸로 돼 있었다.** 부분 인덱스도 있고 테스트도
초록인데 라이브는 **회당 17만 행 그대로**였다. 범인은 옆에 있던
`idx_ad_inf_leads_bio(account_id, bio_checked_at)` — `bio_checked_at IS NULL` 이 99.9%를 통과시켜
**거르는 일은 못 하면서**, 플래너에겐 *동등 조건 두 개*로 보여 **부분 인덱스를 이긴다.**

⇒ 그 인덱스를 **지웠다**(`DROP INDEX IF EXISTS`). `bio_checked_at` 을 WHERE 로 쓰는 곳은 이 쿼리뿐(전수 grep).

### 🩸 이번에 틀렸던 판단 — "레포에서 확인 불가" 가 사실이 아니었다

08-27 테스트가 이렇게 적어 두고 넘어갔다:

> *"인덱스가 실제로 쓰이는지 — SQLite 옵티마이저의 판단이라 레포에서 확인 불가.
>   배포 후 `rows_read` 로만 판정된다"*

**확인 가능하다.** `node:sqlite` 로 플래너를 직접 돌리면 된다 — 업체 쪽
`company-read-amplification.test.ts` 가 이미 쓰던 방법인데 이 파일에는 안 왔다. 그 한 줄이 한 달을 벌었다.
⇒ `influencer-bio-scan.test.ts` 에 ③ 플래너 실증 블록 신설(11건).

### 🩸 픽스처가 두 번째를 잡았다 — DDL 순서

SSOT DDL 을 **그대로 실행**하는 픽스처로 바꿨더니 `idx_ad_inf_leads_bio_links` 가 안 만들어졌다.
그 인덱스가 참조하는 `bio_checked_at` 이 **아래 ALTER 로 생기는 컬럼**이라, 새 DB 에서는 그 문장만
조용히 실패하고(`runDdlOnce` 가 문장마다 `.catch(() => null)`) 체크섬은 저장돼 **영영 안 만들어진다.**
라이브는 컬럼이 이미 있어 만들어졌지만 그건 운이었다.
⇒ ALTER 뒤로 옮겼다. `region_todo` 도 같은 이유로 처음부터 뒤에 뒀다.
**교훈: ALTER 로 생기는 컬럼을 쓰는 인덱스는 반드시 ALTER 뒤에.**

### 넣은 것 (전부 `node:sqlite` 플랜 실증 + 결과 동일 확인)

| 대상 | 하루 | 처방 |
|---|---:|---|
| 링크인바이오 대상 선택 | 4,111만 | 방해하던 `bio` 인덱스 삭제 + `bio_links` 를 ALTER 뒤로 |
| `LOWER(email)`/`LOWER(instagram)` 조회 | 4,626만 | 식 인덱스 2개 (원부 전화와 같은 클래스) |

### 🩸 세 번째 — 끊긴 주입기가 파일을 되돌리지 않았다

`--only 'idx_ad_inf'` 가 0건으로 실패하고 이어 붙인 명령이 타임아웃으로 끊기면서
`influencer-schema.ts` 의 핸들 인덱스가 **주입된 채**(`(account_id, platform)`) 남았다. 그 뒤 검증이
전부 "주입 전에도 빨갛다"로 나왔다. 검증기의 `복원 실패 의심` 줄이 잡아 줬다.
⇒ **주입기를 죽였으면 반드시 `--verify-clean`.** 그리고 `--only` 는 **이름** 부분일치다(파일명 아님).

### 그런데 훨씬 큰 것이 돌고 있었다

```
"Your account has exceeded D1's free tier daily row read limit."   ← 09-02 13:0x KST, 읽기 전면 거부
```

업체 리드 DB(`0e9a8f82`) 테이블 목록을 직접 읽었다:
```
_cf_KV · ad_company_keywords · ad_company_leads · sqlite_sequence
```
**`platform_settings` 가 없다.** `ensureCompanySchema` 의 세 블록(키 v2 · 오수집 정리 · 카테고리 v3)은
전부 그 표의 플래그로 "이미 했다"를 기억한다. 표가 없으니 조회는 `no such table` → `.catch(() => null)`
→ "아직 안 했다", 실행은 **전수 UPDATE/DELETE**(회당 409,697행), 플래그 쓰기도 실패
→ **매 부팅마다 무한 반복.** 최근 12시간 상위 6개가 전부 이것 — 약 **1억 1,500만 행**.

원인은 `runDdlOnce` 가 `CREATE TABLE IF NOT EXISTS platform_settings` 를 **DDL 문장들 뒤**에 둔 것.
그 사이의 모든 플래그 조회가 실패한다.

### 고친 것
1. 설정 표를 **가장 먼저** 만든다(체크섬 조회보다 앞).
2. 기록이 남았는지 **읽어서 확인**하고 `gateStuck` 으로 알린다 — 실패가 조용하면 안 된다.
3. **기억할 수 없으면 비싼 마이그레이션을 안 한다**(데이터는 그대로, 정리만 늦어진다. 표가 생기면 다음
   부팅에서 정상적으로 1회 실행).

### ⚠️ 아직 모르는 것 (다음 세션의 첫 액션)
- **왜 그 DB 에 `platform_settings` 가 없었나.** 이번 수리는 원인과 무관하게 되풀이를 끊지만,
  원인은 안 밝혔다. 한도가 풀린 뒤(자정 UTC = 09:00 KST) 확인할 것:
  `SELECT name FROM sqlite_master` 로 **표가 생겼는지**, `ads_company_key_v2` 등 플래그가 남는지.
- 인플루언서 DB(`d4630482`)·메인 DB 도 같은 상태인지 확인(한도 때문에 못 봤다).
- 그 뒤 24h 재측정 — 업체 DB 가 1억+ → 수백만 대로 떨어져야 한다.

기본 150만/일 = 월 4,500만 < 포함분 5,000만).

## 🚧 2026-09-02 저녁 — 차단기가 걸렸는데 레인이 계속 돌았다 (#1311 에 추가)

### 실측
어드민 하트비트(19:00 KST):
```
ads:read-budget   used=1,708,128  budget=1,500,000  over=true
ads:lanes-paused  paused=true          ← 그 정각 회차는 면제 2개만 띄웠다(cron 게이트 정상)
```
그런데 그 뒤에도 레인이 계속 돌았다:
```
10:15 UTC  collect(rr 85,130) · collect-neis(rw 40,004) · collect-webkr · collect-hira · collect-store-kakao
10:24 UTC  enrich-influencer(rr 194,610) · -3 · -4
```
ur-ads 의 cron 은 `0 * * * *` **하나뿐**이라(wrangler-ads.toml) 10:15·10:24 는 cron 이 아니다.

### 원인 — 레인을 띄우는 길이 셋인데 게이트가 둘에만 있었다
| 길 | 게이트 | |
|---|---|---|
| ① cron `kick` | 있음 (`index.ts` `paused`) | |
| ② DO 알람 | 있음 (`lane-alarm.ts`) | |
| ③ **자기-체인 `SELF.fetch('/__ads/…')`** | **없음** | 인보케이션 천장을 넘기려고 레인이 스스로 다음 회차를 HTTP 로 부른다 |

③ 은 부모의 판단을 한 번도 안 거친다. ⇒ 차단기는 **"새로 시작"만 막고 "이미 달리는 체인"은 못 세웠다.**
⚠️ **같은 구멍이 수동 정지 스위치(`ADS_LANES_PAUSED`)에도 그대로 있었다** — 사고 때 쓰라고 만든
스위치가 사고 때 안 듣는다.

### 처방 — 호출부가 아니라 초크포인트
체인 kick 은 여러 파일에 흩어져 있고 앞으로 더 는다. 호출부마다 검사를 심으면 새로 생긴 하나가
조용히 빠진다(`check-ads-dispatch-bypass` 를 만들어야 했던 그 이유). 모든 길은 결국
`/__ads/*` 라우트로 들어오므로 **미들웨어 하나**로 ①②③ + 아직 없는 ④ 까지 덮는다.
- `self-beat` **뒤**에 둔다 — 막힌 회차도 하트비트를 남겨야 침묵 감시가 죽음으로 오인하지 않는다.
- **200 + `skipped`** 로 돌려준다(5xx 면 체인 부모가 실패로 읽고 재시도 → 그게 또 부하).
- 판정은 순수 함수 `laneEntryBlock`(lane-pause.ts) — **게으름까지 시험이 고정한다**(면제·정지에서
  원장 DO 를 물으면 안 된다 = 서브리퀘스트 낭비).
- 면제에 **관측 4종**(`health`·`alert-test`·`probe-public-data`·`silence-digest`) 추가 —
  같이 막으면 *멈춘 이유를 볼 수 없는 상태로* 멈춘다.

가드: 시험 31건 + 주입 2건 되돌려-검증 빨간불(`--only 초크포인트`).

### 대표 조치 대기 — 읽기 예산이 무료 플랜 숫자다
`ADS_DAILY_READ_BUDGET` 기본 150만/일은 **무료 한도(계정 500만/일)의 30%** 로 잡은 값이다.
유료 포함분은 월 250억 행 = **하루 8.3억** 이라 지금 예산은 그 **0.18%**. 오늘도 10시간 만에 걸렸다.
권고: `ADS_DAILY_READ_BUDGET=200000000`(월 60억 = 포함분 24%).
⚠️ **쓰기(`ADS_DAILY_WRITE_BUDGET`)는 150만 유지** — 포함분 월 5,000만에 실측 3,200만(64%)으로
이쪽이 진짜 빠듯하다. 발굴 폭을 넓히면 쓰기가 먼저 닿고, 그때 차단기가 멈추는 것은 **고장이 아니라
"$5 를 넘지 않는다"는 약속의 이행**이다.

### 🩸 #1321 의 두 값이 라이브에서 안 먹었다 — 진짜 레버는 `collect.runsPerHour` 였다

배포 직후 첫 정각(17:00 UTC) 실측:
```
last_keywords[9]        ← 폭 cap 을 14 로 올렸는데 그대로 9
total_runs 954 → 955    ← 회차를 12 로 올렸는데 시간당 +1
```

**왜 안 먹었나 (둘 다 다른 이유)**
1. `ADS_COLLECT_ROUNDS`(체인 깊이)는 `index.ts` 의 `if (!laneAlarmOn && …)` 안에서만 kick 된다.
   지금은 **DO 알람이 몰고 있어 체인 자체를 안 탄다** → 이 구성에서 **죽은 손잡이**.
2. 폭 cap 은 **천장일 뿐**이다. 실제 처리 수는 `planRoundWidthForShape`(최근 처리량 중앙값×1.2)와
   **인보케이션당 서브리퀘스트 예산**이 정한다(YT 동반 회차: 키워드당 ~6.2 → 예산 56 이면 ~9).
   cap 을 올려도 바닥이 안 밀린다.

⇒ **알람 구성에서 총량을 미는 유일한 축은 인보케이션 수** = `lane-alarm-runners.ts` 의
`collect.runsPerHour`. 이 파일 주석이 이미 그렇게 적어 뒀다(*"자기 인보케이션이 있어야 한다"*).
**1 → 3** 으로 올렸다.

**왜 12 가 아니라 3 인가** — 대표에게 보여 드리고 예산 검증한 숫자가 "3배"다:
```
collect 회차당 쓴 행 ~4,000~5,800 → 하루 ~117,000 (전체 쓰기 693,557 의 17%)
3배  → +234,000 → 하루 ~927,000 / 예산 150만 = 62%   ✅
12배 → +1,290,000 → 하루 ~190만 > 150만              ❌ 차단기가 자정 전에 멈춘다
```
승인 문구가 "다 해줘"라도 **보여 드린 것보다 큰 값은 넣지 않는다.**

⚠️ **다음 세션 교훈**: 이 레포에는 같은 일을 하는 손잡이가 여러 개고 **어느 것이 살아 있는지는
구성(알람이 모나 cron 이 모나)에 달렸다.** 값을 올리기 전에 *그 값을 읽는 코드가 지금 실행 경로에
있는지* 확인할 것 — 안 그러면 "3배 올렸다"고 보고하고 실제로는 아무 일도 안 일어난다(오늘 그랬다).
⚠️ 판정은 하루 뒤 `ads_naver_crawl_block.blocked` — 0 이 아니면 즉시 `runsPerHour: 1` 로 되돌린다.
