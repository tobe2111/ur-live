## 2026-09-01 (오후) — 인플루언서 DB: 한 달 전 수리가 왜 안 먹었나 (#1287)

### 판정 먼저 — #1257·#1284 는 먹었다

```
원부 전화 매칭   22,735,932행/58회  →  9,029행/153회      2,518배
업체 DB 12시간   44,149,063 → 14,595,363                  −67%
```

### 그리고 인플루언서 DB 를 팠다 (하루 1억 1,800만 행 — 업체 DB 의 4배)

**1위(4,111만 행/일)는 이미 2026-08-27 에 고쳐진 걸로 돼 있었다.** 부분 인덱스도 있고 테스트도
초록인데 라이브는 **회당 17만 행 그대로**였다. 범인은 옆에 있던
`idx_ad_inf_leads_bio(account_id, bio_checked_at)` — `bio_checked_at IS NULL` 이 99.9%를 통과시켜
**거르는 일은 못 하면서**, 플래너에겐 *동등 조건 두 개*로 보여 **부분 인덱스를 이긴다.**

⇒ 그 인덱스를 **지웠다**(`DROP INDEX IF EXISTS`). `bio_checked_at` 을 WHERE 로 쓰는 곳은 이 쿼리뿐(전수 grep).

### 🩸 이번에 틀렸던 판단 — "레포에서 확인 불가" 가 사실이 아니었다

08-27 테스트가 이렇게 적어 두고 넘어갔다:

> *"인덱스가 실제로 쓰이는지 — SQLite 옵티마이저의 판단이라 레포에서 확인 불가.
>   배포 후 `rows_read` 로만 판정된다"*

**확인 가능하다.** `node:sqlite` 로 플래너를 직접 돌리면 된다 — 업체 쪽
`company-read-amplification.test.ts` 가 이미 쓰던 방법인데 이 파일에는 안 왔다. 그 한 줄이 한 달을 벌었다.
⇒ `influencer-bio-scan.test.ts` 에 ③ 플래너 실증 블록 신설(11건).

### 🩸 픽스처가 두 번째를 잡았다 — DDL 순서

SSOT DDL 을 **그대로 실행**하는 픽스처로 바꿨더니 `idx_ad_inf_leads_bio_links` 가 안 만들어졌다.
그 인덱스가 참조하는 `bio_checked_at` 이 **아래 ALTER 로 생기는 컬럼**이라, 새 DB 에서는 그 문장만
조용히 실패하고(`runDdlOnce` 가 문장마다 `.catch(() => null)`) 체크섬은 저장돼 **영영 안 만들어진다.**
라이브는 컬럼이 이미 있어 만들어졌지만 그건 운이었다.
⇒ ALTER 뒤로 옮겼다. `region_todo` 도 같은 이유로 처음부터 뒤에 뒀다.
**교훈: ALTER 로 생기는 컬럼을 쓰는 인덱스는 반드시 ALTER 뒤에.**

### 🩸 세 번째 — 끊긴 주입기가 파일을 되돌리지 않았다

`--only 'idx_ad_inf'` 가 0건으로 실패하고 이어 붙인 명령이 타임아웃으로 끊기면서
`influencer-schema.ts` 의 핸들 인덱스가 **주입된 채**(`(account_id, platform)`) 남았다. 그 뒤 검증이
전부 "주입 전에도 빨갛다"로 나왔다. 검증기의 `복원 실패 의심` 줄이 잡아 줬다.
⇒ **주입기를 죽였으면 반드시 `--verify-clean`.** 그리고 `--only` 는 **이름** 부분일치다(파일명 아님).

### 그런데 훨씬 큰 것이 돌고 있었다

```
"Your account has exceeded D1's free tier daily row read limit."   ← 09-02 13:0x KST, 읽기 전면 거부
```

업체 리드 DB(`0e9a8f82`) 테이블 목록을 직접 읽었다:
```
_cf_KV · ad_company_keywords · ad_company_leads · sqlite_sequence
```
**`platform_settings` 가 없다.** `ensureCompanySchema` 의 세 블록(키 v2 · 오수집 정리 · 카테고리 v3)은
전부 그 표의 플래그로 "이미 했다"를 기억한다. 표가 없으니 조회는 `no such table` → `.catch(() => null)`
→ "아직 안 했다", 실행은 **전수 UPDATE/DELETE**(회당 409,697행), 플래그 쓰기도 실패
→ **매 부팅마다 무한 반복.** 최근 12시간 상위 6개가 전부 이것 — 약 **1억 1,500만 행**.

원인은 `runDdlOnce` 가 `CREATE TABLE IF NOT EXISTS platform_settings` 를 **DDL 문장들 뒤**에 둔 것.
그 사이의 모든 플래그 조회가 실패한다.

### 고친 것
1. 설정 표를 **가장 먼저** 만든다(체크섬 조회보다 앞).
2. 기록이 남았는지 **읽어서 확인**하고 `gateStuck` 으로 알린다 — 실패가 조용하면 안 된다.
3. **기억할 수 없으면 비싼 마이그레이션을 안 한다**(데이터는 그대로, 정리만 늦어진다. 표가 생기면 다음
   부팅에서 정상적으로 1회 실행).
