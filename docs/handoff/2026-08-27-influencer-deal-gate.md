# 인플루언서 소개 플로우 수리 (2026-08-27)

대표 지시: 매장·인플루언서·대행사 3주체 제안서를 만들려고 전체 플로우를 점검하다가,
**라이브에서 없는 보상을 약속 중인 화면**을 찾아 먼저 막았다.

## STEP 1 — `/influencer/discover` 거짓 약속 제거 (이 커밋)

**사고 내용**: 이 페이지는 어필리에이트(누구나 공유 2%) 시절 산물이라 *아무 상품이나* 추천
링크를 발급했고, 화면이 **"내 링크로 공구 참여하면 자동 commission 적립 · 매장이 거부한 경우
(드물게) commission 0"** 이라 안내하고 있었다. 어필리에이트는 **2026-08-22 종료**됐고
(대표 "심플하게") 지금 보상은 **매장이 제안한 딜**에만 붙는다 — 그런데 딜은 **0건**이다.
즉 "드물게 0"이 아니라 **항상 0**이었다.

버그보다 무겁다: 인플루언서가 링크를 뿌리고 첫 정산에서 0원을 보면 그 관계는 거기서 끝난다.

**수정**
- `marketing.routes` 카탈로그(`discoverApp.get('/products')`)에 `optionalAuth()` +
  상품마다 `my_deal_pct` 동봉. 딜 조회는 **매장별 1회 배치**(상품마다 `findActiveDealPct` 를
  부르면 100 왕복). 조건 3개는 결제 적립 SSOT 와 **문자 그대로 동일**하게 유지.
  ⚠️ `requireAuth` 가 아니라 `optionalAuth` 인 이유 — 원래 무인증 라우트라 비로그인 카탈로그가
  통째로 401 이 된다. 둘러보기 자체를 막을 이유는 없다.
- `InfluencerDiscoverPage` — 딜 있으면 링크 버튼 + `내 소개비 N%` 배지, 없으면
  "이 매장과 딜을 맺어야 소개비가 붙습니다"(로그인) / "로그인하면 내 딜을 확인"(비로그인).
  하단 안내와 SEO description 을 사실대로 교체.
- 가드 `discover-deal-gate.test.ts` 4건 신설.

## ⚠️ 이번에 가드가 두 번 헛돌았다 — 다음 세션 주의

되돌려-검증에서 **주입했는데 초록**이 두 번 떴다. 둘 다 *앵커를 잘못 잡은* 경우다:

1. `/SELECT[\s\S]*?p\.seller_id/` 로 컬럼 존재를 봤더니, 같은 쿼리 아래쪽
   **`LEFT JOIN sellers s ON s.id = p.seller_id`** 에 걸려 컬럼 목록에서 지워도 통과했다.
   → **`SELECT`~`FROM products` 사이(컬럼 목록)만** 잘라서 검사하도록 교정.
2. `toContain('p.my_deal_pct != null')` 로 버튼 분기를 봤더니, **배지**(`&& (`)에도 같은
   문자열이 있어 버튼 삼항을 `true ? (` 로 바꿔도 통과했다.
   → **`'p.my_deal_pct != null ? ('`(삼항 형태)로 앵커**하도록 교정.

교훈: **같은 문자열이 파일 안 다른 곳에도 있는지 먼저 세어 볼 것.** 그리고
**주입이 실제로 적용됐는지 매번 확인할 것**(A는 처음에 perl 패턴이 안 먹은 줄 알았는데
실제로는 적용됐고 테스트가 헛돈 것이었다 — 확인 없이는 둘을 구분 못 한다).

## STEP 2 — 소개자 프로필(opt-in) + 매장 검색 (같은 PR)

`users` 전체를 셀러에게 열 수는 없고(가입자 전원 노출 + 개인정보 룰 위반), 실적 랭킹은
실적이 있어야 뜨는데 딜이 0건이라 비어 있다(닭-달걀). **소개자 공개 프로필 테이블이 아예 없었다.**

**신설**

## STEP 3 — 매장 영입을 증거 있게 (같은 PR)

**그 전엔 세팅 경로가 어드민 수동 지정 하나뿐**이라, 2% 영입 보상을 약속해 놓고 대표가 매번
손으로 넣어야 했고 분쟁 시 근거가 없었다.

- `/store/new?ref={user_id}` — 소개자 초대 링크로 등록한 매장은 **등록 순간 자동 귀속**
  (`introduced_by_influencer_id` + `introduced_at`). 기산점이 곧 **1년 유효기간의 시작**이다.
- 검증 셋: 실재 유저일 것 · 본인이 자기 매장을 영입할 수 없음 · 실패는 조용히(귀속 실패가
  매장 등록을 막지 않는다).
- ⚠️ **sessionStorage 경유**(`utils/store-referrer.ts`): `/store/new` 는 로그인 필수라 카카오를
  다녀오면 **쿼리스트링이 날아간다.** 그 사이 ref 를 잃으면 소개자가 데려오고도 보상을 못 받는다.
  localStorage 가 아닌 이유 — 몇 달 전 스쳐 본 링크가 엉뚱한 매장에 귀속되면 안 된다.

- 어드민 수동 지정은 **남겼다** — 예외·정정에 필요하다.

## STEP 4 — 대행사 지갑 (게이트 OFF 배선, 같은 PR)

**대표 확정**: *"유어딜은 대행사에게 돈을 주지 않는다. 대행사는 자신들이 직접 중개수수료를 버는
구조"* + 대행사가 낀 매장은 유어딜이 10%가 아니라 **5%만 받아 벌 자리를 비워 준다**.
그런데 `fee-resolver` 는 대행사 몫을 **유어딜 수수료 안에서** 떼고 있었다(정반대).

- `FeeRates.agencyFromOwner` 게이트 신설. **기본 false = 계산이 현행과 byte 동일.**
- 켜지면 대행사 몫이 **2차 재원(결제액 − 유어딜 몫)** 에서 나가고, `platformNet === platform`
  (유어딜 5%/10% 가 온전히 남는다). `ownerGross`·`ownerNet` 에서도 함께 차감 — 안 빼면 합이
  결제액을 넘고 주인 몫이 음수가 된다.
- `FeeBreakdown.agencyFromOwner` 기록 — 불변식이 **모드별로 합계를 다르게 세야** 하고,
  기록에 남아야 나중에 "이 주문은 어느 규칙이었나"를 알 수 있다.
- 불변식 분기: 켜짐이면 `platform + agency + supply + promo + ownerNet = amount` ·
  `platformNet === platform` · `agency ≤ 2차 재원`. 꺼짐이면 종전 그대로.
- 가드 `agency-wallet.test.ts` 9건. 되돌려-검증 3종(게이트 무효화 / ownerNet 차감 누락 /
  기본값을 켜짐으로) 전부 빨강 확인 후 복원.

### ⚠️ 켜기 전 필수 (아직 안 함)
1. **호출부 배선** — 지금은 리졸버(순수함수)만 준비됐다. `loadFeeRates` 가 이 게이트를
   `platform_settings` 에서 읽어 오게 하고, 대행사 몫 지급 레일(`payee_type='agency'`)에
   실제로 태우는 작업이 남았다.
2. **대행사가 맺은 딜은 대행사 몫에서 차감** — 딜에 "누가 맺었나"를 기록해야 판정된다(미구현).
3. **staging 실결제 + 환불 역전** — 네 몫의 합이 1원도 안 틀리는지, 환불 시 **전부** 역전되는지.
   한 곳만 남으면 그게 그대로 손실이다.
4. 대행사 상한(자기 계약 % 이내로만 인플루언서에게 약속 가능) — 미구현. 없으면 대행사가
   남의 돈으로 인심을 쓴다.

## 정산 간소화 (대표 "어드민에서 최대한 간편하게")

**진짜 부담은 규칙이 아니라 손이체였다** — 시스템은 "누구에게 얼마"까지만 계산하고, 대표가
은행에서 **건별로 이체**한 뒤 돌아와 건별로 송금완료를 마킹한다. 수취인 30명이면 매주 30번이다.

- `GET /admin/payouts/transfer-csv` — **은행 대량이체 서식**(정산ID·은행·계좌번호·예금주·금액·적요).
  계좌 3종이 다 있는 건만 싣고 빠진 수는 `X-Skipped-Count` 헤더로. BOM 붙여 엑셀 한글 보존.
  ⚠️ 어드민 가이드는 예전부터 "CSV 다운로드 → 은행 일괄이체 → 완료 후 업로드" 를 안내했는데
  실제 CSV(`/settlement/export-csv`)는 **주문 단위 회계 내역서**라 은행·계좌가 아예 없었다.
  문서가 없는 기능을 안내하고 있었다.
- `PATCH /admin/payouts/bulk-sent` · `/bulk-approve` — 최대 200건.
- ⚠️ **가드를 다시 구현하지 않았다.** 단건 핸들러의 세 겹 가드(계좌 누락 / 기간 중복 / CAS)를
  `worker/utils/payout-sent.ts` 로 뽑아 **단건·일괄이 같은 함수를 부른다.** 따로 짜면 갈리고,
  갈린 쪽이 조용히 이중지급을 만든다.
- 일괄은 실패해도 **전체를 되돌리지 않는다** — 이미 나간 돈을 장부에서 지우면 더 위험하다.
  건별 결과를 돌려주고 화면이 실패분만 다시 처리한다.

### 어드민 화면 (배선 완료)
`/admin/payouts` 에 체크박스(행·전체) + `BulkPayoutBar` — 이체 파일 받기 / 일괄 승인 / 일괄 송금완료.
- **필터를 바꾸면 선택을 비운다** — 안 보이는 행이 선택된 채 남으면 화면엔 3건인데 30건이 처리된다.
- **일괄 송금완료는 건수·합계를 보여 주고 확인받는다.** 이건 *돈이 나갔다는 기록*이라 잘못 누르면
  안 나간 돈이 나간 것으로 박히고 수령자는 영영 못 받는다.
- CSV 응답의 `X-Skipped-Count` 가 0 이 아니면 **경고를 띄운다** — 계좌 없어 빠진 건을 조용히
  넘기면 그 수령자만 계속 못 받는다.

## 🏪 추가 — 유어샵 카드 통일 + 비로그인 둘러보기 (대표 신고 2건, 2026-08-27)

대표: *"유어샵도 지금 이용권 UI가 예전 UI 디자인으로 되어있더라? 그리고 비로그인도 둘러는 볼 수 있게
해야지, 결제 단계에서 로그인을 하게하거나 그게 맞지 않아?"* — 둘 다 사실이었다.

### ① 카드가 두 세대로 갈려 있었다
2026-08-19 에 카드를 한 벌(`GroupBuyFeedCard` + `DealCardMedia`, 그루폰식)로 합쳤는데 **홈·섹션만**
갈아 끼웠고 유어샵은 7월에 통일했던 `BrowseProductCard` 그대로였다. 세 군데였다:
`VouchersTab`(매장 자기 이용권) · `CuratorPinsSection`(사업자 유어샵 핀) · `CuratorPage` PinCard(일반유저 핀).

### ⚠️ 이 통일이 **돈을 조용히 새게 할 뻔했다** — 다음 세션이 꼭 알아야 할 것
담은 핀은 반드시 `/u/{handle}/p/{productId}` 로 가야 한다. 그 경로가 클릭을 기록하고 **`?aff=` 귀속**을
붙인다(`curator.routes.ts` redirect). 그런데 `GroupBuyFeedCard` 는 목적지를 **스스로**
(`canonicalDetailPath`) 정한다 — 그냥 갈아 끼웠으면 **화면은 똑같은데 소개비 귀속만 사라진다.**
에러도 안 나고 아무도 모른다.
→ 카드에 **optional `to`** 를 additive 로 열고(`to ?? canonicalDetailPath(p) ?? …`, 기본 동작 불변),
핀 호출부 2곳이 그걸 넘기는지 `urshop-card-unify.test.ts` 가 고정한다. 매니페스트에도 등록했다.

### 덤: 이용권이 쇼핑 상세를 거쳐 튕기고 있었다
`VouchersTab` 이 `to={/products/:id}`(쇼핑 상세)로 보냈고, 거기서 `canonicalDetailPath` 가
`/group-buy/:id` 로 되돌렸다. **결과는 맞지만 페이지 한 장을 헛로드**했다. 이제 카드가 SSOT 로 직행한다.

### ② 비로그인 둘러보기 — 소비자 경로는 이미 열려 있었다
라이브 실측: 유어샵 `/api/curator/{handle}` **200** · 이용권 목록 **200** · 이용권 상세 **200**.
즉 "둘러보기 열림 → 결제에서 로그인" 원칙은 이미 지켜지고 있었다. 막힌 건 **소개자 카탈로그** 하나.

### 🩸 그리고 그건 내가 어제 잘못 적은 것이었다
어제 PR #1226 에 *"`optionalAuth` 로 비로그인도 둘러볼 수 있게 했다"* 고 적었는데, **라우터 레벨의
`discoverApp.use('*', requireAuth())` 가 먼저 401 을 내서 실제로는 안 열려 있었다.**
라우트에 미들웨어를 덧붙이는 것으로는 **상위 게이트를 못 푼다** — 내 `optionalAuth()` 는 죽은 코드였고,
`authed: false` 분기도 도달 불가였다. 라우터 레벨을 `optionalAuth()` 로 고치고 라우트의 중복은 제거했다.
⇒ **교훈: "고쳤다"는 배포 후 실제로 찔러 봐야 안다.** 이번엔 라이브 curl 이 잡았다.
