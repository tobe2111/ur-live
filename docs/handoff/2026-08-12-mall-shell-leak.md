## 2. 검증 방법 — 라이브 브라우저는 못 쓴다

```
로컬 빌드 + Chromium (실측)
  몰 /test                액자=false  유어딜레일=false   ← 고쳐짐
  유어딜 /my-vouchers      액자=true   유어딜레일=true    ← 정상(대조군)
  유어딜 /wishlist         액자=true   유어딜레일=true    ← 정상(대조군)
```

⚠️ **첫 대조군을 `/vouchers` 로 잡았다가 둘 다 false 가 나왔다** — 그 페이지는 원래 풀너비
(`isFullBleedPcPath`)라 대조군이 못 된다. **측정 대상이 0 이면 통과처럼 보인다**는 이 레포의
단골 함정을 그대로 밟을 뻔했다. 액자를 쓰는 페이지로 다시 잡아야 판정이 성립한다.

⚠️ **라이브 URL 로는 브라우저 검증 불가**: `urdeal.kr` 은 curl 로는 되는데
**headless Chromium 은 프록시에서 `ERR_CONNECTION_RESET`** 이다(`*.pages.dev` 프리뷰는 CONNECT 403).
⇒ 시각 회귀는 **로컬 빌드 + 실브라우저**로 보고, 라이브는 curl(상태/메타)로만 본다.

### 🐛 되돌려-검증이 **테스트 자체의 결함**을 잡았다 (오늘 네 번째·다섯 번째)

배너를 실제로 렌더해 보는 동작 테스트를 붙였는데, 주입 2건이 **초록으로 빠져나갔다.**
주입이 적용됐는지부터 확인(`grep`)했더니 적용은 돼 있었다 — 원인은 테스트 쪽이었다:

1. **`waitFor(() => expect(innerHTML).toBe(''))` 는 처음부터 비어 있으면 첫 시도에 즉시 통과**한다.
   조회가 끝난 뒤 간판이 채워져도 못 잡는다. ⇒ `settle(fetchSpy)` 로 **조회 완료를 기다린 뒤** 단언.
2. **이름 가드를 지워도 `undefined.slice()` 크래시가 대신 막아** 결과가 같았다.
   가드가 일한 게 아니라 **우연히 안전**했던 것. ⇒ 이름을 먼저 정규화하고 그 값으로 판정하도록 수정
   (우연에 기대지 않는다). 그러자 가드 제거 주입이 제대로 빨강이 됐다.

⚠️ 그리고 **브라우저 E2E 로는 이 화면을 못 본다**: 로컬엔 워커가 없어 `/checkout` 이 로그인·장바구니
데이터를 못 받고 **결제 본문에 도달조차 못 한다**(홈 셸이 렌더된다). 그 상태로 "간판 없음"을 확인하면
*측정 대상 0* 인 통과다 — 오늘 같은 함정을 네 번 만났다.

## 9. 주문 내역 — **서버가** 가게를 찍는다 (같은 날, 대표 "계속 해")

세션 흔적으로는 여기를 못 고친다. **"이번 세션에 몰을 지나갔다" 와 "이 주문이 몰 주문이다" 는
다른 명제**이고, 주문 내역은 지난 주문이라 흔적이 아예 없다. ⇒ `products.mall_id`(서버)가 답이다.

- `stampOrdersMall(DB, orders)` (`worker/utils/mall-consumer.ts`) — 주문 N 개에 **쿼리 1회**
  (`order_items ⋈ products ⋈ wholesale_malls`, IN + GROUP BY). fail-closed 3중은
  `pickConsumerMall` 과 동일(`consumer_path=1` · `active=1`) — **도매몰이 소비자 주문 내역에
  가게로 뜨면 서비스 분리가 깨진다.** 실패·컬럼 미적용은 조용히 no-op
  (주문 목록이 안 뜨는 것보다 가게 이름이 없는 편이 낫다).

  (undefined) 종전 표시 그대로 — **본진 화면 무영향**.
- ⚠️ `types/order.ts` 는 인덱스 시그니처가 `unknown` 이라 **필드를 명시하지 않으면 JSX 에서

### 🐛 죽어 있던 라우트를 하나 더 찾았다 (두 겹)

```

클라   /api/seller/support-contact    →  라우터 마운트는 /api/seller/gb  (경로 자체가 다름)
```

⇒ 정적 경로를 `/:id` **앞으로** 이동 + 클라 경로 교정. 테스트가 **등록 순서를 인덱스로** 고정한다.

### 운영자가 자기 링크를 몰랐다

운영자 화면 전체에 `mall_slug` 참조가 **0건**이었다. 공구 서비스의 유통 경로가 카톡 공유 하나인데

⇒ `GET /api/seller/gb/mall`(연결 여부·슬러그·이름) + `MyMallAddress`(주소·복사 버튼, **미연결이면
"본점에 올라간다"고 알림**). 조회 실패는 미노출이지만 **미연결은 조회 성공 사실이라 반드시 보여 준다.**

## 12. 운영자 셀프 온보딩 — **최소안 구현** (대표 "최소안으로 진행해줘")

몰 생성(`super_admin` + IP whitelist)과 셀러↔몰 연결(`UPDATE sellers SET mall_id`)이 **둘 다 수동**이라
매장이 열 곳만 돼도 대표가 매번 붙어야 했다. ⇒ **운영자가 신청 · 어드민은 승인만.**

| | 무엇 |
|---|---|
| `worker/utils/mall-applications.ts` | 신규 — `mall_applications` ensure(WeakSet 메모이즈) + partial UNIQUE(셀러당 pending 1건) |
| `POST /api/seller/gb/mall/apply` | 신청. 🔴 **아무것도 만들지 않는다** — 슬러그는 영구 주소라 사람이 한 번 본다 |
| `GET /api/admin/wholesale-malls/applications` | 대기열(super only) |
| `POST …/applications/:id/approve` | 몰 생성 + 셀러 연결 + **기존 본진 상품 이관**을 한 번에 |
| `MyMallAddress` | 미연결이면 신청 폼, 심사 중이면 "심사 중" |
| `MallApplicationsPanel` | 어드민 대기열(0건이면 미렌더) |

### 🔴 승인은 **선점 먼저**(claim-before-create)

`pending → approved` CAS 로 이 요청만 진행시킨다. 먼저 만들고 나중에 표시하면 동시 승인 두 건이
**몰을 둘 만든다**(슬러그 UNIQUE 가 두 번째를 막아도 첫 번째는 이미 생겼다).
실패하면 `pending` 으로 되돌린다 — 안 그러면 그 신청이 대기열에서 영영 사라진다.

슬러그 판정은 **양쪽 모두 기존 SSOT** 를 쓴다(신청=`isMallSlugCandidate`, 승인=`rejectReservedSlug`
— 그 파일의 몰 생성과 같은 함수). 경로마다 기준이 갈리면 신청 경유로만 통과하는 예약어가 생기고,
그건 소비자 라우트를 죽인다.

### 🐛 같은 실수를 하루에 두 번 했다

주석에 **`mall_id=1`** 이라고 쓴 것만으로 `mall-id-isolation` 래칫이 빨강이 됐다 —
오늘 아침 #1137 에서 이미 겪은 것과 **같은 함정**이다(그때도 가드가 아니라 주석을 고쳤다).
⇒ 본문 표기를 `본진 몰(id 1)` 로. **가드는 옳았다.**

그리고 CI 가 잡은 것: 나는 `mall-surface-boundary` 와 `mall-origin-banner` **둘만** 돌리고
`mall-id-isolation` 을 안 돌렸다. ⇒ **`mall-*` 전체를 돌린다**(16파일 257건, 명령은 §13).

되돌려-검증 5건 빨강 확인(신청이 몰 생성 · 슬러그 SSOT 우회 · 선점 없이 생성 · 실패 시 복원 없음 ·
슈퍼관리자 게이트 제거).

## 15. 🐛 자체 점검이 잡은 것 — **되돌리기가 반쪽이었다** (같은 날 후속)

CI 초록 뒤에 승인 경로를 다시 읽었더니 세 군데가 틀려 있었다. 셋 다 **내가 오늘 쓴 코드**다.

| | 무엇이 틀렸나 | 결과 |
|---|---|---|
| A | 실패 시 신청만 `pending` 으로 돌리고 **만든 몰은 남겼다** | 재승인이 slug 중복 검사에 걸려 **영원히 409** — 대기열엔 보이는데 안 열리고 화면에 이유가 없다 |
| B | `UPDATE sellers SET mall_id` 에 **가드가 없었다** | 신청 후 어드민이 그 셀러를 다른 몰에 수동 연결해 두면 묵은 신청 승인이 **덮어쓰고 상품까지 옮긴다** |
| C | 상품 이관을 `.catch(() => null)` 로 삼켰다 | 조용히 **빈 가게**가 열린다 — §12(⑤)가 없애려던 *"왜 내 가게엔 안 보이지"* 를 그대로 재생산 |

수정: 되돌리기를 **만든 순서의 역순 전부**로(상품 원복 → 셀러 연결 원복 → 몰 삭제 → 신청 `pending`),
셀러 연결은 `WHERE id = ? AND COALESCE(mall_id, ?) = ?` 로 **본진에 있을 때만**, 상품 이관은 안 삼킨다.

🔑 **교훈**: *"실패하면 되돌린다"* 라고 주석에 쓴 것이 곧 되돌아간다는 뜻이 아니다.
**무엇을 만들었는지 세어 보고 그만큼 되돌리는지**를 확인해야 한다. 나는 주석을 써 놓고 반만 짰다.
그리고 이건 **가드가 아니라 다시 읽어서** 찾았다 — CI 는 전부 초록이었다.

되돌려-검증 3건(몰 삭제 제거 · 셀러 가드 제거 · 이관 재삼킴) 각각 해당 테스트만 빨강 확인 후 복원.

## 16. 남은 보완점 처리 (대표 *"남은 보완점 너가 최대한 이상적으로 해줘"*)

### ① 결제 완료의 몰 판정 → **서버 신호** (잠금 파일 추가 접촉 **0**)

세션 흔적은 **양방향으로 틀린다**: 새 탭·복귀면 몰 손님인데 흔적이 없고, 구경만 하고 본진 상품을
산 손님에겐 흔적이 남는다. ⇒ 결제 완료 URL 의 `?orderId=` 로 **주문 자체**를 묻는다.

- `GET /api/mall/of-order/:orderNumber` — `requireAuth` + `orders.user_id` 대조.
  **주문번호만 알면 남의 주문 가게를 알 수 있게 두지 않는다.** 비로그인·실패는 `mall: null`(200).
- 배너가 **스스로** 묻는다. 서버가 "몰 주문 아님"이라고 답하면 **흔적이 있어도 안 그린다.**
- 🔒 `PaymentSuccessPage` **추가 수정 0** — 렌더 1줄 그대로다. 판정을 잠금 파일로 올리면
  다음 세션이 거기에 조건을 얹기 시작하고 승인 절차가 이름만 남는다.

### ② 한 주문에 두 가게가 섞이면 — **승자를 명시로**

`GROUP BY oi.order_id` 에 몰 컬럼을 얹어 두면 SQLite 가 **임의 행**을 고른다 → 같은 주문이
조회마다 다른 가게로 보일 수 있었다. ⇒ **품목 수 많은 가게**, 동수면 **몰 id 작은 쪽**.
판정은 순수함수 `pickOrderMall` 로 빼서 DB 없이 고정했다(`auditMallSlugs` 와 같은 방침).

### ③ 다크 짝 색 파생 — **AA 를 증명하며**

`branding.ts` 주석이 *"임의 파생이 AA 를 깨면 확정을 어긴다"* 며 다크를 항상 기본 딥그린으로
뒀었다. 맞는 경계였지만 그 말은 **파생 금지가 아니라 증명하며 파생하라**는 뜻이다.
⇒ `deriveMallColorDark` — 밝기를 올리며 잉크 글자 대비 **AA 를 만족하는 첫 지점**을 고르고,
색상을 지키면서 못 만들면 **기본값으로 물러난다**(안 보이는 버튼은 브랜딩이 아니다).
색상환 24개 + 극단값 7개 전수 통과.

> 🔴 **여기서 내가 앞서 한 말이 틀렸다**: 체크아웃 색 승계의 관문은 *대비*가 아니라 **잠금**이다.
> 결제 버튼은 `TossPaymentWidget.tsx`(Toss 감사 잠금) 안에 있다. 대비 쪽은 이제 끝났으니
> **대표 승인만 있으면** 색 적용은 바로 된다. 승인 없이 잠금 파일을 건드리지 않았다.

### ④ 신청 화면이 운영자를 기다리게 두지 않는다

- `GET /mall/slug-check` — 주소가 되는지 **타이핑 중에** 안다(판정은 신청·승인과 같은 SSOT).
- 승인되면 **스스로 다시 묻는다**(탭 복귀 + 심사 중 60초, 연결되면 폴링 중지).
  그전엔 승인이 끝나도 "심사 중"이 남아 운영자가 *"안 됐나 보다"* 로 읽었다.

### 🐛 오늘 여섯 번째 — **타입 주석과 정리 코드가 가드를 만족시켰다**

새로 만든 가드 두 개가 되돌려-검증에서 **초록으로 빠져나갔다**:
- `/visibilitychange/` → **`removeEventListener('visibilitychange'`** 가 남아 통과
- `/setInterval/` → **`ReturnType<typeof setInterval>`**(타입 주석)이 남아 통과
- `isMallSlugCandidate` → 슬라이스를 파일 끝까지 잘라 **아래 `/mall/apply` 의 같은 호출**이 잡힘

⇒ **거는 쪽**(`addEventListener('visibilitychange'` · `= setInterval(`)을 앵커하고, 슬라이스는
**그 핸들러까지만** 자른다. 재주입하니 셋 다 빨강.

🔑 오늘 하루에 같은 클래스를 여섯 번 만났다. 공통점은 하나다 —
**"그 이름이 파일에 있다"는 "그 동작이 살아 있다"가 아니다.**

## 19. **어드민 카테고리 분류** — 넷째 서비스가 밴드를 못 받고 있었다 (대표 2026-08-16)

> 대표: *"어드민 대시보드 카테고리 페이지들 분류를 제대로 할 필요가 있어."*

### 왜 8/14 에 고쳤는데 또 나왔나 — 폴백이 원인이었다

8/14 에 공구 서비스 밴드를 만들며 *"서비스가 넷이면 밴드도 넷"* 이라고 적었는데, 실측해 보니

**"⚙️ 공통 · 회원·재무·검증·시스템"** 헤더 아래에 그려지고 있었다.

원인은 사람의 누락이 아니라 구조다. `navSectionOf` 가 그룹 **제목을 문자열로 맞춰보고**
안 맞으면 조용히 `'common'` 으로 떨어뜨렸다 — **아무것도 안 하면 공통 서랍으로 빨려 들어가는
기본값**. 게다가 라벨은 자주 바뀌므로(8/14 에도 바꿨다) **이름을 고치면 밴드가 말없이 이동**하는

⇒ `NavGroup.section` 을 **필수 필드**로 만들고 폴백을 없앴다. 이제 새 그룹은 밴드를
*말해야만 컴파일된다*. `domain`(RBAC)과 `section`(렌더)도 분리했다 — 한 값에 묶여 있으면
한쪽만 바꾸는 게 불가능하다.
