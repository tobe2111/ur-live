**① 인계가 지목한 레인이 틀렸다.** 넘어온 인계는 *"나라장터 수집(`collect-nara-vendor`)이 유력"* 이라고

### ① 전화번호 하이픈 위치 — **고쳤다** (873건)

```
0704-667-2900  ← 070-4667-2900    16682606     ← 1668-2606 (8자리는 매칭 실패)
```

⚠️ **다음 세션은 v2 누계로 다시 판정할 것.** v1 의 98% 를 인용하지 마라.
⚠️ 그리고 `guess 2.65%` 도 v1 값이라 일부 오염됐다(webkr 강등분). v2 를 기다려라.

## 20차 (2026-08-18 오전) — **B2B** 수집: 무너진 건 수확이 아니라 회차였다

대표 *"지금 b2b db 수집하는 거 맞지? 자동으로 계속 수집량을 유지 및 확대할 수 있도록 해줘"*.
19차까지는 인플루언서 쪽만 봤다. B2B 를 따로 재니 **더 심각했다.**

### 실측 — B2B 는 사실상 레인 하나다

```
업체 일별(KST)   08-11 13,409 → 08-15 9,705 → 08-17 4,223 → 08-18 ~3,500 페이스   (−70%)
소스 구성        commerce 95%+ · storeinfo 소진(1,413 → 0) · local/webkr/nara 합쳐 200 안팎
```

그리고 **원인은 고갈이 아니었다**:
```
회차당 수확   ~990 으로 완전히 안정(490·144 는 부분 회차)
신규율        saved 982 / found 1,000 = 98%          ← 소스는 아직 한참 남았다
회차 수       08-13 10회 · 08-15 11회 · 08-16 9회 · 08-17 **4회**
```
⇒ **수확이 준 게 아니라 회차가 안 돌았다.** (하루 상한은 12회 = 짝수시.)

### 왜 회차당 건수를 못 올리는가 (손대면 안 되는 손잡이)

`commerce-notify-collect.ts` 헤더가 **CPU 사망을 겪고** 내려잡은 값이라고 못 박고 있다 —
*"수확을 되찾으려면 마감선을 올릴 게 아니라 레코드당 CPU 를 줄여야 한다"*.
현재 회차: `found=1000 elapsed_ms=19,370 stopped_by=records`(상한에 실제로 닿는다).
**`MAX_RECORDS_PER_RUN`·`RUN_DEADLINE_MS` 는 건드리지 말 것** — `ads-cpu-deadline.test.ts` 가 지킨다.

### 그래서 고친 것 — 주기를 **상수가 아니라 제어 루프**로

남은 손잡이는 주기뿐인데, **공공 API 일일 한도를 우리는 모른다**(CLAUDE.md: 미조사).
고정으로 2h→1h 를 박으면 한도가 있을 경우 **가장 큰 B2B 소스를 통째로 깨뜨린다.**

`lane-adaptive-interval.ts` — 연속 6회 무사고 **그리고** 신규율 ≥50% 일 때만 간격을 절반으로.
사고 한 번이면 즉시 기본으로(비대칭은 의도 — 조이는 데 증거 6회, 푸는 데 1회).
한도에 부딪히면 오류로 나타나 **스스로 물러난다**(한도를 몰라도 된다).

- ⚠️ **`ceil` 이다.** `floor` 면 base 3 이 1 이 되어 3배가 된다. 지금 모든 레인이 base 2 라
  **겉으론 같아 보이는 것이 함정**이고, 실제로 그 주입이 처음엔 초록이었다(가상 base 3·5 로 고정).
- 🔒 신규율 게이트가 **소진된 레인을 자동 배제**한다 — storeinfo(found 50 · saved 0)는 오류가 없어
  무사고로 보이지만 신규율이 낮아 조여지지 않는다. 없으면 중복만 두 배로 긁는다.

### 그리고 — **실패한 회차가 슬롯을 먹고 있었다**

```
08-18 00:00   외부 API 네트워크 오류 · 0건   → lastRunAt 스탬프 → 01:00 유휴 → 02:00 에야 982건
```
스탬프를 안 찍으면 다음 시간이 곧바로 재시도한다(시간당 1회 상한이 폭주를 막는다). 08-17 의 빈 슬롯
8개가 이 클래스라면 회차당 ~990 × 8 ≈ **8,000건**이 그냥 버려진 것이다.

| 근거 부족 시 **침묵** | 새 축·데이터 공백에서 헛경보 |
| **상태 전이에만** 알림 | 무너진 동안 매일 같은 경보 → 채널이 꺼짐 |

### 🩸 그리고 첫 설계가 **완만한 하락을 못 잡았다**

⚠️ **임계를 낮춰 맞추지 않았다** — 한 표본에 임계를 맞추는 건 과적합이고 오경보를 늘린다.

## 24차 (2026-08-19 오후) — **부족분 자동 보강** (대표 *"다른 곳에서 보강하듯 자동으로 조절"*)

⇒ **보강은 부족분의 10% 안팎이다. 대체재가 아니다.** 그래도 하는 이유 둘:
① 네이버 검색 API 쿼터는 25,000/일 중 **0.7%** 만 쓴다 — 막는 건 상대가 아니라 우리 예산이다.

### 설계 — 조이기·감속과 같은 비대칭

|---|---|
| **유효기간**(30h) | 감시가 멎어도 보강이 남아 **켜진 채 잊힌다**(이 레포의 반복 클래스) |

| **하루 1회 판정에서만** | 매시간 밀어 넣으면 진동한다 |
