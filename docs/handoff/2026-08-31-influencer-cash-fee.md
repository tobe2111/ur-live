# 현금 정산 수수료 — 마진을 상품이 아니라 현금 출구에서 걷는다

**대표 확정** (2026-08-31): *"현금으로 정산받을 땐 수수료 10%이고, 딜로 교환권, 이용권은 공짜로."*
+ *"계속 진행해줘."*

## 왜 이 방향인가 (앞 세션의 결론)

보너스를 **딜 쪽에** 얹으면 딜의 구매력이 **상품 마진에 의존**한다. 교환권 마크업이 20% 라서
딜 보너스 20% 가 성립했고, 마진이 5~10% 인 이용권에 같은 딜을 쓰면 유어딜이 건당 8~14원 적자였다.
수수료를 **현금 쪽에** 두면 딜은 언제나 액면 그대로라 **어떤 상품에 써도 안 깨진다**(1딜 = 1원 고정).

## 무엇을 넣었나

- **신규 SSOT** `src/shared/influencer-payout-math.ts` — `computeCashPayout()` 가
  총액 → 수수료 → 과세표준 → 원천징수 → 실송금액을 한 번에 낸다.
- 설정 `platform_settings.influencer_payout_cash_fee_pct`, **기본 0**.
  어드민 `/admin/commission-settings` 에 입력칸 추가(딜 보너스 바로 아래 — 한 쌍이라 같은 자리에).
- 🔴 **기본 0 이라 머지만으로는 라이브 정산이 1원도 안 바뀐다.**

### 곁가지로 고친 것 — 원천징수가 세 곳에서 따로 계산되고 있었다

`cron/influencer-payout.ts` · `marketing.routes.ts` · `AdminInfluencerPayoutsPage.tsx` 가
각자 계산했다. 수수료를 얹으면 **네 번째**가 된다. 셋을 SSOT 로 모았다.
갈리면 "화면엔 90만원인데 실제로 보내야 할 건 87만원" 이 되고, **송금은 사람이 손으로 하므로
그 숫자가 곧 오지급**이다.

`/payouts/process` 는 이제 현금 경로에서 내역을 계산해 **응답으로 돌려준다** — 그전엔 잔액만
0 으로 밀고 끝이라, 얼마를 보낼지는 화면이 자기 상수로 따로 계산했다.

## 🔴 세무 확인이 필요한 지점 (대표 판단)

**원천징수 대상액 = 총액 − 수수료** 로 구현했다("지급되는 금액이 곧 소득"). 대안은 총액을 소득으로
보고 원천징수한 뒤 수수료를 따로 떼는 것이다.

| 100만원 · 수수료 10% · 사업소득 3.3% | 실송금 |
|---|---|
| 현재 구현 (과세표준 = 90만원) | **870,300원** |
| 대안 (과세표준 = 100만원) | 867,000원 |

수수료가 0 인 동안은 두 해석의 결과가 같다. **율을 올리기 전에 확정할 것.**

⚠️ **"수수료 먼저냐 원천징수 먼저냐"로 생각하면 틀린다** — 둘 다 곱셈이라 순서는 결과를 안 바꾼다.
갈리는 것은 *과세표준에서 수수료를 빼느냐* 다. (내가 처음에 순서 문제로 적었다가 테스트가 잡았다.)

## 이번에 틀렸던 판단 (다음 세션이 같은 데서 안 미끄러지게)

1. **"순서가 갈림"** — 위 참조. 교환법칙 때문에 순서는 무의미하다.
2. **원천징수를 `rate * 100` 한 %로 계산**했다. `0.088 * 100 = 8.799999999999999` 이라
   100만원 기타소득에서 **87,999원**이 나왔다(분수로 곱하면 88,000원). 옛 코드 세 곳이 전부
   그랬다. 1원이지만 국가에 낼 세금이고 매 건마다 난다 → 분수로 곱하도록 고쳤다.
   ⚠️ 그래서 **기타소득 현금 정산은 옛 코드 대비 원천징수가 1원 늘어난다**(실송금 1원 감소).
3. **가드 두 개가 헛돌았다** — 주입해 보고 알았다.
   - 수수료 `||` 폴백: **기본값이 0 이라** `Number('0') || 0` 도 0 이라 동작으로는 구분 불가.
     → 소스 검사로 고정(기본값이 0 이 아니게 되는 날 조용히 깨질 자리).
   - 어드민 화면 자체계산 회귀: 파일에 호출이 **하나만 남아도** 통과했다(두 자리인데).
     → 호출 자리 수(≥2)로 고정.
   ⇒ **주입해 보기 전엔 가드가 산다고 믿지 말 것.**

## CI 가 잡은 것 (첫 푸시 빨간불)

**파일크기 래칫** — 수수료를 얹으니 `marketing.routes.ts` 가 820줄(baseline 801)이 됐다.
CLAUDE.md 의 처방은 리베이스라인이 아니라 **분리**라, 어드민 송금 엔드포인트 2개를
`marketing/payouts.ts` 로 떼어냈다(`marketing/discovery.ts` 선례, 로직 이동만 — 상대경로
깊이 한 단계와 섹션 헤더 주석 외 diff 0). 736줄로 내려왔다.

그리고 **이동이 내 테스트를 낡은 지도로 만들었다** — SITES 가 `marketing.routes.ts` 를
가리킨 채여서 코드 없는 파일을 검사하게 됐다. 테스트가 빨간불로 잡았고 경로를 따라갔다.
같은 이동에서 슬라이스 기반 검사도 두 번 깨졌다:
1. `\n  }\n` 로 블록을 잘랐는데 함수 안으로 들어가며 들여쓰기가 2칸 깊어져 슬라이스가 넘어갔다
   → 위치 비교(indexOf 순서)로 교체.
2. 이름만 검사해 `ReturnType<typeof computeCashPayout>` **타입 선언**이 걸렸다 → 호출은
   괄호까지(`computeCashPayout(`) 봐야 한다.
⇒ **소스를 문자열로 자르는 가드는 리팩토링에 약하다.** 위치·토큰 기준으로 쓸 것.

되돌려-검증 4종을 **이동 후에 다시** 돌려 전부 빨간불 확인했다(이동 전 결과는 못 믿는다).

**두 번째 빨간불 — SQL bind 불일치.** 알림 문구에 수수료를 넣으면서 `bind()` 인자 **안에서**
중첩 템플릿 리터럴을 만들었는데, 그 안의 **콤마** 때문에 `check-sql-bind-params` 가 인자를
2개가 아니라 3개로 셌다(placeholders=2, bind args=3).

⚠️ 이건 CLAUDE.md 가 다른 가드에서 이미 겪은 함정과 같은 클래스다 —
*"콤마 split 로 짰더니 `${...}` 표현식 **안의** 콤마 때문에…"*.
⇒ **bind 인자 안에서 문자열을 조립하지 말 것.** 밖에서 만들고 변수만 넘긴다.
