## 결론 — 페이지는 있었다. 닿을 수가 없었다.

`/seller/group-buy`(목록·발행현황·매장 PIN·**수정 진입**)가 곧 이용권 관리 통합 페이지다.
세 신고가 **한 뿌리**에서 나왔다:

1. **그룹 전체가 `mode: 'store'`** → `isStoreOwner` 가 아닌 셀러에겐 통째로 숨김.
   그런데 **이용권 *등록*은 `common`**(2026-08-23 대표 지시) → **만들 수는 있는데 그 뒤가 없는** 상태.
   라이브 실측(D1 읽기): 대표 개인 셀러 2개(`tobe2111`·`tobe211111831`)가 **둘 다 `influencer`**,
   `store_owner` 는 홍대돈까스(id 14) 하나뿐. 즉 대표가 개인 계정으로 보면 **정말로 메뉴가 없다.**
2. **수정 버튼은 그 페이지 안에만 있다.** 상품 목록(`/seller/products`)은 `SELLER_STORE_ONLY_MODE`
   로 nav 에서 빠져 있어, 관리 페이지가 숨으면 **이용권을 수정할 화면 경로가 0** 이 된다.
3. 매장 단독 셀러의 심플 nav 에선 보이긴 했는데 이름이 **"내 딜"** — 찾는 단어가 아니다.
4. 덤: 이용권 하나를 운영하는 일이 **세 화면에 흩어져** 있었다(목록 / 사용처리 / 후기 인증).

  **이용권 등록 + 이용권 관리** 두 항목(대표 *"이용권 등록이랑 같이 이용권 통합 관리 페이지"*) —

- **`src/shared/seller-handle.ts`(신규 SSOT)**: 서버 자동 발급 아이디(`store_<base36>` ·

## 후속 ④ — 번들 예산이 **아무도 안 받는 바이트**를 세고 있었다 (CI red 규명)

#1336 Verify 가 `총 raw JS 8.60 MB > 8.6 MB` 로 빨간불. 라벨 30여 개를 추가한 것이 선을 넘겼다.

**규명**: 총량 예산이 **여섯 언어 청크를 전부** 더하고 있었다(ja 291 · ko 275 · fr 271 · es 266 ·
en 247 · zh 239 = **약 1.55 MB, 총 raw 의 18%**). 그런데 `src/i18n.ts` 는 사용자 언어 **하나만**
dynamic import 한다 — 나머지 다섯은 **어떤 사용자도 받지 않는다.**
⇒ 이 예산은 실제 무게가 아니라 *"번역을 추가했는가"* 를 재고 있었고, CLAUDE.md 가 6개 언어 동시
추가를 **의무화**하므로 **규칙을 지킬수록 예산이 깨지는** 구조였다.

**수정(교정이지 완화가 아니다)**: 가장 큰 언어 하나만 센다. 임계값도 그만큼 내렸다 —
`8.6 → 7.45`(실측 7.34) · gzip `2.9 → 2.45`(실측 2.30). **비-언어 코드에 걸리는 압력은 오히려 세졌다**:
종전 여유 0.09 MB 는 1.55 MB 짜리 언어 완충재 위에 있었다. critical-path(240 KB) 는 무접촉.
이 파일 이력이 남긴 지침 그대로다 — *"다음에 닿으면 상향이 아니라 lazy 청크 정리"*(08-03) ·
*"정리 후보: locale-ja/ko 각 ~280KB"*(08-04). **9번째 상향을 하지 않았다.**

**실제로 깨뜨려 확인**: dist 에 가짜 400KB 청크 → 7.73 로 빨간불(감지기 살아 있음) ·
가짜 `locale-ko-*` 400KB → **그것이 최대 언어가 되어** 총량에 반영 + gzip 예산이 잡음(사각지대 없음).
가드 `bundle-budget-locale-2026-09-03.test.ts` 7건 — **전제(언어 1개만 로드)** 까지 고정한다.
누군가 i18n 을 "전부 preload" 로 바꾸면 이 교정의 전제가 깨지므로 그때 빨간불이 뜬다.
되돌려-검증 3건(제외 해제 / 임계값 8.6 환원 / 정적 로드) 빨간불 확인.
