# 2026-08-05 — B2B 수집 페이지가 느린 이유는 **화면에 없는 917KB** 였다

대표 신고: *"대시보드의 b2b 수집 페이지가 너무 느려."*

## 1. 실측 — 마운트가 받는 네 요청

```
/api/admin/partner-pool/meta        1.4 KB   0.60s
/api/admin/partner-pool/keywords  917.0 KB   1.36s   ← 4,546개
/api/admin/partner-pool/stats      17.0 KB   1.44s
/api/admin/partner-pool?limit=50   38.0 KB   0.51s
```

키워드 하나가 **나머지 셋 합의 16배**다. 그런데 그걸 쓰는 패널(`CompanyKeywordManager`)은
`showOps` 안에 있고 **기본이 접힘**이다 — 그 917KB 는 **한 번도 화면에 그려지지 않은 채**
매 진입마다 전송됐다.

🩸 **왜 오래 안 보였나**: 렌더 쪽은 이미 최적화돼 있었다 — `details` 게이트, 상위 80개 미리보기,
`useMemo`. 코드를 보면 "이 패널은 최적화됨"으로 읽힌다. **비용이 렌더가 아니라 전송에 있었기 때문**에
그 최적화들이 오히려 시야를 가렸다.
⇒ **느린 화면은 렌더보다 "마운트가 실제로 받는 바이트"를 먼저 재라.**

## 2. 수리

`loadKeywords()` 를 마운트 이펙트에서 빼고 `showOps` 가 처음 켜질 때 한 번만 부른다(`useRef` 1회 가드).
`onChanged={loadKeywords}` 재조회는 그대로 — 사용자가 키워드를 켜고 끄면 즉시 반영돼야 한다.

**효과**: 초기 전송 **917KB → 0**(패널을 열 때만). 나머지 셋은 상단 카드가 항상 쓰므로 손대지 않았다.

## 3. 안 고친 것 (알고 남긴다)

- `stats` 1.44s — 서버 계산이 무겁다. 상단 카드·경보가 항상 쓰므로 지연 대상이 아니다.
  줄이려면 **서버 쿼리를 쪼개야** 한다(별건).
- `keywords` 가 4,546개를 통째로 주는 것 자체 — 검색이 **클라이언트**라 서버에서 자르면 검색이 깨진다.
  서버 검색으로 옮기면 그때 자를 수 있다.

## 4. 가드

`partner-pool-lazy-keywords.test.ts` 5개 — 마운트 이펙트가 키워드를 **안** 부름 · `showOps` 배선 ·
1회 가드 · `onChanged` 재조회 유지 · meta/stats 는 지연 안 함. 주입 1건(마운트로 되돌리기) 빨강 확인.

## 5. 같은 브랜치에서 **분리해 보류한 것**

유튜브 발굴의 `videos` 콜 수확 계측(`DiscoverCalls.videos_email/contact/cat/empty`)을 만들었다가
**stash 로 뺐다**(`git stash list` → `yt-videos-yield-instrumentation`).

이유: 그 변경이 `influencer-discovery.ts` 를 건드려 `check-rules-version-bump` 가 뜬다
(REEXTRACT_RULES_VERSION). 내용은 **카운터뿐이고 추출 규칙은 안 바뀌었지만**, 가드는 그걸 구분 못 한다.
- **bump 는 지금 해롭다** — 어제 3으로 올린 재추출 패스가 **진행 중**인데 4로 올리면 그 진행을 버리고
  같은 추출기로 36,880행을 다시 돈다. CPU 가 지금 가장 희소한 자원이다.
- **`rules-version-ok` 예외는 영구다** — 상수 줄에 붙으면 이후 *진짜* 규칙 변경도 조용히 통과한다.

⇒ 둘 다 나쁘므로 **판단을 미루고 관심사를 분리**했다. 다음 세션이 정할 것:
   ⓐ 계측을 규칙 파일 밖으로 옮긴다(구조 변경) ⓑ 예외를 쓰고 다음 규칙 변경 때 제거(기억 의존) ⓒ 재추출
   패스가 끝난 뒤 bump(대기).

## 6. 왜 이 계측이 다음 순서인가 — 발굴 우선 방향(2026-08-05 대표)

대표 확정: *"지금은 발굴에 최대한 힘 쏟고, 발굴 가치가 떨어질 때쯤 측정에 유료전환."*

발굴 병목 실측(03:00 회차):
```

picks     planned 16 → processed 6                 ← 예산 51/56 소진으로 10개 키워드 미처리
수확      yt found 119 → saved 38  |  naver found 563 → saved 386
```
**유튜브 쿼터는 24/90 밖에 안 쓴다** — 병목은 구글이 아니라 서브리퀘스트다. 그 24개를 줄이면
키워드 처리량이 바로 오르는데, **그 24개가 뭘 벌어오는지는 아직 아무도 안 셌다.**
찍어서 줄이면 수율이 같이 떨어진다 → 그래서 `videos_empty` 비율부터 재는 것이다.
