# 미실행 키워드 구제 — 회차당 1개로 충분한가 (2026-08-06)

## 배경: #1079 라이브 판정은 **실패**였다

배포 3시간 뒤 실측(KST 08-05 05:10) — 목표 축이 **하나도** 안 움직였다:

| 카테고리 | 미실행 (배포 전 → 후) | 3h 실행 |
|---|---|---|
| 숙소 | 12/19 → **12/19 그대로** | 0 |
| 골프 | 6/6 → **6/6 그대로** | 0 |
| 외식창업 | 6/18 → **6/18 그대로** | 0 |

**#1079(축 배수)는 축 *사이* 몫을 고쳤는데, 이 굶주림은 축 *안*의 위치 문제였다** —
셋 다 우선/일반 풀의 id 순 뒤쪽에 붙어 커서를 며칠 기다린다. 축에 슬롯을 더 줘도 순번 시점은 안 바뀐다.

⚠️ **내가 순서를 잘못 잡았다.** "가장 이상적"으로 셋(①신규를 커서 자리에서 ②배수 ③계획=예산)을 꼽고
**②만 구현**했는데 증상의 원인은 **①**이었다.

## 🔁 중복 구현을 걷어냈다 (이 세션의 결론)

①을 `pickWithStarvedFirst`(축별 슬롯의 **절반**)로 구현해 PR #1089 까지 올렸는데,
그 사이 **다른 세션이 같은 아이디어를 main 에 먼저 머지**했다 — `pickStarvationRescue`
(회차당 **1개**, 미실행 중 id 최소). 두 벌을 두면 반드시 갈라지므로 **내 것을 철회**하고
main 것을 SSOT 로 둔다. (#1055·#1060 에서 같은 판단을 한 전례가 있다.)

## ⚠️ 다음 세션이 판정할 것 — 회차당 1개면 며칠 걸린다

미실행 **59개**(08-05 실측) ÷ 1개/회차 ≈ **2.5일**(시간당 1회차 가정).
`pickWithStarvedFirst` 였다면 하루 안이었다. 어느 쪽이 맞는지는 **라이브가 답한다**:

```sql
SELECT category, COUNT(*) n, SUM(CASE WHEN last_run_at IS NULL THEN 1 ELSE 0 END) never,
       SUM(CASE WHEN last_run_at >= datetime('now','-1 day') THEN 1 ELSE 0 END) d1
  FROM ad_discovery_keywords WHERE active=1 GROUP BY category ORDER BY n DESC
```
- **하루 뒤 `never` 합계가 59 → 35 안팎이면** 회차당 1개가 예상대로 도는 것 — 그대로 두고 이틀 더 기다린다.
- **거의 안 줄면** 구제가 실제로는 회차당 1개도 못 태우는 것이다. 그때 후보는 두 가지:
  ① `pickStarvationRescue` 몫을 1 → 슬롯 비례로 올린다(**함수 하나만** 고칠 것 — 두 벌 만들지 말 것)
  ② 진짜 병목이 **회차당 처리량**(계획 16 vs 처리 6, 예산 51/56)이므로 그쪽으로 간다

### ⚠️ 내가 틀렸던 것 — 처리량 걱정은 기우였다
나는 *"회차당 1개면 59개 소진에 2.5일"* 로 계산하고, 내 `pickWithStarvedFirst`(슬롯의 절반)가
**더 낫다**고 인계에 적었다. 실제는 **하루 미만**이었다. 계산이 놓친 것:
**구제 1개는 정상 순환에 *더해지는* 몫**이고, 미실행분은 커서가 도달하면서도 소진된다 —
둘을 더하지 않고 구제분만으로 나눈 게 오산이었다.
⇒ **내 중복 구현을 철회한 판단은 결과적으로도 옳았다.** 절반 방식이었다면 과잉이었고,
  그만큼 정상 순환(수확 있는 키워드)의 몫을 불필요하게 빼앗았을 것이다.
