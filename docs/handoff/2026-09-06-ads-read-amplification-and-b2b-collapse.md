# 2026-09-06 — 유어애즈 읽기 증폭 2건 · B2B 업체 수집 붕괴 규명

> 대표 신고: *"지금 b2b쪽 db 수집이 잘 안되는 것 같은데?"* → 실측 확인 후 *"응 해"* → *"계속 진행"*

## 다음 세션의 첫 액션

**배포 후 판정 — 단, 09:00 KST 이후에 볼 것.**

⏰ **먼저 시각을 확인하라.** 읽기 예산은 **UTC 자정 = 09:00 KST** 에 리셋된다(`read-budget.ts` `utcDay`).
배포는 2026-09-06 15:10 KST 에 끝났는데 **그날 예산은 11:32 KST 에 이미 소진**돼 그 뒤로 레인이
하나도 안 돌았다 ⇒ **새 코드는 그날 한 번도 실행되지 않았다.**

🩸 **그래서 하트비트에 남은 883만·19.6만은 배포 *전* 값이다.** 09:00 이전에 그 값을 보고
"수정이 안 먹었다"고 판정하면 틀린다. 하트비트의 `at` 이 **배포(09-06 15:10 KST) 이후**인지
먼저 확인하고, 아니면 아직 판정 시점이 아니다.

PR #1368 은 `2f917a56` 로 머지됐고 배포 실행 #4683 성공(06:10 UTC). 아래 두 숫자를 본다.

```bash
# 어드민 토큰 → CF 토큰 (CLAUDE.md "어드민 진단 접근" 절차 그대로)
# 그다음 main DB(d9530ba6-7a26-4c02-9295-3ce5aef112a3) 에서:
SELECT key, value FROM platform_settings
 WHERE key IN ('ads_lane_alarm_last:collect','ads_lane_alarm_last:enrich-influencer-2',
               'cron_hb:ads:read-budget')
```

| 보는 값 | 배포 전 | 배포 후 기대 |
|---|---:|---|
| `collect` 의 `rr` | 8,829,466 | **급락**(점 조회로 바뀜) |
| `enrich-influencer-2` 의 `rr` | 196,518 | **2,600 안팎** |
| `cron_hb:ads:read-budget` 의 `used` | 3시간 만에 2억 | 창이 늘어야 정상 |

그 다음 **B2B 업체 수집**이 회복되는지(아래 §2). 회복되면 읽기 예산 상향은 불필요할 수도 있다 —
**낭비를 걷어낸 뒤의 실수요로 판단할 것.**

## 1. 이번에 고친 것 (PR #1368)

### ① `collect` 레인 — 회차당 883만 행 (측정된 읽기의 83%)

`influencer-save.ts` 의 백필 조회가 복합 유니크 인덱스 `(account_id, platform, channel_id)` 에서
`platform` 을 빼고 물어 **계정 전체(18.9만 행)를 훑고 있었다.** 라이브 실행계획으로 확인:

```
platform 없음  SEARCH ... USING INDEX idx_ad_inf_leads_instagram_ci (account_id=?)
platform 포함  SEARCH ... USING INDEX sqlite_autoindex_ad_influencer_leads_1
```

🩸 **이 조회는 2026-09-04(#1348)에 쓰기를 줄이려고 내가 넣은 것이다.** 쓰기는 줄었지만 훨씬 비싼
읽기를 샀고, 그 읽기가 일일 예산을 태워 B2B 붕괴의 상당 부분을 만들었다.
⇒ 수정: 청크를 플랫폼별로 갈라 점 조회. 가드 `ads-backfill-noop.test.ts` ⑯.

### ② enrich 샤드 — 회차당 19.6만 행을 읽고 **산출 0**

```
rr 196,518 = bio 폴백 193,898 + naver 선정 2,619 + 설정 1
결과       = selected 0 · bio 0 · spent 0
```

샤드 4개 × 시간당 30회차 ⇒ **시간당 2,330만 행.** 링크인바이오 큐는 이미 고갈(후보 0건).

부분 인덱스는 2026-08-27 에 만들어 뒀는데 **계획기가 안 골랐다** — `bio_checked_at IS NULL` 이
전체의 99.9%라 `idx_ad_inf_leads_bio` 는 거르는 일을 못 하는데, 통계가 없으면 계획기는
"두 컬럼을 다 쓸 수 있는 쪽"을 고른다. 라이브 **193,898행 vs 2,573행(75배)**.
⇒ 수정: `INDEXED BY idx_ad_inf_leads_bio_links` + 실패 시 이름 없는 조회로 폴백(fail-open).
가드 `ads-bio-scan-index.test.ts` 5건.

## 2. B2B 붕괴 — 두 줄기 중 **한쪽만** 무너졌다 (이번 세션이 정정한 판단)

⚠️ 세션 초반에 "B2B 수집이 무너졌다"고 뭉뚱그려 보고했는데 **절반만 맞았다.**

```
              업체(ad_company_leads)   매장후보(store_prospects)
08-30              7,867                    3,128
09-01              6,276                    2,473
09-04                 78  ←98% 감소         2,207   ← 안 무너졌다
09-05                122                    1,259
09-06(14시)          376                    1,896
```

- **업체(대행사)** = `commerce` 레인(통신판매업 신고). **이쪽만 붕괴.** B2B 물량의 92%.
- **매장후보** = HIRA·지방행정 인허가. 계속 돌고 있었다. **다른 DB·다른 테이블**이라 놓치기 쉽다.
  - `store_prospects` 는 **`d4630482`(urads-leads-db)** 에 있고 시각 컬럼은 `collected_at`.

🔑 **끊긴 쪽이 하필 대표가 제안을 보낼 "대행사" 줄기**다(이메일 보유율 79%로 이미 발송 준비된 쪽).

### 붕괴의 3층 구조

1. **읽기 예산 차단기**가 하루 창을 00~02 UTC(3시간)로 좁힘 ← 원인은 §1 의 두 조회
2. **시각 고정**된 레인 9개가 그 창 밖이라 영영 안 돎 → #1362 로 수리(배포 완료, 오늘 실제로 돌았다)
3. **공공 API 가 58% 실패** — `collect-commerce` 5/12 · `collect-hira` 5/12 (HTTP 522·타임아웃·네트워크)

3번은 원본 서버 문제이고 **평소엔 문제가 아니었다** — 24회차 중 절반이 실패해도 12회차가 남는다.
창이 3시간이 되자 2~3회차만 남았고 거기에 58%가 **곱해져** 0이 됐다.
⇒ 재시도 로직보다 **창 복구가 맞는 처방**이다(창이 넓으면 다음 회차가 이어받는다).

## 3. 비용 — 9월 D1

```
쓴 행    50,045,104 / 50,000,000  (100.1%)   ← 9/6 에 넘었다
읽은 행   1,426,285,044 / 25,000,000,000  (5.7%)   ← 읽기는 돈이 아니다
```

| | 쓴 행 | 비중 |
|---|---:|---:|
| 유어애즈-업체 | 44,780,842 | **89.5%** |
| 유어애즈-리드 | 5,017,293 | 10.0% |
| 유어딜(본진) | 246,959 | **0.5%** |

일별로 보면 **9/02 하루가 9월 전체의 91%**(45,546,328). 업체 DB 전면 재기록 폭주였고 **이미 끝났다**.
9/3 에 넣은 쓰기 차단기가 재발을 막는다. 현재 속도 하루 42만 → 월 약 6천만 → 초과 1천만 → **약 $10**.
유어애즈를 완전히 멈춰도 이미 넘긴 45,104행 때문에 **$1은 확정**(이번 달 한정).

⚠️ **읽기는 포함분의 5.7%**라 비용이 아니다. 읽기 예산 차단기는 *돈*이 아니라 *레인 창*을 지키는 장치다 —
이 둘을 섞어 판단하지 말 것.

## 4. 이번 세션이 틀렸던 판단 (제일 값진 부분)

1. **"B2B 붕괴는 읽기 예산 탓"** — 맞지만 그 예산을 태운 큰 몫이 **내가 하루 전에 넣은 코드**였다(§1①).
   원인을 외부(예산 설정)에서 찾기 전에 **내 최근 diff 를 먼저 의심할 것.**
2. **"B2B 수집이 무너졌다"** — 두 줄기 중 하나만 무너졌다(§2). 테이블이 다른 DB 에 있으면 통계가 갈린다.
3. **계획기 시험이 초록불인데 라이브는 다른 인덱스를 골랐다** — 합성 픽스처는 몇 줄뿐이라
   "99.9%가 통과한다"가 재현되지 않는다. 작은 표에선 좁은 인덱스가 이기고 18만 행에서는 진다.
   ⇒ **계획기 시험은 "탈 수 있는 모양인가"까지만 증명한다. "실제로 탄다"는 라이브 `rows_read` 로만.**
   그 한계를 `influencer-bio-scan.test.ts` 에 적어 뒀다.
4. **고정 길이 창으로 소스를 자르는 가드는 양쪽으로 깨진다** — 짧으면 가짜 빨강(`influencer-bio-scan`
   이 주입 없이도 빨갛게 됨), 길면 가짜 초록(`ads-lane-alarm` 이 이웃 레인을 대신 매치해 결함을 심어도
   초록불). **끝을 구조로 잡을 것.**
5. 🩸 **`node -e "import('./scripts/check-guard-mutations.mjs')"` 를 실행하지 말 것** — import 만으로
   러너가 돈다. 타임아웃으로 끊어도 **자식이 안 죽고** 주입 잔재가 남는다(이번에도
   `demo-image-rehost.ts` 에 잔재 1건). 문법 확인은 `node --check`.

## 5. 남은 것 · 대표 판단 대기

- **읽기 예산 상향(2억 → 6억)** — 대표 판단. 단 **#1368 배포 후 실수요를 보고** 정할 것.
  낭비를 그대로 두고 예산만 올리면 같은 돈으로 같은 낭비를 더 한다.
  ⚠️ 플랫폼 쓰기는 세션이 하지 않는다(CLAUDE.md) — 세션은 판정만 보고하고 대표가 대시보드에서 직접.
- **공공 API 3개 간헐 실패** — `collect-nps` HTTP 503(9/1부터 연속) · `collect-commerce` 네트워크 ·
  `collect-hira` 522/타임아웃. 창이 넓어진 뒤에도 nps 가 계속 503 이면 별건으로 볼 것.
- **링크인바이오 큐 고갈(후보 0건)** — 이제 회차당 2,573행으로 싸지만 여전히 산출 0 이다.
  더 줄이려면 "빈 큐 기억" 백오프를 얹을 수 있다(이번엔 한 커밋 한 원인 원칙으로 안 넣었다).
