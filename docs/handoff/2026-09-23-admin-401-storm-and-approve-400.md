# 어드민 재방문 401 일곱 개 · 승인 400 — 영구 수리 (2026-09-23)

대표 신고: *"어드민 대시보드에서 승인해주고 이런 것들이 왜이리 느리지? 로딩이 길어"* + 콘솔 붙여넣기
(`/api/admin/*` 401 일곱 개 · `PATCH /api/admin/sellers/24/approve` 400) → *"모두 다 영구적으로 해줘"*.

## 무엇이었나 (실측)

### ① 401 일곱 개 = 만료된 토큰을 **보내 보고 나서** 갱신

어드민 access 토큰 수명은 **24시간**이다. 사전 갱신 훅(`useTokenAutoRefresh`)은 두 가지를 못 했다.

1. **이미 만료된 토큰에서 손을 뗐다** — 소스에 `if (remainingMs <= 0) return // 인터셉터에 맡김`.
2. **훅은 구조적으로 늦다** — React 는 자식 effect 를 부모보다 **먼저** 돌린다. 부모 레이아웃의 훅이
   갱신을 시작하기 전에 자식 화면의 쿼리 일곱 개가 이미 나가 있다.

⇒ 하루 뒤 재방문 첫 화면은 매번 **[요청 7 → 401 7 → 갱신 1 → 재시도 7]**. 왕복이 두 배다.
에러가 콘솔에만 남고 화면은 **결국 떠서** 아무도 결함으로 신고하지 않는 종류였다.

> 🩸 내가 처음에 의심한 것: *"내 자동화 계정 로그인이 대표 세션을 밀어냈나(SESSION_SUPERSEDED)"*.
> **아니었다** — 대표는 `tobe2111@naver.com`(id 5), 자동화는 `claude@ur-team.com`(id 10) 으로 **좌석이 다르다.**
> ⚠️ 그리고 **콘솔만으로는 "토큰 만료" 와 "토큰 부재" 를 구분할 수 없다.** 가르는 신호는 401 **본문의
> `code`** 다(`SESSION_SUPERSEDED` 였다면 `/admin/login` 으로 튕겼을 것이고, 대표는 안 튕겼다).

### ② 승인 400 = 이미 승인된 매장인데 **목록이 낡아** 그 줄이 남아 있었다

`admin-sellers.routes.ts` 의 `if (rows[0].status === 'approved') → 400`. 400 이 왔다는 것 자체가
**토큰은 정상 수용됐다**는 뜻이다(그 라우터는 `requireAdmin()` 뒤에 있다). 화면 쪽 결함은 한 줄:
`approve()` 가 **성공에서만** `load()` 를 불렀다. 그래서 실패하면 그 줄이 그대로 남아 또 누르게 되고,
돌아오는 건 같은 400 뿐이다.

## 고친 것

| 자리 | 무엇 |
|---|---|
| `src/lib/dashboard-token.ts` (신규) | 신선도 **판정**만 하는 순수 함수(저장소·네트워크 0). 훅과 인터셉터가 같은 규칙을 쓴다 |
| `src/lib/dashboard-refresh.ts` (신규) | 갱신 **실행** + **inflight 락 한 개**. 종전엔 갱신 경로가 둘이었고 훅 쪽엔 락이 없었다 |
| `src/lib/api.ts` | 요청 인터셉터의 **대시보드 토큰 부착 8곳 전부**가 `ensureFreshDashboardToken` 경유. refresh 요청 자신은 조기 반환 |
| `src/hooks/useTokenAutoRefresh.ts` | 만료 토큰도 **1회 시도**. 생 `axios.post` 제거(공용 락 공유) |
| `admin-sellers.routes.ts` | 400 에 안정적인 `code: 'ALREADY_APPROVED'` |
| `AdminSellerApprovalPage.tsx` | 승인·거절 **성공/실패 무관하게 `finally` 에서 `load()`**. '이미 승인됨'은 `toast.info` |
| `src/utils/api-error-code.ts` (신규) | `errorCode(err)` — 화면이 **문구가 아니라 code** 로 분기하게 |

**🔒 고치는 자리는 훅이 아니라 요청 인터셉터다.** 모든 요청이 지나는 단 하나의 길목이고,
effect 순서와 무관하게 **보내기 직전**이다. 훅만 고쳐서는 401 을 못 없앤다.

**⚠️ 2026-07-04 무한재귀 사고 가드는 손대지 않았다.** 그 사고는 *재스케줄* 문제였지 *1회 시도* 문제가
아니다 — `shouldRescheduleAfterAttempt` 는 그대로이고, 갱신에 실패하면 여전히 재스케줄하지 않는다
(만료 토큰으로 루프가 돌 수 없다). 기존 9건 단언 전부 통과.

**⚠️ 사전 갱신 창은 일부러 좁다(10초).** 넉넉한 창은 훅이 이미 맡고 있고, 여기서까지 넓히면 멀쩡한
토큰을 요청마다 갈아 끼워 refresh 호출만 는다(회전 토큰이라 다른 탭이 stale 로 튕길 수 있다).

## 이 수리가 **못 하는 것**

- **왕복 수는 브라우저에서 재야 한다.** 단위 시험은 *판정 규칙*과 *배선*만 고정한다.
- **소비자(user) 세션은 대상 아님** — 쿠키 기반이라 이 경로를 안 탄다.
- **refresh 토큰(30일)까지 만료됐으면** 종전과 똑같이 401 → 강제 로그아웃이다. 그게 맞다.

## 다음 세션의 첫 액션 (E4 판정)

배포 후 대표에게 **하루 지난 탭**으로 `/admin/seller-approval` 을 열게 하고 콘솔을 본다.

- ✅ 통과: `/api/admin/*` **401 이 0개**, 첫 화면이 눈에 띄게 빨라짐.
- ❌ 실패: 401 이 남아 있으면 **본문의 `code`** 를 볼 것 — `SESSION_SUPERSEDED` 면 이 수리와 무관한
  다른 축(단일 세션 좌석 경합)이고, 코드가 없으면 갱신 자체가 실패한 것(refresh 토큰 만료 = 정상).
- 승인 화면: 이미 승인된 매장을 눌러 **파란 안내 + 그 줄이 목록에서 사라지는지**(빨간 '승인 실패' 아님).
