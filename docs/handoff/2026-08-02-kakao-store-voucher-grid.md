# 08-02 — 매장 풀의 97.6%가 학원이었다. 대표가 지목한 네 업종은 **0건**

> ⏰ 시각은 KST. DB 스탬프는 `Z` 없는 UTC 문자열이라 그대로 읽으면 9시간 어긋난다(+9h 변환).

## 한 줄

인허가 레인이 `HTTP 500` 으로 죽어 있는 동안 **음식점·카페·미용·숙박이 정확히 0건**이었다.
그걸 채울 수 있는 유일한 살아있는 경로(카카오 로컬)에 그 네 업종을 붙였다.

## 실측 (08-02 23:0x KST)

```
store_prospects  45,458  ── 학원 44,348 (97.6%) · 무인아이스크림 1,049 · 무인판매점 61
                            일반음식점 0 · 휴게음식점 0 · 미용업 0 · 숙박업 0   ← 대표 07-29 지시 대상
인허가 레인      total_saved 0 · diag "API: HTTP 500 — Unexpected errors" · 21회차
파트너 풀 source='local'(카카오)   전체의 3% 인데 **전화의 80%**(2,926/3,677)
```

세 사실이 한 방향을 가리킨다. 대표가 "음식점, 카페, 미용실, 숙박에 힘을 써"라고 한 게 07-29 인데
**한 달 가까이 0** 이었던 이유는 그 업종을 담당하는 소스가 인허가 하나뿐이었고 그게 죽어 있었기 때문이다.
그리고 인허가는 우리가 못 연다(대표의 data.go.kr 확인 대기).

## 무엇을 바꿨나

`store-kakao-collect.ts` — 무인매장 전용이던 레인을 **2블록**으로.

| 블록 | 그리드 | 커서 | 회차 몫 |
|---|---|---|---|
| `voucher` (신규) | 235지역 × **15업태** = 3,525 | `ads_store_kakao_cursor_v` | 70% |
| `unmanned` (기존) | 235지역 × 4업태 = 940 | `ads_store_kakao_cursor` *(값·의미 불변)* | 나머지 |

**왜 배열에 덧붙이지 않고 블록을 나눴나**: `for region { for trade }` 구조라 업태를 추가하면
**모든 인덱스가 밀린다.** 라이브 커서가 가리키던 자리가 달라져 일부 지역이 영영 미조회가 된다.
(파일 주석이 "순서 고정(커서가 의미를 유지해야 한다)"이라고 이미 경고하고 있었다.)

곁들여 고친 것 셋 — 전부 **이미 이 레포에서 사고가 났던 클래스**다:

1. **마감선(`RUN_DEADLINE_MS = 12s`)** — 커서 저장이 루프 뒤에 있는데 시간 가드가 **하나도 없었다**.
   키워드당 10초 타임아웃 × 13개 = 최악 130초 ≫ CPU 벽 26초. 죽으면 커서가 안 올라가
   다음 회차가 같은 키워드를 또 훑는다 ⇒ **영원히 전진 0**. 통신판매가 정확히 그래서 며칠 멈춰 있었다(#927).
   아직 안 터진 건 카카오가 빨라서였을 뿐이다.
2. **지역을 주소에서 유도**(`regionFromAddress`) — 복합키 2번째가 지역인데 **키워드 지역**을 박고 있었다.
   같은 가게가 이웃 구 키워드마다 별개 행이 된다. 파트너 풀에서 같은 실수로 **중복 38.4%** 가 났고
   이미 고친 함수가 있다 — 그걸 그대로 쓴다(두 곳이 갈라지지 않게).
3. **페이지네이션(최대 3페이지)** — 1페이지(15건)만 봐서 한 바퀴 돈 뒤 재방문 수확이 **0** 이었다.
   커서는 영원히 도는데 우물은 15건에서 말라 있었다.

4. **몫 배분(`blockSlots`)** — 처음엔 "우선업종 70% → 남은 걸 무인" 으로 짰는데, 우선업종이 키워드당
   3페이지를 쓰다 보니 **무인이 매 회차 0 키워드**가 되는 경로가 있었다. 그건 대표가 07-28 에 요청한
   레인을 에러 없이 죽이는 것이다(커서도 안 움직여 아무도 모른다). 무인 몫을 **슬롯과 예산 양쪽에서**
   먼저 떼도록 순수함수로 분리했다 — 어떤 예산에서도 양쪽 커서가 최소 1칸씩 전진한다.

**관측**: `stopped_by` / `elapsed_ms` / `blocks{voucher,unmanned}` 를 스냅샷에 싣고,
어드민 `/admin/store-prospects` 상태줄에 카카오 레인 한 줄을 추가했다 — **이 레인은 매장 풀을 실제로
늘리고 있는 유일한 축인데 화면 어디에도 없었다**(무인 1,110건이 어디서 왔는지 물어야만 알 수 있었다).

## ⚠️ 다음 세션이 반드시 알아야 할 것

- **`category` 는 `PRIORITY_UPJONG` 과 글자까지 같아야 한다.** '음식점' vs '일반음식점' 한 글자 차이로
  우선순위 SQL 에 조용히 안 걸린다. 시험이 고정했고 guard-mutations 에 주입 항목이 있다.
- **업종 라벨은 카카오 검색어이지 인허가 분류가 아니다.** '음식점' 검색 결과가 전부 일반음식점 인허가는
  아니다. 우리가 저장하는 `category` 는 *무슨 의도로 찾았는지*이고 카카오 원문은 `uptae` 에 남는다(허위 0).
- **한 바퀴가 길다.** 3,525키워드 × 3페이지를 회차당 ~6키워드로 돈다 ⇒ 전 지역 1주기가 **한 달 규모**다.
  이건 결함이 아니라 무료 플랜 서브리퀘스트(≈50/인보케이션)의 결과다. 조급해서 슬라이스를 올리지 말 것 —
  올린 날 죽고 회복이 없었던 전례가 두 건 있다(NEIS 6→3 · NPS 100→40, #927).

## 다음 액션 (판정 명령까지)

1. **머지 후 다음 정시**에 카카오 레인 한 회차를 보고 아래를 확인:
   ```bash
   curl -sS "https://live.ur-team.com/api/admin/store-prospects/stats" \
     -H "Authorization: Bearer $TOK" -H "User-Agent: $UA" \
     | python3 -c "import sys,json;d=json.load(sys.stdin);print(d['byCategory']);print(d.get('storeKakao'))"
   ```
   - `storeKakao.run.blocks.voucher.found > 0` → 우선업종이 실제로 걸린다
   - `byCategory` 에 **일반음식점/휴게음식점/미용업/숙박업이 등장** → 목표 달성
   - `stopped_by === 'deadline'` 이 매번이면 슬라이스를 줄여야 한다는 신호(예산이 아니라 시간이 병목)
2. `storeKakao.gate` 가 `false` 면 아직 `ADS_STORE_KAKAO_ENABLED` 가 꺼진 것이다 — **대표만 켤 수 있다**
   (2026-07-29 지시로 세션은 플랫폼 env 를 안 만진다).
3. `storeinfo` 는 14,979행에 **이메일 11개**(2%)다. 줄일 후보 — 다만 아직 대표 판단 전이다.

## 이번에 틀렸던 판단

- 처음엔 "`UNMANNED_TRADES` 에 업태를 덧붙이면 된다"고 생각했다. **커서가 인덱스 기반이라 그러면 안 된다.**
  파일 주석이 경고하고 있었는데 한 번 읽고 지나쳤다. 블록 분리로 바꿨고 시험으로 고정했다.
- 그 다음엔 "블록 하나에 몰아넣고 커서를 0 으로 리셋" 을 고려했다. 무인 940키워드의 진행분을 버리는
  선택이라 기각했다 — 상태를 버리는 결정은 되돌릴 수 없다.
- 몫을 `우선업종 70% → 나머지 무인` 으로 짰다가 **무인이 0 이 되는 경로**를 뒤늦게 봤다. 슬롯만 나누고
  예산을 안 남기면 앞 블록이 지갑을 비워 뒤 블록은 첫 검사에서 튕긴다 — 배분이 무의미해진다.
- 시험 하나가 처음에 **빨간불이었는데 코드가 아니라 시험이 틀렸다**(`[^)]*` 가 `buildVoucherKeywords()` 의
  괄호를 못 넘음). 코드를 고치지 않고 정규식을 고쳤다 — 판정을 통과시키려고 코드를 바꾸면 안 된다.
