## 4. 열려 있는 것 ②  **키워드 순환 편식 (미완 — 여기서 멈췄다)**

경보: *"한 바퀴 5.5일인데 가장 밀린 키워드가 3.6바퀴째 순번을 못 받음"*

### 실측해 둔 것 (다음 세션은 다시 재지 말 것)

```
전체: active 459 · never_run 54 · ran24h 81 · 최고령 13.5일 · 평균 6.2일 · 11일초과 155개(34%)
```

| 축 | 개수 | 24h | **실측 한 바퀴** | 최고령 |
|---|---:|---:|---:|---:|
| 집중(마케팅대행사) | 27 | 15 | **1.8일** | 1.5일 |
| 일반 | 75 | 25 | **3.0일** | 13.5일 |
| **우선**(맛집·숙소·뷰티…) | **357** | 41 | **8.7일** | 13.2일 |

설계 의도는 집중:우선:일반 = **3:2:1**(배수가 클수록 빨리 돈다). 즉 **우선이 일반보다 빨라야** 하는데
실측은 **3배 느리다.** 그리고 전체의 **78%가 우선 축**에 있다.

### ⚠️ 내가 세웠다가 **스스로 반증한** 가설 (같은 길로 가지 말 것)

> ~~"회전 슬롯 3 vs 축 3 → 바닥이 슬롯을 다 먹어 비례 배분이 실행조차 안 된다"~~

**틀렸다.** 호출부(`influencer-auto-collect.ts:232`)를 보면 실제 슬롯은
`totalPick = batch + NAVER_EXTRA(기본 12)` = 경보의 **"16"** 이다. 계산하면:

```
w = [27×3, 357×2, 75×1] = [81, 714, 75]
바닥 3 → 나머지 13 을 비례 배분 → 집중 2 · 우선 12 · 일반 2
예상 한 바퀴 비율 1 : 2.2 : 2.8   (의도 1:1.5:3 에 근접 — 수식은 대체로 작동 중)
```

경보의 "회전 3개/라운드"는 총 슬롯이 아니라 **성과가중 3과 짝을 이루는 커서 순환 몫**이다. 혼동하지 말 것.

### 🎯 다음 세션의 첫 액션 — **배분이 아니라 "6/16"을 볼 것**

경보에 `키워드 6/16 처리` · `예산 54/56` 이 있다. **계획 16 중 6만 실제로 돈다**(서브리퀘스트 예산 소진).

⇒ 16을 어떻게 나누든 **6개만 실행되면 어느 6개가 살아남는가**가 결과를 정한다. 그 절단 지점이
`interleavePicks`(YT픽 ↔ 커서픽 교대) + 예산 소진 순서에 있고, **거기가 축별 편차의 직접 원인일 가능성이 높다.**

1. `finalPicks` 16개 중 실제 실행된 6개의 **축 구성**을 라이브에서 확인(진단 로그/스탬프 추가가 필요할 수 있다).
2. 절단이 특정 축을 계통적으로 자르면 → **거기가 진짜 원인.** 배분(`planKeywordSplit`)은 무죄다.
3. 절단이 공평하면 → 그때 비로소 배분·경보 임계를 의심한다.

❌ **`planKeywordSplit` 을 먼저 고치지 말 것.** 나눗셈을 고쳐도 실행되지 않으면 아무 변화가 없다 —
오늘 `found` 으로 판정하려다 틀린 것과 **정확히 같은 함정**이다.

### 덧 — 함께 확인된 사실

- **미실행이 0 → 54로 되돌아왔다.** 풀이 399 → 459 로 커지며 새로 들어온 것들이다.
  구제 슬롯(회차당 1개)은 돌지만 **유입이 계속되면 잔량은 유지된다** — 이건 고장이 아니라 정상상태다.
- **11일 넘게 안 돈 키워드 155개**는 *미실행이 아니다.* `pickStarvationRescue` 는 **never-run 만** 구제한다
  (docblock 에 명시). 즉 이 155개를 구제하는 장치는 **현재 없다** — 의도된 설계이고, 경보가 보는 것은 이쪽이다.
- 경보 임계(`ROTATION_STARVE_CYCLES = 3`)는 **집계 한 바퀴**로 판정하는데 축마다 한 바퀴가 다르다.
  오늘 고친 `cpu_risk` 와 **같은 클래스의 함정**일 수 있다(측정 대상과 판정 기준의 불일치). 3번 항목 확인 후 재검토.

## 5. 오늘 내가 틀린 것 — **8건**, 그리고 공통 원인

1. "레인이 배차를 못 받는다" → `skipped=odd_hour`(짝수시 레인이라 건너뛴 것)
2. "`collect-neis` 가 다음에 죽을 후보" → 페이지 편차(24.2→23.0→29.2→17.5→30.7 요동)
3. "사망점의 절반으로 재보정" → 사망점은 레인이 아니라 **회차**의 성질
4. "`found` 으로 CPU 절감을 판정" → 마감선이 1페이지에서 끊어 `found` 은 구조적으로 고정
5. "마감선은 I/O 예산이라 올려도 CPU 무관" → **CI 가 잡았다**(간접적으로 늘린다)
6. "문턱에 붙은 레인 6개" → **지표가 CPU 를 안 쟀다**(그래서 #1105)
7. "`phase=quality` 가 다시 죽었다" → **7일 전 기록**을 현재로 읽었다(`at`/`stale` 미확인)
8. "회전 바닥이 슬롯을 다 먹는다" → 슬롯은 3이 아니라 16. **구현하려 호출부를 열어 스스로 잡음**

🧠 **공통 원인은 하나다 — 한 번 본 것으로 결론을 냈다.**
8건 중 기계가 잡은 건 1건(#5), 스스로 잡은 건 1건(#8), 나머지 6건은 **라이브에 나간 뒤** 드러났다.

⇒ 그래서 오늘 만든 것 중 가장 값진 건 수확 2배가 아니라 **`cpu_deaths` 카운터**다.
   이 시스템은 지금까지 "누가 실제로 죽는지"를 **기록조차 안 했고**(성공 한 번이면 사망 기록이 지워졌다),
   그 빈자리를 벽시계 추측이 채우면서 반대 방향을 가리키고 있었다.
