## 2. 수리 ① `check-branch-scope` — 거짓 빨간불 (`764d8d9`)

`git diff --name-only origin/main...HEAD` 가 0건이고 HEAD≠base 면 **무조건** 실패시켰다.
0건의 원인은 둘인데 구분하지 않았다:

- ⓐ base ref 가 낡았다 → 비교 대상이 틀렸으니 통과시키면 안 된다
- ⓑ HEAD 가 base 의 **자손이고 내용 변화가 0** 이다(내용 없는 머지 커밋 · 빈 커밋)

ⓑ 를 ⓐ 로 오진하면 **처방까지 틀린다** — 가드가 안내한 `git fetch origin main` 을 하고 다시
돌려도 같은 빨간불이었다(실측). 해결되지 않는 명령을 안내하는 거짓 빨간불은 다음 세션을
`SKIP_PREPUSH_GATE=1` 로 밀어 **게이트 자체를 무력화**시킨다.

구분 기준은 `merge-base --is-ancestor base HEAD` 하나다. 조상이면 3점 diff 의 merge-base 가 곧
base 라 2점 diff 와 같고, 0건은 *HEAD 의 트리가 base 의 트리와 같다* 는 **참값**이다 — 브랜치가
들여온 변경이 0 이므로 주입본이 숨을 자리가 구조적으로 없다.

🔒 **"측정 0 = 통과 아님" 을 약화하지 않았다**: 갈라진 경우(ⓐ)는 그대로 실패다. 가드 자신이 겪은
낡은-base 사례도 0건이 아니라 **608파일**로 나타났다(소스 주석) — ⓐ 는 이 분기에 거의 안 온다.

가드 `branch-scope-empty-descendant-2026-11-01` **5건** — 합성 git 저장소에서 **실제 스크립트를
돌려 종료코드로** 판정한다(①동일 커밋 통과 ②자손+0 통과 ③**갈라짐+0 실패** ④실제 변경은 종전대로
훑는다 ⑤조상 판정이 소스에 실재). 주입 **3건** 되돌려-검증 전부 빨간불 확인(둘이 반대 방향).

## 3. 수리 ② 배포 후 상품 상세 스모크 — 조용한 skip (`f649caa`)

**모든 배포에서 건너뛰어지고 있었다.** 그 검사는 2026-06-10 교환권 상세 500 사고
(`SELECT p.*` 컬럼 한도 — *목록은 멀쩡한데 상세만 깨진다*)를 잡으려고 만든 바로 그 검사다.

기제: 라이브 `/api/products` 는 `{success, data:[…], pagination}` 이라 **`data` 가 리스트**인데
파서 첫 분기가 `(d.get('data') or {}).get('products')` 다. 리스트는 truthy 라 `.get` 에서
**AttributeError** 가 나고 뒤에 붙인 `or` 폴백 셋은 **도달조차 못 한다**. 그 예외를 `2>/dev/null`
이 숨기고 `|| echo ""` 가 빈 값으로 바꿔 "파싱 실패 → skip" 이 된다.

🧭 **방어하려고 붙인 `or` 사슬이 흔한 경우에서 먼저 터지는** 모양이었다. 일행은 제어 흐름을 못
쓰니 사슬이 되고, 사슬은 순서가 곧 규칙이라 조용히 틀린다 ⇒ 처방은 사슬을 늘리는 것이 아니라
**일행을 없애는 것**이다.

- 신규 `scripts/first-list-id.mjs`(+`.d.mts`) — 세 모양을 **타입으로** 가른다. 숫자로 읽히는 id
  만 받는다(문자열을 통과시키면 `/api/products/undefined` 가 **404 로 "정상"** 처리된다 — 스모크는
  5xx 만 실패로 보므로 또 조용해진다).
- **"비었다"(`__EMPTY__`)와 "못 찾았다"(`__FAIL__ 이유`)를 가른다.** 종전엔 둘 다 빈 문자열이라
  호출부가 구분할 수 없었고 **파서 고장이 "상품이 없다" 로 위장**됐다.
- `main.yml` — 숫자 id 면 검사 · 빈 목록이면 시끄러운 skip · **그 밖이면 FAIL 집계**.
  판정은 종료코드가 아니라 **출력으로** 한다(파이프 뒤 exit code 를 그 명령의 결과로 읽는 함정을
  새로 만들지 않는다).

🔬 **켜기 전에 라이브를 먼저 쟀다** — 파서가 id **3120** 을 뽑고 `/api/products/3120`·`/2919` 둘 다
**200**. 즉 검사가 처음 돌아도 배포가 빨간불이 되지 않는다.

가드 `smoke-first-list-id-2026-11-01` **5건** + 주입 **4건** 전부 빨간불 확인(둘이 반대 방향).

## 4. 🩸 이번에 틀린 판단

1. **제 시험이 거짓 빨간불을 냈다** — 제거를 기록한 주석이 옛 python 일행을 **인용**하는데 YAML
   원문 전체를 검사했다. 판정을 **주석 뺀 실행되는 줄**로 옮겼다. CLAUDE.md 가 두 번(`d1-migrate`
   · robots) 적어 둔 함정을 **세 번째로** 밟았다 ⇒ *제거를 기록하는 주석과 제거를 검사하는 단언은
   같은 문자열을 공유할 수 없다.*
2. **"TypeScript errors" 를 믿을 뻔했다** — pre-commit 이 `❌ Commit blocked. Fix TypeScript errors.`
   를 냈는데 출력 꼬리가 `Aborted` + node 힙 주소, 즉 **OOM** 이었다. 힙을 올려 돌리니 `tsc`
   **에러 0건**. 메시지를 그대로 믿었으면 없는 타입 에러를 쫓았을 것이다(§5 참조).
3. **브랜치 정렬을 force-push 로 하려 했다** — 거부됐고, 그게 맞다. 비파괴 경로(main 머지)는
   §2 의 거짓 빨간불에 막혔는데, **그 막힘이 오히려 ①번 수리의 발견 경로였다.**

## 5. ⚠️ 남은 것 · 대표 판단

### ⓐ pre-commit 훅이 OOM 을 "타입 에러" 로 보고하던 것 — ✅ **수리됨** (대표 승인 *"응 고쳐"*)

§4-2 의 그 건. 같은 날 세 번째 "틀린 원인 보고" 였고 별건으로 올렸다가 **대표 승인으로 고쳤다.**

**실측 근거(이 레포 · 머신 16GB)**: node 기본 힙 상한 **2,096 MB → OOM** · 4,096 MB → 통과 ·
8,192 MB → 통과(도는 중 실제 tsc 프로세스 RSS 1,553 MB). ⇒ 메모리가 **없는 게 아니라**
node 기본값이 2GB 인데 이 레포 규모가 그걸 넘는다.

- **힙을 머신에서 계산**한다(총 메모리의 절반 · 상한 8192 · 하한은 node 기본값). 숫자를 박으면
  4GB 기계에서 OOM-killer 를 불러 **지금보다 나빠진다**. 사람이 이미 정했으면 **덮지 않는다**.
- **원인을 가려** 말한다 — 진짜 타입 에러(파일:줄 있는 `error TS`) / 설정·CLI 오류(파일:줄 없는
  `error TS` → *"tsc 가 파일을 하나도 안 보고 멈췄다"*) / 끝까지 못 돎(OOM · exit 127 …).
- 파이프를 거치지 않고 `|| TSC_EXIT=$?` 로 **tsc 자신의 종료코드**를 읽는다.
- ⚠️ 훅은 `set -e` 다 — 테스트되지 않은 실패는 훅을 **즉시 중단**시켜 이 메시지조차 못 나오게
  한다(종전 한 줄이 `||` 를 쓴 이유이기도 하다). 가드 ④가 그 안전성까지 함께 판정한다.

🔬 **라이브 검증**: 수리된 훅을 설치하고 `NODE_OPTIONS` 를 **손으로 주지 않은 채** 커밋하니
OOM 없이 끝까지 돌았고, 마침 섞여 있던 **진짜 타입 에러를 파일:줄까지** 가리켰다(TS2769 —
`ProcessEnv` 확장 키). 종전 훅이라면 같은 자리에서 "Fix TypeScript errors" 만 냈을 것이다.

가드 `precommit-tsc-cause-2026-11-01` **8건**(가짜 `npx` 로 다섯 결과를 실제로 흉내 낸다) +
주입 **4건** 되돌려-검증 전부 빨간불 확인.
🩸 그 주입 하나는 처음 **no-op** 이었다(주석만 바꿔 `case` 패턴이 그대로였다) — 러너가
