# 시트 미러가 8월 2일부터 멈춰 있었다 — 커서가 스냅샷을 지나쳐 영구 고착

> 2026-08-03 세션. 유어애즈 4축(① 수집 ② 카테고리화 ③ 필터링 ④ 정보 최대 수집) 중
> ④의 **전달 경로**가 조용히 죽어 있었고, 그 대가를 ①이 치르고 있었다.

## 1) 다음 세션의 첫 액션

배포 후 **한 회차**만 지나면 판정된다. D1 읽기 전용:

```sql
SELECT key, value FROM platform_settings WHERE key LIKE 'ads_sheets%';
```

* **고쳐졌다** = `ads_sheets_cursor.off` 가 `total` 보다 **작다**(또는 0 에서 다시 출발).
  그리고 `ads_sheets_last_sync.ok = true`.
* **아직이다** = `off` 가 여전히 `total` 이상이고 `error` 가 `WRITE: …행부터 기록 실패(400)`.

같이 볼 것 — 이 레인이 회차 예산을 그만 태우는지:

```sql
SELECT job_name, COUNT(*) n FROM cron_failures
WHERE created_at >= datetime('now','-24 hours') GROUP BY job_name ORDER BY n DESC;
```

`ads:sheets-sync` 가 목록에서 사라지거나 1~2건으로 떨어져야 한다(수리 전 24시간 **7건**).

## 2) 무엇이 고장나 있었나 (실측)

라이브 값이 그대로 증거다:

```
ads_sheets_cursor    = {"off":44000,"total":43597,"at":"2026-08-03T00:01:00.931Z"}
ads_sheets_last_sync = {"ok":false,"rows":8000,"error":"WRITE: 44002행부터 기록 실패(400)"}
```

`off(44000) > total(43597)`. 이 부등호가 성립하면 안 된다.

연쇄는 이렇다:

1. 사이클 **시작 시점의 total** 로만 그리드를 넓힌다 — `ensurePoolSheet(token, sheetId, total + 2, …)`,
   그것도 `off === 0` 분기 안에서만.
2. 그런데 읽기 루프엔 상한이 `ROWS_PER_RUN` 뿐이라 **페이지가 마를 때까지** 간다. 사이클은 4회차
   (12,000 × 4 ≈ 48k)에 걸치는데 그동안 풀은 계속 자란다(하루 ~1,600행).
3. 그래서 사이클 꼬리에서 **그리드 밖 행**을 쓴다 → Sheets 400.
4. 실패는 `saveSheetCursor(env, off + i, total)` 로 **그 자리에 커서를 저장**하고 끝난다.
5. ⇒ `off` 가 다시 0 이 되는 길이 없다 ⇒ `ensurePoolSheet` 가 **영영 안 불린다** ⇒
   다음 회차도 같은 행에서 400. **한 번 넘어가면 영구 고착.**

즉 "가끔 실패"가 아니라 **자기 자신을 고칠 수 없는 상태로 들어가는** 형태다.
그리고 각 시도는 실패하러 가는 데 11.7초를 쓰고 CPU 사망을 동반한다 —
회차 예산이 **2~3칸**(AIMD 학습값 `ads_lanes_learned.cap`)뿐인 지금, 한 칸을 계속 태운 것이다.

## 3) 수리 (두 겹)

`src/features/marketing/api/sheets-sync.ts` — 순수함수 2개 + 호출부 2줄.

* **`cycleRoom(off, total)`** — 이 사이클은 **자기 스냅샷까지만** 쓴다. 루프의
  `Math.min(PAGE, ROWS_PER_RUN - wrote, room)` 에 상한으로 들어간다. 도중에 늘어난 행은
  버리는 게 아니라 **다음 사이클 몫**이다(다음 사이클이 그만큼 넓힌 뒤 쓴다).
* **`startCursor(cur)`** — 이미 지나친 커서(`off >= total`)는 새 사이클(`{off:0,total:0}`)로 되돌린다.
  ⚠️ `total` 을 **0 으로** 돌리는 게 핵심이다. 그래야 호출부의 `off === 0` 분기가 총계를 다시 세고
  그리드를 넓힌다. 이게 없으면 **이미 고착된 라이브 상태는 배포해도 안 풀린다.**

`total === 0`(총계 미상)이면 `cycleRoom` 은 `Infinity` — 종전 동작 그대로다.

검증: 유닛 15 pass · **주입 3종 전부 빨강**(`startCursor` 무력화 / `Math.max(0,…)` 제거 /
루프 상한 제거) · tsc 0 · audit-gate **84 GREEN**.

## 4) 이번에 틀렸던 판단

**"sheets-sync 는 CPU 가 무거워서 죽는다"** 고 읽고 넘길 뻔했다. 하트비트에 실제로
`Worker exceeded CPU time limit` 이 6건 찍혀 있었기 때문이다. 그런데 24시간 CPU 사망 29건을
**시각순으로** 펼쳐 보니 08:00 ×5 · 07:00 ×4 · 17:01 ×4 처럼 **여러 레인이 같은 분에 동시에** 죽는다 —
이건 개별 레인이 무거운 게 아니라 **부모 예산이 바닥나 in-flight 자식이 한꺼번에 죽는** 그림이다.
sheets-sync 의 진짜 고유 실패는 그 밑에 깔린 `400` 하나였고, 그건 CPU 와 무관하다.

⇒ **집계만 보면 원인을 반대로 짚는다.** 같은 분에 몰렸는지를 보라.

## 5) 곁가지로 확인한 것 — **측정 병목이 뒤집혔다(네이버만)**

2026-07-29 인계는 네 축의 병목을 하나로 봤다 — *"측정(20/시간)이 유입(101/시간)의 1/5이라 백로그가
시간당 133씩 벌어진다"*. 오늘 플랫폼별로 갈라 재니 **한 축은 뒤집혔고 나머지는 그대로**였다:

| platform | 유입 24h | 측정 24h | 미측정 백로그 | 순증/일 |
|---|---:|---:|---:|---:|
| naver_blog | 1,572 | 2,529 | 20,601 | **−957** |
| youtube | 264 | 72 | 4,152 | **+192** |
| naver_cafe | 0 | 0 | 3,147 | 0 |
| tistory | 81 | 0 | 378 | +81 |

* **naver_blog 는 이제 줄어든다** — 이 속도면 백로그 소진에 ~21일. 인계의 진단은 이 축에 한해 낡았다.
* **youtube 는 여전히 벌어진다.** 그런데 같은 시각 `yt_budget = {used:12, total:90}` — **쿼터를 13%밖에
  안 쓴다.** 즉 유튜브 측정을 막는 건 API 한도가 아니라 **레인 차례**다. 다음 세션의 가장 큰 레버.
* **naver_cafe(3,147) · tistory(378) 는 측정 경로가 아예 없다**(느린 게 아니다 — 확인함).
  `influencer-performance.ts` 의 선택 쿼리는 **플랫폼이 박혀 있다**: 유튜브 경로는
  `WHERE … platform = 'youtube'`, 네이버 경로는 블로그 핸들(`deriveNaverHandle`) 전용.
  카페·티스토리는 어느 쪽에도 안 걸리므로 `perf_checked_at` 이 **영원히 NULL** 이다

⚠️ 이 표는 `perf_checked_at` 기준이다. 분류(`category_source`)·연락처는 다른 열이라 같이 보지 말 것.

## 6) 남은 것 / 대표 판단 대기

* **부모 CPU 10초**(무료)가 남은 유일한 구조적 천장이다. AIMD 학습기가 레인 수를 자동으로
  줄여 붕괴는 막지만(실측 `cap` 6→4→2), 그만큼 각 레인의 차례가 늦게 온다. 유료 전환은 대표 판단.
* `orphan_lanes` 의 24시간 임계는 추정치다 — 주간·월간 레인이 생기면 오탐이 난다.
* 시트 미러는 이제 **사이클 경계에서 최신 몇 행이 한 사이클 늦게** 반영된다(설계상 트레이드오프).
  전량 즉시 반영이 필요해지면 그리드 확장을 회차마다 하는 쪽으로 바꿔야 하는데, 그건 서브리퀘스트를
  회차당 1 더 쓴다.
