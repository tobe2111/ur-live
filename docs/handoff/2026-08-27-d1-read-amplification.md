# 2026-08-27 — D1 읽기 낭비 규명 (하루 6.19억 행)

대표 질문 *"B2B/인플루언서 DB를 구글 스프레드시트에 넣으면 용량 문제 없지 않냐"* 에서 시작.
답은 **아니오**였지만, 그걸 확인하려고 실측하다가 **진짜 문제가 용량이 아님**을 찾았다.

## 실측 (2026-08-27)

```
저장:   urads-leads 337MB · urads-company 151MB · 나머지 40MB   합계 529MB   ← 문제 아님
읽기:   하루 618,931,025 행                                      ← 문제
쓰기:   하루   1,055,345 행
유입:   인플루언서 5,181/일 · 업체 4,848/일 (약 4MB/일)
```

## 원인 두 개를 특정했다

### ① 업체 DB 1.63억/일 — 저장 관문의 전수 COUNT (PR #1222)
모든 수집 소스가 지나는 `saveCompanyLeadsCounted` 가 신규 건수를 알려고 **저장 전후로
`SELECT COUNT(*)`**(372,730행)를 돌렸다. 하루 219회 저장 × 2 = 1.63억.
⇒ 넣으려는 `company_key` 가 이미 있는지만 UNIQUE 인덱스로 확인(청크 50개). **값은 동일**.
⚠️ 청크 내 중복 키를 고유키로 세지 않으면 한 업체를 신규 2건으로 보고한다(가드 등록).
⚠️ 청크마다 쿼리가 1개 늘어 `webkr-collect` 예산식을 `3+ceil` → `1+2*ceil` 로 함께 고쳤다.

### ② leads-db 3.78억/일 — 링크인바이오 보강의 전수 스캔 (이 PR)
```
대상 선택 쿼리 1회 →  rows_read 153,223 · 168ms · 결과 0건
전체 153,312 · bio_checked_at IS NULL 153,221(99.9%) · links 보유 2,410(1.6%) · 링크트리류 74(0.05%)
```
`idx_ad_inf_leads_bio(account_id, bio_checked_at)` 가 **거르는 일을 못 한다** — 99.9%가 통과.
거기에 `ORDER BY subscriber_count DESC`(인덱스 밖)가 붙어 그 전부를 임시 B-트리로 정렬.
**0.05%를 찾으려고 100%를 읽고 정렬**했고, 결과가 0건이라 상태줄엔 흔적이 없었다.
⇒ 부분 인덱스 `(account_id, id) WHERE links IS NOT NULL AND bio_checked_at IS NULL` + `ORDER BY id DESC`.

⚠️ **인덱스는 LIKE 를 겨냥하지 않는다** — `LIKE '%linktr.ee%'` 는 앞에 `%` 라 원리적으로 불가.
   노리는 것은 그 앞 단계(2,410명으로 63배 축소)이고 LIKE 는 그 안에서만 돈다.

## 이번에 틀렸던 판단 (제일 값진 것)

1. **사용량만 보고 요금제를 단정했다.** D1 실사용이 무료 한도의 124배라 "이미 유료"라고 대표에게
   보고했는데 **대표가 무료라고 정정**했다. ⇒ 그러면 이 숫자는 안심 신호가 아니라 **왜 안 멎는지
   모르는 상태**다. 가능성 셋: 무료 한도가 내가 아는 것과 다름 / 실은 유료 / **조용히 제한당하는 중**.
   세 번째면 수집량이 원래 나올 것보다 적다는 뜻이라 그냥 넘길 문제가 아니다.
   **다음 세션의 첫 액션: 대표에게 Cloudflare 대시보드 D1 사용량 화면 확인 요청**(내 토큰은 요금제를 못 읽는다).
2. **감사 게이트가 15분을 넘겼다**(주입 491건). `timeout 900` 으로 감쌌다가 SIGTERM 으로 죽었다.
   ⚠️ **게이트가 도는 중 `git add` 금지** — 하네스가 주입한 결함이 커밋에 섞이는 사고가 이 세션에서
   이미 두 번 났다. `pkill -f check-guard-mutations` 는 **자기 쉘을 죽인다**(패턴이 자기 명령줄에 매치).
   PID 로 죽이고 `git status` 가 두 번 연속 같은지 본 뒤 스테이징할 것.
3. **기존 가드가 내 예산식 변경을 잡았다** — 상수(`3 + Math.ceil`)까지 앵커돼 있었다. 지켜야 할 것은
   "리드 수에 비례해 D1 실비를 뺀다"이지 계수가 아니라서 완화했다(낡은 지도 클래스, 이번 주 세 번째).

## 남은 것

- 위 둘을 고쳐도 남는 읽기가 있으면 같은 방법으로 추적(EXPLAIN QUERY PLAN + 실제 쿼리의 `meta.rows_read`).
  이 방법이 이번에 효과적이었다 — **추측하지 말고 실제 쿼리를 라이브에 던져 `rows_read` 를 읽으면 된다**(읽기 전용).
- 스프레드시트 안: **저장소로는 반대, 발송 명단 내보내기로는 찬성**. 셀 1,000만 상한이라 45만 행 × 20컬럼 = 900만 셀로 이미 초과.
