# 크롤 처리량 붕괴 — 대행사 이메일이 안 늘어나는 진짜 이유 (2026-08-03, 머지 직후 실측)

> PR #1002 머지 후 라이브 D1 을 직접 조회해 얻은 숫자다. **추정 아님.**
> 다음 세션은 이 문서의 "첫 액션"부터 하면 된다.

## 1. 내가 방금 만든 전화→이메일 조인의 **천장은 10건**이다 (기대 이하)

대표 요청(*"파트너풀에서 전화번호를 통해 이메일을 알아낼 수 있는 방법"*)으로
`registry-phone-match.ts` 를 만들어 머지했다. 동작은 맞고 오매칭 방어(대표번호·모호 매칭 차단)도 있다.
**그런데 실제로 이어 붙일 수 있는 행이 거의 없다.**

```sql
-- 파트너풀 내부 조인 상한(대표번호·모호 제외, 정규화 9~12자리)
→ 대행사 9건.  그 외 카테고리 0건.
-- 매장풀(store_prospects) × 통신판매 원부 전화 조인 상한
→ 1건.
```

**왜 이렇게 적은가**: 통신판매업 원부의 전화번호는 *온라인 판매사업자*의 것이고, 우리가 전화만 갖고 있는
행은 *대행사·간판·전문서비스*다. **두 모집단이 겹치지 않는다.** 번호 표기 문제가 아니라 모집단 문제다.

⇒ 이 기능은 유지할 가치는 있지만(비용 0, 외부 호출 0, 새 리드가 들어오면 자동으로 더 잡는다)
**"전화 27,831건이 이메일로 바뀐다"는 기대는 접어야 한다.** 다음 세션이 이 기능을 다시 파지 않도록 못 박는다.

## 2. 전화만 있는 리드의 진짜 레버는 **홈페이지 크롤**이고, 그 레인이 죽어 가고 있다

이메일 없는 리드 중 **홈페이지가 있어 지금 당장 크롤 가능한 것**:

| 카테고리 | 크롤 가능(website 有) | 홈페이지 없음 |
|---|---|---|
| **대행사** | **261** | 1,617 |
| 전문서비스 | 127 | 255 |
| 창업 | 61 | 49 |
| 간판 | 35 | 993 |

대행사 이메일이 현재 **111건**이니 261 을 다 훑으면 체감이 다르다. 그런데 —

```
크롤 도장(enrich_checked_at) 일자별:  07-28: 401  07-29: 263  07-30: 17  08-01: 30  08-02: 81
홈페이지 보유 후보 1,599건 중 enrich_v=0(한 번도 안 훑음): 381건, 마지막 접촉 07-27
```

**처리량이 5~20배 떨어졌다.** 후보 순서는 `website 보유 우선`이라 이 381건이 맨 앞줄인데도 못 닿는다.

## 3. 라운드가 **예산의 75% 를 남기고** 3건에서 죽는다 — 원인이 기록되지 않는다

```jsonc
// platform_settings.ads_enrich_last (마지막 회차)
{ "processed": 3, "crawls": 1, "budget_total": 60, "spent": 15,
  "limit_hit": false, "deadline_hit": false, "partial": true,
  "elapsed_ms": 2220, "at": "cr:https://www.busan.com", "targets": 120 }
// ads_enrich_rollup (08-03 KST): rounds 2, processed 6, crash 0
```

읽는 법:
- `partial:true` = 정상 종료 지점(`snapshot(false)`)에 **도달하지 못했다.**
- `limit_hit:false` → 서브리퀘스트 한도 아님. `deadline_hit:false`·`elapsed_ms 2220` → 20s 자체 상한 아님.
- `crash:0` → 잡힌 예외도 아님.
- ⇒ 남는 것은 **예외 없이 사라지는 죽음**: 부모 CPU 한도 또는 waitUntil isolate 취소.
  이 레포가 이름 붙여 온 *"조용한 전진 0"* 과 같은 계열이다.
- 게다가 **회차 자체가 하루 2번**이다(rounds:2). 처리량 붕괴의 절반은 여기다.

### ⚠️ 다음 세션이 하지 말아야 할 것
`budget_total` 을 올리는 것. **이미 45가 남는다.** 예산은 병목이 아니다.
`targetCap`(120)을 올리는 것도 무의미하다 — 3건에서 죽는다.

### 다음 세션의 첫 액션 (판정까지)
1. `ads_enrich_last` 의 `at` 값을 몇 회차 모아 본다. 매번 `cr:` (크롤 중)에서 멈추는지,
   아니면 위치가 흩어지는지. **한 곳에 몰리면 그 사이트가 원인**(느린 응답 → CPU 아닌 벽시계),
   **흩어지면 부모 CPU 한도**다. 이 구분이 처방을 가른다.
2. 부모 CPU 라면 이 레인이 `kick()`(자식 인보케이션) 경로에 있는지 확인 —
   생 `ctx.waitUntil(await import(…))` 이면 **부모가 직접 CPU 를 태운다**(`check-ads-dispatch-bypass` 가 보는 클래스).
3. 회차 수(rounds:2)가 의도인지 확인. 알람 기반으로 옮긴 다른 레인과 달리 이 레인만 뒤처졌을 수 있다.

## 5. 이번에 틀렸던 판단 (반복 방지)

- **"전화번호로 이메일을 알아낼 수 있다"** 를 기능을 만들기 전에 수량으로 확인하지 않았다.
  만들고 나서 재 보니 천장이 10이었다. **모집단 겹침을 먼저 세었어야 했다** — 쿼리 한 번이면 됐다.
  (기능 자체는 옳고 비용도 0이라 되돌리지 않는다. 틀린 것은 *순서*다.)
- 대행사 이메일이 안 느는 이유를 *분류 문제*로 의심했었는데, 분류는 멀쩡하고
  **크롤 처리량**이 문제였다. 카테고리별 숫자만 보면 분류 탓으로 보인다 — 도장 추이를 같이 봐야 한다.
