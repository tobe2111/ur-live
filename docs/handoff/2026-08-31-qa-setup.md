# 2026-08-31 — 대표 QA 준비: 홍대돈까스 접근 구조 (내가 두 번 헛짚은 자리)

대표가 게시 전 전체 QA 를 직접 돌린다. 대상 매장은 **홍대돈까스(seller 14)**.
다음 세션이 같은 곳에서 헤매지 않게 실측을 남긴다.

## 🩸 내가 틀린 것 둘 — 둘 다 "한쪽만 보고 없다고 단정"

### ① "홍대돈까스에 연결된 계정이 없다" → **틀렸다**
`sellers.linked_user_id` 가 NULL 이고 `email` 이 빈 문자열이라 그렇게 읽었다.
**그 칸은 의도적으로 비운다.** `seller-stores.routes.ts:383` 주석이 명시한다:

> `linked_user_id` 는 **비움**(UNIQUE 1인1행): 접근은 `seller_operators` 관계로.

한 유저가 `linked_user_id` 로 가질 수 있는 셀러는 **하나**뿐인데(UNIQUE), 대표는 이미
셀러 5(정지원)를 갖고 있다. 그래서 매장 등록 흐름은 **운영 권한 테이블**로 붙인다.

실측:
```
seller_operators: seller_id=14 · user_id=3 · role=operator · revoked_at=NULL
                  granted_at 2026-08-26 07:28:25 (매장 created_at 과 1초 차)
```
⇒ **매장 접근 여부는 `seller_operators` 로 판정할 것.** `linked_user_id` 만 보면 오답이 나온다.

### ② "활성 셀러 0곳" → **틀렸다**
`WHERE status='active'` 로 조회했는데 **실제 값은 `'approved'`** 다. 실제는 승인 4곳
(5·9·12·14) / 정지 7곳. 게시 준비 판단(=A/B 는 이르다)은 그대로지만 숫자가 틀렸다.
⇒ `sellers.status` 의 값 집합을 확인하고 쓸 것.

`approved_at` 이 비어 있는 행이 있다**는 걸 알고 있어야 한다.

## QA 시나리오 (오늘 머지분 4건을 한 번에 검증)
1. 홍대돈까스로 이용권 1개 등록 — **금액 작게**(Toss 라이브 키다)
2. `brokered` 결제 1건 → 원장 fee **5%** / 어드민에서 `direct` 로 바꿔 1건 → **10%** (#1234)
3. 다른 유저가 유어샵에 담기 → 매장이 **10% 소개비 제안**(예전엔 400) → 결제 → 소개자 몫 10% (#1247)
4. 소개자가 **딜 수령** 선택 → 어드민 지급 목록에 **1원부터** 뜨는지 (#1252)

## 다른 세션과의 조정
영입 2% 를 **직접 입점 매장에만**(미지정=미지급) + 예산 아비터 켜기가 다른 세션에서 진행 중.
홍대돈까스는 `brokered` 라 그 규칙이 들어오면 **영입 2% 대상이 아니다**. 그 축까지 QA 하려면
채널을 `direct` 로 바꿔야 한다. 순서는 **그 PR 을 먼저 머지 → 확정된 규칙으로 QA** 를 권했다.
