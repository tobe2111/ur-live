### 🩸 첫 시도(ROUTES 에 넣기)를 버린 이유 — 남은 묶음기 결함

`ROUTES` 는 vite 묶음기(`scripts/surface-chunks.mjs`)의 입력이기도 하다. 거기 넣자 묶음이 다시 짜였다:
1. 공용 봉투(`lz-common`) 기준이 **lazy 사용자까지** 센다 → 결제 위젯이 lz-common 에 들어가 stripe·toss 를 끌고 와 **전 화면 +15~21KB(br)**.
   lazy 전용 모듈을 빼는 수리는 효과가 있었지만(어드민 −14 · 에이전시 −20KB) 일부 화면 청크 수가 +1 돼 런타임 래칫에 걸렸다.
2. 공용 기준 **고정값 4** → 표면 19곳에서 기존 화면 +7~9KB. 40% 비례로 바꾸면 바이트는 줄지만 파일이 +2~5개.
⇒ 둘 다 이 PR 에서 되돌렸다. **표면을 `ROUTES` 로 옮기는 날 다시 드러난다** — 그때 1번(lazy 전용 제외)부터 손볼 것.

## 6. 2단계 시험 — 서버가 React 로 상세(`/pass/2919`)를 완성하면

방법: 지금 빌드되는 노드용 SSR 번들(`dist/server/entry-server.mjs`)에 라이브 상세 시드를 쥐여 주고 `renderAppComplete('/pass/2919')` 를 돌렸다
(스크래치 `ssr/pilot.mjs`). 그 HTML 을 라이브 문서의 첫 화면 노드 자리에 끼워 A/B(`ssr/ab.mjs` — 문서만 바꾸고 나머지 자산은 라이브·감속 그대로).

- **그려지나**: 된다 — 글자 582자(가게·주소·전화·가격·수량·구매하기·이용 안내·유의사항), 스켈레톤 0, 번역 키 노출 0.
  막힌 것은 **전역 `window` 하나**뿐이었다(창 객체 흉내만 넣으면 됨 → 실제로는 그 접근을 찾아 고쳐야 한다).
- **CPU**: 따뜻한 렌더 **8~17ms**(이 컨테이너 노드 기준) · 첫 렌더 95ms · 모듈 적재 240ms(격리마다 한 번).
  유료 요금제 포함량 3천만 ms/월 ⇒ 상세 100만 뷰 × 15ms = 1,500만 ms — **포함량 안**. 상품별로 엣지에 캐시하면 거의 0.
- **크기**: 그 렌더가 실제로 적재한 코드 = 앱 101KB + 라이브러리 121KB(gzip). 워커 게이트(7MB)와 비교해 문제 없음.
- **속도(3회)**: 가격·구매하기가 화면에 뜨는 시각 **3.8~4.4초 → 1.5~1.9초**. 첫 페인트는 1.65 → 1.7~2.0초(문서가 26KB 커져 +0.1~0.3초).
  **누를 수 있게 되는 시각은 그대로 3.8~4.0초** — 그 2초 동안 구매하기를 눌러도 반응이 없다(서버 렌더의 대가).

### 확대 전에 풀어야 할 것
1. 첫 화면 노드에 **페이지 부분만** 그릴 것(지금 시험은 앱 전체 껍데기까지 그려 마운트 직전 하단 탭이 겹칠 수 있다).
2. 마운트 때 React 가 다시 그린 결과와 **글자·박스가 같아야** 안 튄다(createRoot 라 교체한다) — 로그인·잔액·찜처럼 사람마다 다른 자리는 비워 그린다.
3. 반응 없는 2초 — 버튼을 "준비 중" 으로 두거나, 그 사이 누름을 기억했다가 마운트 뒤 실행.
4. HTML 을 상품별로 엣지 캐시(사람마다 같은 HTML 이어야 가능 — 3과 같은 조건).
