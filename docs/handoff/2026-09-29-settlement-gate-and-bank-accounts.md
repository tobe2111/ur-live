## ① 게이트 `settlement_skip_ledgered` 의 안내 문구가 **거짓이었다** (수정 + 가드)

대표가 *"2번 내가 어떻게 하는데?"* 라고 물어 어드민 화면을 열어 보니, 그 스위치에 붙은 두 문구가
**반대로** 말하고 있었다:

- 스위치 hint: *"원장 적립이 실제로 돌기 시작한 뒤에 켠다"*
- 게이트 레지스트리 `turn_on_when`: *"그전엔 켜면 정산이 통째로 빠진다"*

**둘 다 사실이 아니다.** 코드로 확인한 세 가지:

1. skip 절이 **`NOT EXISTS`** 다 — 원장에 그 이용권 행이 **있을 때만** 자동정산이 건너뛴다.
   원장이 비어 있으면 건너뛸 것이 없어 자동정산은 종전과 똑같이 돈다 ⇒ "통째로 빠진다"는
   **구조적으로 일어날 수 없다.**
2. 원장 기록(`recordVoucherUsedLedger`)은 이용권 사용 시점에 **게이트 없이** 돈다
   (`group-buy-voucher.routes.ts` 의 `waitUntil` — 조건은 `merchantId && amount > 0` 뿐).
3. 그 원장은 실제로 지급까지 간다 — `payouts-generate` 가 `credit_account LIKE 'merchant:%'`
   를 집계해 payout 행을 만든다.

⇒ **켜는 것이 보호**이고, 켜지 않은 채 두 레일을 살려 두는 것이 **이중 지급 위험**이다.

🩸 **더 고약한 것**: 같은 기능의 cron 머리말 주석(`auto-settlement.ts`)은 **이미 그렇게 적혀
있었다** — *"두 레일은 서로의 멱등 마커를 안 본다 ⇒ 같은 매출을 두 번 지급할 수 있다 … 그 경로까지
닫는 것은 게이트 flip"*. 즉 **코드 주석과 어드민 화면이 정반대**였고, **대표가 읽는 자리는 화면**이다.
그 오기 때문에 세션이 두 번(09-24 · 09-28) 켤 수 있는 스위치를 미뤘다.

**수정**: 두 문구를 기제 설명으로 교체하고, `turn_on_when` 에는 **정정 기록을 남겼다**(낡은 문장을
그냥 지우면 다음 세션이 같은 오판을 반복한다 — 이미 두 번 그랬다).

**가드**: `settlement-gate-direction-2026-09-29.test.ts` 9건. 문구가 아니라 **그 문구가 참이 되게
하는 세 가지 사실**을 고정한다(NOT EXISTS · 원장 무게이트 · merchant 집계). 주입 6건 전부
**되돌려-검증 빨간불 확인**.

🩸 **주입이 내 시험 하나를 헛돈다고 잡았다**: 원장 기록 앞 **400자**만 보고 게이트 유무를 판정했는데,
심은 게이트가 약 450자로 밀려나 **초록**이 떴다. 창 크기는 임의 숫자다 ⇒ **구조로 앵커**
(`waitUntil` 블록 전체에 `platform_settings` 가 없는지)로 교체.

### ⏳ 대표가 할 것

> 어드민 → `/admin/platform-settings` → 머니 스위치 **⑨ 자동정산에서 원장 기록분 제외** → `ON` → 저장

**지금이 가장 안전하다** — 양쪽 레일의 정산행이 아직 0이라 켜도 아무 일이 안 일어나고, 이용권이
팔린 뒤엔 이미 양쪽에 적힌 것을 손으로 맞춰야 한다. 결재 파일: `docs/decisions/2026-09-24-settlement-single-rail.md`

## ③ 계좌 0곳 — **화면 문제가 아니었다** (판정, 코드 변경 없음)

대표 질문: *"9곳 중 0곳인 게 영업 문제인지 화면이 안 보이는 문제인지"*

**화면은 멀쩡하다.** 셀러 정산 화면에 경고 카드 + `[계좌 등록]` 버튼이 있고
(`SellerSettlementsPage:214`), `/seller/business-info?tab=bank` 에서 `PUT /api/seller/profile` 로
저장된다(2026-04-22 에 *"등록 UI 자체가 없어서 settlements 버그 유발"* 을 고치며 만든 화면).

**진짜 원인** — 라이브 실측(2026-09-29):

| id | 매장 | 계좌 | 연결(`linked_user_id`) | email | 비번 | 활성상품 |
|---|---|---|---|---|---|---|
| 14 | 홍대돈까스 | - | **없음** | **없음** | **없음** | **1** |
| 15·16·17 | `[테스트] 클로드분식·카페·미용실` | - | 없음 | 있음 | 없음 | 0 |
| 20 | 청룡갈비 | - | 없음 | 있음 | 없음 | 0 |
| 21 | 해운대해수욕장 | - | 없음 | 있음 | 없음 | 0 |
| 22 | 구서우성아파트 | - | 없음 | 있음 | 없음 | 0 |
| 23 | 박달집흑염소 | - | 없음 | 있음 | 없음 | 0 |
| 24 | 현정 | - | **40** | 있음 | 있음 | 1 |

**9곳 중 8곳은 계좌를 넣을 사람이 아예 없다** — `linked_user_id` 가 NULL 이면 그 매장에 로그인할
계정이 연결되지 않은 것이고, 전부 어드민이 대리 등록한 매장이다. 사장님이 유어딜에 들어온 적이 없다.
⇒ **화면 탓이 아니라 연결(영업) 문제다.** 실제로 "안 넣은" 경우는 로그인 가능한 **24번(현정) 한 곳**뿐.

**어드민 도구는 이미 있다**: `/admin/pending-sellers` → "카카오 미연결 셀러 (N)" → 핸들 입력
원클릭 연결(`PATCH /api/admin/sellers/:id/link-user`). email 이 같으면 카카오 로그인만으로 자동 연결도 된다.

### 🔴 두 가지 보고

1. **매장 14(홍대돈까스)가 최악이다** — email·비번·연결 **전부 없음** = 로그인 경로가 0 인데
   **활성 상품 1개**(라이브에서 팔리는 유일한 실제 이용권, `/group-buy/2888`). 팔리면 정산
   대상이 되는데 **본인이 계좌를 넣을 방법이 없다.** 어드민 원클릭 연결로 사람을 붙여야 한다.
2. **테스트 매장 3곳이 라이브 승인 목록에 남아 있다** — `[테스트] 클로드분식·카페·미용실`
   (제가 이전 세션에 만든 시드). 상품 0개라 소비자 화면엔 안 뜨지만 **승인 매장 수를 9로 부풀린다**
   (실제 매장 6곳). 프로덕션 데이터라 건드리지 않았다 — 정리할지는 대표 판단.
