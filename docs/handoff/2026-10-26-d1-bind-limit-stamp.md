## 2. 무슨 일이 있었나

PR #2013(내보낸 리드 도장 — 500행 묶음)이 머지·배포됐는데 **라이브에서 도장이 한 건도 안 찍혔다.**

## 8. 🔴 같은 날 후속 — 같은 병이 **이미 터져 있던** 자리 (`/api/fcfs/active`)

도장을 고치고 손으로 `IN (?,?,…)` 을 조립하는 자리를 전수로 세니 **171곳**이었고, 그중 하나는
**지뢰가 아니라 이미 터진 사고**였다(라이브 실측):

```
/api/fcfs/active  →  {"success":true,"data":[]}   HTTP 200
  원인: fcfs_enabled='1' 상품이 395개 → 바인딩 395 > 100 → 두 쿼리 모두 실패
        .catch(() => ({results:[]})) 가 삼켜 빈 목록이 "정상" 으로 나갔다
  피해: 지도 선착순 배지 · 상권관 체험단 목록(LocalTownPage) 이 통째로 비어 있었다
```

**처방은 쪼개기가 아니었다** — 쪼개면 `ORDER BY` 를 JS 로 베껴야 하고, 그 정렬엔 2026-07-04 대표
지시(데모-후순위)가 들어 있어 **두 벌이 되면 한쪽에서만 지켜진다**. 필터를 **SQL JOIN** 으로 옮겼다:

```sql
JOIN product_supply_meta mf ON mf.product_id = p.id AND mf.key = 'fcfs_enabled' AND mf.value = '1'
```
`product_supply_meta` 는 `PRIMARY KEY (product_id, key)` 라 행이 안 늘고(실측 중복 **0**), 바인딩은
region 분기의 **0~1개**, 정렬은 한 글자도 안 바뀐다. 라이브 D1 에 새 SQL 을 직접 돌려 **363행** 확인
(395 − 비활성 32 · orphan 0 — 숫자가 정확히 맞는다).

같은 커밋에서 **아직 안 터진 지뢰 셋**도 치웠다 — 추첨 **승계 판정**(`user_id NOT IN (당첨자)` = 1+N
바인딩 → 100명 넘으면 승계인데 "첫 선정" 문안) · **당첨자 알림톡 전화 조회**(100명 넘으면 전원
미발송) · 은퇴한 `d1-backup` 의 `rowid IN` 500개(라이브 백업은 `d1-backup-chunked` 의 범위 페이징이
하므로 피해는 없었다 — §6 의 정정 참조).

- 숫자코드 **5,713**(아직 통신판매 5,537) → **커서가 이미 지나갔다**(미해소, 대표 판단 대기)
- 한글 1,430 → 이미 79% 구체 라벨 · `종합몰` 403건 실재(10-25 수리가 돈다는 증거)
- 🔴 "이메일 보유 우선 재수집" 은 **구조적으로 불가능**(detail 은 API 페이지 순서대로 받는다)
- 📎 `description` 원문 승계를 네 겹으로 좁혀 넣었다(가드 13건 + 주입 8건)

## 10. 🏷️ 같은 날 후속 — 버킷 표는 **넓힐 게 아니라 고칠 것 둘**이었다

예정 작업이 *"버킷 표 넓히기(추측 금지)"* 였다. 넓히려고 라이브 한글 품목 **1,393건을 전수로**
읽었더니 어휘가 **닫힌 11종**(공정위 통신판매 신고 표준)이었고, 넓힐 자리가 아니라 **고칠 자리**가 있었다.

```
종합몰 · 의류/패션/잡화/뷰티 · 건강/식품 · 교육/도서/완구/오락 · 레저/여행/공연
가구/수납용품 · 컴퓨터/사무용품 · 자동차/자동차용품 · 가전 · 성인/성인용품 · 기타
```
(복합 신고는 공백으로 이어 준다 — `종합몰 의류/패션/잡화/뷰티` 26행.)

그 11종을 `productBucket` 에 **실제로 돌려** 보니 둘이 엉뚱한 버킷으로 갔다:

| 공정위 라벨 | 갔던 곳 | 왜 | 라이브 |
|---|---|---|---|
| `컴퓨터/사무용품` | **도서·문구** | 그 정규식의 `사무용품` 이 2번째라 `컴퓨터` 를 가로챘다 | **45행** |
| `가구/수납용품` | **생활·주방** | 그 정규식의 `수납` 이 7번째라 `가구` 를 가로챘다 | **28행** |

2026-10-25 에 `완구` 가 `교육·도서` 를 가로챈 것과 **같은 클래스**이고, 그 코드 주석이 이미
*"뒤쪽 낱말 하나에 걸려 좁은 업종으로 오분류"* 라고 경고해 둔 바로 그 함정이다.
**순서가 곧 규칙인데 순서는 눈에 안 보인다** — 그래서 가드가 진짜 함수를 돌린다.

### 10-1. 앵커를 슬래시째 리터럴로 둔 이유

`['가전·디지털', /컴퓨터\/사무용품/]` — 이 문자열은 **공정위 라벨에서만** 나오므로 자유 텍스트
(블로그·크롤 문구)에 걸릴 수 없다. 낱말(`컴퓨터`·`가구`)로 올리면 *"컴퓨터 서적 · 프로그래밍 도서"* 가
가전·디지털로 끌려온다 — 가드가 그 **반대 방향**을 따로 고정한다(주입 `앵커를 낱말로 넓힌다`).
`종합몰` 은 여전히 맨 앞이라 최상위 포괄 라벨은 안 밀린다.

### 10-2. 일부러 버킷을 안 준 둘

`성인/성인용품`(11행)은 B2B 마케팅 풀에 둘 라벨이 아니고, `기타`(421행)는 공정위 자신의 '기타' 라
우리가 뜻을 지어낼 수 없다. 둘 다 `통신판매` 로 남는다 — **조용히 생기지 않게** 주입이 막는다.

### 10-3. 🔴 이미 찍힌 73행은 이 수리가 못 고친다

`ON CONFLICT` 는 총칭(`통신판매`)만 승격하고 **구체 라벨은 보존**한다. 그래서 `도서·문구` 145행 중
`컴퓨터/사무용품` 을 가진 **45행**, `생활·주방` 37행 중 `가구/수납용품` 을 가진 **28행**은 그대로다.
데이터 UPDATE 는 **결재**이고, 이 수리가 하는 일은 *그 뒤로 더 안 늘게* 막는 것이다.
⇒ **틀린 라벨은 늦게 고칠수록 비싸다**(매 회차 쌓인다).

### 10-4. 🩸 라이브 숫자를 필터로 가르지 말 것

`종합몰` 을 `email IS NOT NULL` 로 세어 **134** 가 나왔고, 전날 인계의 **403** 과 비교해
*"수리가 퇴행했다"* 로 오진할 뻔했다. 전수로는 **420**(그 사이 늘었다 = 수리가 라이브에서 돈다).
전날 숫자가 어느 모수였는지 확인하지 않고 비교한 것이 원인이다.

### 10-5. 함께 판정한 것 (예정 작업 ①②)

- **① 도장 창(1→7일) — 레인 단위 통과**: `ads_lane_runs:collect-neis` 최근 **12회차 12/12 `n < f`**,
  f **68,601** → n **483** = **스킵 99.3%**. 예측 정상상태(79%)보다 **높다** — *"효과가 줄었다"* 가 아니다.
  ⚠️ **누적(`top=collect-neis`) 비교는 못 했다** — 하트비트 `r` 문자열이 `top=collect:90705,collect-`
  에서 잘린다(`BEAT_TOP_LANES` 2개 · 전체 표는 DO 내부 `/budget?full=1` 뿐이라 외부에서 못 읽는다).
  레인 단위 값이 더 직접적인 신호이고, 그 값으로 판정했다.
- **② 업종 비율**: `통신판매` 93.0% → **92.49%**(이메일 64,334 중 59,503) · 모수가 62,757 → 64,334 로
  **함께 늘었다**(모수만 늘면 비율은 안 내려간다 — 그래서 새 라벨의 **등장**이 1차 신호다).
  `종합몰` 420 · `패션·잡화` 484 · `식품` 214 · `도서·문구` 145 전부 실재.
- 🛑 **코드표 결재는 기각됐다**(`docs/decisions/archive/2026-10-25-commerce-goods-code-table.md`) —
  숫자 코드(`취급 12` 1,269 · `06` 1,113 · `01` 784 · `08` 547 …)의 뜻은 범위 밖이고 **대표께 다시 묻지 말 것**.
  💡 다만 길은 하나 남아 있다: detail 응답이 코드와 한글을 **같은 레코드에** 준다(coverage 31%).
  그 쌍을 둘 다 저장하면 코드표를 **실측으로 도출**할 수 있다 — 표준 목록을 외부에서 구할 필요가 없다(별건).
