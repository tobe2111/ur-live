### 🔧 구조적 고도화 — "로컬 tsc 는 죽어 있다" 의 진짜 원인을 찾았다

여러 세션이 인계에 *"로컬 tsc 는 죽어 있다(TS 6.0.2 + baseUrl). CI 가 유일한 타입 검증"* 이라고 적어 왔다.
원인은 **`tsconfig.json` 의 `baseUrl` 한 줄**이었다 — TS 6 부터 경고가 아니라 **에러(TS5101)** 라서
설정 로드 단계에서 tsc 가 **즉시 중단하고 파일을 하나도 안 본다**. 출력이 2줄뿐이라 "에러 없음"과 똑같이 보인다.

**수리**: `baseUrl` 제거 + `paths` 를 상대경로(`./src/*`)로. TS 4.1+ 형태라 5·6 양쪽 동작 + TS 7 대비.
- `baseUrl` 의존 비상대 import **0건** 확인 · `@/` 4,094건 그대로 · vite·vitest·esbuild 는 각자 alias 정의라 무관
- ⚠️ `ignoreDeprecations: "6.0"` 은 **쓰면 안 된다** — 고정 TS 5.5 가 그 값을 거부해 CI 가 깨진다
- 실측: baseUrl 있을 때 출력 2줄 / 없앤 뒤 전량 검사

**남은 절반은 이 컨테이너에서 못 푼다** — `node_modules` 가 없어(레지스트리 **전면 403**, 패키지별 정책 아님·
오프라인 캐시도 불완전) 서드파티 타입이 전부 미해결이다. 즉 **npm 접근이 열리는 환경에서만** 로컬 tsc 가 실용적이다.
그 환경에서는 이제 최신 tsc 로도 정상 동작한다(이전엔 조용히 0개 검사).

가드 2종: `check-tsconfig-resolution`(설정) + verify.yml **검사 대상 수 하한 500**(설정은 멀쩡한데 대상이 0인 경우).

### B1(번들 raw 다이어트) 조사 — **raw 는 잘못된 표적이었다**

raw 8.8MB 는 예산이 **5번** 올라간 결과라 다이어트 대상으로 보였는데, 실제로 보니 아니다.

- `firebase`(가장 무거운 후보) 정적 import 7건 중 **6건이 `import type`** → 번들 비용 0.
  나머지 1건도 `vite.config.ts:86` 이 `firebase` 청크로, 래퍼는 `app-firebase-wrapper` 로 분리한다.
  즉 **임계 경로가 아니다** — raw 총량만 키운다. `@stripe/*`·`drizzle-orm` 등도 같은 성격(lazy).

### 🌐 라이브 계약 검증 (신설 — 이 세션 마지막 작업)

`scripts/check-live-contracts.mjs` + `.github/workflows/live-contracts.yml`(주기 실행 전용).
**오늘 내가 손으로 해서 12건을 찾은 작업**(예열 404 9건 + sitemap 죽은 URL 3종)을 기계가 하게 했다.
코드에 선언된 URL — `HOT_PATHS` · `SSR_KV_PATHS` · `sitemap.xml` 정적 `loc` — 을 추출해 실제로 두드린다.

**설계에서 실측으로 배운 것 3가지** (그냥 200 만 통과시키면 전부 오탐이 됐다):
1. **3xx 를 실패로 세면 안 된다.** `live.ur-team.com` 은 `urdeal.kr` 로 **영구 301** 중이라
   소비자 sitemap URL 12건이 전부 301 이다. → **경로가 같은 3xx = 통과**, **경로가 바뀌는 3xx = 실패**
   (`/group-buy → /` 를 이 규칙이 잡는다). 리다이렉트 대상을 따라가지 않고도 판정된다.
2. **프록시 차단은 status 0 이 아니라 403 응답으로 온다.** 이 컨테이너는 `utongstart.com`·`urdeal.kr` 을
   CONNECT 403 으로 막는데, node `fetch` 에는 **정상적인 403 응답**처럼 보인다. → "오리진의 *모든* 대상이
   *동일* 실패" 면 오리진 레벨 조건으로 보고 **스킵**(눈에 띄게 보고). 일부만 실패하면 진짜 죽은 URL 이라 잡는다.
3. **동시성을 올리면 가짜 503 이 쏟아진다.** 4-way 로 돌렸더니 12건이 503 이었는데 같은 URL 을 단건으로
   curl 하면 301 이었다 — 중계 구간 throttling. → **동시성 2 + 요청 간 250ms + 3회 재시도(2s→4s)** 로 고정.
   여기서 "죽었다"고 결론냈으면 멀쩡한 sitemap 을 지울 뻔했다.

**현재 상태**: 34건 검사 전부 통과(도매 4건은 프록시 차단으로 스킵 — CI 러너에서는 실제 검사됨).
sitemap 의 `encodeURIComponent('편의점')` 같은 **정적으로 확정되는 템플릿 loc 도 풀어서 검사**한다
(오늘 죽어 있던 카테고리 URL 6종이 정확히 그 형태였다).

⚠️ **PR 게이트로 승격 금지.** 외부 네트워크 의존이라 간헐 실패가 머지를 막는다. 주기 실행 + 수동 실행만.
uptime.yml(10분 주기, 사이트 생존)과 역할이 다르다 — 이건 **선언과 현실의 어긋남**을 본다.

`Sitemap:` 누락은 색인 발견성에도 직접 영향.

**아직 모르는 것(가장 중요)**: **정본 도메인 `urdeal.kr` 도 같은 상태인지 확인 못 했다.**
