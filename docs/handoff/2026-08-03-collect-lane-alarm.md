# 수집 레인을 알람으로 — 대표의 1순위 축이 34개 중 가장 굶고 있었다

> 대표: *"어떻게 하는게 가장 이상적이야?"* → *"응 해줘"*

## 무엇이 문제였나 (전부 실측)

`ads:collect` 는 **마지막 성공이 KST 03:01, 그 뒤 6시간 30분 정지**였다. 그동안 리드 0건, 커서 0전진.
원인이 **둘이 겹쳐 있었다**.

### ① 순번을 거의 못 받는다

```
KST 09:00 회차 (per_tick 3 · 무료 플랜)
  influencer  budget 1 → run:[inbound-onboarding]
                         deferred:[collect, consented-reminder, social-maintenance]
  company     budget 1 → run:[3개]  always:2
  prospect    budget 1 → run:[collect-hira]  deferred:[4개]
  wholesale   budget 0 → run:[collect-maker]
```

인플루언서 도메인은 **레인 4개가 시간당 예산 1칸**을 나눠 쓴다 → collect 는 잘해야 4시간에 한 번.

### ② 그 한 번마저 죽는다

```
22:00:35  디스패치 (run:['collect'])
22:00:38  ads:collect            Worker exceeded CPU time limit.   ← 3초 뒤
22:00:38  ads:enrich-company     Worker exceeded CPU time limit.
22:00:38  ads:collect-storeinfo  Worker exceeded CPU time limit.
22:00:37  ads:sheets-sync        Worker exceeded CPU time limit.
```

자식 인보케이션의 CPU 는 부모에게 청구되므로 B2B 29개와 **같은 벽**에 부딪힌다.
24시간 CPU 사망 29건의 최다 소비자는 `sheets-sync` 6 · `enrich-company` 6 — **둘 다 인플루언서 축이 아니다.**

⇒ **예산 재분배로는 못 푼다.** 누가 굶느냐만 바뀌고 벽은 그대로라, 순번을 받아도 또 죽는다.

## ✅ 처방 — `collect` 를 DO 알람 레인으로 (`ALARM_LANES` 등록부)

자기 인보케이션·자기 CPU 를 갖는다 → B2B 29개와의 경쟁이 **끝난다**.
어젯밤 같은 패턴을 두 번 검증했다(`enrich-influencer`·`maintenance` 둘 다 fail_streak 0, 시간당 12회차 안정).
부수 효과로 인플루언서 도메인 예산 1칸이 비어 **나머지 3개 레인 순번도 빨라진다.**

### ⚠️ `runsPerHour: 1` — 증설이 아니라 복원이다

cron 이 원래 `0 * * * *`(시간당 1회)다. 기본값 12를 그대로 받으면 **설계 의도를 12배 넘는 증설**이고,
그건 네이버로 나가는 요청을 늘리는 일이라 **대표 판단 사항**이다. 여기서는 의도한 값으로 되돌리기만 한다.

### 🩸 내가 어제 틀렸던 판단 (이게 이 문서에서 제일 중요하다)

어제 나는 이 처방을 **"외부 검색량 4배"라며 보류**했다. 세 가지를 잘못 봤다:

1. **YT 검색량은 안 늘어난다** — `ytBudgetTotal`(하루 90~100)이 하드캡이라 회차 수와 무관하게 총량이 같다.
2. **네이버는 하루 25,000 쿼터에 실사용 ~2%** — 4배여도 8%.
3. 무엇보다 **"4배"의 기준이 설계 의도가 아니라 *고장 난 현재*(6시간에 한 번)였다.**

그리고 대표가 "밀지 마라"고 한 건 **측정 레인을 4조각으로 쪼개는 건**이었다. 그건 네이버에 **동시 요청**을
4배로 늘리는 일이라 성격이 완전히 다르다. **나는 그 판단을 엉뚱한 건에 가져다 붙였다.**
⇒ 교훈: *"과거 지시를 새 건에 적용하기 전에, 그 지시가 무엇을 걱정한 것인지부터 맞춰볼 것."*

## 🪦 축 줄이기를 자연스럽게 (대표 *"줄이기도 자연스럽게 만들어줘"*)

### 왜 필요했나 — 늘리기와 줄이기가 비대칭이었다

**늘리기는 이미 자연스러웠다.** 규칙 하나 추가하면 `CLASSIFIED_CATEGORIES` 가 자동 파생되고,
어드민 필터 누락은 유닛이 막고, 기존 리드도 재분류가 ~2시간 안에 끌어온다(골프 축 222명이 증거).

**줄이기는 반대였다.** 규칙만 지우면 세 군데에 잔재가 남는다:

```
① 리드의 카테고리 값 — 아무 규칙도 안 만드는 유령 값으로 영구 잔존
② 키워드의 카테고리 — 폴백(resolveCategory)이 새 리드에 계속 그 값을 붙임
③ 수집 슬롯        — 죽은 축 키워드가 희소한 회차(시간당 1회·16픽)를 계속 먹음
```

라이브는 아직 **저장 카테고리 18개 = 분류기 18개**로 일치한다 —
**아직 아무것도 지운 적이 없어서** 문제가 안 드러난 상태였다.

### ⚠️ 왜 "규칙에 없으면 지운다"로 일반화하지 않았나

`shouldClearCategory` 의 docblock 이 정면으로 경고한다 —
*"모르는 값을 지우면 사람이 손으로 고친 분류까지 날린다."*

**분류기가 안 만드는 값 ≠ 잘못된 값**이다. 키워드 폴백은 키워드에 적힌 **어떤 문자열이든** 붙일 수 있고
그건 정당한 경로다(실측: 활성 키워드 카테고리 18종 중 `자동` 은 분류기가 안 만든다).
⇒ 추론이 아니라 **선언**(`RETIRED_CATEGORIES`)으로 받는다. 사람이 "끝났다"고 말한 것만 지운다.

### 줄이는 절차 — 이제 두 줄이다

1. `RULES` 에서 그 규칙 제거   2. `RETIRED_CATEGORIES` 에 이름 추가.
끝. 리드 정리·신규 유입 차단·슬롯 회수는 자동이다.

### 🧪 헛도는 가드를 만들 뻔했다 (기록해 둔다)

첫 구현의 동작 검사가 `for (const c of RETIRED_CATEGORIES)` 였는데 **그 목록이 비어 있다**
(접은 축이 아직 없다) → **0건을 돌며 영원히 통과**. 이 레포가 반복해 겪은 바로 그 클래스다.
⇒ `shouldClearCategory` / `resolveCategory` 에 **주입구**(`retired = RETIRED_CATEGORIES`)를 냈다.
`pickYtKeywords(…, priorityCats)` 와 같은 기존 seam 패턴이라 이질적이지 않다.
테스트는 가짜 은퇴 축(`접은축`)으로 **진짜 동작을 검사**한다.

가드 4건 전부 주입해 빨간불 확인(비우기 제거 · 폴백차단 제거 · 슬롯필터 제거 · 규칙과 은퇴 동시선언).

### 📌 아직 못 하는 것

- **어드민 필터(`POOL_CATEGORIES`) 정리는 수동**이다. 리드가 다 비워지면 빈 필터 항목이 남는다(무해).
- `저장된 카테고리 ⊆ 분류기 ∪ 키워드 ∪ 은퇴유예` 는 **DB 를 봐야 알 수 있어** CI 가 못 본다.
  줄인 뒤 한 바퀴(~2시간) 지나서 `SELECT category, COUNT(*) … GROUP BY category` 로 확인할 것.

### 발견 요약

```
유튜브 쿼터 10,000/일
  검색  배정 9,000(90회) · 실사용 2,200(22회)   ← 6,800 유휴
  성과  배정 2,000       · 실사용 2,003         ← 소진 → 그날 남은 시간 측정 0
  총 사용 4,200 (42%)

수율   유튜브 45.2%(1,437/3,181)  vs  네이버 블로그 28.6%(3,811/13,337)
       ⇒ **멎은 쪽이 더 좋은 축이었다.** 미측정 YT 3,161 × 45% ≈ 이메일 1,420명
효율   PT 하루 2,003 units 로 106행 = **19콜/행** (코드상 건당 2~3콜)
```

### ①-a 재선택 churn — 19콜/행의 정체 (**가장 중요**)

선택 순서가 `(pub_checked_at IS NULL) DESC, subscriber_count DESC` 인데, 예산으로 건너뛴 행의
UPDATE 가 `pub_checked_at` 을 **안 찍었다**. 그래서 그 행은 **다음 회차에도 맨 앞**이고,
회차마다 `channels.list` 를 다시 태운다. 예산 14로는 20행 중 앞 ~11행만 완주 → 나머지는 영구 churn.

🔑 여기까지 왔다는 건 `if (!chJson) return 0` 을 통과했다는 뜻 = **channels.list 는 성공**했고
About/개설일/카테고리를 지금 쓰고 있다. 즉 "pub 은 확인됨"이 **사실인데 스탬프만 없었다.**
⇒ 스탬프를 찍는다. `perf_checked_at` 은 **여전히 안 찍는다**(0 각인 금지 — 기존 사고 그대로).

### ①-b 성과 상한이 고정 2,000

상수 주석은 *"검색 예산을 크게 **올릴** 때는 이 값을 낮출 것"* 이라고 **한 방향만** 대비했다.
반대(검색이 배정을 안 쓰는 경우)가 실제로 일어났다 — 키워드 쿨다운·고갈 억제가 검색을 22회로 누른다.
⇒ `resolveYtPerfCap(검색실사용)` — 검색 바닥(3,000)은 지키고 나머지를 성과가 받는다.
   실측 대입: 2,200 → **상한 7,000**(3.5배). 기본값 2,000 밑으로는 절대 안 내려간다.

### ③ 선두 교대가 알람에서 반쪽 — ①-b 와 **한 몸**

`depth % 2 === 1 || starvedLastRound(prev)` 인데 **알람은 `depth` 가 항상 0**(`chain.rounds: 1`).
`0 % 2 === 1` 은 영원히 거짓 ⇒ 결정적 교대가 **한 번도 발화한 적 없다.**
지금은 앞 레인이 0을 내서 무해했지만, **①-b 로 YT 가 살아나면 블로거가 굶는다.**
⇒ 깊이 대신 **직전 선두**(`led`)로 교대.

🪦 **기존 유닛이 이 죽은 식을 못 박고 있었다** — *"두 신호를 OR 로 묶는다 — 어느 하나가 죽어도
교대가 산다"* 라고 적어 놓고 실제로는 반쪽을 고정. 가드가 **사실이 아닌 것을 지키는** 형태였다.
그 테스트를 교체하고 왜 바꿨는지 그 자리에 남겼다(되돌리지 말라는 경고 포함).

### ④ cron 시절 창(7초)이 알람에 그대로

7초의 근거는 *"부모 인보케이션이 10.5초에 회수되고 자식이 함께 죽는다"*. **알람엔 부모가 없다.**
증거: 같은 알람의 `collect` 가 **28,643ms 완주**(2회차 연속, fail_streak 0). ⇒ 알람 경로 20초.

①-b 와 짝이어야 의미가 있다.


루프 **뒤**에 `DB.batch(stmts)` 가 온다 — **이 회차 측정 결과 전량의 유일한 쓰기**다. D1 도
서브리퀘스트라 루프가 마지막 칸까지 쓰면 batch 가 던지고 `.catch(() => null)` 이 삼킨다.
그러면 **채널콜·영상콜 쿼터를 다 태우고 저장 0** 이고, 스탬프(`perf_checked_at`)도 안 찍히니
그 행들이 다음 회차에도 맨 앞이다 — **이 PR 이 잡으려던 재선택 churn 을 되레 만드는** 경로다.
①-b 로 YT 상한이 2,000 → 7,000 이 되면 이 루프가 예산 끝까지 도는 회차가 실제로 생긴다.

베이스라인에서 그 항목을 지웠다(2건 → 1건, `franchise-collect.ts:91` 만 남음). 남겨 두면
*미래에* 그 좌표에서 생기는 새 위반이 조용히 통과한다.
