# 08-02 — 수량 실측: 양은 문제가 아니다. **연락처가 안 채워진다**

> ⏰ 시각은 KST. DB 스탬프는 `Z` 없는 UTC 문자열이라 그대로 읽으면 9시간 어긋난다(+9h 변환).

## 한 줄

풀 **173,824건** 중 **86.6%(150,529건)가 연락처 없음**. 그리고 그걸 채우는 두 레인의
**적중률이 0** 이다 — 빨리 돌려도 안 채워진다. 이건 처리량 문제가 아니라 **수집원 선택의 결과**다.

## 왜 연락처가 안 채워지나 (산수)

```
백로그                150,529건
카카오 전화 스윕       시간당 37건 시도 → found 0 (누적 total_found 82)
이메일 보강            시간당 3~5건 처리 → enriched 0 (hit_rate 0)
```

시간당 ~40건으로 15만 건 ⇒ **157일**. 그런데 **적중률이 0** 이라 그 157일을 다 써도 안 채워진다.

원인은 크롤러가 아니라 **대상 자체**다:

```
대행사 3,195건 — 홈페이지 없음 2,324 (73%) · 크롤 시도 722 → 이메일 105 (14.5%)
```

**73% 는 크롤할 대상이 없다.** 크롤러 개선으로 넘을 수 없는 벽이다.

## 그래서 ③의 원인은 ①이다 (전략 판단 — 대표 확인 필요)

- **통신판매 원부**(전체의 75%)는 **대량이지만 연락처가 빈약**하다. 프로브 실응답에서 `telno: "N/A"` 를 직접 확인했다.
- **카카오 로컬**(`store-kakao`)은 코드 주석대로 **전화가 함께 들어온다**(네이버 지역검색은 전화가 빈값).

⇒ 지금 전략은 *"많이 모으고 나중에 채운다"* 인데 **채우는 쪽이 구조적으로 작동하지 않는다.**
더 모으면 **연락처 없는 리드만 늘어난다.**

⚠️ **아직 검증 안 된 것**: 수집원별 연락처 보유율을 직접 세지 않았다(위 판단은 통신판매 표본의
`telno: "N/A"` + 대행사 깔때기 + 코드 주석 근거). **다음 세션의 첫 액션은 이 수치를 세는 것이다** —
`ad_company_leads` 를 `source` 별로 GROUP BY 해서 `phone IS NOT NULL` / `email IS NOT NULL` 비율을 낸다.
그 표가 나오면 "어느 수집원을 늘리고 어느 것을 줄일지" 가 **의견이 아니라 데이터**가 된다.

## 다음 세션의 우선순위

1. **수집원별 연락처 보유율 집계** (위) — 이게 나오기 전엔 수집 전략을 바꾸지 말 것.
2. **회사/대행사 레인이 왜 07-31 에 멈췄나** — `collect-company` 는 08-01 14:00 KST 에 `err=Error`
   기록이 있다(원문 없음 — #912 이전). 다음 실행 때 `detail` 이 붙는다.
3. **가맹·나라장터 404 를 라이브가 스스로 찾게** — 이 레포엔 이미 그 패턴이 있다(`license-url.ts`
   의 variant 프로브). 후보 엔드포인트를 몇 개 넣고 라이브가 200 을 주는 것을 고르게 하면
   대표의 수동 확인 없이도 열릴 수 있다. ⚠️ 후보는 **URL 문법 안에서 bounded** 여야 한다(찍기 금지).
4. `cpu_risk` 를 경보 경로에 연결 — 지금은 보이기만 하고 아무도 안 부른다.
