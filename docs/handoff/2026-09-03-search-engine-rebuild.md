## 왜 trigram 이 답이 아닌가 (중요)

SQLite FTS5 trigram 은 **3글자 미만 쿼리에 결과를 내지 못한다.** 지금 잘 되는
`커트`·`네일`·`헤어`·`미용` 이 전부 2글자다. 한국어 상용 검색어는 2글자가 압도적이라
trigram 단독 전환은 교환이 아니라 **손실**이다. 이 판단이 이번 설계의 분기점이다.

## 처방 — 부분매칭 LIKE + SQL 랭킹을 1급으로

신규 SSOT `features/products/repositories/search-query.ts`:
- 토큰 **AND** · 컬럼 **OR**(`name`·**`restaurant_name`**·`description`·`category`)
- 부분매칭 `%q%` → 2글자도, 단어 안쪽도, 매장명도 한 번에
- 랭킹: 상품명 정확(1000) > 시작(800) > 포함(600) > 매장명(500) > 카테고리(300) > 그 외(100),
  동점은 판매량 → 평점 → 최신
- 동의어 확장은 기존 사전을 **주입**받는다(모듈은 사전을 모른다)
- LIKE 이스케이프 + 토큰 5개·40자 상한(거대 LIKE 방지)

`ProductRepository.searchByText` 가 이 SSOT 를 쓰도록 교체. 도매 원본·고아 general 격리 조건은 승계.

**규모 근거**: 활성 상품 **2,606개**. 이 규모에서 FTS 의 이점은 없고 함정만 있다.
🔭 **한계**: `%q%` 는 인덱스를 못 탄다. 활성 상품이 **수만 건**을 넘으면 다시 봐야 하고,
그때 처방은 "FTS 부활"이 아니라 **trigram FTS + 2글자 LIKE 병행**이다(위 2글자 문제 때문).

## UI — 이용권 행으로 통일

`RestaurantRow`(홈 지도 목록이 쓰던 행)를 `pages/restaurant-map/RestaurantRow.tsx` 로 **옮기고**
`/search` 가 같은 파일을 쓴다. **마크업은 옮기기만 했다** — 홈은 최고 트래픽 표면이라 시각 변화 0 이 조건.
검색은 `userLoc=null`·`fcfs` 미전달·`isSelected=false` 로 넘기면 되어 **새 prop 이 하나도 없다**.

죽은 필터 칩 5개 제거(`카테고리·3만원 이하·무료배송·브랜드·평점`). 동작하는 정렬은 유지.
