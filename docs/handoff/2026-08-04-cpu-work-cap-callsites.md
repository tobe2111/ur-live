## 2. 무엇을 왜 바꿨나

### 핵심 발견 — **CPU 시간은 벽시계를 넘을 수 없다**

08-03 에 두 레인에 붙인 처방은 **벽시계 마감선**이었다. 08-04 라이브에서 **둘 다 자기 마감선에
닿기도 전에** 죽었다:

```
ads:reclassify-company?passes=5   ms=1316   마감선 1,800ms   ← 못 닿고 사망
ads:sweep-kakao-chain             ms=6640   마감선 12,000ms  ← 못 닿고 사망
ads:collect-company               ms= 985                    (미수리)
ads:collect-hira                  ms=6409                    (미수리)
```

같은 날 `ads:sheets-sync` 는 **19,038ms 를 살아서 성공**했다. 19초를 살고도 멀쩡한 레인이 있는데
985ms 에 죽는 레인이 있다 ⇒ **문제는 시간이 아니라 계산량**이다. 대기(I/O)는 CPU 를 안 쓰므로,
외부 호출이 없는 경로일수록 **벽시계가 안 흐르는데 CPU 만 탄다** — 벽시계 근사가 가장 나쁘게
어긋나는 자리다.

이건 이 레포가 07-31 에 이미 세운 교리(`ads-cpu-work-cap`: *"막아야 하는 건 페이지 크기가 아니라
**인보케이션당 총 작업량**"*)와 같은 말이다. **교리는 맞았고 호출부 두 곳이 그걸 안 지키고 있었다.**

### 수리 ①: 카카오 전화 스윕 — 예산이 못 쓸 행은 읽지도 않는다

`LIMIT 600` 으로 행을 읽고 **나서** 예산을 계산했다. 예산 천장은 무료 플랫폼 캡(기본 60)이라
시도 가능한 행은 **~50개**. 나머지 550행은 D1 역직렬화만 되고 루프 `break` 에 버려졌다.

→ 예산 계산을 SELECT **앞**으로 옮기고 `rowsWorthReading(예산, 상한)` 으로 좁혔다.
**처리 대상·순서 불변**(잘린 꼬리는 원래도 안 쓰던 행, 도장은 시도분에만 → 기아 없음).

### 수리 ②: 소급 재분류 — 시간 대신 행 총량

5패스 × 1,000행 × 행당 정규식 ~20개 = **10만 회**. 무료 기준 **250행 × 최대 4패스 = 1,000행**
(2만 회, 1/5)로 묶었다. `reclassifyWorkPlan(env)` — **유료 값은 종전 그대로**(1,000/5,000)라
요금제를 올리면 자동으로 원복된다. 시간 상한은 **제거가 아니라 병행**(먼저 닿는 쪽이 멈춘다).
커서가 이어받으므로 **커버리지 손실 0** — 한 바퀴에 시간이 더 걸릴 뿐이다.

## 3. 이번에 틀렸던 판단 / 바로잡은 것

### ① 다른 세션의 결론을 그대로 이어받을 뻔했다
`2026-08-04-tick-cpu-ceiling.md` 는 *"틱 전체가 CPU 를 넘겨 뒤에 오는 레인이 죽는다 —
레인 하나를 고쳐도 다음이 대신 죽는다"* 고 적었다. 근거는 *"같은 시각·같은 예외"* 였다.

**그 추론은 `ms` 를 안 봤다.** 레인은 동시에 띄워지므로(`runLanes` 가 한 번에 map) 부모가 죽었다면
`ms` 가 **비슷해야** 한다. 실제로는 985 vs 6,640 — 6.7배 차이다. **각자 다른 시점에 죽었다** =
각 자식이 자기 CPU 예산을 태운 것이다. 그래서 "레인별 수리는 두더지잡기" 가 아니라 **레인별 수리가 맞다.**

⚠️ 단 이건 `ms` 해석에 기댄 추론이지 계측이 아니다. 배포 후 그 두 레인만 살아나면 확정된다
(부모 탓이었다면 셋 다 그대로일 것이다) — **그게 §1 판정이 갈라 주는 것**이다.

### ② 내가 어제 "유료로도 이 자리는 안 고쳐진다"고 보고했다 — 절반만 맞았다
그건 **부모 꼬리** 얘기였다. 지금 드러난 레인 사망은 무료 플랜 인보케이션 CPU 한도라
**유료 전환이 직접 해결하는 종류**다. 대표께 정정해 보고했다.

### ③ 파일 크기 캡을 두 번 밟았다
