# 2026-10-01 — 메인에선 숨기고 직링크로는 팔리게 (A 방식) + 그때 드러난 검색 누수

## 왜 이 작업을 했나

대표: *"일단 상품 비활성화 말고 어드민만 보게끔도 가능한가? 상품 링크로 접속하면 결제 가능하지만
유어딜 메인페이지에선 안나타나는거지."* → 시안 제시 후 **"2916을 그렇게 A 방식으로 해줘"**.

배경: 테스트 상품 2916(`[테스트] 클로드분식 1,000원 이용권`)의 커버가 **내가 임의로 만든
사업자등록증 이미지**라, 유어딜 메인에 뜨는 걸 보고 대표가 직접 `is_active=0` 으로 내려 뒀다.
그런데 P16/P17(부분환불) 실결제 테스트에는 그 상품이 **살아 있어야** 한다.

## 1. 다음 세션의 첫 액션

**(a) P16/P17 실결제 테스트는 지금 바로 시작할 수 있다.** 2916 은 직링크로 구매 가능 상태다.
```
https://urdeal.kr/group-buy/2916      # 1,000원 · 재고 10 · group_buy_status=active
```
주문 기준선: **총 89건, 최신 id 89** → 대표 결제분은 id 90 부터.

**(b) ⚠️ 그런데 ②단계(이용권 1장 사용)는 2916 으로 불가능하다.** 세 경로가 전부 막혀 있다
(§4 에 실측 표). 대표 판단 대기 중 — 새 테스트 매장을 만들면 풀린다.

**(c) 롤백 명령** (테스트 끝나면):
```bash
curl -X PATCH .../api/admin/products/2916  -d '{"is_active":0}'   # 상품 내리기
curl -X PATCH .../api/admin/sellers/15/approve                     # 매장 복구
```

## 2. 완료분

| 내용 | 상태 |
|---|---|
| 셀러 15 정지 + 상품 2916 재활성 (A 방식) | 라이브 적용·검증 완료 (코드 변경 0) |
| 검색·자동완성의 정지 매장 누수 수리 | 이 브랜치 (`claude/taste-skill-install-n1s63z`) |

### A 방식이 기대는 구조 (실측)

| 축 | 거르는 조건 | 2916 |
|---|---|---|
| 메인 노출(피드·섹션·지도·홈캐시·prelaunch) | `approvedSellerProductSql` = 셀러 `status` | **가려짐** (셀러 15 `suspended`) |
| 상세 페이지 | 아무것도 안 봄 (`baseWhere` 에 `is_active` 조차 없다) | 200 |
| 구매(join) | `is_active = 1` + 이용권 카테고리 | 통과 |

적용 순서가 중요했다 — **매장 정지를 먼저, 상품 재활성을 나중에.** 반대로 하면
`(승인 매장 + 활성 상품)` 창이 잠깐 열려 메인·엣지캐시에 실릴 수 있다.

⚠️ `DELETE /api/admin/sellers/:id` 는 이름과 달리 삭제가 아니라 `status='suspended'` 이고,
**그 매장 상품을 전부 `is_active=0`** 으로 만든다. 그래서 상품 재활성이 두 번째 단계로 필요했다.

## 3. 이번에 틀렸던 판단 — 그리고 A 방식이 드러낸 진짜 결함

### 🩸 "메인에서 가려졌다" 를 확인하고 끝낼 뻔했다

피드·섹션·쇼핑 카탈로그 세 곳에서 2916 이 사라진 걸 보고 완료로 보고하려다, 한 축 더 재 보니
**검색과 자동완성에는 그대로 떴다**:

```
/api/products?search=이용권  → HIT     /api/products/search/suggestions?q=분식 → ["[테스트] 클로드분식 …"]
/api/products?search=분식    → HIT     /api/products/search/suggestions?q=클로드 → ["클로드분식", …]
```

`이용권` 은 흔한 검색어다. **"메인에서 안 보인다"와 "소비자가 못 찾는다"는 다른 명제였다.**

### 그리고 그건 2916 문제가 아니라 문서화된 회귀였다

`ProductRepository.findAll` 머리말이 **2026-04-22 부터** 그 술어를 이렇게 적어 두고 있었다:

> `// 🛡️ 2026-04-22: suspended/inactive seller 상품 숨김 (검색/브라우즈 방어)`

**검색이 그 방어를 갖고 있지 않았다.** 2026-09-03 FTS 재작성이 `searchProducts` 를 새로 쓰며
술어를 빠뜨렸고, 자동완성은 애초에 가진 적이 없다. 즉 주석이 약속한 것과 코드가 어긋나 있었다.

**왜 몇 달간 안 보였나**: 둘 다 `is_active = 1` 은 갖고 있고, 정지 엔드포인트가 그 매장 상품을
전부 `is_active=0` 으로 만든다 → `(정지 매장 + 활성 상품)` 조합이 라이브에 존재한 적이 없었다.
A 방식이 **정확히 그 조합을 처음 만들어** 즉시 드러났다.

🧭 **교훈: 한 축에서 사라진 걸 확인하고 "숨겼다" 라고 쓰지 말 것.** 노출 표면을 전수로 셀 것
(피드·섹션·카탈로그·검색·자동완성·사이트맵·유어샵 핀). 그리고 **주석이 약속하는 방어는
그 자리에 실제로 있는지 확인할 것** — 이 레포에서 주석과 코드가 갈린 사례가 또 나왔다.

### 영향 범위를 먼저 쟀다 (고치기 전)

```
셀러 있는 활성 상품을 셀러 상태별로:
  approved  + is_active=1  →  2건
  suspended + is_active=0  →  1건   ← 2916 하나뿐
```
오늘 이 수리가 가리는 상품은 **2916 하나**다. 되돌릴 일 없이 안전.

## 6. 🩸 머지 후속 — 자동완성이 **두 벌**이었다 (2026-10-01, PR #1600 배포 직후)

PR #1600 머지·배포 후 E4 판정에서 검색은 깨끗해졌는데 자동완성이 그대로 샜다. 두 가지를 배웠다.

### ① 내가 틀린 주소를 쟀다

```
/api/search/suggestions           → []        ← SearchPage.tsx:122 가 실제로 부르는 자리. 고쳐졌다 ✅
/api/products/search/suggestions  → ["[테스트] 클로드분식 …"]   ← 프론트 호출자 0, 그러나 공개 접근 가능 ❌
```

처음에 두 번째만 재고 **"자동완성 수리 실패"** 라고 보고했다. 틀렸다 — 수리는 실제 경로에서 작동했고,
남은 건 **다른 핸들러**였다. ⇒ **엔드포인트가 여럿인 기능은 "그 화면이 부르는 주소"를 먼저 확정하고 재라.**

### ② 같은 규칙이 복제돼 있었고, 가드가 그 복제본을 못 봤다

자동완성 구현이 둘이다:

| 라우트 | 구현 | 이번 수리 전 |
|---|---|---|
| `productsRoutes.get('/suggestions')` → `/api/search/suggestions` | `search-suggestions.ts` `buildSearchSuggestions` | PR #1600 에서 고침 |
| `productsRoutes.get('/search/suggestions')` → `/api/products/search/suggestions` | **products.routes.ts 안의 인라인 SQL** | **안 고쳐짐** |

그리고 소스 주석이 두 번째를 *"라우트 마운트 때문에 안 닿는다"* 고 적어 두고 있었다 — **그 설명이 틀렸다**
(라이브에서 200 이 나온다). 주석을 믿었으면 영영 안 봤을 자리다.

🧭 **교훈: 배선 검사를 한 파일에 앵커하면 복제본을 구조적으로 못 본다.** ③-2 는 초록이었는데
라이브는 샜다. ⇒ 가드를 **전수**로 바꿨다(④-2): 두 파일에서 `name LIKE` 로 상품명을 긁는 SQL
리터럴을 **전부 모아** 술어 보유를 확인하고, `${scope}` 같은 간접 보유도 템플릿을 한 단계 펼쳐 본다.

### ③ 주입이 또 하나의 사각지대를 찾았다 (가드를 쓰는 중에)

"수집기가 눈이 머는가" 를 시험하려고 `FROM products` → `FROM products p` 로 별칭을 붙였더니
가드가 통과했다. 재 보니 **그건 수집기 문제가 아니라 진짜 결함**이었다 — 별칭을 붙이면 술어 안의
`products.seller_id` 가 해석 불가라 SQLite 가 던지고, 호출부의 `.catch(() => ({ results: [] }))` 가
삼켜 **자동완성이 조용히 빈 배열**이 된다(빨간불도 에러 로그도 없다). ⇒ ④-2-1 신설: 술어에 넘긴
별칭이 그 쿼리의 `FROM` 별칭과 같은지 대조.

**주입을 설계하다가 결함을 찾은 경우다.** 주입이 통과하면 "가드가 헛돈다" 를 먼저 의심하되,
**"주입이 사실은 결함이 아니다"** 도 같은 빈도로 의심할 것.
