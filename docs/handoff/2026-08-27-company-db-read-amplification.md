## 🔧 한 일

### ① 재분류 — "할 일 없음"을 확인하는 데 하루 1.3억 행
`classified_v < 9` 인 행이 1,854건 남아 있지만 **전부 접힌 행**(`merged_into`)이라 배치는 언제나 0건이다.
그런데 쿼리가 `ORDER BY id ASC LIMIT n` 이라 플래너가 PK 를 택해 **끝까지 걸어가서 빈손으로 돌아온다.**
→ `hasReclassifyWork()` 선검사(1행) + 부분·식 인덱스 `idx_company_leads_classify_todo`.
로컬 동일 데이터 재현 **57ms → 0.07ms**.

- ⚠️ `COALESCE(classified_v,-1)` 로 감싼 이유: `IS NULL OR < ?` 는 범위가 둘로 갈려 인덱스 한 번으로 못 짚는다.
- ⚠️ 선검사는 **커서를 일부러 안 본다** — 거짓 양성은 무해(예전과 같은 비용)하고 거짓 음성은 불가능해야 한다.
- ⚠️ 조회 실패는 **"일이 있다"** 로 답한다. 못 물어봤다고 재분류를 멈추면 그게 조용한 부재다.

### ② 보강 대상 — 400건 고르려고 33만 행 정렬
`WHERE` 가 331,641행을 통과시키고 `ORDER BY` 가 그 전부를 임시 B-트리로 정렬한 뒤 앞 400건만 쓴다.
→ 정렬 키를 그대로 담은 부분·식 인덱스 `idx_company_leads_enrich_order`.
로컬 재현 **86.5ms → 0.3ms**, `TEMP B-TREE FOR ORDER BY` 소멸, **결과 집합 동일**.

### ③ 잔여 백로그 COUNT — 상태줄 숫자 하나에 회당 32만 행
14분마다 정확할 이유가 없는 게이지다 → `REMAINING_TTL_MS`(1시간). 하루 105회 → 24회.
안 세는 회차는 **직전 값을 이어 쓴다**(0 으로 두면 "백로그가 사라졌다"로 읽힌다).

## 🛡️ 가드 — `src/tests/unit/company-read-amplification.test.ts` (11건)

**이 파일은 `node:sqlite` 로 실제 SQLite 를 띄워 `EXPLAIN QUERY PLAN` 을 본다.** 문자열 검사로는
"인덱스를 DDL 에 넣었다"만 알 수 있는데, **컬럼 순서나 `DESC` 하나만 어긋나도 플래너가 그냥 무시하고
결과는 똑같이 나온다.** 그게 이 수리의 유일한 실패 모드라 거기에 가드를 건다.

## ⏳ 남은 것

### 카카오 전화 스윕 3,940만 행/일 — **손대지 않았다**
`ROW_NUMBER() OVER (PARTITION BY source …)` 가 대상 317,137행을 전부 정렬해야 60건을 뽑는다.
부분 인덱스를 붙여 봤지만 **로컬에서 개선 0**(585ms → 598ms) — 창(window)은 어차피 전체를 재료로 쓴다.

진짜 수리는 **소스별로 상위 60건씩 뽑아 JS 에서 rank 로 섞는 것**이다(같은 결과, 480행). 다만
`kakao-sweep-query.ts` 는 주석이 *"WHERE 는 두 수리에서 한 번도 안 건드렸다"* 고 못 박은 자리라
**다음 세션이 별건으로, 로컬 동치 검증과 함께** 하는 게 맞다.

### ⚠️ 같이 지켜볼 것 — **쓰기(rowsWritten)**
인덱스는 공짜가 아니다. 업체 DB 는 하루 **70,061행을 쓰고** 있고(무료 한도 10만), 이 테이블에
인덱스가 6개 → **8개**가 됐다. 삽입·갱신마다 유지할 b-트리가 33% 늘어난다.

그래도 하는 이유: **읽기는 한도의 78배였고 쓰기는 70%다.** 읽기 −85% 와 쓰기 +최대 30% 는
바꿀 만한 거래다. 다만 판정할 때 `rowsWritten` 도 함께 볼 것 — 10만을 넘기 시작하면
그때는 인덱스를 줄이는 게 아니라 **수집 쓰기(upsert 빈도)** 를 봐야 한다.

## ❗ 이번에 틀렸던 판단

1. **"reclassify 는 대상이 0건이라 싸겠지"** — 정반대였다. 0건일 때가 **가장 비싸다**(끝까지 걷는다).
   *"결과가 비었으니 일을 안 했겠지"* 는 이 계에서 통하지 않는다.
2. **부분 인덱스를 붙이면 창 함수도 싸질 것이라 예상** — 로컬에서 **개선 0**. 안 재고 붙였으면
   쓰이지도 않는 인덱스의 쓰기 비용만 남길 뻔했다. **인덱스는 붙이기 전에 재라.**
3. `db.prepare(...)` 로 만든 로컬 재현이 라이브와 같은 플랜을 내는지 **먼저 대조**하고 나서 결론을 냈다
   (BEFORE 플랜이 라이브와 일치 — 이 대조를 건너뛰면 로컬 결과는 아무 근거도 아니다).
