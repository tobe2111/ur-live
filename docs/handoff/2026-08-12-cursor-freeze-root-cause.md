# 키워드 순환 기아의 **진짜 원인** — 커서는 맨 앞 축 하나만 전진한다 (2026-08-12)

어제(#1134) 축 배분을 고쳐 회전율 비가 **7.3 : 1 : 3.2 → 2.5 : 1 : 1.8** 로 내려왔다(설계 1.5 : 1 : 0.5).
그런데 `starved` 경보는 안 꺼졌다. 파 보니 **별개의 원인**이 있었고, 그게 이 문서다.

## 라이브에서 확정한 원인

커서 전진은 `prefixDone`(처리된 **선행** 픽 수)인데 회차가 예산에서 잘린다(계획 16 → 처리 7).
⇒ **뒤쪽 축의 픽은 매번 잘려 `prefixDone = 0` → 그 축 커서가 영원히 제자리 → 다음 회차도 같은
키워드를 내놓고 또 잘린다.** 무한 반복이다.

커서 값이 그대로 증거다 — **앞자리가 바뀌자 움직이는 커서도 그대로 바뀌었다**:

```
#1134 이전 (집중이 맨 앞)   집중 17 전진   ·  우선  5 정지  ·  일반 52 정지
#1134 이후 (우선이 맨 앞)   우선 5→51 전진 ·  집중  1 정지  ·  일반 53 정지
```

그래서 우선 축 위치 50~149(102개)가 **15일간 한 번도 순번을 못 받았다.** 4분 간격 커서 관측으로
정각 회차마다 +3 씩 오르는 것을 확인했고, **11:00 회차에 48 → 51 로 통과**하면서 그 구간이 실제로
열렸다(위치 50·51·53~56 실행). 되감김이 아니라 통과다.

## 수리 두 가지 (짝이다)

| | 무엇 | 역할 |
|---|---|---|
| 🔄 `mergeKeywordPicks(…, lead)` | 맨 앞자리를 회차마다 축끼리 돌린다(`roundIndex % 3`) | **얼어붙지 않게** 하는 보험 |
| 📏 `planRoundWidth(...)` | 최근 처리 수 중앙값 + 여유 20% 로 계획 폭을 맞춘다 | **빨리 돌게** 하는 근본 처방 |

⚠️ **총 처리량은 안 줄어든다** — 예산이 상한이라 처리 수는 그대로고, 줄어드는 건 "뽑아 놓고 버리는 수"뿐이다.
그 대가로 **모든 축의 커서가 전진**한다. 발굴 가속이 아니므로 미측정 백로그도 안 키운다.

⚠️ 회전만으론 부족하다(3회차당 +1 은 일반 풀 76개 한 바퀴에 9일). 폭 맞춤이 있어야 실제로 빨라진다.
⚠️ `planKeywordSplit` 의 몫·불변식 ④(최소 1슬롯)는 **무접촉**이다. 순서와 폭만 바꿨다.

**세 커서가 모두 움직였는지**가 판정이다(지금은 우선만 움직인다). 그리고:

(경보 = 최고령 ÷ 한 바퀴 > 3, 08-12 실측 16.1 ÷ 4.7 = 3.44).

## 이번에 틀렸던 판단 (반복 방지 — 이게 제일 값지다)

원인을 찾는 동안 **가설 넷을 세워 넷 다 데이터로 반증했다**:
1. 저수율 자동 억제 → 정체군 연락처율 24.7% 로 오히려 평균(23.5%)보다 높음. 억제 대상은 107 중 7개뿐
2. 은퇴 축이라 제외 → `RETIRED_CATEGORIES` 는 **비어 있다**
3. 커서가 못 닿는 id 구간 → 같은 id 구간의 다른 키워드는 정상 실행 중
4. 커서 명단이 ~50개로 잘려 되감김 → **11:00 회차에 48→51 통과**. 되감기지 않았다

🧭 **집계만 보고 기전을 추측하면 틀린다.** 답은 커서 값을 **4분 간격으로 실제로 지켜봐서** 나왔다
(정각에만 +3 → 시간당 1회차 → 앞자리 축만 전진). 앞선 세션들이 같은 함정에 반복해 빠졌으니,
다음에도 **"그 레인이 남긴 값을 시간축으로 찍어 보는 것"** 을 먼저 할 것.
