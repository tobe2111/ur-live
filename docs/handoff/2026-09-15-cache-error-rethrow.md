## 이번에 고친 것

### ① 에러를 빈 목록으로 위장하던 훅 11개

`queryFn` 의 `.catch(() => readCache(key, []))` 는 네트워크 실패를 **성공한 빈 목록**으로
바꾼다. 2026-07-02 에 `readCacheOrNull` 로 발견된 함정인데 **7개 훅에만** 적용되고
**11개가 남아** 있었다.

남아 있던 대가가 실물로 있었다 — `WishlistPage.tsx:37` 은 `isError` 로 에러 문구와 재시도
버튼을 만들어 놓고도 **그 분기가 도달 불가**였다(훅이 삼켜서 `isError` 가 영원히 false).
2026-07-02 주석이 *"페이지 에러 UI가 dead branch 화"* 라고 예고한 일이 그대로 일어나 있었다.

### ② 판정을 SSOT 하나로 — `cacheOrRethrow`

손으로 쓰던 7곳은 **`if (cached) return cached`** 였다. 배열엔 맞지만 **숫자엔 틀린다** —
캐시된 `0`(장바구니 0개·안 읽은 알림 0개)이 falsy 라 멀쩡한 값을 버리고 던진다.
판정은 `!== null` 이어야 하고, 그 한 글자를 훅마다 다시 쓰게 두면 언젠가 또 틀린다.
⇒ `localCache.ts` 의 `cacheOrRethrow` 하나로 **19곳 전부** 통일.

### ③ 에러 분기가 없던 화면 셋에 신설

`AddressManagementPage` · `InterestListPage` · `NotificationDropdown`.
문구는 이미 6개 언어에 있는 `common.loadFailed` / `common.retry` 재사용(신규 키 0).

### ④ `useMyCounts` 의 중복 요청 제거

잠금표는 *"useMyVouchers 재사용(별도 fetch 금지)"* 를 요구하는데 **이용권에만** 적용돼
있었다. 위시리스트·쿠폰은 여기서 다시 `api.get` 했고, 실측상 `/user/profile` 진입 때
`/api/wishlists` 가 **30ms 간격 2회** 나갔다. 셋 다 RQ 훅으로 통일(잠금 강화이지 해제 아님).
`null`(모름) ↔ `0`(없음) 구분은 그대로 유지했다.

## 이번에 틀렸던 판단 — 이게 제일 값지다

1. 🩸 **워터폴만 보고 "중복 요청 4종"이라고 볼 뻔했다.** 모든 엔드포인트를 200 으로 채워
   다시 재니 셋이 사라졌다 — **내 가짜 세션이 만든 401 재시도**였다. 진짜 중복은 하나뿐.
   ⇒ 보호 라우트를 잴 때는 **성공 응답까지 채우고** 재라. 안 그러면 내 하네스가 만든
   부작용을 제품 결함으로 보고하게 된다(이 세션에서 두 번째로 걸린 함정).
2. 🩸 **`--only` 는 파일명이 아니라 주입 *이름* 에 부분일치한다.** 파일명으로 부르면
   **0건을 돌고도 "성함" 초록**이 뜬다(검사가 실패할 수 없는 그 클래스). 접두사(`[캐시]` 등)로 부를 것.
3. 🩸 **판정 낱말을 화면 제목과 겹치게 고르지 말 것.** 실패 주입 렌더에서 `/interest-list` 가
   "아직 거짓말한다" 로 나왔는데, 내가 고른 낱말 `관심` 이 **페이지 제목("관심 맛집")** 에 걸린
   것이었다(실제 빈 상태 문구는 `관심 등록한 맛집이 없습니다`). 화면은 정상이었다.
   ⇒ **이 세션에서 세 번째** 로 겪은 "목록 기반 탐지가 엉뚱한 것을 잡는" 실패다. 판정 낱말은
   i18n 의 **실제 문자열**에서 가져올 것.
4. ⚠️ **canonical 패턴을 그대로 복제하지 말 것.** `useMyStays` 의 `if (cached)` 를 11곳에
   그대로 퍼뜨렸으면 숫자 훅 두 개가 조용히 틀렸을 것이다. 베끼기 전에 타입을 보라.

## 덧붙임 — 안 쓸 요청을 첫 화면에서 받아 오던 것 (같은 세션 후속)

대표의 *"더 빨라지거나"* 를 답하려고 워터폴을 재다 찾았다. `PushNotificationSetup` 은
구독(`subscribe`)을 **8초 미뤄** 두었는데 **VAPID 키 조회는 안 미뤘다** — 권한이 `'default'`
(=아직 안 물어본 대다수)인 사람도 진입마다 `/api/push/vapid-public-key` 를 받아 놓고
바로 다음 줄 `if (permission !== 'granted') return` 에서 돌아섰다. **결과를 안 쓰는 요청**이다.

또 "지연 의도가 절반만 적용" 된 경우다(이 세션에서 세 번째 만난 그 모양).

수정은 그 검사를 `resolveVapidKey()` **위로** 옮긴 것 하나다. 키는 granted 경로에서만 쓰이고
`_vapidKeyPromise` 가 메모하므로 순서만 바꾸면 동작이 같다(호출처 2곳 전수 확인).

가드 `push-vapid-defer-2026-09-15.test.tsx` 는 **fetch 가 실제로 나갔는지**를 잰다(소스 문자열
아님). granted 에서 **받아 오는지도** 함께 잰다 — 그게 없으면 fetch 를 통째로 지워도 초록이 된다.

🩸 **내 시험 자체에 결함이 있었다**: `_vapidKeyPromise` 가 모듈 스코프 메모라 시험끼리 상태가
   샜다(한 번 받아 오면 다음 시험에선 fetch 가 안 나간다). `vi.resetModules()` + 동적 import 로
   격리했다. **모듈 스코프 메모가 있는 파일을 시험할 때는 모듈을 매번 새로 불러올 것.**
