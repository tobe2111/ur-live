# 레인 학습기 건강 판정은 `ads_tick_history` 톱니로 — `cron_failures` 임의 창으로 하지 말 것

**2026-08-05 · 문서(교훈)** · 관련 PR: #1076(CPU 학습배수 배선) · #1083/#1085(발굴량 실측 정정)

## 무엇을 틀렸나

대표에게 *"배포 후 CPU 사망 0건 — 안정적"* 이라고 두 번 보고했다. 결론은 맞았지만 **근거가 틀렸다.**
조회를 이렇게 했다:

```sql
SELECT COUNT(*) FROM cron_failures
 WHERE created_at > '2026-08-05 03:04:00' AND error_message LIKE '%CPU%'   -- 03:04 UTC = 12:04 KST
```

그 창은 **실패가 있던 07·09·11시(KST)를 통째로 뺐다.** 0 이 나온 건 시스템이 건강해서가 아니라
**아픈 구간을 안 봐서**다. 우연히 결론이 맞은 이유는 실패들이 전부 CPU 수정 배포(12:00 KST) *이전*
이었기 때문이고, 그건 조회 시점에 내가 알던 사실이 아니었다.

⇒ **오늘 네 번째 좁은 창 오류다**(경보 6건→원장 3배 · 30시간→3주 17배 진폭 · 키워드 소진 오추정 · 이번).

## 올바른 판정법 — 톱니를 복원해 관측값과 맞춰 본다

`platform_settings.ads_tick_history` 는 회차별 요약(`ok`/`fail`/`miss`/`bad`)을 갖고 있다.
`ads_lanes_learned`(cap/clean/pinned)만 보면 "느리다/빠르다"를 오판하지만, **이력으로 톱니를 재구성해
현재 상태와 일치하는지 보면** 학습기가 정상인지 즉시 판정된다.

규칙(SSOT `src/worker-ads/lane-aimd.ts`): 깨끗한 회차 `RECOVER_CLEAN_TICKS=2` 연속 → `+1` ·
해로운 회차 → `×BACKOFF_FACTOR(0.75)`(최소 −1, 바닥 `MIN_LANES_PER_TICK=2`).

2026-08-05 실측 재구성 — **관측값 cap 4 · clean 0 과 정확히 일치**했다:

```
  시작(05:38 KST)         cap 3 clean 1
  06:00 clean             cap 4 clean 0   되찾음
  07:00 fail 4            cap 3 clean 0   물러남
  08:00 clean             cap 3 clean 1
  09:00 빠짐(기록 없음)    cap 2 clean 0   물러남   ← miss 도 해로운 신호다
  10:00 clean             cap 2 clean 1
  11:00 fail 2            cap 2 clean 0   물러남(바닥)
  12:00~15:00 전부 clean   cap 4 clean 0   되찾음 ×2   ← CPU 수정 배포 이후
```

**해석**: 회복이 느려 보인 건 학습기 문제가 아니라 **12:00 이전 실패 3건**이 카운터를 계속 되돌린 것.
배포 이후 4회차 연속 깨끗 → 수정이 실제로 듣고 있다.

## 다음 세션이 쓸 절차

1. `SELECT value FROM platform_settings WHERE key='ads_tick_history'` 로 이력을 뽑고
2. 위 규칙으로 톱니를 굴려 `ads_lanes_learned` 와 맞는지 확인한다(어긋나면 그때가 진짜 결함)
3. 실패 회차는 `bad[]` 로 **어느 레인**인지 바로 나온다 — `cron_failures` 를 창으로 훑지 말 것
4. `miss`(기록 없는 회차)도 해로 센다. **배포가 그 원인이 될 수 있다** — 소스 주석이 명시하고
   이 레포는 머지가 잦다. 다만 08-05 09:00 의 빠짐 근처엔 머지가 없었다(05:33 → 11:46) = 진짜 붕괴
