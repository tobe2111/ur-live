# 학습기가 조일수록 레인이 늘어났다 — `0` 을 두 함수가 정반대로 읽음

> 2026-08-03 세션. 어젯밤부터 이어진 부모 CPU 붕괴의 **근본 원인**이다.
> 앞선 세 PR(#969 학습기 · #983 빈자리 감지 · #998 시트 미러)이 전부 이것 때문에 효과를 못 봤다.

## 1) 다음 세션의 첫 액션

한 회차만 지나면 판정된다. D1 읽기 전용:

```sql
SELECT value FROM platform_settings WHERE key = 'ads_dispatch_last';
```

* **고쳐졌다** = 도메인별 `run` 개수 합이 `per_tick` 근처다(예산 0 을 받은 도메인은 `run` 이
  `always` 개수와 같고 `deferred` 가 채워져 있다).
* **아직이다** = 예산 0 인 도메인이 여전히 3~6개를 띄운다.

이어서 볼 것 — 이게 풀리면 그 다음이 순서대로 살아난다:

```sql
SELECT key, value FROM platform_settings
WHERE key IN ('ads_tick_history','ads_sheets_cursor','ads_sheets_last_sync','ads_lanes_learned');
```

1. `ads_tick_history` 에 **매시간** 항목이 생긴다(그동안 절반이 비어 있었다).
2. `ads_sheets_cursor.off` 가 `total` 밑으로 — #998 수리가 비로소 실행된다.
3. `ads_lanes_learned.cap` 이 2(바닥)에서 올라간다.

## 2) 무엇이 고장나 있었나 (실측)

11:00 KST 회차, 학습 cap **2**인데 실제로 **11개**가 떴다:

| domain | budget | always | run | deferred |
|---|---:|---:|---:|---:|
| influencer | **0** | 0 | **3** | 0 |
| company | **0** | 2 | **6** | 0 |
| prospect | 1 | 0 | 1 | 4 ← 예산이 실제로 통제된 유일한 조 |
| wholesale | 1 | 0 | 1 | 0 |

두 함수가 같은 숫자를 정반대로 읽는다:

* `domainBudgets`(lane-domains.ts)는 예산이 도메인 수보다 적으면 **일부러 0 을 주고 `tick` 으로
  회전**시킨다. docblock 이 명시한다 — *"매 회차 다른 도메인이 자리를 받게 한다"*. **0 = "쉬어라"**.
* `selectLanesForTick`(dispatch-budget.ts)은 `perTick >= 1` 일 때만 값을 믿고,
  **0 을 "미설정"으로 보아 `FREE_LANES_PER_TICK`(6)으로 바꿔치기**했다.

숫자가 정확히 맞는다: company `always 2` → `max(1, 6−2)=4` `+2` = **6** · influencer `cap 6`인데
movable 3 = **3**. 네 조 전부 예측과 일치 — 가설이 아니라 확정이다.

### 왜 이게 폭주하는가

cap 이 **도메인 수(4) 밑으로** 내려가는 순간 0 을 받는 조가 생기고, 그 조들이 오히려 6 으로 풀린다.
**조일수록 늘어나는 제어 반전**이다. 그리고 그 붕괴가 부모 꼬리에 달린
`writeTickSummary` 와 `sheets-sync` 를 지운다 → 이력에 빈자리가 생긴다 →
`missedTicks`(#983)가 그걸 피해로 읽고 **더 조인다** → 더 나빠진다.

즉 #983 의 빈자리 감지는 옳게 동작했지만, 그 신호가 **반전된 액추에이터**로 들어가 가속기가 됐다.
학습기가 `{"cap":2,"clean":0,"pinned":1}` 로 바닥에 붙어 있던 게 그 결과다.

## 3) 수리

`dispatch-budget.ts` 두 줄.

* `perTick >= 1` → **`perTick >= 0`** — 유한한 음이 아닌 값은 그대로 믿는다.
  NaN·undefined·음수만 "미설정"으로 보고 기본값(종전 동작 보존 — 오타로 파이프라인이 멈추면 안 된다).
* `cap = Math.max(1, budget - always)` → **`budget <= 0 ? 0 : …`** — 쉬는 회차엔 하한도 없다.
  하한 1 을 남겨 두면 "쉬어라"가 다시 "1개는 돌려라"가 되고, 도메인 수만큼 곱해져 판단이 또 안 맞는다.

굶주림 걱정은 없다 — 쉬는 조는 `domainBudgets` 의 회전이 다음 회차에 자리를 준다. 그리고 쉬는 회차는
`pickFrom(_, 0, c)` 가 커서를 전진시키지 않아 다음 회차가 **같은 머리부터** 집는다(공평성 불변).

검증: 유닛 4,574 pass(신규 5) · tsc 0 · audit-gate **84 GREEN** · 주입 **119건 전부 빨강**.

## 4) 이번에 틀렸던 판단

1. **"학습기가 cap 을 6→4→2 로 낮췄다 = 작동 확인"** 이라고 보고했다(2026-08-03 새벽).
   판단은 맞게 하고 있었지만 **11개 중 9개에 집행되지 않았다.** 절반만 맞은 보고였다.
   ⇒ 제어 루프를 검증할 땐 **결정값이 아니라 결과값**을 봐야 한다. `ads_lanes_learned.cap` 이 아니라
   `ads_dispatch_last` 의 run 합계가 진짜 지표다.
2. **시트 미러가 "회차 예산에서 한 칸을 태운다"** 고 썼는데 기전이 틀렸다. `sheets-sync` 는 예산 밖
   생 `waitUntil` 이라 **레인 자리를 안 먹고 서브리퀘스트·부모 CPU 를 먹는다.**
3. 처음엔 유튜브 측정 부진을 **레인 선두 다툼**으로 의심했다. 실제로는 자기 일일 상한
   (`ADS_YT_PERF_UNITS`, 기본 2000 · 08-02 에 1,753 소진)에 닿아 있었다 — 별개 원인이다.

## 5) 주입 매니페스트가 낡아 있었다 (부수 발견)

이 수리로 `const cap = …` 줄이 바뀌자 **기존 주입 2건의 앵커가 통째로 죽었다**
(`예산 차감 제거` · `cap 하한 1 제거`). 해네스의 "낡은 지도" 검사가 그 자리에서 잡았다 —
**가드가 나를 잡은 것**이고, 없었으면 그 두 불변식이 조용히 사라진 채 초록이 떴을 것이다.
⇒ 코드를 옮기면 매니페스트 앵커를 같이 옮길 것. 이건 문서 규칙이 아니라 CI 가 강제한다.

## 6) 남은 것 / 대표 판단 대기

* **바깥 `perTick` 도 같은 conflation 이 남아 있다**(`planDomainDispatch` 쪽, 현재 라인 483).
  거기선 `ADS_LANES_PER_TICK=0` 을 "미설정"으로 읽어 6 이 된다 — **정지 스위치가 정반대로 도는**
  형태다. 지금은 학습기 바닥이 2 라 라이브에서 발화하지 않아 손대지 않았다. 0 을 "전체 정지"로
  볼지는 운영 의미를 정하는 문제라 대표 판단.
* **`ADS_YT_PERF_UNITS`(기본 2000) 상향** — 유튜브 리드는 이메일 확보율이 네이버 블로그의 2.9배
  (33.6% vs 11.6%)인데 측정은 35배 적다. 다만 코드의 "units" 가 API 쿼터인지 서브리퀘스트인지
  이름이 모호하다(1,753 units 로 72채널 = 채널당 24, 부자연스럽다). **단위 확정 전에는 올리지 말 것** —
  잘못 올리면 유튜브 쿼터를 태워 수집까지 멈춘다.
* **`naver_cafe`(3,142) · `tistory`(378) 는 측정 경로가 아예 없다.** `influencer-performance.ts` 의
  선택 쿼리가 `platform='youtube'` 와 네이버 블로그 핸들 전용이라 어느 쪽에도 안 걸린다.
  이메일 0건 · 영구 미측정 — **늘릴지가 아니라 수집을 멈출지**를 물어야 하는 쪽이다.
