# 부모 틱이 CPU 천장에 닿았다 — 레인이 하나씩 죽는 진짜 이유 (2026-08-04, 라이브 하트비트 실측)

> `GET /api/admin/cron-heartbeats` 원본. **추정 아님.**
> 어제(`2026-08-03-enrich-throughput-collapse.md`)가 남긴 "첫 액션"을 실행한 결과이고,
> **그 문서의 결론을 갱신한다.**

## 1. 어제의 "처리량 붕괴"는 해소됐다 — 그 문장을 믿고 다시 파지 말 것

| | 08-03 | 08-04 |
|---|---|---|
| 라운드 | 2 | **19** |
| 처리 | 6건 | **119건** |
| 조용한 죽음 | 대부분 | 5 / 19 |
| 적중률 | — | 25/119 = **21%** |

⇒ 어제 문서의 *"그 레인이 죽어 가고 있다"* 는 **더 이상 사실이 아니다.**
사망 지점(`deaths`)도 다섯 곳이 전부 다른 주소라 **특정 사이트 탓이 아니다**(어제 판정 규칙대로면 "부모 CPU").

## 2. 진짜 천장 — **같은 틱에서 여러 레인이 동시에 CPU 로 죽는다**

```
05:00 UTC (KST 14:00) — 한 틱에서 셋이 동시에:
  ads:sweep-kakao-chain     Worker exceeded CPU time limit
  ads:collect-company       Worker exceeded CPU time limit
  ads:sheets-sync           Worker exceeded CPU time limit
01:00 UTC (KST 10:00) — 둘이 동시에:
  ads:collect-hira          Worker exceeded CPU time limit
  ads:reclassify-company    Worker exceeded CPU time limit
```

**세 레인이 각자 고장 난 게 아니다.** 같은 시각·같은 예외다 —
**틱 전체가 CPU 를 넘겨서 뒤에 오는 레인이 죽는 것**이고, 어느 레인이 죽느냐는 순서 문제다.
⇒ 레인 하나를 고쳐도 **다음 레인이 대신 죽는다.** 여기를 안 보면 두더지잡기가 된다.

`cpu_risk` 표시도 같은 방향이다: `collect-storeinfo 27.2s` · `collect-neis 69.8s` ·
`maintenance-rescan 80.3s` · `schema-repair-daily 163.4s`(danger).

### 🔎 눈여겨볼 것 — 죽은 셋 중 하나가 **예산 우회 레인**이다
`check-ads-dispatch-bypass` 의 남은 우회 1건이 `./sheets-mirror-lane` 인데,
죽은 목록에 **`ads:sheets-sync` 가 들어 있다.** 우회 레인은 `kick()`(자식 인보케이션)이 아니라
**부모가 직접 CPU 를 태운다.** 인과가 어느 쪽인지는 아직 안 밝혔지만 **첫 번째로 볼 자리**다.

## 3. 보강 체인이 depth 3 에서 끊기는 이유

```
ads:enrich-company  ms=9764  result="planned=8 depth=3 chained=true"
```

- 라운드 하나가 **9.76초** — 무료 인보케이션이 회수되는 **≈10.5초** 바로 앞이다
  (그 10.5초는 `ENRICH_DEADLINE_MS_DEFAULT = 7_000` 의 근거로 코드에 적혀 있는 실측값).
- `chained=true` 인데 depth 4 의 하트비트가 **없다** → 자식이 태어나긴 했는데 기록 전에 사라졌다.
- ⇒ 계획 8라운드 중 **3~4라운드**만 산다. 관측된 시간당 1.4회차와 일치한다.

### ⚠️ 여기서 하지 말아야 할 것
- **`ADS_ENRICH_DEADLINE_MS` 를 올리는 것.** 7초는 10.5초 벽에서 역산한 값이다. 올리면
  라운드가 벽에 부딪혀 **조용한 죽음으로 되돌아간다**(어제 겪은 그 상태).
- **`budget_total` 을 올리는 것.** 회차당 60 중 **32만 쓴다.** 예산은 병목이 아니다(어제와 동일).

### 다음 세션이 시험해 볼 가설 (측정 먼저)
**라운드를 더 짧게 만들면 총 처리량이 오른다** — 한 라운드가 4~5초면 같은 부모 수명 안에
체인이 더 깊이 가고, **각 라운드는 새 서브리퀘스트 예산을 받는다.**
9.76초 × 3라운드 = 29초 vs 5초 × 6라운드 = 30초인데 **후자가 예산을 2배 받는다.**
⚠️ 다만 이건 **가설이다.** 짧게 잡으면 사이트당 크롤이 중도에 끊겨 적중률(21%)이 떨어질 수 있다 —
`ADS_ENRICH_DEADLINE_MS` 를 4000 으로 하루 돌려 **처리량 × 적중률**을 같이 재고 판단할 것.

## 4. 이번에 내가 틀렸던 판단 (반복 방지)

- 대표께 *"차단 호스트가 예산을 먹고 있다"* 고 먼저 보고했다. **틀렸다** — `blocked_host` 는
  2026-07-28 에 이미 처리됐고(site=null 로 만들어 발견 경로로 넘김), 애초에 **예산이 병목이 아니다.**
  스냅샷 한 장(`crawl_reason`)만 보고 원인을 단정한 것이 실수다. **누적(`rollup`)과 하트비트를
  같이 봤어야 했다** — 그러니 숫자가 정반대(붕괴가 아니라 20배 회복)로 나왔다.
- 공정위 가맹정보 후임 주소를 **이름 규칙으로 9번 추측**했다가 전부 code 12 였다.
  나라장터에서 한 번 맞은 것이 요행이었다. **포털 페이지가 유일한 출처**이고 이 환경은 403 이라
  대표께 End Point 를 받는 것이 정답이다(전통시장 때 그렇게 1분에 끝났다).

## 6. 같은 날 **더 판 두 가지 — 둘 다 헛다리였다**(재파지 말 것)

### ⛔ 지역(region) 백필 — 신뢰할 수 있는 신호는 **4%** 뿐

제안 가능 리드(이메일 보유·거부 제외) **7,611명 중 5,789명(76%)에 region 이 없다.**
③ 필터링 축의 최대 결측이라 "본문에서 지역어를 뽑아 채우자"가 자연스러워 보인다. 실측:

| 신호 | 건수 | 신뢰도 |
|---|---|---|
| 채널명 | 133 | 강함 — 자기 텃밭을 이름에 넣는다("부산맛집투어") |
| 수집 키워드 | 148 | 강함 — 지역 키워드로 발굴됐다는 뜻 |
| **강한 신호 합집합** | **253** | ← 실제 상한 |
| 설명(description) | 2,059 | **약함** — 대부분 *여행 다녀온 얘기*다 |

전체로 세면 2,091건이라 커 보이지만 **97%가 설명 기반**이고, 캠핑·여행 채널이 대다수라
"제주도 다녀왔어요"를 근거로 region=제주를 박으면 **틀린 지역이 붙는다.**
필터링에서 **틀린 지역은 빈 지역보다 나쁘다**(부산 캠페인이 서울 창작자에게 간다).
⇒ 5,789 중 253(4%)을 위해 오염 위험을 지는 거래다. **하지 않는다.**

### ⛔ `sheets-mirror-lane` 이 부모 CPU 를 태운다? — **아니다**

§2 에서 *"죽은 셋 중 하나가 예산 우회 레인과 겹친다 — 첫 번째로 볼 자리"* 라고 적었는데,
코드를 읽어 보니 **이 레인은 이미 무거운 일을 자식으로 넘긴다**:

```
부모가 하는 것: D1 읽기 1 + SELF.fetch 1 + JSON 파싱 + (오류 바뀌면) Discord 1 + 하트비트
실제 동기화:   /__ads/sheets-sync?by=cron — 별도 인보케이션
```

소스 주석도 그렇게 말한다(*"동기화 자체는 SELF 인보케이션에서 … 경보 판단만 여기서 —
1 fetch + D1 1읽기라 가벼움"*). 하트비트에 `sheets-sync ok=false CPU limit` 이 찍힌 것은
**이 레인이 원인이라서가 아니라, 부모가 죽을 때 마침 이 레인이 진행 중이었다는 뜻**이다.
⇒ `kick()` 으로 옮겨도 CPU 는 거의 안 준다. §2 의 그 문장은 **취소한다.**

### 그래서 다음 세션이 볼 자리 (수정판)
추측을 두 번 죽였으니 **다음은 계측부터** 한다. `cpu_risk` 가 danger 인 것부터:
`schema-repair-daily 163s` · `maintenance-rescan 80s` · `collect-neis 70s` · `collect-storeinfo 27s`.
단 이 `ms` 는 **벽시계지 CPU 가 아니다** — 외부 fetch 대기는 CPU 를 안 쓴다.
⇒ 벽시계가 긴 레인과 CPU 를 태우는 레인을 **구분할 계측이 아직 없다.** 그것부터 만들어야
"누가 틱을 넘기는가"가 추측이 아니게 된다.
