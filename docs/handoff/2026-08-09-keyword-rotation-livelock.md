## 2. 발견한 결함 — 은퇴↔승격 livelock (수리 완료)

**메커니즘**(호출부 3개를 다 열고 확인): 은퇴 3문(F-30·barren·수율)은 `active=0` 만 쓰고 **`hits` 는
재채굴마다 계속 쌓인다**(upsert 는 active 무관). 승격 후보 쿼리(`influencer-keyword-promote.ts`)는
`active=0 AND hits>=5` 뿐이라 은퇴자가 그 회차 topTags 에 다시 채굴되면 `hits DESC` 로 신선 큐를 제치고
**재승격**된다. 그런데 세 은퇴 조건은 전부 **평생 카운터**(found/saved/streak 리셋 없음)라, 재승격자는
다음 회차 시작의 은퇴 batch 가 **한 번도 안 돌리고 다시 은퇴**시킨다 — 승격 슬롯만 태우는 순환.

- **실측**: 좀비 5개(재테크 hits 260 · 동작카페 124 · 감성카페 103 · 재테크블로그 56 · 중랑네일 49),
  그중 4개가 카테고리 게이트 통과(맛집/네일) = 재승격 가능. 수율 은퇴가 도는 한 이 집합은 **단조 증가**.
- **왜 지금까지 안 터졌나**: #1106 전엔 room 0 고착이라 승격 자체가 없었다 — **cap 개방이 무장시킨 결함**.
- **수리**: `AUTO_RETIRE_WHERE`(은퇴 3문 WHERE 조각)를 rotation SSOT 로 추출, 은퇴문과 승격 차단
  (`PROMOTE_NOT_RETIRABLE_SQL` = 3조각의 NOT)이 **같은 문자열**을 쓴다. 승격 후보 쿼리에 차단 배선.
- ⚠️ **COALESCE 필수**: 미실행 후보는 found/saved/barren 이 NULL — bare 비교면 `NOT(NULL OR …)`=NULL 로
  **신선 후보 전체가 승격에서 조용히 빠진다**(가드가 정반대로 뒤집히는 함정). 테스트가 COALESCE 를 강제.
- **막지 않는 것(의도)**: 07-29 결정(`healBarrenStreakOnce`)의 복귀 경로 — 오염 barren 으로 잘못 은퇴됐다
  힐링된 고수율 키워드(맛집 saved 414 · 피부관리 363 …)는 세 조건 어디에도 안 걸려 재승격된다.
  실제로 #1106 직후 그 경로로 ~15개 복귀했고 전원 온타깃이었다(관측 표본 확인).

## 3. 문서 오류 정정 — barren_streak 의 의미

`yieldPenalty` docblock 과 #1106 주석이 *"barren 은 found==0 회차만 센다"* 고 적었는데 **코드와 다르다**
— 카운터는 `CASE WHEN v.saved > 0`(저장 0 회차 연속)이다. 진짜 사각지대는 "많이 찾는 키워드" 일반이
아니라 **가끔 1명씩 떨궈 streak 을 리셋하는 저수율(drip)** 키워드다(좀비 5 중 4가 정확히 이 부류,
saved 2~9). 두 docblock + 변이 매니페스트 why 를 정정 — 틀린 문서가 다음 세션을 잘못 이끄는 게
이 레포의 반복 사고 클래스라 코드보다 급했다.

## §15. YT 쿼터 소진 회차의 유휴 예산 회수 (2026-08-12 대표 승인 "응 해")

§14 를 보고하며 남긴 관측을 대표가 승인해 같은 세션에서 구현했다.

### 무엇이 유휴였나 (라이브 06:00 회차)

diag.yt.error "QUOTA: 오늘 YT 검색 예산(90회) 소진"   yt_calls 전부 0

YT 검색 쿼터(일 90회)는 하루의 이른 시간에 소진된다. 그 뒤의 회차는 **네이버 전용**이라 키워드당

### 수리 — 조건부다(상수를 그냥 올린 것이 아니다)
- `isNaverOnlyRound()` 로 이 회차가 YT 검색을 못 하는 회차인지 판정(순수함수)
- 그런 회차만 `naverOnlyRoundCap()`(18 — 실제 상한은 여전히 **예산**과 **계획 폭**)
- **YT 살아있는 회차는 9 그대로** — 실측 56/56 이라 넓혀도 안 늘고 YT 쿼터만 빨리 태운다
- 계획 폭도 **형상별 이력**으로(`planRoundWidthForShape`) — 두 형상(처리 ~9 / ~17)을 한 중앙값에
  섞으면 둘 다 틀린다(YT 회차 과대 → #1142 커서 기아 재발 · 네이버 회차 과소 → 확장 무효)

### 🧨 §15 후속 — 이번 세션 두 번째 실수: `kill -9` 가 주입을 복원하지 못한다

`audit-gate` 의 주입 검증(`check-guard-mutations.mjs -s`)이 도는 중에 커밋해야 할 상황이 되어
러너를 종료했다. SIGTERM 이 안 먹는 것처럼 보여(실은 `pgrep -f` 가 **내 셸 명령줄까지 매칭**해
판정을 흐렸다) **`kill -9`** 를 썼고, 그 순간 injected 상태였던 변이가 **복원되지 않았다**:

```
find    '(focusCursor + focusDone)'   →   replace   '(focusCursor + nFocus)'
```
그대로 커밋·푸시했고 CI 가 `ads-keyword-focus-split.test.ts:281` 에서 잡았다(main #1142 가 심어 둔
바로 그 가드가 제 역할을 했다 — 커서 leapfrog 회귀 방지).

⚠️ **왜 내 검증이 놓쳤나**: 커밋 전에 "주입 표적 문자열이 원본대로인가"를 확인했는데 **내가 이번에
추가한 5개만** 봤다. 잔재는 *다른 사람의* 변이였다.

⇒ 규칙 두 개:
1. **주입 러너는 `SIGKILL` 로 죽이지 않는다.** 복원은 `process.on('SIGINT'/'SIGTERM'/'exit')` 훅에
   달려 있어 SIGKILL 은 그것을 건너뛴다. 안 죽으면 **기다린다**(그게 유일하게 안전한 선택).
2. **커밋 전 검증은 `git diff origin/main` 전문 검토**다 — 내 앵커 몇 개 확인이 아니다.
   주입 잔재는 정의상 "내가 안 건드린 파일"에 남는다.
3. `pgrep -f <패턴>` 은 **자기 자신의 셸을 매칭**한다(명령줄에 그 패턴이 들어 있으므로).
   프로세스 판정은 `/proc/<pid>/cmdline` 을 직접 읽어 `node` 프로세스만 골라야 정확하다.

- 서브리퀘스트 추가 **0** — 읽기는 기존 `SETTING_KEYS` 배치, 쓰기는 기존 마감 배치에 1줄.

### ⚠️ 정직하게 — "절대 안 줄어든다"는 보장 못 한다
조율기는 *사람이 개입하지 않아도 마르지 않게* 하는 장치다. 넘을 수 없는 것:
- 후보 풀(`hits>=5` 대기)이 마르면 캡을 올려도 채울 게 없다 → 그때는 **해시태그 유입**이 병목
- 무료 티어 하드 상한: 회차당 서브리퀘스트 56 · YT 검색 쿼터 90/일(이미 초과 상태)
- 캡 상한 300(그 이상은 한 바퀴가 3.5일+ 로 늘어 신선도 효과가 상쇄) → `at-ceiling` 이 뜨면 사람 판단
⇒ 이 세 경우 조율기는 **`reason` 으로 사실을 남긴다**(추측 대신 관측). 어드민 문구가 그대로 안내한다.

### 🎯 다음 세션의 첫 액션 — 판정(배포 +24h, 그리고 +3일)
```sql
-- ① 조율기가 실제로 넓혔나 (0 으로 굳으면 배선 사망)
SELECT value FROM platform_settings WHERE key='ads_auto_keyword_cap';   -- 120 에서 올라가야 한다
SELECT json_extract(value,'$.freshness') FROM platform_settings WHERE key='ads_autocollect_stats';
-- ② 신선도가 실제로 들어왔나
SELECT MAX(activated_at), COUNT(*) FROM ad_discovery_keywords WHERE active=1 AND source='auto';
-- ③ 그래서 발굴량이 돌아왔나 (일별로 볼 것 — 회차 하나로 판정 금지)
SELECT DATE(collected_at,'+9 hours') d, COUNT(*) n FROM ad_influencer_leads
 WHERE collected_at >= datetime('now','-7 days') GROUP BY d ORDER BY d;
-- 🚨 그리고 차단 — 확장이 차단을 불렀으면 즉시 되돌린다
SELECT value FROM platform_settings WHERE key='ads_naver_crawl_block';
```
기대: 캡 120 → 140~180 · auto 활성화 재개 · 일 발굴 3,400 → 5,000대 회복.
⚠️ **하루로 판정하지 말 것** — 승격 물결은 다음날 수확으로 나타난다(08-10 활성화 → 08-12 정점).
⚠️ 차단이 뜨면 조율기가 스스로 동결한다. 그래도 `blocked>0` 이 며칠 이어지면 캡을 손으로 되돌릴 것.

## §18. 체험단 축 신설 (2026-08-17 대표 "체험단 키워드로도 인플루언서 db 수집 필요해")

### 실측으로 드러난 것 — 이미 잘 잡히는데 **게이트가 막고 있었다**
```
활성(seed)  체험단 모집  found 1,041 → 저장 290 · 이메일 62 (21.5%)
            공구 협찬    found   547 → 저장 183 · 이메일 60 (33.1%)  ← 전체 최고 수준
            체험단 대행  found   925 → 저장 171 · 이메일 20 (11.8%)
대기(차단)  체험단(hits 78) · 체험단모집(71) · 블로그체험단(40) · 협찬플러스(21) · 제품협찬(12)
            맛집체험단(6) · 리뷰어스(6) · 협찬(6) · 강남맛집체험단(5) · 인스타체험단(3) …
```
차단 이유: 분류 룰에 체험단이 없어 `category='자동'` → `canAutoPromote('자동')=false` → **승격 게이트에서
영구 차단**. `hits` 가 78이든 780이든 안 들어간다. **키워드 정원(§17 조율기)을 늘려도 소용없다 —
게이트가 정원보다 먼저 막는다.** 이게 대표 요청의 실체였다.

### 수리
- **분류 룰 신설** `{ cat: '체험단', re: /체험단(?!\s*(모집|대행|운영))|서포터즈|협찬|리뷰어/i }`
  — 대행사 룰 **뒤**(모집·대행·운영은 *운영하는 쪽*이라 대행사가 옳다), 음식 계열 **앞**(맛집체험단은
  주제보다 "참여한다"는 **행위 신호**가 값지다).
- **승격 허용목록**(`AUTO_PROMOTE_CATEGORIES`)에 '체험단' — 분류와 게이트는 **다른 층**이다(한쪽만 고치면 승격 0).
- **참여자 시드 19개** 신설(`체험단 후기`·`협찬 후기`·`블로그 체험단`…) — 해시태그 승격을 기다리지 않고
  즉시 수집. 시드는 체크섬 기반 재시드라 별도 버전 bump 불필요.
- **우선 축 편입**(`PRIORITY_CATEGORIES`) — 근거는 위 수율(21.5~33.1% vs 우선 평균 24.4%).
  대가: 우선 풀 ~358 → ~370(그 축 안에서 3% 희석 · 축 간 영향 0). 되돌리기 = 배열에서 한 항목.
- **어드민 필터**(`POOL_CATEGORIES`)에 추가 — 가드(`ads-category-ui-sync`)가 잡아 줬다. 안 넣으면
  수집은 되는데 **화면에서 그 축을 골라 볼 수 없다**.
- 맨 `무료 체험` 은 **넣지 않았다** — `체험단` 이 `무료 체험단` 을 이미 잡고, 나머지는 학원·헬스 오탐이다.
  **라이브 후보 목록에 없는 패턴은 넣지 않는다**(추측으로 넓히면 축이 오염된다).

### 🧭 이번에 두 번 틀린 판단 (기록 — 되돌려-검증이 둘 다 잡았다)
1. *"룰 순서를 뒤집으면 대행사 축이 통째로 흘러간다"* → **틀렸다.** 룰을 맨 앞으로 옮겨도
   `체험단 모집` 은 대행사로 갔다 — negative lookahead 가 막는다.
2. 그래서 *"축을 지키는 건 순서가 아니라 lookahead 다"* 로 정정 → **이것도 부정확했다.**
   lookahead 만 지워도 동작은 그대로다(순서가 막는다). 실체는 **중복 방어**이고, 그래서
   **어느 한쪽만 없애는 주입은 빨강이 안 된다**(주입 검증이 실제로 통과해 버렸다).
   ⇒ 두 방어의 **존재를 각각 명시로 고정**하는 테스트를 추가해 해결. 중복 방어를 발견하면
      "테스트가 통과하니 안전"이 아니라 **각 겹을 따로 고정**해야 한다 — 아니면 하나씩 지워 나가는
      경로가 열려 있고, 두 번째를 지우는 순간 조용히 사고가 난다.

### 🛡️ 가드
테스트 8건 신설(핵심: *"라이브에서 막혀 있던 후보 15개가 전부 게이트를 통과한다"*) +
mutation 3건(분류 룰 소실 · 허용목록 누락 · lookahead 소실) — 전부 되돌려-검증 빨강 확인.

### 🎯 판정 (배포 +24h)
```sql
-- ① 체험단 축이 실제로 활성화됐나(시드 19개 + 승격)
SELECT category, COUNT(*) n, SUM(active) act FROM ad_discovery_keywords
 WHERE category='체험단' GROUP BY category;
-- ② 막혀 있던 후보가 승격됐나
SELECT keyword, active, hits, activated_at FROM ad_discovery_keywords
 WHERE keyword IN ('체험단','블로그체험단','제품협찬','협찬플러스') ORDER BY hits DESC;
-- ③ 그 축이 실제로 사람을 물어오나 + 이메일 수율
SELECT k.category, COUNT(*) leads, SUM(CASE WHEN l.email IS NOT NULL AND l.email<>'' THEN 1 ELSE 0 END) em
  FROM ad_influencer_leads l JOIN ad_discovery_keywords k ON k.keyword=l.source_keyword
 WHERE l.collected_at >= datetime('now','-1 day') GROUP BY k.category ORDER BY leads DESC;
```
기대: 체험단 키워드 22개+ 활성 · 대기 후보 승격 · 이메일 수율 20%+ 유지.
⚠️ 수율이 우선 축 평균(24.4%)을 **크게 밑돌면** `PRIORITY_CATEGORIES` 에서 빼고 일반 축으로 내릴 것
   (한 항목 제거 = 롤백 전부). 그때도 수집 자체는 계속된다.
