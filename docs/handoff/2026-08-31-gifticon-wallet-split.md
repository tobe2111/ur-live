# 2026-08-31 — 교환권은 교환권 페이지에서, 이용권은 이용권 페이지에서 (지갑 분리)

대표 지시: *"지금은 유어딜 교환권을 사면 이용권 페이지에서 확인되는데 교환권 페이지에서 볼 수 있게끔
해야할 것 같아. 이용권은 이용권 페이지에서. UX/UI 는 AI 가 만든 티가 안 나야 해."*

## 무엇이 어긋나 있었나

**산 곳과 보관되는 곳이 달랐다.** 교환권(기프티콘)은 `/vouchers` 에서 사는데, 확인은 하단 탭 **'이용권'**
(`/my-vouchers`) 안의 세그먼트 탭으로 들어가야 했다. 그 탭은 **교환권을 가진 사람에게만 나타나서**
"내가 산 게 어디 갔지" 를 겪고 나서야 발견하는 구조였다.

한 배열(`GET /api/vouchers/my`)에 두 축이 섞여 오는 것이 근본 원인이다 —
① 내부 이용권(`vouchers` 테이블, 매장 QR/PIN) ② KT-Alpha 교환권(`voucher_orders`, 문자 발송).

## 한 일

| | 이용권 | 교환권 |
|---|---|---|
| 산다 | `/`(동네딜) · `/group-buy/:id` | `/vouchers` · `/vouchers/:id` |
| **본다** | **`/my-vouchers`(내 이용권)** | **`/my-gifticons`(내 교환권 — 신설)** |
| 쓴다 | 매장 QR/PIN(지도·D-N·QR 모달) | 문자 쿠폰 / 인앱 바코드 |

- **판정 SSOT 1곳** `src/shared/voucher-wallet.ts` — `isGifticonVoucher` / `isStoreVoucher`.
  기준은 `source='kt_alpha'` **또는** `deal_only=1`(결제흐름 SSOT `product-flow.ts` 와 같은 기준).
  ⚠️ **카테고리로 나누지 말 것** — `meal_voucher` 는 이용권이다(`check-payment-flow-ssot.mjs`).
- **`/vouchers` 헤더 우측 '보관함'**(모바일) + **PC 좌레일 '내 교환권' 행** — 산 자리에서 바로 간다.
  카카오 선물하기의 '선물함' 자리와 같은 위치라 학습이 필요 없다.
- **이용권 지갑엔 한 줄 다리** — 교환권을 갖고 있을 때만 "내 교환권 N장 ›" 행. 분리의 유일한 부작용
  ("내 교환권 어디 갔지")이 나는 자리에 정확히 놓았다. 없으면 아예 렌더하지 않는다.
- **도착지 정리** — 딜 교환 성공 3경로(`VoucherDetailPage`·`GroupBuyDetailPage`·`ProductDetailPage`) ·
  `FLOW_CONFIG.voucher_deal.successPath` · KT 발송/실패 알림 · `voucher_issued` 인앱 알림(deal_only 분기)
  전부 `/my-gifticons`.
- **마이페이지 2행** — '내 이용권'/'내 교환권' 각각 자기 개수(같은 RQ 캐시를 나눠 셈).
- 서버 `/api/vouchers/my` 는 `p.deal_only` **한 컬럼만 추가**(폴백 SELECT 는 무변경 — 없으면 `source` 로 판정).

## 되돌려-검증 (가드가 실제로 실패하는가)

`src/tests/unit/voucher-wallet-split.test.ts` 14건 + `check-guard-mutations` 매니페스트 **3건 등록**,
셋 다 주입 → **빨간불 확인**:
`이용권 지갑이 교환권을 다시 섞어 보여준다` · `교환권 보관함이 이용권을 담는다(판정 반전)` ·
`교환권을 사고 나면 옛 이용권 지갑으로 떨어진다`.

## 이번에 틀렸던/확인한 판단

- 처음엔 "교환권 = `source='kt_alpha'`" 하나로 나누려 했다. **라이브 실측**(D1): `deal_only=1` 상품
  2,260개가 **전부** KT 교환권이고 그 반대도 참 — 오늘은 일치한다. 그래도 판정에 `deal_only` 를 함께
  넣었다. 결제흐름 SSOT 가 교환권을 그 컬럼으로 정의하므로, 언젠가 KT 아닌 딜 상품이 생겨도
  "딜로 샀는데 이용권 지갑에 있다" 가 구조적으로 안 난다.
- `TypeScript weak-type` 함정: 전부 선택 프로퍼티인 인터페이스는 `MyVoucher`(인덱스 시그니처만 가진
  느슨한 타입)를 **거부**한다("no properties in common"). 입력 타입을 union 으로 받아 해결.

## 시안 대신 실제 화면을 찍었다 (그리고 결함을 하나 잡았다)

대표가 *"시안을 봤어야 할 것 같아"* 라고 해서, 그림 대신 **구현된 화면을 Playwright 로 캡처**했다
(dev 서버 + `localStorage.user_id` 시드로 `ProtectedRoute` 통과 + `**/api/**` 픽스처 라우팅 —
로그인 전용 페이지를 이 환경에서 보는 방법이다. 스크립트는 스크래치패드, 재현법은 이 문단이 전부다).

그 캡처에서 **다크 모드 결함**이 드러났다 — 그림으로는 절대 못 봤을 것이다:
`WalletPageWrapper` 가 배경/글자색을 **인라인 스타일**(`background: #FFFFFF`)로 칠하는데 내용은 전부
`dark:` variant 라, 다크 모드에서 **흰 배경 + 흰 글자**가 됐다. 실측: `h1 rgb(255,255,255)` on
`페이지 배경 rgb(255,255,255)` → 제목("내 이용권"/"내 교환권")과 "사용 완료" 라벨이 통째로 안 보였다.
**인라인이라 `check-theme-consistency`(클래스 기반)의 사각지대**였고, 이 지갑을 쓰는 세 페이지
(`/my-vouchers`·`/my-gifticons`·`/wishlist`) 전부 같은 상태였다 — 즉 **라이브의 이용권 지갑도 오늘까지 그랬다.**

수정: 라이트 지갑은 색을 클래스로 칠해 다크 토글을 따라간다(`bg-white dark:bg-[#0D0F12]` +
`text-gray-900 dark:text-white`). 라이트 렌더는 동일, 다크 호출자 경로는 불변. 캡처로 3페이지 × 2모드 재확인.
가드: 테스트 2건 + guard-mutations 매니페스트 1건(주입 → 빨간불 확인).

⚠️ **교훈**: 인라인 스타일로 칠한 배경은 테마 가드가 못 본다. 지갑처럼 "라이트 고정" 이라고 적힌
표면도 다크 토글 사용자에겐 반쪽만 적용된다 — 새 표면을 만들 때 배경색은 클래스로 칠할 것.

## 다음 세션의 첫 액션 — 배포 후 실측

이 환경에선 **로그인 상태의 화면을 못 본다**(두 페이지 모두 `ProtectedRoute`). 그래서 배포 후 판정:

1. 교환권을 딜로 1건 사고 → **`/my-gifticons` 로 떨어지는지** + 그 카드가 거기 있는지.
2. `/my-vouchers` 에 그 교환권이 **없는지**(섞임 0) + 교환권 보유 시 "내 교환권 N장" 다리가 뜨는지.
3. 결제 직후 '발송 중' 카드가 보였다가 문자 도착 후 '사용 가능' 으로 바뀌는지(교환권만 있는 상태).
4. 마이페이지 두 행의 개수가 각 페이지 실제 개수와 같은지.
