## ② 이용권 매출 단일 레일 (결재 기본안 1번 — **PR 대기, 머지 전 staging 필수**)

### 무엇이 문제였나

같은 이용권 한 장에 매장 적립이 **두 번**(구매 `seller:N` · 사용 `merchant:N`).
`payouts-generate` 는 계정 **문자열**로 GROUP BY 하므로 둘이 상쇄되지 않는다 —
**1,000원 판매가 1,850원**으로 집계된다(실측).

### 고친 것

신규 SSOT **`voucherPurchaseCredit()`**(`ledger.ts`)이 구매 적립의 자리를 한 곳에서 정한다.

| 자리 | 바뀐 것 |
|---|---|
| 구매 3곳 | 매장 있으면 `platform:escrow` + `fee_amount 0` · 없으면 **종전 그대로** |
| 사용 시점 | `merchant:N` → `sellerLedgerAccount(merchant_id)` = `seller:N` |
| owner-promo 3곳 | 같은 이름으로 통일(적립과 차감이 상쇄돼야 한다) |
| 셀러 매출 조회 | `credit_account IN (merchant:N, seller:N)` — 통일 전후로 매출이 0 이 되지 않게 |
| `sellerLedgerAccount` | `number` → `number \| string` (동작 불변) |

🔑 **`seller:null` 유령 계정의 진짜 원인을 찾았다**: 그 함수 시그니처가 `number` 만 받아서,
id 가 `number | string` 인 호출부들이 **SSOT 를 쓸 수 없어 손으로 템플릿을 조립**하고 있었다.
받는 폭만 넓히니 그 자리들이 전부 SSOT 로 들어왔다. (라이브의 `seller:null` 1행은 가드가 생기기
전인 8월 행이라 지금 코드엔 생산자가 없다.)

### 🍀 지금이 가장 안전한 시점

라이브 원장 전체가 **3행**, `merchant:%` **0건**, payouts **0건**, 사용된 이용권 **0장**,
계좌 등록 매장 **0곳** ⇒ 마이그레이션 없음, 잘못 나간 돈 **0원**.

### ⚠️ 안 고친 것 (의도)

`recordRefundLedger` 는 `platform:revenue → platform:escrow` 라 새 모델에선 방향이 안 맞는다.
**payout 대상 계정이 아니라서 나가는 돈엔 영향이 없고**(아무도 escrow 잔액을 읽지 않는다 — 실측),
환불 분개를 바꾸는 건 별도 판단이 필요하다. 시험 머리말에 "못 막는 것"으로 명시.
