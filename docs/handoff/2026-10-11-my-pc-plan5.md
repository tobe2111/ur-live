## 2) 🔴 '옹졸함'의 실체는 디자인이 아니라 **CSS 한 줄**이었다

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 1440px 화면에서 본문 폭 | **644px** | **1136px** |
| 양옆 빈 칸 | 약 800px | 304px(정상 여백) |

`.ur-account-pc` 가 `max-width: 1200px; margin: 0 auto` 를 갖고 있었는데 **`width: 100%` 가 없었다.**
부모(`UserProfilePage` 루트)가 `flex flex-col` → 가로가 **교차축** → 교차축의 `auto` 마진이
`align-self: stretch` 를 **끈다**(Flexbox §8.1) → 박스가 내용 폭으로 줄고 `max-width` 는 영영 안 걸린다.
**즉 1200px 는 한 번도 쓰인 적이 없다.**

🩸 **이 레포는 같은 함정을 이미 밟고 고쳤다** — `.ur-content-*` 의 2026-05-03 주석이 토씨까지 같은
설명을 달고 `width: 100%` 를 명시한다. 이 블록만 그 짝을 빠뜨렸고, 에러가 없어 몇 달을 갔다.
⚠️ `align-self: stretch` 로는 **안 고쳐진다**(auto 마진이 이긴다). 주입이 그 오답을 고정한다.

## 3) 안 5 로 바뀐 것 (PC 전용 — 폰은 한 글자도 안 바뀐다)

- **머리 한 줄 띠**(신규 `AccountPcBand.tsx`) — [아바타·이름·프로필 편집] … [숫자 셋/넷] [알림].
  종전엔 프로필이 좁은 오른쪽 칸의 **흰 판 카드**였고 숫자는 따로 한 줄이라 머리 정보가 흩어져 있었다.
  🔢 숫자는 **`MyStats` 그 부품**(`inline` 모드)이다 — 두 호출부가 같은 세 prop 을 넘기는지 시험이 대조한다.
- **판은 파는 쪽에만** — 손님 칸의 판 둘(프로필 카드 · `shadow-lift` 타일 셋)을 걷었다.
- **PC 도 폰과 같은 손님 목록** — 종전 PC 타일은 셋(숙소·단골·찜)뿐이라
  **쿠폰함·주문 내역·배송지·내 리뷰는 PC 에서 갈 길이 아예 없었다.** 같은 `ShoppingGroup` 을 쓰니
  고아도 갈림도 구조적으로 불가능하다.
- **설정은 왼쪽 아래로** — 정의는 한 벌(`settingsBlock`), 자리만 `pcSplit` 로 바꿔 건다.
  ⚠️ `pcSplit = isPc && stores.length > 0` — `isPc` 만이면 좌석 0곳에서 설정이 **본문보다 먼저** 그려진다.
- **두 열 7:5**(1136 − gap 24 → 왼 649 / 오 463. 오른쪽이 폰 폭 430 보다 넓어야 한다).
- **비셀러는 820px** — 폭을 되찾자 평면 줄이 1136px 가 되어 `내 이용권` 과 `0 ›` 사이가 1,000px
  벌어졌다(렌더로 확인). 빵부스러기도 **칸 안으로** 옮겨 왼쪽 끝을 맞췄다.

## 4) 이번에 **틀렸던 판단 / 값을 치른 것**

1. 🩸 **주입 러너를 강제 종료해 트리에 잔재가 남았다.** `--changed` 가 full 로 떨어져(러너 자신의
   주석을 고치면 그렇게 된다) 80분짜리가 돌길래 `pkill` 했더니 `src/index.css` 에
   `width: 2.5rem`(tap-reach 주입)이 남았다. `check-no-injection-in-progress.sh` 가 잡았다.
   ⚠️ **그 안내대로 `git checkout -- src/` 를 하면 안 된다** — 내 작업이 통째로 날아간다.
   `--verify-clean` 이 **파일과 주입 이름**을 찍어 주므로 그 한 hunk 만 손으로 되돌렸다.
2. 🩸 **내 시험 하나가 헛돌았다(주입이 잡았다).** `{!isPc && <ShoppingGroup …>}` 주입에
   `toContain('<ShoppingGroup counts={counts} />')` 과 위치 검사가 **둘 다 통과**했다 —
   문자열은 중괄호 안에 남고 위치도 안 변한다. ⇒ 줄머리 정규식(`\n {6}<ShoppingGroup`)으로 교체.
3. 🩸 **번들 예산 — main 자신이 이미 넘어 있었다.** PR Verify 가 `Bundle size budget` 하나로
   빨갰는데, `origin/main`(9d61a4eb)을 그대로 빌드하니 **7.57047 > 7.57** 로 exit 1 이다.
   이 검사는 `verify.yml`(= `pull_request`)에만 있고 **main push 워크플로엔 없어서**, PR 각자가
   통과한 값이 머지 뒤 합쳐져 선을 넘어도 다음 PR 이 열릴 때까지 **아무 신호가 없다.**
   ⇒ **올리기 전에 main 을 먼저 재서** 자기 델타와 선재 초과를 구분할 것.
   내 델타는 두 번 빌드해 대조했다: **+12.17 KB raw**, critical path 196.7 → 197.1 KB gzip.
4. ⚠️ **PC 마이 폭 버그를 "디자인 문제" 로 읽을 뻔했다.** 시안을 넷이나 그렸는데 실제로 필요한
   것의 절반은 CSS 한 줄이었다. 조판이 이상하면 **먼저 브라우저로 박스를 재라** — 시안은 그 다음이다.

## 6) 남은 것 / 대표 판단 대기

- **E4 라이브 판정**(위 표) — 로그인이 필요해 이 세션에서 못 쟀다.
- **`NotificationsPage` 는 아직 자기 목록을 갖는다.** 의도적이다(페이지네이션 + 딥링크 —
  `NotificationPanel` 머리말이 그 이유를 적어 뒀다). 다만 **목록이 두 벌인 것은 사실**이므로,
  페이지를 패널 위에 다시 지을 때가 오면 그때 합칠 것.
- ~~**번들 예산을 main push 에서도 재는 문제**~~ → **같은 PR 에서 고쳤다**(대표 *"이젠 이런 문제가
  없도록 해줘"*): 신규 `.github/workflows/bundle-budget-main.yml` 이 main push 마다 빌드해서
  `check:bundle:budget` 을 돌린다. **배포는 안 막는다**(별도 워크플로 — 예산은 후행 지표이지 장애가
  아니다). 목적은 *main 이 빨갛게 보이는 것* 하나이고, 그 신호가 있어야 다음 세션이
  "내 델타 vs 선재 초과" 를 구분한다.
- ~~띄어 쓴 가운뎃점 래칫~~ → **가드 자신의 오탐을 고쳤다.** 이 검사는 줄의 **첫 글자**로 주석을
  걸렀는데, 이 레포의 긴 한국어 블록 주석은 **이어지는 줄이 `*` 로 시작하지 않는다**. 그래서
  *설명을 쓰는 것만으로* 대외 문구 래칫이 올라 푸시가 막혔다(실제로 막혔다). 블록 상태를 추적하도록
  고치고 **자기시험 2건**(오탐 재현 + "주석 뒤 본문은 여전히 잡는가")을 넣었다. 동결 27 → **25**
  (사라진 셋은 전부 주석이고, 진짜 문구 둘은 그대로 잡힌다 — 확인했다).
