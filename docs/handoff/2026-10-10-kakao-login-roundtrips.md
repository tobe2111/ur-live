## ✅ ① 첫 렌더가 세션 교환을 기다리던 것 — 표식 쿠키

- 콜백은 **cross-site 302** 에 세션 쿠키를 심는데 iOS/WebKit 이 유실한다 → 2026-06-20 에
  티켓(`#st=`) + `POST /api/auth/session/establish` 를 **렌더 앞에서** `await` 하게 만들었다.
- 그 처방은 옳다. 문제는 **크롬·안드로이드는 302 쿠키를 잘 받는데도** 같은 기다림(실측 왕복
  0.7~1.0s)을 치렀다는 것 — 7일 실측 establish 성공 6건이 전부 비-iOS 다.
- 세션 쿠키는 `HttpOnly` 라 앱이 그 존재를 **못 본다** ⇒ 같은 응답에 `HttpOnly` 만 뺀 표식
  (`ur_sess_set`, 120초)을 하나 더 심고, 보이면 **안 기다리고 그린다**(교환은 배경).
- 🔒 **iOS 는 표식도 함께 유실** → 종전 차단 경로 그대로. 처방 무접촉, 조건이 하나 늘었을 뿐.
- 🔒 **인증 신호가 아니다** — 서버는 안 읽는다(가드 고정). 위조해도 "안 기다린다" 뿐이고
  세션이 없으면 API 401 → 비로그인 렌더(오늘 establish 실패 시와 같다).
- ⚠️ 표식 경로엔 **재시도·reload 미배선** — 쿠키가 있는데 reload 하면 그게 회귀다.

## ✅ ② D1 왕복 4 → 2 (기존 회원)

🩸 **제가 처음 대표에게 "2왕복" 이라고 보고한 것은 오보였다** — 마지막 재조회를 놓쳤다. 실제는 4:

```
조회(kakao_id) → 갱신(id) → 재조회(id) → 셀러 자동연결     = 4왕복 (전부 직렬)
batch[ 갱신(kakao_id) ;; 조회(kakao_id) ] → 셀러 자동연결   = 2왕복
```

- 셋이 직렬이던 이유는 갱신이 앞 조회의 `id` 에 묶여서다. `WHERE kakao_id = ?` 로 걸면 끊긴다.
- batch 안에서 갱신 **다음** 조회가 돌아 **갱신된 행**을 그대로 받으므로 재조회도 사라진다.
- 🔒 한 행만 맞는다: `idx_users_kakao_id_unique`(partial UNIQUE) 실재 + **라이브 중복 0 실측**.
- 🆕 신규 회원은 왕복이 **안 늘어난다**(batch 가 선행 조회 자리를 대체 → 0행 no-op + null → INSERT 경로).
- ⚠️ 레거시 스키마면 batch 가 throw → `fastOk=false` → **종전 직렬 경로 + 폴백 계단 3단 그대로**.

### 🩸 측정이 내 시험의 결함 둘을 잡았다 (다음 세션이 같은 함정에 안 빠지게)
1. SET 절을 `'SET '` **포함**해 자르는 바람에 첫 컬럼(`name`)이 조용히 빠졌다. 두 UPDATE 가
   **똑같이** 빠져서 "둘이 같은가" 비교는 통과했고, **기대값을 손으로 적어 둔 단언만이** 잡았다.
   ⇒ **비교만 두면 둘 다 틀려도 초록이다.**
2. 조회가 돌려주는 컬럼은 6개뿐(`id·kakao_id·name·email·profile_image·created_at`)인데
   `last_login_at`·`phone` 을 그 행에서 단언해 빨간불 — **코드가 아니라 시험의 오류**였다.
