## 이번에 틀렸던 판단
- **숙박 만료를 "자동 환불" 로 고쳤다가 대표가 바로잡았다**: *"숙소는 시간 지나면 자동환불이 아니라 사용 완료로 환불이 안되는건데"*. 코드가 환불을 시도하다 실패하고 있었기에 "환불이 의도" 라고 읽었다. 의도한 규칙은 코드가 아니라 대표의 말에서 확인할 것.
- **KT 발송 판정 SQL 이 조용히 거짓이었다**: 시험 DB 가 숫자를 실수로 묶어 `'u' || 5.0 || '-%'` 가 됐다. `CAST(… AS INTEGER)` 로 고정. 그리고 발송 성공 때 연결 키를 KT 주문번호로 덮어쓰고 있어, 판정 SQL 만 고쳤다면 라이브에서도 조용히 거짓이었다. 측정기가 0 을 내면 측정기부터 의심.
- 어드민 조사 보고의 "`pending` 지급을 바로 `sent` 로 넘길 수 있다" · "viewer 가 환불할 수 있다" 는 **코드 읽기(E1)** 다. 시험으로 돌린 것은 "역할 admin 이 지급 승인에서 403" 하나뿐.

## 안 고친 것 (돈·장부, 위에서부터 급한 순)
1. 부분 환불 라우트가 매장 몫을 잘못 뺀다(사장님 조사 보고, 미실행)
2. 셀프 취소 환불의 원장 줄이 `platform:revenue → platform:escrow` 로 적힌다(계정이 틀림) · 만료 환불은 원장 줄이 없다
3. 지급 완료된 소개비는 환불돼도 회수되지 않는다
4. 숙박 주문은 `order_items` 가 없어 사장님 "오늘 매출" 에 안 잡힌다
5. ~~`StoreBankPage` 문구 "매주 목요일" 이 틀렸다~~ → **이 항목이 틀렸다(2026-11-25 아침 정정).** "매주 목요일" 은 대표가 정한 규칙이다(`src/shared/partners-facts.ts` `storePayoutDay` · `settlement-schedule.ts` "월~일 사용분 → 차주 목요일", 2026-06-23·2026-11-03 대표 결정). 문구는 맞다. 남는 확인거리는 문구가 아니라 **장치가 둘이라는 것**이다: 목요일에 도는 `auto-settlement`(라이브 `restaurant_settlements` 0행)와 월요일 09:45 에 지급 대상을 만드는 `payouts-generate`(보류 14일). 실제 송금이 목요일 약속대로 나가는지는 어느 장치가 돈을 내보내는지부터 재야 한다(미실행). 같은 날 대표 보고에서도 "문구가 틀렸다" 고 말했고 아침 보고에서 바로잡았다.
6. 어드민 경영 지표의 수수료 가정 5% (원장은 10%)
7. 지급 대상이 계좌 없는 매장에도 만들어진다(송금 단계에서 막히긴 한다)
