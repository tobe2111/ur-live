# 키워드 순환 `starved` — 배분이 아니라 **잘림**이 범인이었다 (2026-08-11)

대표가 붙여넣은 경보: *"한 바퀴 4.9일인데 가장 밀린 키워드가 3.1바퀴째 순번을 못 받음 …
처방은 순환 가속이 아니라 배분 확인(집중/우선/일반 몫 · 커서 전진)"*.

경보의 처방이 정확했다. 배분을 확인했더니 **대표가 정한 축 우선순위가 코드에서 뒤집혀 있었다.**

## 실측 (라이브 D1, 19:07 KST)

```
              풀 크기   24h 실행   키워드 1개당 회전율(우선=1)
집중(마케팅대행사)   25       21        7.3      ← 설계 1.5
우선(맛집·뷰티·숙소·공동구매) 358       41        1.0
일반                76       28        3.2      ← 설계 0.5
활성 459 · 24h 실행 90 → 한 바퀴 5.1일 · 최고령 15.4일 = 3.0바퀴
```

`AXIS_ROTATION_MULTIPLIER = { focus: 3, priority: 2, general: 1 }` 이므로 목표는 **1.5 : 1 : 0.5**.
실측은 **7.3 : 1 : 3.2** — 전체의 78%인 본업 축이 가장 느리게 돈다.

## 원인 — 실제 함수를 라이브 풀 크기로 돌려 특정했다

`planKeywordSplit` 은 정상이었다. 범인은 `mergeKeywordPicks` 의 **1:1:1 라운드로빈**이다.

```
계획(total=9)  focus 1 · pri 6 · gen 2      → F p g p g p p p p
예산 5에서 잘림                              → F p g p g      (우선 6개 중 4개 상실)

키워드 1개당 회전율(우선=1)      설계 1.5 : 1 : 0.5
  계획대로면                     2.39 : 1 : 1.57
  5에서 잘리면                   7.2  : 1 : 4.7     ← 라이브 실측 7.3 : 1 : 3.2 과 일치
```

세 축을 한 개씩 번갈아 놓으면 **작은 축은 몫을 다 지키고 큰 축만 깎인다.**
2026-08-04 수리(앞머리 독점 제거)는 "잘릴 때 공평하게"를 노렸지만, 거기서 말한 공평은
*각 축이 조금씩 잃는 것*이었고 비례 공평이 아니었다.

## 수리 — 순서만 바꿨다(몫 무접촉)

균등 배치(Bresenham/smooth WRR): 각 축의 n번째 픽을 `(n+0.5)/몫` 위치에 놓는다.
**어느 지점에서 잘라도** 앞부분 구성이 몫 비율에 수렴한다.

```
before  F p g p g p p p p     예산 5 → 우선 2
after   p p g p F p p g p     예산 5 → 우선 3
```

⚠️ 남는 비대칭(집중이 설계 1.5 보다 높음)은 `planKeywordSplit` 불변식 ④(비지 않은 축 최소 1슬롯)의
**의도된 대가**다. 그 바닥을 없애면 작은 전략 축이 매 회차 0 이 된다 — 건드리지 않았다.
회차 폭이 축 수보다 넉넉해지면 저절로 옅어진다.

## 다음 세션의 첫 액션 — 판정 (배포 +24h)

```sql
SELECT CASE WHEN category='마케팅대행사' THEN 'focus'
            WHEN category IN ('공동구매','맛집','푸드','외식창업','숙소','네일','뷰티') THEN 'priority'
            ELSE 'general' END axis,
       COUNT(*) pool, SUM(CASE WHEN last_run_at > datetime('now','-24 hours') THEN 1 ELSE 0 END) ran24h
FROM ad_discovery_keywords WHERE active=1 GROUP BY axis;
```
**판정 기준**: 키워드 1개당 회전율 비(우선=1)가 **7.3 : 1 : 3.2 → 대략 2~3 : 1 : 1.5 안쪽**으로
내려오면 성공. 설계값(1.5 : 1 : 0.5)에 정확히 닿지는 **않는다** — 위 바닥 때문이다.
그리고 `judgeRotation` 의 `starved` 경보가 멎는지(최고령 ÷ 한 바퀴 ≤ 3).

⚠️ 안 내려오면 다음 후보는 **회차 폭이 아니라 예산**이다 — 계획 9 중 5만 처리되는 것이
비대칭의 전제였으므로, 예산이 9개를 다 태우면 계획 비율(2.39 : 1 : 1.57)이 그대로 나온다.
발굴 가속은 하지 말 것(미측정 백로그를 키운다 — `CLAUDE.md` 유어애즈 절).
