## ✅ 2026-07-29 (9차-e) — **cron 경보가 매일 오탐을 울리고 있었다 (ur-ads 레인 주기 신고)**

9차-d(#835 머지 + 인계 분리) 후속. 대표 "더 개선 및 고도화 요소들 찾아서 진행해줘".
**실측에서 이미 발생 중이던 결함**을 하나 잡았다 — 가설이 아니라 라이브 응답에 찍혀 있던 것이다.

### 무엇이 잘못돼 있었나

ur-ads 의 `adsBeat` 은 모든 레인에 **워커의 cron 식(`event.cron` = `0 * * * *`, 매시간)** 을 붙여
하트비트를 기록했다. 그런데 하나의 cron 이 **주기가 제각각인 레인들을 디스패치**한다:

| 레인 | 실제 주기 | 매시간으로 신고했을 때 |
|---|---|---|
| 일 1회 9개(`hourUTC === 15/16/17/19/20/21/22/23`) — NPS·고용24·나라장터·MX 스윕 … | 24시간 | 150분 지나면 stale → **하루 21.5시간을 매일 '멈춤'** |
| 짝/홀수시 4개(`hourUTC % 2`) — 상가정보·통신판매·기업수집 … | 2시간 | 여유 30분뿐 |
| 유지보수 5단계 순환(`PHASES[hourUTC % 5]`) | **최대 9시간** | 항상 stale |

`expectedMaxAgeMinutes('0 * * * *')` = 150분이고, 그 판정은
`/api/_healthcheck/cron` → `uptime.yml`(10분) → **이슈 + 메일**로 나간다.

**라이브 증거(2026-07-29 05:47)**: `ads:maintenance?phase=quality` 가 `age 167분 · stale: true`.
5단계 순환이라 정상 동작인데도 경보 대상이었다.

`cron-heartbeat.ts` 의 주석은 **"확실히 이상한 것만 울리는 게 목적"** 이라고 못박고 있다 —
매일 울리는 오탐은 그 설계 의도를 정면으로 깨고, 결국 경보 전체를 무력화한다.

### 고친 방식 — 조건과 주기를 **한 자리에서** 나오게

주기를 따로 적게 두면 언젠가 어긋나고, 어긋나도 조용하다(경보만 늘 뿐). 그래서 분리하지 않았다.

- 신규 `src/worker-ads/lane-cadence.ts`(순수) — `makeHourGates(hourUTC, kick)` 이
  **발화 조건과 주기 신고를 함께** 만든다. `gates.dailyAt(16, …)` / `gates.everyNHours(2, 0, …)`.
  시각 게이트 **12곳 전부** 전환(raw `kick` + `hourUTC` 동거 0건).
- `maxPhaseGapHours(phaseCount)` — 단계 순환의 최대 간격을 계산한다. **단순히 단계 수가 아니다**:
  24가 나누어떨어지지 않으면 자정에서 간격이 벌어진다(5단계 → 단계 4 는 19시 다음이 다음날 4시 = **9시간**).
  단계를 6개로 늘리면 24 % 6 === 0 이라 자동으로 6이 된다.
- `recordCronBeat(..., maxGapMin?)` — 작업이 자기 주기를 **직접 신고**하면 cron 식보다 우선.
  없으면 종전대로 cron 식에서 유도(기존 메인 워커 cron 은 **동작 불변**).
- `listCronHeartbeats` / `getCronHealth` 가 신고값 우선 + `max_gap_min` 을 응답에 노출
  (어드민이 "왜 stale 로 봤나"를 화면에서 알 수 있게 — 판정 근거가 안 보이면 또 오진한다).

### 검증

- 신규 유닛 **20개** — 공식 동치성(`staleGapMinutes(60) === expectedMaxAgeMinutes('0 * * * *')`)을
  고정해 두 곳이 갈라지면 실패한다 · 자정 불연속 · 게이트 발화 횟수.
- **가드를 깨뜨려 확인**: NPS 사이트를 원래 버그 모양(`if (hourUTC === 16 …) kick(…)`)으로 되돌리자
  회귀 테스트가 정확히 그 줄을 잡고 실패 → 복원 후 통과.
- 전체: `tsc 0` · 유닛 **2,948 pass(232 파일)** · `npm run build` exit 0 · **audit-gate 63 ALL GREEN**.
- 머니 경로 무접촉.

### ② 이어서 — **"한 번도 발화하지 않은 레인"도 보이게** (같은 PR)

위 수정의 한계로 남겨뒀던 것을 바로 이었다. 하트비트는 **기록된 행**만 보므로,
게이트는 켜져 있는데 한 번도 안 돈 레인은 목록에 아예 없어 `stale` 판정 대상조차 아니다 —
**"안 도는 건지 원래 없는 건지" 화면에서 구분이 안 된다.** `ads:collect-nps` 가 지금 그 상태이고,
그 때문에 세션 여러 개가 같은 질문을 반복했다.

**손복제 없이 목록을 얻는 방법**: 시각 게이트가 `makeHourGates` 안으로 들어간 덕분에
**발화하지 않는 시각에도 헬퍼는 호출된다** → 그 순간 레인 이름을 알 수 있다.
즉 이 목록은 손으로 관리하는 표가 아니라 **디스패치 코드가 그 자리에서 뱉는 사실**이다
(레인을 추가/삭제하면 자동으로 따라온다 — 이 레포가 반복해 데인 "목록이 사본" 클래스를 피한다).

- `createLaneRegistry()` 가 게이트 통과 레인을 모으고, 스케줄 실행당 **D1 쓰기 1회**로
  `platform_settings.ads_known_lanes` 에 남긴다(부모 예산 +1, fail-soft).
- `GET /api/admin/cron-heartbeats` 응답에 **`never_fired`** + `known_lanes_at` 추가.
- 쿼리는 떼고 비교한다 — 안 그러면 `maintenance?phase=*` 5단계 중 4개가 매번 오탐된다.
- **어드민 화면 배선까지 같은 커밋에서** — `/admin/system-monitoring` 에 '🔭 한 번도 안 돈 레인'
  카드 + 각 행에 판정 근거(`기준 N시간`) 표시. ⚠️ 안 그러면 **내가 고치려던 그 클래스를 내가 만든다**
  ("서버는 고쳤는데 볼 곳이 없다"). 실제로 UI 는 `stale` 만 읽고 있어서 새 필드가 안 보일 뻔했다.

### ⚠️ 이 수정이 **못** 하는 것 (과신 금지)

- `gates.*` 를 쓰되 **잘못된 시각/N** 을 넣는 경우는 못 잡는다(값의 정합은 검사 밖).
- **게이트가 OFF 인 레인은 여전히 안 보인다** — 의도적 정지와 구분할 수 없어 일부러 제외했다.
  게이트 상태는 `/__ads/health` 가 따로 노출한다(파트너풀 stats 가 이미 읽는다).
- `never_fired` 는 ur-ads 스케줄러가 **한 번 이상 돈 뒤**에야 채워진다(첫 배포 직후엔 빈 배열).
