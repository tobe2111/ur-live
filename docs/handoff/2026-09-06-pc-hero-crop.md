# PC 상세 사진도 스마트 크롭 + 남아 있던 두 항목 판정 (2026-09-06)

대표: *"이용권 업로드할 때 사진 최대 5장 선택해서 올릴 수 있게 해뒀어? 남은 두 작업도 다 해줘"*

## ① 사진 5장 — **이미 돼 있었다**(확인만)
`PhotoGalleryEditor`(2026-09-03, `#1336` 에 포함) 가 `multiple` 파일 입력 + `PHOTO_MAX = 5`,
첫 장이 대표, `←`/`→` 로 순서 변경. 서버도 `images` 를 받아 저장한다(`seller-orders.routes.ts:876`).
main 에 포함돼 있음을 `git merge-base --is-ancestor` 로 확인했다.

## ② PC 상세 히어로 스마트 크롭 — **했다**
08-31 에 모바일만 3:2 `gravity=auto` 로 바꾸고 PC 는 *"별도로 다룬다"* 며 미뤄 뒀다.
그때 적은 이유는 *"PC 는 감시 `<img>` 와 URL 을 공유해 트래픽 0 인 구조라 한쪽만 바꾸면 요청이
두 배"* 였는데 — **그건 한쪽만 바꿀 때의 이야기다.** 배경·감시·워커 preload 셋이 같은 함수를
부르면 URL 이 같아 요청은 그대로 하나다(브라우저 실측: 변형 정확히 2종).

- SSOT `shared/detail-hero-image.ts` 에 `detailCropUrl(src, w, ratio)` 신설. 모바일 함수는 그걸
  3:2 로 부르는 얇은 껍데기가 됐다.
- PC 대형 = `multi ? 4:3 : 16:9`(CSS `aspectRatio` 와 같은 값), 썸네일 = 5:4(레이아웃에서 유도).
- **갤러리 목록 계산도 SSOT 로 올렸다**(`detailGalleryImages`) — PC 프레임이 **장수로 갈리므로**
  워커가 화면과 같은 방법으로 세야 한다. 두 벌이면 경계에서 갈려 preload 가 버려진다
  (2026-09-02 에 실제로 났던 사고와 같은 클래스).

### 📏 실측 — 바이트는 **26% 준다**
```
8장 합계   평면 1,568KB  →  크롭 1,155KB   (−26%)
히어로 칸  798 × 449 = 정확히 16:9 (CSS 와 일치, 뷰포트 1280/1440/1920 동일)
```
평면 리사이즈는 **어차피 잘려 나갈 부분까지** 보내고 브라우저가 버린다.

🩸 **여기서 크게 틀릴 뻔했다**: 처음엔 사진 1장짜리(=16:9 프레임) 상품들에 4:3 을 재고
*"바이트가 두 배로 는다"* 는 반대 결론을 내 대표에게 그렇게 보고했다가, 비율을 바로잡아 정정했다.
⇒ **장수에 따라 프레임이 갈리므로, 재려면 그 상품의 진짜 비율로 재라.** 틀리면 부호까지 뒤집힌다.

## ③ 미검증 CDN 호스트 승격 — **할 대상이 없어졌다**(실측)
```
활성 상품 커버 100건 →  R2 98 · 외부 2(둘 다 검증된 호스트)
상세 40건의 갤러리 49장 →  R2 49 · 외부 0
```
2026-09-01 에 되살린 `demo-image-rehost` cron 이 사진을 전부 R2 로 옮겼다. 워커 프록시로
새는 사진이 **라이브에 0장**이라 승격할 호스트가 없다. ⇒ 이 항목은 구조적으로 닫혔다.
(부수 효과로 **PC 크롭이 실제로 먹는다** — 전부 리사이저를 타므로.)
