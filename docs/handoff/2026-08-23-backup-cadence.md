## 1. 왜 바꿨나 (실측)

```

유어애즈 DB                     약 754,000행
```

수요일 상태로 담긴다 — **시점이 어긋난 스냅샷**이라 복구했을 때 정합이 깨진다.

시간당 4회면 15시간 → **하루 안에 한 벌**이 들어온다. 대표 선택(A안): 코드만 바꾸고
**cron 스케줄(트리거)은 손대지 않는다** — 스케줄 PUT 은 원자적 전체 교체라 과거에 전체 cron
등록이 무산된 사고가 있었다.

## 2. 무엇을 바꿨나

## 2-b. 🧱 기존 가드가 이 변경을 잡았다 (그리고 그게 옳았다)

`cron-slot-gate.test.ts` 는 `scheduled.ts` 를 읽어 `slotDue(..., { minute: N })` 의 **N 을 파싱**해
① 5의 배수인가 ② 다른 게이트와 겹치지 않는가를 검사한다. 그런데 이번 변경은 `{ minute: m }` —
**변수**라 `Number('m') = NaN` 이 되어 CI 가 빨갛게 떴다.

⚠️ **여기서 "NaN 이면 건너뛰자"로 고치면 안 된다.** 그러면 백업 슬롯 4개가 통째로 검사 밖으로
나가고, 5의 배수 규칙도 겹침 규칙도 그 슬롯엔 안 걸린다 — 가드를 통과시키려고 가드를 무력화하는
전형적인 길이다. ⇒ **배열 리터럴을 펼쳐서 똑같이 검사**하도록 파서를 확장했다.
되돌려-검증: 배열에 `33`(5의 배수 아님)·`25`(기존 게이트와 겹침)를 넣어 각각 빨강 확인.

📌 슬롯 선택 근거 — 기존 분 게이트는 `25`(매시) · `30@3시` · `35@3시` · `40@9시` · `45@0시 월요일`.
`[5,20,35,50]` 은 매시 게이트(25)와 안 겹치고, `35@3시` 와는 **하루 한 번** 스칠 뿐이다

## 🩸 후속 (2026-08-24 11:10 KST) — **주기를 4배로 올렸는데 실제로는 안 늘었다**

배포는 됐다. 라이브 워커 번들을 내려받아 확인했다:

```
if (cron === "*/5 * * * *" && [5, 20, 35, 50].some((m) => slotDue(event.scheduledTime, { minute: m })))
  ctx.waitUntil(slotCron("5,20,35,50 * * * *")("d1-backup-chunked", ...))
```

그런데 **실제로는 시간당 1회만 찍힌다.** 실측(하트비트 `at`):

```
d1-backup-chunked  01:20:30   ← 그 뒤 :35 · :50 · 02:05 전부 없음
__tick             02:05:18   ← 5분 틱 자체는 매번 정상
```

`__tick` 은 매 틱 찍히므로 **핸들러는 돌았다.** 그런데 백업만 흔적이 없다 —
`cron_failures` 에도 없고(같은 3시간 창에 다른 작업 실패는 기록돼 있다), `cpu_deaths` 도 0 이다.
**성공도 실패도 아닌 완전한 침묵**이고, 이 레포가 반복해 만난 그 클래스다.

### 무엇이 그럴 수 있나

같은 `*/5` 인보케이션에 **작업 40개**가 얹혀 있고 서브리퀘스트 예산은 **무료 50** 을 나눠 쓴다
(`cron-slot.ts` 상단 주석이 그렇게 적고 있다). 백업 한 회차만 **reads=25 + R2 쓰기** 라 절반을 먹는다.
02:05 틱에는 매-틱 작업 10개가 같은 초에 실행됐다. 예산이 바닥나면 백업의 D1 읽기가 죽고,
**하트비트를 쓰려는 그 write 도 서브리퀘스트라 같이 죽는다** → `recordCronBeat` 의 fail-soft
`catch` 가 삼켜 **아무 기록도 안 남는다.** 관측이 실패 자체를 못 남기는 구조다.

⚠️ **단정하지 않는다** — 위는 정황이 맞는 가설이고, 이 환경에서는 `wrangler tail` 이 프록시에
막혀(wss 업그레이드 차단) 직접 확인할 수단이 없다. 확실한 것은 두 가지뿐이다:
**(a) 코드는 올바르게 배포돼 있다 (b) 그래도 시간당 1회만 돈다.**

### 권고 (대표 판단 사항 — 플랫폼 쓰기라 세션이 하지 않는다)

**백업에게 전용 cron 트리거를 준다.** 트리거는 계정당 5개인데 그중 하나(`0 20 * * SUN`)가
**죽어 있다** — 그 자리의 `d1-backup` 은 **503시간째 미실행**이고(`cron_failures` id 571),
DB가 워커 메모리를 넘겨 08-02 에 멈춘 뒤 지금의 분할 백업이 그 역할을 대신하고 있다.
⇒ 그 트리거를 `*/15 * * * *` 로 바꾸면 백업이 남의 예산을 안 뺏고 자기 인보케이션에서 돈다.
(코드 쪽 대응 — `scheduled.ts` 에 그 식 분기 추가 — 은 트리거를 바꾸기로 정한 뒤에 한다.
지금 미리 넣으면 `cron-unmatched` 만 늘어난다.)

**그때까지의 실제 기대치는 60시간이지 15시간이 아니다.** 이 문서 앞부분의 15시간은
"슬롯이 다 돈다면"의 값이다 — 라이브 실측으로 정정한다.

## 후속 4 — 백업 전용 cron 트리거 (2026-08-25, 대표 "트리거 바꿀게, 코드 쪽 대응 붙여줘")

**무엇이 문제였나**: 분할 백업은 `*/5` 틱 위 `:05/:20/:35/:50` 게이트로 돌았는데, 그 인보케이션은
작업 40개가 **서브리퀘스트 예산(무료 ~50)을 나눠 쓴다.** 백업 차례에 예산이 남지 않으면
`recordCronBeat` 의 write 조차 실패하고 fail-soft catch 가 삼킨다 → **에러 0, 하트비트만 늙는다.**
실측으로 자동 실행이 하루 7시간씩 끊겨 있었고, 08-23~24 의 완료 2건은 전부 수동 구동이었다.

**대응(코드 쪽)**:
- `wrangler.toml` — 4번째 슬롯을 `0 20 * * SUN`(죽은 주간 전체덤프) → **`*/15 * * * *`** 로 **교체**.
  ⚠️ 추가가 아니다. 계정 한도 5(ur-live 4 + ur-ads 1)라 5번째를 넣으면 스케줄 PUT 이 통째로 거부된다.
- `scheduled.ts` — 그 분기가 이제 **분할 백업**을 부른다(`handleD1Backup` 전체덤프는 DB 가 커져
  08-02 이후 OOM 으로 죽은 코드라 import 째 제거). 주간 표기 3종도 같은 분기가 계속 받는다 —

## 후속 7 — `*/15` 전용 트리거가 **등록은 됐는데 발화 흔적이 없다** (2026-08-25, 미결)

배포 후 실측:
```
CF API /workers/scripts/ur-live/schedules → '*/15 * * * *' 등록됨 (07:33:20 생성)
배포된 코드(origin/main) → 분기·EXPECTED 목록 모두 정상
그런데 cron='*/15 * * * *' 로 기록된 하트비트  0건
발화 기회 07:45 · 08:00 모두 백업 미실행 (08:05 는 `*/5` 슬롯이 수행)
```

### 가설 — `*/15` 의 분이 전부 `*/5` 의 분이다

`*/15` 는 :00/:15/:30/:45 에 울린다. **넷 다 `*/5` 의 분이기도 하다.** CF 가 한 스크립트에
같은 분 하나의 scheduled 이벤트만 전달한다면 `*/15` 는 **구조적으로 영원히 가려진다** —
등록돼 있고, 발화 안 하고, 에러도 없다.

⚠️ 설계할 때 *"`*/15` 와 `*/5` **백업 슬롯**(:05/:20/:35/:50)이 안 겹친다"* 만 확인했다.
**`*/5` 트리거 자체와는 매 회 겹친다**는 걸 놓쳤다.

⚠️ **아직 단정하지 않는다** — 관측 2회차뿐이다. 오늘만 좁은 창으로 두 번 틀렸다.

### 그래서 계측을 먼저 붙였다 (후속 7의 실제 산출물)

`__tick` 진단 프로브가 **전역 키 하나**라 같은 분에 여러 트리거가 울리면 마지막이 덮어썼다.
⇒ `__tick:<cron식>` 으로 쪼갰다. **쓰기 횟수는 그대로**(키만 변경).

| 질문 | 전역 키로는 | `__tick:<식>` 으로는 |
|---|---|---|
| `*/15` 가 발화하나 | ❌ 구분 불가 | ✅ 그 키가 갱신되는가 |
| 08-24 `0 18` 미발화인가 사망인가 | ❌ | ✅ tick 있고 작업 없음=사망 / 둘 다 없음=미발화 |

### ✅ 판정 완료 — 그림자 가설 성립, 처방 적용됨

발화 기회 **3/3 미실행**(07:45 · 08:00 · 08:15). 매 회차 같은 분에 `*/5` 는 정상 발화했고
(`__tick` 08:15:48 갱신) 백업만 안 돌았다. 코드 경로는 **조기 return 이 없어** 울렸다면
하트비트가 반드시 남는다 — 즉 그 인보케이션 자체가 없었다.

⇒ `*/15` → **`2,17,32,47 * * * *`**(:02/:17/:32/:47). `*/5` 와 한 분도 안 겹친다.
   5곳을 **한 커밋에서 함께** 옮겼다: `wrangler.toml` · `scheduled.ts` 분기 ·
   `cron-expected` 목록 · 테스트 · 주입 좌표.

🛡️ **영구 가드 신설**: `cron-schedule.test.ts` — 등록된 트리거끼리 **분을 공유하면 빨강**.

   *"`*/5` 와 `*/15` 가 분 0,15,30,45 을 공유한다 — 뒤엣것이 조용히 안 울린다."*

🧭 **교훈**: 새 트리거를 넣을 때 본 것은 *"`*/5` **슬롯 게이트**(:05/:20/:35/:50)와 겹치나"* 였다.

```
down &&  open  → (아무것도 안 함)        ← 여기서 21일이 지나갔다
```

### 수리 — 판정 단위를 `down` 에서 **침묵 중인 이름의 집합**으로

- 프로브가 HTTP 코드만이 아니라 `stale[].name` 목록까지 뽑는다.
- 열려 있는 동안에도 **집합이 바뀌면** 코멘트한다(➕ 새로 침묵 / ➖ 해소). 안 바뀌면 조용하다 —
  #845 가 코멘트 84개로 불어난 교훈은 그대로 지킨다.
- 비교 기준은 이슈 본문의 표식(`<!-- stale:… -->`)에 남기고 매번 갱신한다.
- ⚠️ **파싱 실패는 빈 목록이 아니라 `?`** — 섞으면 헬스체크가 죽은 순간 "전부 해소" 코멘트가
  나가고 그게 이 경보의 신뢰를 끝낸다.
- ⚠️ `[ ... ] && ...` 맨몸 문장을 쓰지 않는다 — Actions 기본 셸이 `bash -e` 라 그 자리에서 죽는다.

⇒ 수리: 대상 0건일 때만 **`STRICT` 와 무관하게 무조건 `exit 1`**. 나머지 위반은 관례대로 warn 이지만,
*"잴 대상이 0개"* 는 위반이 아니라 **가드 자신이 고장난 것**이라 경고로 넘길 성질이 아니다.
되돌려-검증: 경로를 없는 파일로 바꿔 실행 → warn 모드인데도 `exit=1` 확인.

주간 백업이 08-05·12·19 **3주 연속 실패**했다. 화면 안내문이 사고를 만든 사례다.

### 수리

- 저장 실패 시 **서버가 준 사유를 그대로** 표시 + 401/403(세션)과 네트워크를 구분해 말한다.
- 자격 카드 안에 **자체 저장 버튼**(같은 `save()` 호출 — 손 닿는 자리에 하나 더).
- 안내문을 오늘 실측으로 확정된 권한 목록으로 교체(만료일 비우기 + Edit 범위 + User 항목).

### 🧭 교훈

이 세션은 하루 종일 *"에러가 안 나서 아무도 모르는 고장"* 을 팠는데, **마지막 것은 사람에게
직접 일어났다.** 화면이 "실패"라고만 하고 이유를 안 말하면, 그건 로그가 없는 것과 같다 —
**대표가 사람이라서 다를 뿐, 구조는 같은 병이다.**

⚠️ 그리고 이 왕복의 절반은 **내 안내가 틀려서**였다: 새 토큰을 만들라고 해 놓고
다음 메시지에서 *"값이 안 바뀌므로 어드민에 다시 넣을 필요 없다"* 고 했다(편집한 경우에만 맞는 말).
**두 경로를 섞어 말하면 상대는 둘 다 안 하게 된다.**

## 후속 22 — **진짜 원인은 UI 가 아니었다: 페이로드가 커서 저장이 매번 죽었다** (2026-08-25)

> 🩸 **후속 21 의 진단은 절반만 맞았다.** "엔드포인트는 멀쩡했다 — 같은 값으로 되쓰기해 보니
> `updated_at` 이 갱신됐다" 고 적었는데, 그때 **내가 보낸 건 키 한 개짜리 페이로드**였다.
> 대표 화면이 보내는 건 **200행대**다. 같은 엔드포인트가 전자는 살고 후자는 죽는다.
> ⇒ **"엔드포인트를 찔러 봤다"로 "화면도 된다"를 결론짓지 말 것.** 화면이 실제로 보내는
> 페이로드로 찔러야 같은 것을 시험한 것이다.

### 무엇이 있었나

UI 3건을 고쳐 올린 뒤에도 대표는 **여전히 "저장 실패"** 였다. 코드를 다시 읽고 나온 것:

```
폼 시드:  setSettings(settingsQ.data)        ← platform_settings **전체 행**
저장:     api.put(..., { ...settings })      ← 그 전부를 되보냄
서버:     for (key of body) await DB.prepare(...).run()   ← 키당 D1 왕복 1회
```

`platform_settings` 에는 설정이 아닌 행이 훨씬 많다 — **`cron_hb:*` 하트비트만 129개**
(이 레포 소스 주석이 그 숫자를 적고 있다), `backup_chunk:*` 커서 등. 무료 플랜은
**인보케이션당 서브리퀘스트 50** 이고 D1 호출도 거기 센다.
⇒ 저장 요청이 **매번 한도에서 끊겨 한 줄도 안 써졌다.**

**대표가 무엇을 입력하든 상관없었다. 값이 틀려서가 아니라 페이로드가 커서다.**

그리고 이건 어느 날 갑자기 생긴 선이 아니다 — 하트비트가 하나씩 쌓이다 50 을 넘는 순간부터
페이지가 **조용히 먹통**이 됐다. 배포도 없었고 경보도 없었다. 화면의 "저장 실패" 넉 자가 전부였다.
(`cf_api_token.updated_at` 이 **2026-08-02** 에 멈춰 있는 것이 그 날짜의 화석이다.)

### 수리 — 두 겹

1. **호출부** (`AdminPlatformSettingsPage`) — 서버 스냅샷을 `serverSnapshot` ref 에 보관하고,
   저장은 **그와 다른 키만** 보낸다(보통 1~3개). 순수 함수 `buildSettingsPayload(settings, base)`
   로 분리해 시험 가능하게. 바뀐 게 없으면 요청 자체를 안 보낸다("변경된 값이 없습니다").
2. **서버** (`admin-tools.routes.ts PUT /settings`) — 키당 왕복 → **`DB.batch()` (왕복 1회)**,
   100개 조각. 호출부가 언제 또 커지든 크기가 생사를 가르지 않게.

가드: `src/tests/unit/admin-settings-save-payload.test.ts` (6건 — 라이브를 닮은 139행 픽스처로
"한 칸 고치면 한 키만 나간다"·"빈 자격은 안 나간다"·"서버가 batch 를 쓴다") + 주입 매니페스트 2건.
**둘 다 되돌려-검증 빨강 확인**(①은 3건 빨강, ②는 1건 빨강).

### ⚠️ 같이 발견한 것 — **CF 토큰이 죽었다**

스크래치패드에 캐시해 둔 토큰(`…2254`)이 이제 `1000 Invalid API Token` 을 준다.
오늘 낮까지는 D1 쿼리가 됐고 주간 백업도 그 토큰으로 성공했다 ⇒ **대표가 권한을 고치는 과정에서
값이 굴러갔다**(roll 또는 재발급). D1 에 저장된 값도 그 죽은 토큰이다.
⇒ **새 토큰 값을 어드민에 넣어야 한다. 그런데 그 저장이 위 버그로 막혀 있었다** — 그래서
이 수리가 배포되기 전까지는 대표가 넣을 방법이 없었다.

### 🧭 교훈

**"엔드포인트가 200 을 준다"는 "이 화면이 저장된다"가 아니다.** 재현할 때는 *화면이 보내는 것*을
보내야 한다. 후속 21 에서 한 키만 찔러 보고 "서버는 멀쩡"이라 적은 탓에, 원인을 UI 쪽에서만
찾다가 한 사이클을 더 썼다.
