# 미사용 만료 환불이 한 번도 돈 적 없다(🔴) · 머니 스위치 번호가 겹쳐 지시가 안 통했다

대표 질문 셋: *"스위치 on 어떤거 얘기하는거야? 지금 이 페이지 너무 복잡해 이해하기도 어렵고
말들이.. 그럼 이제 다 된거야? 정산 과정 완벽해?"*

`[E2]` 검증됨 — ②는 배포 대기, ①은 결재 대기(코드 미변경).

## 답 ①: 스위치는 **이미 켜져 있다**. 그리고 내가 짚을 수 없는 번호를 말했다

라이브 실측: `settlement_skip_ledgered = true`. 09-29 에 부탁한 그 스위치는 켜져 있다.

🩸 **대표가 못 찾은 이유는 페이지가 아니라 내 지시였다** — 내가 *"머니 스위치 ⑨"* 라고 했는데
**화면에 ⑨ 가 둘**이다. 실측:

```
③ ×3   채널별 요율 · 셀러 소개비 필드 (+③-a/③-b 가 가리키는 대상)
⑧ ×3   담기 적립 · 이용권 일부 환불 · 이용권 장바구니
⑨ ×2   소개 정산 사용 뒤로 · 자동정산 원장 제외      ← 지시가 통하지 않은 자리
⑩ ×2   중개사 몫 · 제휴 제안 자동 발송
```

원래 ①②③④ 는 8월 flip **활성화 순서**이고 hint 들이 서로 그 번호를 참조한다. 뒤 세션들이 새
스위치에 "다음 번호"를 붙이며 부딪혔다. 그래서 `③-a 직접 입점 요율` 의 *"③ 이 ON 일 때만"* 이
**정반대를 가리키고 있었다** — 활성화 순서의 ③ 은 셀러 소개비 필드인데 실제 부모는 채널별 요율이다.

**수정(표시만 — 키·기본값·옵션·로직 무접촉)**: 순서가 있는 넷만 `[순서 1~4]`, 나머지는 **이름으로**,
부속 값 필드는 `↳` + **부모 바로 아래로 이동**(채널 요율의 a/b 사이에 무관한 스위치가 끼어 있었다).
hint 상호참조도 번호 → 이름. 머리말에 규약을 박았다.

가드 `money-switch-labels-2026-09-30.test.ts` 8건 + 주입 7건 **전부 빨간불 확인**.
그중 하나가 **키 집합 불변**을 고정한다 — 표시를 고치다 손잡이를 잃는 것이 이 파일의 반복 사고다.

🩸 **주입이 내 시험 하나를 헛돈다고 잡았다**: `↳ 개수 >= 4` 로 셌더니 ↳ 하나를 떼도 넷이 남아
초록이었다. **개수는 불변식이 아니다** → 어느 값 필드가 어느 스위치에 딸렸는지(`DEPENDENTS`)를
직접 적고, 부모와 자식 사이에 무관한 스위치가 끼면 빨간불.

🩸 **그리고 `readCode` 는 주석을 이미 지운 값이다** — 머리말 검사를 `readCode` 로 썼더니 빈
문자열을 검사하고 있었다(규약을 통째로 지워도 초록). 주석을 볼 때는 `readRaw`.

## 답 ②: **아니다 — 정산은 완벽하지 않다.** 🔴 환불 결함을 지금 찾았다

**미사용 만료 이용권 자동환불이 구조적으로 한 번도 돌 수 없다.** 두 cron 이 같은 행을 다툰다:

| | 하는 일 | 주기 |
|---|---|---|
| 🅰️ `handleExpiredVoucherRefunds`(`auto-settlement.ts:281`) | 만료 표시 **+ 환불 + 알림 + 커미션 회수** | **하루 1회** 18:00 UTC |
| 🅱️ `scheduled-cleanup.ts:252` | 만료 표시**만** | **매시 :10**(`scheduled.ts:220`) |

🅱️ 가 최대 23시간 먼저 `status='expired'` 로 바꾸고, 🅰️ 의 `WHERE status='unused'` 는 아무것도
못 찾는다 ⇒ **환불 0**. 에러가 안 난다 — 🅰️ 하트비트는 `ok:true`(찾을 게 없었다고 판단).

**라이브 증거**: 이용권 id=1 이 `2026-08-22T02:55Z` 만료 · `deal_points` 1,800원 ·
`refund_status=null` · `orders.refunded_amount=0` · user 3 포인트 환불 **0건** · 만료 알림 **0건**.
🅱️ 가 `03:10Z` 에 잡았고 🅰️ 는 `18:00Z` 에 빈손 — 시각이 정확히 맞는다.

소비자 화면은 *"미사용 시 100% 자동환불"* 을 약속한다. **지금 구조로는 불가능하다.**
같이 죽는 것: 미수령 차감의 `unclaimed_forfeit` 원장 기록 · 만료 이용권 커미션 회수.

**지금 손해는 0** (만료 1장이 대표 테스트 계정). 하지만 확률이 아니라 **구조**라 첫 실손님에서 재현된다.

⇒ 환불 경로 = 등급 C ⇒ **코드를 고치지 않고 결재함에 올렸다**:
`docs/decisions/2026-09-30-expired-voucher-refund-stolen.md` (안 3개 + 기본안 + 롤백)

### 이번에 틀렸던 판단

1. **"적립 계정 한 줄만 바꾸면 된다"** — 실제로 그렇게 고쳐 봤다가 되돌렸다.
   `seller:N` 에는 **차감**(인플 커미션·추천 보너스·중개사 몫·부분환불)이 걸려 있고,
   `payouts-generate` 는 계정 **문자열**로 GROUP BY 하므로 `seller:14` 와 `merchant:14` 가
   **서로 차감되지 않는다.** 구매 적립만 옮기면 `seller:14` 에 차감만 남아 음수가 되고,
   음수는 최소출금액 미달로 스킵돼 **매장이 부담해야 할 커미션을 아무도 안 내게 된다**(플랫폼 손실).
   ⇒ 한 매장에 계정 이름이 둘인 것이 진짜 뿌리다.
2. **CI 블로커를 "dev 전용 4건" 이라고 대표에게 보고한 것** — 틀렸다. 그 4건은 #1580 이 이미
   main 에서 고쳐 놨고, 남아 있던 것은 **런타임 axios 5건**이었다. 로컬 audit 이 `.git/COMMIT_EDITMSG`
   에 남은 `[SKIP_AUDIT]` 때문에 계속 건너뛰어져서 진짜 실패를 못 보고 있었다.
   ⇒ `[SKIP_AUDIT]` 는 `git commit -F -`/`-m` 으로는 **조용히 안 먹는다**. 늘 먹는 건 `SKIP_NPM_AUDIT=1`.
3. **주입이 내 단언을 헛돈다고 잡았다** — `/expiredVoucherSelectSql\(/` 로만 보면 import 줄과
   폴백 호출(`(false)`) 때문에 주 경로를 인라인 SQL 로 갈아도 초록이었다. 인자까지 고정해야 한다.

## ✅ E4 판정 통과 — 환불이 실제로 나갔다 (2026-10-02 새벽 3시 KST 회차)

머지 `2993c7c` (PR #1582) 배포 후 첫 `daily-lane('money')` 회차(`0 18 * * *` UTC)에서 실측:

| 무엇 | 실측값 |
|---|---|
| `vouchers` id=1 | `status='expired'` · **`refund_status='refunded'`** |
| `point_transactions` id=33 | `type='refund'` · `amount=1800` · "바우처 만료 환불 (아메리카노(Hot)(TAKE-OUT))" · `2026-10-01 18:00:30` UTC |
| `user_points` user 3 | **12,100** (= 10,300 + 1,800 — 실제로 입금됐다) |
| cron 하트비트 `expired-voucher-refund` | `ok:true` · `ms:6235` · `rr:144` · **`rw:10`**(실제 쓰기 10건) |

⇒ 선점을 `refund_status` 로 옮긴 처방이 **라이브에서 의도한 효과를 냈다.** 청소 cron 이 매시간 돌아
`status='expired'` 로 바꿔 놓은 그 행을, 환불 cron 이 정상적으로 집어 환불했다.

⚠️ `points_amount` 가 0 인 것은 결함이 아니다 — `amount` 가 입금액이고 잔액 증가(10,300 → 12,100)가
그 증거다. 옛 행들이 둘 다 채운 것은 다른 경로(`donate`/`공동구매 자동 환불`)의 관례다.

## 🔴 그리고 이중적립이 **실제로 발화했다** (예고 하루 만에)

같은 조회에서 발견: **이용권 2번이 `used` 로 바뀌어 있었다**(`used_at` = `2026-10-01 14:37:33` UTC
= 2026-10-01 밤 11시 37분 KST). 즉 어제 결재를 올리면서 *"첫 손님이 쓰는 순간부터 회수 문제가 된다"*
고 적은 그 일이 **그날 밤에 일어났다.**

라이브 원장 실측(`payouts-generate` 의 집계 SQL 그대로):

```
merchant:14  →  950      (사용 시점, ledger id=4 · event_type='voucher_used')
seller:14    →  950      (구매 시점, ledger id=3 · event_type='group_buy_join')
                          ⇒ 가게 14 에 지급될 합계 1,900원 / 판매액 1,000원 = 190%
seller:null  → 1,710     (플랫폼 상품 — payouts 의 `/^\d+$/` 가드가 걸러낸다)
user:3       → -2,800
```

그리고 `platform:escrow` 는 **−1,000** 이다(id=4·5 가 escrow 를 빼는데 아무것도 escrow 에 넣지 않았다)
— 장부가 안 맞는다는 직접 증거다.

**나간 돈은 아직 0원**: `payouts` 0행 · seller 14(홍대돈까스, `approved`) **계좌 없음** · 최소출금액
10,000원 미달. ⇒ 지금 고치면 손실 0 이고, **계좌가 등록되는 순간부터는 회수 문제가 된다.**
