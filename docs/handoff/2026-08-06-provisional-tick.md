# 학습기가 멀쩡한 자기 목을 졸랐다 — 빈자리를 붕괴로 읽어 cap 6 → 2

**2026-08-06 · 유어애즈 레인 학습기(AIMD)** · 대표 지시 *"고치자 완벽하게"*

## 무슨 일이 있었나 (라이브 실측)

8/5 저녁 19:00 에 cap 이 6 에 도달했다고 대표에게 보고했는데, 다음 날 아침 **2(바닥)** 였다.
원장을 보니 밤사이 회차 이력에 **빈자리가 9개**였다:

```
05일 19:00 → 06일 00:00   (4회차 없음)
06일 00:00 → 04:00        (3회차 없음)
06일 05:00 → 08:00        (2회차 없음)
```

**그런데 그 시각 레인 하트비트는 전부 `ok=true` 였다** — 07시 프랜차이즈, 05시 지역데이터,
08시 제조사·나라장터·match-registry… 전부 정상 완료. `ads_dispatch_last` 도 매시간 최신이었다.

⇒ **레인은 다 돌았다. 죽은 건 관측(부모 꼬리)뿐이다.** 그런데 학습기는 빈자리를 붕괴로 읽고
(`missedTicks`) 처리량을 절반 이하로 깎았다. 대가는 실측된다 — 8/5 19시 B2B 시간당 2,124건이
밤사이 대부분 0~100건으로 떨어졌다.

## 왜 그랬나 — 기록이 꼬리에만 있었다

회차 요약은 `closeTick` → `writeTickSummary`, 즉 **부모 꼬리에서만** 쓰였다. 부모가 거기까지
못 살면 그 회차는 이력에 없다. 그리고 `lane-aimd.ts` 주석이 그 빈자리를 *"fail 보다 더 강한
붕괴 신호"* 로 규정했다(#983). 의도는 옳았다 — 그때는 진짜 붕괴를 놓치는 편향이 있었다.

문제는 **두 경우가 똑같이 생겼다는 것**이다:
- 부모가 디스패치 **전에** 죽음 → 회차가 통째로 없음 → 진짜 붕괴
- 부모가 디스패치 **후 꼬리에서** 죽음 → 레인은 다 돎 → 관측만 실패

8/4 에 꼬리 상한을 25s → 10s 로 줄여 봤지만 구멍은 그대로였다. `tail-bound.ts` 헤더가
정확히 예고했다: *"줄지 않으면 원인이 대기 시간이 아니다 — 값을 또 만지지 말고 계측을 붙일 것."*

## 수리 — 기록을 꼬리에 의존하지 않게

디스패치 지점은 **매 회차 반드시 산다**(`ads_dispatch_last` 가 라이브에서 늘 최신 = 증거).
거기서 **잠정 회차**(`p:1`, 결과 미상)를 먼저 박고, 꼬리가 돌면 **같은 `at` 으로 교체**한다.

| 항목 | 파일 |
|---|---|
| `provisionalTick()` · `isProvisionalTick()` · `TickSummary.p` | `worker-ads/tick-history.ts` |
| `missedTicksJudged()` — 직전이 잠정이면 빈자리 0 | `worker-ads/lane-aimd.ts` |
| 디스패치 배치에 잠정 항목 write(기존 읽기/배치에 얹음) | `worker-ads/lane-runner.ts` |
| 호출부가 `at: tickStartIso` 전달 | `worker-ads/index.ts` |
| 꼬리가 *자기 자신*을 직전으로 안 쓰게 | `worker-ads/tick-history-write.ts` |

**비용 0**: 이력 읽기는 기존 커서 왕복에 키 하나 추가(`IN (?, ?, ?)`), 쓰기는 기존 배치에 한 줄.

**잃지 않은 것**: 부모가 디스패치 전에 죽으면 잠정 항목도 없다 → 빈자리 → 여전히 해로 잡힌다.
이 변경은 두 경우를 **비로소 구분**한다.

⚠️ **`at` 은 꼬리와 같아야 한다.** 디스패치 시점의 `new Date()` 를 쓰면 교체가 안 돼 한 회차가
두 줄이 되고 "얼마나 자주 도는가" 가 부풀려진다. 테스트가 이걸 고정한다.

   ⚠️ **그건 이 수리가 고치는 대상이 아니다.** 부모가 왜 꼬리까지 못 사는지는 **여전히 미확정**

   오판하지 않게* 만든 것이다. 원인 규명은 별건이고, 잠정 항목의 비율이 그 규모를 알려 준다.
