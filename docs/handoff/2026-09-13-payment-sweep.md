## 🔴 찾아서 고친 것 — 복구 새로고침이 예산을 우회했다

라이브 `frontend_errors` 에 **오늘 08:33, `/group-buy/confirm-payment` 가 51초에 31번 다시 로드**된
기록이 있다(서로 다른 문서 31개). 다른 경로의 boot-stuck 은 3주에 4건 — 이 페이지만의 폭주다.

```
08:33:03  /group-buy/confirm-payment          ← 쿼리가 아예 없다 (#1418 이 고친 그 버그의 현장 증거)
08:33:04  ?__cb=mtzk3sfc   entryRan=n
…  초당 한 번, 08:33:54 까지 (그 뒤 재발 0)
```

**원인(코드 사실)**: 재시도 카운터가 `reloadOnce` **안에** 있었고, 복구 오버레이의 30초 자동
재시도가 `setTimeout(bustReload, 30000)` 으로 **카운터 없는 함수를 직접** 불러 5분/8회 상한을
통째로 지나갔다. ⇒ 예산을 `takeReloadBudget()` 로 빼서 **두 경로가 같은 카운터**를 쓰게 했다.
소진되면 자동 재시도는 멈추고 오버레이와 버튼이 남는다(그게 8회 캡을 둔 이유다).

`sessionStorage` 가 막힌 환경에선 1 을 돌려준다 — **복구를 고치려다 복구를 끄면 안 된다**(주입이 고정).

**규명 못 한 것**: 왜 엔트리가 실행조차 안 했는지(`entryRan=n`). 청크 404 아님(자산 전부 200) ·
낡은 HTML 아님(`no-cache`) · CSP 아님(nonce 정상) · 배포 중 아님(직전 프로덕션 배포 09-09).
**이 컨테이너는 프록시가 브라우저를 막아 재현을 못 했다**(`ERR_CONNECTION_RESET`). 한계로 남긴다.

## 🩸 내가 틀렸던 것 — 다음 세션이 같은 걸 밟지 말라고

**"`/seller/youtube-growth` 는 App.tsx 에 라우트가 없는 죽은 페이지"** 라고 대표께 보고했다가
**정정했다.** 라우트는 `src/routes/seller.routes.tsx` 에 있다 — 이 레포의 라우트는 **네 파일**에
나뉘어 있다(`App.tsx` · `routes/{seller,admin,supplier}.routes.tsx`). `App.tsx` 만 grep 한 탓이다.
같은 실수를 내가 만든 가드도 처음에 저질러 **살아 있는 셀러 페이지 3개에 거짓 빨간불**을 냈다.

⇒ **라우트 존재를 확인할 땐 `<Route path=` 를 가진 파일을 전부 봐라.** 가드가 이제 그렇게 한다.
