# 08-01 — 통신판매 API 는 멀쩡했다. 고장은 우리 쪽 파라미터다

## 한 줄

며칠째 "비JSON 응답"으로 죽어 있던 **통신판매(최대 공급원, 누적 13만 건)** 는 **API 문제가 아니었다.**
직접 찔러보니 **HTTP 200 · 정상 JSON · totalCount 2,649,409**.

## 실측 (08-01 00:35 KST, `POST /api/admin/partner-pool/probe-public-data`)

| 대상 | HTTP | JSON | 본문 |
|---|---|---|---|
| 통신판매 등록현황 | **200** | ✅ | `resultCode "00" NORMAL SERVICE` · totalCount **2,649,409** |
| 통신판매 등록상세 | **200** | ✅ | `resultCode "00" NORMAL SERVICE` · totalCount **2,725,333** |
| 국민연금 사업장 | **200** | ✅ | `NORMAL_CODE` |
| 공정위 가맹 | **404** | ❌ | `API not found` → **하드실패** |
| 나라장터 조달업체 | **404** | ❌ | `API not found` → **하드실패** |
| 인허가(일반음식점) | **500** | ❌ | `Unexpected errors` |

**같은 키로 2개는 되고 4개는 안 된다** ⇒ 계정·키 문제가 **아니다**. 서비스별 문제로 확정.
(대조군을 함께 찌르도록 설계한 값이 정확히 여기서 나왔다 — 하나만 찔렀으면 "키가 죽었나"를 또 의심했을 것이다.)

## 왜 레인만 깨지나 — 남은 차이는 파라미터 하나

| | 프로브 | 레인 |
|---|---|---|
| `numOfRows` | **1** | **500** |
| `pageNo` | 1 | 63 |

프로브 모듈의 한계 주석이 이 경우를 **미리 예고**했다:
> "레인의 실제 파라미터까지 재현하지 않으므로 '인증·엔드포인트는 되는데 특정 파라미터에서 깨진다'면
> 프로브는 초록으로 나온다. 그건 그것대로 원인을 파라미터로 좁혀 주는 신호다."

⇒ #922 에서 `rows`/`page` 를 흔들 수 있게 하고 **사다리**(`ladder=1,50,100,200,500`)를 추가했다.

## 다음 세션의 첫 액션

```
POST /api/admin/partner-pool/probe-public-data?target=commerce-status&ladder=1,50,100,200,500
```
1. **첫 실패 rows** 를 확정한다(200/JSON → 비JSON 으로 넘어가는 지점).
2. `commerce-notify-collect.ts:184` 의 `numOfRows=500` 을 그 아래 안전값으로 내린다.
   ⚠️ 페이지당 건수가 줄면 같은 범위를 훑는 데 요청이 더 든다 — 서브리퀘스트 예산(레인당 ~50)과
   함께 봐야 한다. 무작정 1로 내리면 수집 속도가 500배 느려진다.
3. `pageNo=63` 자체가 문제일 가능성도 남아 있다 → `ladder` 를 `page=63` 로도 한 번 돌려 갈라낼 것.

## 대표 확인 대기 (한 화면에서 3분)

data.go.kr → 마이페이지 → 오픈API → **활용신청 현황**:

| API | 확인할 것 |
|---|---|
| 지방행정 인허가 (`1741000`) | 승인 상태 · 활용기간 만료 여부 (HTTP 500) |
| 공정위 가맹사업 | **요청주소(End Point)** — 현재 404 이므로 우리 주소가 틀렸다 |
| 나라장터 조달업체 | **요청주소(End Point)** — 동일 |

⚠️ **키를 새로 발급할 필요는 없다** — 같은 키로 통신판매·국민연금이 정상 동작함이 확인됐다.
⚠️ 이 환경은 `apis.data.go.kr` 은 나가지만 **data.go.kr 포털 화면은 프록시에 막혀** 있어
   요청주소를 세션이 직접 확인할 수 없다. 후보를 찍어 넣는 것은 추측이라 하지 않았다.

## 오늘 내가 틀렸던 것 (같은 오진 반복 방지)

1. **"D1 레인은 살고 외부 HTTP 레인만 죽는다"** — 틀렸다. `collect-maker`(외부 HTTP)는 beat 를 남겼고
   `match-registry`(D1 전용)는 안 남겼다. 가르는 축은 **프로토콜이 아니라 완료 시점**이다.
2. **"franchise·nara 가 07-29 에 고장났다"** — 틀렸다. 07-29 는 **그날부터 기록하기 시작**한 날이다
   (#837 이 백오프 추적을 붙였고, 그 커밋 설명이 이미 "13회·10회 연속 404" 를 적고 있다).
   `first_failed_at` 을 고장 시점으로 읽으면 안 된다.
3. **"배포 창은 대표 판단 사항"** — 틀렸다. `deploy-ads.yml` 은 레포 안의 파일이라 PR 로 고칠 수 있다.
   플랫폼 설정(CF 대시보드)과 혼동했다.
4. **사다리 시험이 헛돌았다** — 마지막 단만 실패시켰더니 '중간 break' 를 주입해도 초록이었다.
   중간 단이 실패하는 시나리오로 바꿔 RED 를 확인했다. (오늘 이 클래스 세 번째다.)
