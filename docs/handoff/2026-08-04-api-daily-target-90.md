# 2026-08-04 — 외부 API 일일 목표 90% (대표 지시 *"유료 api 각각 90%씩은 쓰자"*)

## 0. 먼저 알아야 할 것 — 이건 **늘리는 값이 아니라 멈추는 값**이다

실측(2026-08-04):

```
네이버 오픈API    396 / 25,000   (1.6%)
유튜브 units    3,100 / 10,000   (31%  ← 검색 24×100 + 성과측정 700)
유튜브 검색        24 / 90        (우리 자체 예산의 27%)
카카오 조회       360 / ?         (앱별 쿼터 — 코드가 모른다)
```

**오늘의 병목은 쿼터가 아니다.** 같은 시각 `23:00 KST` 틱 하나에서 네 레인이 CPU 한도로 죽었다
(`collect-commerce` · `collect-storeinfo` · `enrich-company` · `enrich-prospects`, 전부 8.1~8.6초).
서브리퀘스트 학습 상한도 38~60 으로 천장(60)에 붙어 있다.
⇒ **90% 목표를 넣어도 오늘 수집량은 1건도 안 는다.** 그래도 넣는 이유는 유료 전환이다:
천장이 60→900(×15)이 되면 쿼터를 넘겨 429 를 받기 시작하고, **실패 호출도 쿼터를 먹으므로**
회차 후반 작업이 통째로 버려진다. 90% 는 그때 멈춰 주는 브레이크다.

## 1. 무엇을 했나

| API | 전 | 후 |
|---|---|---|
| 네이버 | 카운터만 있고 **게이트 없음** | 22,500(90%) 에서 정지 |
| 유튜브 | 검색 90회 (=90%인데 우연처럼 보임) | `쿼터×90%÷단가` 로 **유도** + 테스트 고정 |
| 카카오 | 게이트 없음 | **그대로**(§3 참조) |

- `naver-api-usage.ts` — `NAVER_DAILY_TARGET_PCT=0.9` · `NAVER_DAILY_TARGET_CALLS=22,500` ·
  `noteNaverCall` 이 이제 **boolean 을 돌려준다**(false=쏘지 마라) · `armNaverDailyAllowance` ·
  `armNaverAndReadSettings`(레인이 원래 하던 설정 읽기에 얹어 **왕복 추가 0** 으로 장전).
- 래퍼 3곳(`fetch-with-err` · `contact-enrich` · `company-collect`)이 반환값을 본다.
- 장전: 인플루언서 레인 + **B2B 레인**. 쿼터는 앱 단위라 한쪽만 무장하면 다른 쪽이 그 위에 얹혀 넘긴다.
- `YT_SEARCH_BUDGET_DEFAULT = floor(10,000 × 0.9 / 100) = 90`. 100 으로 올리면 성과측정(1 unit)
  몫이 0 이 되어 하루 종일 403 (2026-07-27 실사고).

**기본값은 무제한(`allowance = null`)이다.** 무장을 잊은 레인이 *조용히 멈추는* 쪽보다,
*넘겨서 429 로 드러나는* 쪽이 낫다고 판단했다. 그 대가로 장전 한 줄이 사라지면 게이트가 **에러 없이
전면 무효**가 되므로, 그 경로를 주입 검증으로 막았다(아래).

## 3. 남은 것 — 대표 판단이 필요한 두 가지

### ~~① 카카오 일일 쿼터 숫자~~ → **해결됨(2026-08-05 대표 확인). 게이트는 안 만든다.**

대표가 개발자센터 쿼터 화면을 확인해 줬다. **전제가 하나 틀렸었다 — 카카오는 일간이 아니라 월간이다.**

```
월간 최대 제공량   3,000,000   ([open][무료 API Total] 기본앱, 앱당 월쿼터 300만)
월간 사용량            3,548   ← 0.12%
```

⚠️ **"무료 API Total" = 앱의 모든 카카오 API 가 공유하는 풀**이다(로컬 검색 + 지도 + 좌표변환 +
소비자 지도 프록시 전부 합쳐 3,548). 로컬 전용 한도가 따로 있는 게 아니다.

**⇒ 게이트를 만들지 않기로 했다.** 90% = 월 270만인데 실사용이 월 3,548 이라 **도달 가능성이 없고**,
게이트는 회차마다 D1 읽기를 하나 더 쓴다 — **막을 일이 없는 것을 막느라 가장 희소한 예산을 쓴다.**
네이버(게이트 부재)·유튜브(검색 100회면 쿼터 소진)와는 성격이 다르다.
⚠️ 대표 지시 *"각각 90%"* 와는 어긋나는 판단이므로, 원하면 넣는다(해롭진 않고 값을 못 할 뿐).

**🔑 이 숫자가 확정한 더 중요한 사실**: 전화 캐기의 천장은 카카오가 아니다.
```
쿼터가 허용하는 속도   ≈ 100,000 조회/일  →  스윕 대상 148,297건을 **이틀**에 훑는다
실제 속도                    360 조회/일  →  **1년 넘게** 걸린다
```
그 **278배 차이는 전부 Cloudflare CPU** 다. 유료 전환은 발굴뿐 아니라 **이미 가진 15만 건에서
전화를 꺼내는 속도**도 같이 푼다 — 전환 이득을 계산할 때 이 몫을 빼먹지 말 것.

### ② (원문 보존) 공개 페이지 크롤 — **쿼터가 아예 없는 축**
연락처는 오픈API 가 아니라 이걸로 캔다:
```
rss.blog.naver.com/{handle}.xml     · m.blog.naver.com/{handle}  (브라우저 UA)
```
쿼터 0 · 계측 0 · 승인 0. 오늘 naver_blog 4,157건 측정 → **하루 4천~8천 요청**.
네이버 리드가 전체의 78%(39,833/51,345)라 차단당하면 연락처 수집의 주 경로가 멎는다.

🔴 **그런데 차단을 감지할 방법이 지금 없다** — `if (!res.ok) return ''` / `catch { return '' }` 라
429·403 이 "본문 없음"과 구별되지 않는다. 더 나쁜 건 그 0을 `suppressLowRotationYield` 가
**"이 키워드가 나쁘다"로 학습**해 억제한다는 것이다. 네이버가 막았을 뿐인데 멀쩡한 키워드가 영구히 꺼진다.
⇒ **유료 전환 전에** 이 축의 계측 + 별도 상한을 넣어야 한다(다음 세션 최우선).

# §5 — 공개 페이지 크롤 차단 감지 (같은 브랜치 후속)

## 5.1 실측 정정 — 크롤의 주 발생지는 발굴이 아니라 **측정 레인**이다

처음엔 `influencer-discovery.ts` 의 컨택 보충(키워드당 ≤8)을 주범으로 봤는데 틀렸다.
실제 볼륨은 `influencer-performance.ts` 의 네이버 성과 측정이다 — **리드당 RSS + 홈 2 fetch**,
하루 4,157건 측정이면 **약 8천 요청/일**. 쿼터도 승인도 계측도 없는 축이다.

## 5.2 진짜 위험은 "멎는 것"이 아니라 **잘못 배우는 것**

```
차단 → 본문 0 → (기존 코드는) perf_checked_at 스탬프 → nb_measured(수율의 분모) 상승
     → suppressLowRotationYield 가 "이 키워드가 나쁘다"로 학습 → 영구 억제
     → 억제되면 증거가 갱신되지 않아 **차단이 풀려도 안 돌아온다**
```
게다가 그 사이 백로그가 한 바퀴 통째로 소모된다.

## 5.3 무엇을 했나

- 신규 `naver-crawl-block.ts` — **429/403 만** 차단으로 세고, **연속 3회**에서 발동, 성공 1회로 해제,
  예외(타임아웃/DNS)는 연속을 늘리지도 지우지도 않는다. 일별 카운터를 `ads_naver_crawl_block` 에 기록.
  - ⚠️ 좁게 잡은 이유: *"느리다"는 "막혔다"가 아니다*(2026-07-29 `shouldNoindexMissingEntity` 와 같은 규칙).
    404/410 을 포함하면 **삭제된 블로그 세 개에 측정 레인이 통째로 멈춘다.**
- `influencer-performance.ts` — 두 fetch 의 상태를 기록하고, **차단이면 스탬프를 안 찍고 멈춘다**
  (NULL 로 남겨 다음 회차가 다시 집는다). 회차 말 `crawl_block` 스냅샷 + 일별 flush.
- `influencer-discovery.ts` — 같은 기록 + 컨택 보충 루프도 차단이면 중단.
- 가드: `naver-crawl-block.test.ts` 11개 + 주입 2건.

⚠️ **못 잡는 것**: 네이버가 **200 + 빈 페이지**로 주는 소프트 차단. 상태코드로 판정 불가라
**수율 급락**으로만 보인다 — 그래서 일별 카운터를 남겼다(사람이 볼 근거).

## 5.4 곁가지로 찾은 가드 버그 — `rules-version-ok` 가 처음부터 안 걸렸다

`check-rules-version-bump.mjs` 가 안내하는 유일한 예외 통로가 **동작하지 않았다**: 버전 상수를 집는
정규식이 `(\d+)` 에서 끝나 매치에 주석이 안 들어오는데, 예외 판정은 그 매치를 본다.
문서에만 있는 탈출구는 막다른 길의 세션을 **더 나쁜 선택**으로 민다. `.*$` 를 붙여 수리 +
`rules-version-exemption.test.ts` 4개 + 주입 1건.

**그리고 이 세션은 그 예외를 쓰지 않았다.** `REEXTRACT_RULES_VERSION` 을 2→3 으로 올렸다 —
예외 주석은 고위험 가드를 **영구히** 침묵시키는데, 재추출 한 바퀴는 D1 전용·커서 페이스라
외부 API 예산과 무관하기 때문이다. (남은 🟡 `CRAWL_RULES_VERSION` 은 low + 7일 폴백이라 방치.)
