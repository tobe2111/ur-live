# 2026-08-09 — B2B 수집 레인이 CPU 한도로 죽는다: 원인은 "낡은 보정값"

## 실측 (라이브 하트비트 · `cron_hb:*`)

2026-08-08 **23:00 KST** 한 회차에서 **셋이 동시에** 죽었다. 셋 다 **B2B** 다.

```
collect-hira       ms 21,067   err=Error detail=Worker exceeded CPU time limit
collect-commerce   ms 13,921   err=Error detail=Worker exceeded CPU time limit
collect-storeinfo  ms 13,833   err=Error detail=Worker exceeded CPU time limit
```

⚠️ **벽시계가 판별자가 아니다** — 같은 날 `collect-neis` 는 **24,218ms 에 성공**했다(found 3,000).
13.8초에 죽고 24.2초에 사는 것은 시간이 아니라 **CPU 밀도**가 다르기 때문이다.
`collect-commerce` 는 레코드마다 필드 전수를 정규식으로 훑는다(`anyEmail` 이 `Object.values` 전부,
`anyDomain` 이 `Object.entries` 전부) — 1,499건이면 수만 번이다. `neis` 는 벌크 삽입이라 I/O 지배적이다.

**CPU 위험 경고는 이미 6개 더 있다**(죽지 않았을 뿐 문턱): `collect-nara-contract` 25.4초 ·
`collect-neis` 24.2초 · `collect-localdata-chain` 22.4초 · `maintenance-rescan` 19.5초 ·
`collect-nps` 16.0초 · `maintenance?phase=reextract` 16.1초.

## 근본 원인 — 방어는 있었다. **보정값이 낡았다.**

`commerce-notify-collect.ts` 는 이미 마감선(`RUN_DEADLINE_MS`)과 레코드 상한(`MAX_RECORDS_PER_RUN`)을
갖고 있고, 소스 주석이 12초를 고른 근거를 명시한다 — *"죽는 지점(26초)의 절반 이하"*.

**그 전제가 더는 참이 아니다:**

```
마지막 성공 08-08 21:00 KST  elapsed_ms 13,935  stopped_by="deadline"  found 1,499
사망        08-08 23:00 KST  ms        13,921  CPU limit
```
사망점이 26초 → **13.9초**로 내려오면서 12초 마감선은 사망점의 **87%** 가 됐다 — 여유가 사실상 0.
그리고 마지막 성공 회차는 **마감선(12초)과 레코드 상한(1,500)에 동시에** 닿아 있었다. 둘 다 한계였다.

> 🔑 **왜 이런 낡음이 조용한가**: 워커는 CPU 시간을 안 준다. 그래서 마감선은 **CPU 의 대리 측정**이고,
> 대리값은 사망점이 움직이면 자동으로 낡는다. 게다가 **죽으면 루프 뒤 커서 저장이 안 돌아** 다음 회차가
> 같은 페이지를 또 훑는다(소스 주석의 *"영원히 전진 0"*) — 즉 **죽는 것은 느린 것보다 훨씬 나쁘다.**

## 실측 (08-09 07:00 KST, (b) 배포 후 첫 회차)

```
collect-commerce   ok  ms=16,509  found=500  page 357→358  elapsed_ms=12,013  stopped_by=deadline
                       total_saved 182,114 → 182,662 (+548)
collect-hira       ok  ms=14,284  found=100  page 69→71
collect-storeinfo  ok  ms=80,696  found=150  page 52→55        ← 80.7초인데 **살았다**
```

`found` 이 **499 → 500**. 안 늘었다. 그런데 이건 (b)가 실패한 게 아니라 **판정 기준이 틀렸다.**

## 왜 `found` 으로는 (b)를 볼 수 없나

`elapsed_ms=12,013` 인데 `RUN_DEADLINE_MS = 6,000` 이다. 루프는 **페이지를 받은 뒤** 마감선을 보므로,
한 페이지 fetch 가 ~10초 걸리면 **첫 페이지에서 무조건 끊긴다**. 즉 지금 `found` 은 CPU 와 무관하게
**항상 1페이지(≈500)** 에 고정돼 있다 — 레코드당 CPU 를 아무리 줄여도 여기엔 나타날 수가 없다.

## 🔑 그래서 드러난 더 큰 것 — **마감선은 CPU 가드가 아니었다**

워커에서 `Date.now()` 는 **I/O 에서만 흐른다**(CPU 구간엔 시계가 멈춘다). 그러므로
`elapsed_ms` 도 `ms` 도 **I/O 시간**이고, 마감선은 사실상 **"몇 페이지를 받을 것인가"** 를 정하는
*I/O 예산*이다. CPU 와의 관계는 간접적(페이지 수 → 레코드 수 → CPU)일 뿐이다.

이번 회차가 그걸 못 박는다: **`collect-storeinfo` 가 80,696ms 에 살아남았다**(13,833ms 에 죽었던 레인).
벽시계와 CPU 사망 사이에 **관계가 없다**는 증거다.

⇒ 내가 어제 "마감선 = CPU 의 대리 측정" 이라고 쓴 것도, 오늘 "found 으로 판정" 이라고 한 것도
  **같은 오해에서 나왔다.** 실제 역할은 이렇게 갈린다:
    · `RUN_DEADLINE_MS`      = **I/O 예산**(몇 페이지 받나 · 얼마나 기다리나). CPU 비용 ≈ 0
    · `MAX_RECORDS_PER_RUN`  = **진짜 CPU 가드**(몇 건을 파싱하나). ← 지금은 **한 번도 안 걸린다**(500 < 700)

## 다음 세션 첫 액션 — 두 상수의 역할을 분리한다

지금은 마감선이 레코드 상한의 일을 **엉성하게 대신**하고 있어서, 수확만 깎이고 CPU 는 그대로다.

1. `RUN_DEADLINE_MS` 를 **올린다**(I/O 예산이니 CPU 를 안 쓴다 — 페이지 fetch 를 기다릴 뿐).
   기준: 페이지 2장을 받을 만큼(현재 페이지당 ~10초 관측 ⇒ 22~24초). 값은 **관측 후** 정할 것.
2. **CPU 는 `MAX_RECORDS_PER_RUN` 으로만 묶는다.** (b)로 레코드당 비용이 줄었으니 이 값은
   **올릴 여지가 생겼다** — 다만 얼마나 줄었는지는 아직 못 쟀다(아래 참조).
3. ⚠️ 그 전에 **(b)의 효과를 실제로 재는 방법**을 정해야 한다. `found`·`ms`·`elapsed_ms` 는 전부 못 본다.
   유일하게 남은 관측: **같은 레코드 수에서 CPU 사망이 줄어드는가**(여러 회차 누적) — 즉 통계적으로만 보인다.
   ⇒ 단일 회차로 (b)를 판정하려 하지 말 것. 이번에 내가 그러려다 틀렸다.

# 후속 3 — **두 상수의 역할을 분리했다** (수확 회복)

`RUN_DEADLINE_MS` **6,000 → 20,000**. `MAX_RECORDS_PER_RUN` 은 **700 그대로**.

| 상수 | 실제 역할 | 왜 이 값 |
|---|---|---|
| `RUN_DEADLINE_MS` | **I/O 예산** (얼마나 기다리나) — CPU 비용 ≈ 0 | 페이지당 10~12초 실측 ⇒ 2페이지째를 받으려면 20초 |
| `MAX_RECORDS_PER_RUN` | **진짜 CPU 가드** (몇 건 파싱하나) | 죽던 회차 1,499건의 절반 아래 |

6초일 때 레코드 상한은 **한 번도 안 걸렸다**(500 < 700) — 마감선이 CPU 가드의 일을 엉성하게 대신하며
**수확만 깎고 있었다.** 20초면 2페이지째를 받고 그때 상한이 실제로 작동한다(500 → 1,000 에서 정지).
죽던 시절 1,499 보다 **여전히 33% 적은 CPU** 이고, 수확은 500 → ~1,000 으로 2배.

🛟 안전판: 페이지가 느린 회차(1장에 20초 초과)엔 자동으로 1페이지로 되돌아간다.

테스트도 새 모델로 바꿨다 — 마감선 천장을 **없애고**(그건 CPU 가드가 아니다) 대신
**"레코드 상한이 실제로 걸릴 만큼은 마감선을 줘야 한다"**(≥15초)를 강제한다. 안 그러면 CPU 가드가 죽은 코드다.
주입도 마감선 → **레코드 상한**으로 옮겼다(가짜 대상을 지키고 있었다).

- 기대: `found` **500 → ~1,000** · `stopped_by=records`(deadline 이 아니라) · `ok=true`
- ⚠️ `stopped_by` 가 여전히 `deadline` 이면 페이지가 20초보다 느린 것 — 마감선을 더 올릴지 판단
- ⚠️ `ok=false`(CPU 사망)가 나오면 **레코드 상한을 내린다**(마감선이 아니라). 그게 CPU 손잡이다


## ⚠️ 후속 3 정정 — **CI 가 내 오류를 잡았다**

위 "후속 3" 에서 나는 *"마감선은 I/O 예산이니 올려도 CPU 비용 ≈ 0"* 이라고 썼다. **틀렸다.**
기존 가드 `ads-cpu-deadline.test.ts`(08-02 신설)가 `RUN_DEADLINE_MS <= 13_000` 으로 막아 세웠고,
읽어 보니 **그 가드가 맞았다** — 마감선을 올리면 페이지가 한 장 더 들어오고 그만큼 파싱량 = CPU 가 는다.

정확한 문장은 이것이다:
> 마감선은 CPU 를 **간접적으로**(마감선 → 페이지 수 → 레코드 수 → CPU) 늘리고,
> `MAX_RECORDS_PER_RUN` 은 그 총량에 **직접** 천장을 씌운다.

그럼 왜 올려도 되나 — **그 가드가 쓰인 시점엔 상한이 1,500 이라 마감선이 유일한 제동이었다.**
지금은 700 이라 상한이 먼저 걸린다. 실효 상한은 이렇게 계산된다(상한은 페이지를 **받기 전에** 보므로 한 장 넘침):

```
실효 상한 = MAX_RECORDS_PER_RUN + PAGE_ROWS = 700 + 500 = 1,200  <  죽던 회차 1,499
```

⇒ 가드를 **시간 상한 → 실효 파싱량 상한**으로 다시 썼다. 마감선은 "살아 있고 유료 마감선을 넘지 않는다"만 본다.
   이러면 마감선을 얼마로 두든 CPU 천장은 유지되고, 수확만 회복된다.

   그 사이에 잘못된 보고가 대표에게 나갔다. *가드가 막아설 때는 덮어쓰기 전에 그 가드를 먼저 읽을 것* —
   이번엔 읽어서 내가 틀렸다는 걸 알았다.
