## 🛡️ 2026-07-29 — "한 번도 안 뛴 cron" 탐지 가드 (실사고 후 환원)

**사고**: `scheduled.ts` 는 10개 cron 식으로 분기하는데 라이브 `ur-live` Worker 엔 **3개만 등록**돼 있었다
(`0 18`·`0 19`·`*/5`). `payouts-generate`(**주간 정산 지급**)·`d1-backup`(**주간 백업**)·`toss-refund-retry` 가
**한 번도 안 돌았고 몇 달간 아무도 몰랐다** — 에러가 안 나기 때문이다.

**왜 기존 감시가 못 잡았나**: `getCronHealth` 는 하트비트 **기록이 있는** 작업만 순회한다. 한 번도 안 뛴
작업은 목록에 **아예 없어** 판정 대상에 들어가지도 않았다(실측: 그 상태에서 `missing: []` 반환).
⇒ **부재는 침묵과 다르게 생겼다.** 정적 기대 목록과 대조해야만 보인다.

**수정**: 신규 `worker/utils/cron-expected.ts`(순수) + `getCronHealth` 에 `never_fired` 추가.
- 기대 목록(정적, 코드) vs 실제 기록(런타임, 하트비트) 대조. **둘 다 있어야** 판정된다
- 목록을 `scheduled.ts` **밖**에 둔 이유: 그 파일은 번들 cron 게이트가 있는 머니 인접 파일이라
  관측용 상수로 건드리지 않는다. **드리프트는 테스트가 강제**(분기 파싱 ↔ 목록 집합 동일성)
- 🛡️ **오탐 방지가 핵심**: 주간 작업은 추적 7일이 지나야 판정한다. 창이 짧으면 **조용히 보류** —
  배포 직후 전건 빨강을 만들지 않는다. (조사 때 창이 4.7시간뿐이라 일간·주간을 보류한 절제가
  실제로 오진을 막았다 — `0 18`·`0 19` 는 등록돼 있었다.)
- `never_fired` 가 있으면 **`ok:false`**. 초록불인데 지급이 안 나가는 상태를 다시 만들지 않는다

**되돌려-검증 2종**(빨강 확인 후 복원): 목록에서 한 식 삭제(드리프트) → 빨강 / 오탐 방지 조건 제거 → 빨강.

### ⚠️ 이 가드가 **못** 막는 것 (주석에도 명시)
1. **대시보드의 실제 트리거 목록** — 레포가 못 읽는다. 판정은 *"코드가 기대하는데 기록이 0"* 까지고,
   원인 확정(미등록인가 / 등록됐는데 실패인가)은 사람이 대시보드를 봐야 한다.
2. 🔴 **바인딩 축** — 같은 사고에서 캐리어 Worker 바인딩이 **5개뿐**이라 `toss-refund-retry` 가
   `TOSS_SECRET_KEY` 없이 돌고, `cache-prewarm` 의 SSR KV 워밍이 `CACHE_KV` 부재로 전량 skip 되고 있었다.
   **그건 하트비트에 `ok:true` 로 남는다** — 이 가드가 못 본다. 별도 축이다.
