# 2026-11-11 [LOADING_ADDITIVE] 문서 사진 빠른 길 (`src/lib/image-compress.ts`)

- **대표 신고**: *"사진 올리는 속도 최적화 필요"* (가게 등록 `/store/biz-cert`, 카카오톡 인앱 브라우저).
- **무엇**: `encodeDocumentFast` 추가 — 브라우저 내장 기능으로 긴 변 2000px · WebP 0.8(못 만들면 JPEG 0.85)로 한 번에 다시 담는다. `compressForDocument` 가 이것을 먼저 타고, 실패·천장 초과면 종전 길(라이브러리)로 물러난다.
- **잠긴 항목은 그대로**: `browser-image-compression` 은 여전히 함수 안 dynamic import 다(빠른 길은 그것을 부르지 않는다 — 내려받는 것이 오히려 준다).
- **왜 느렸나**: ① 2MB 미만은 원본 그대로 올림 ② 2MB 이상은 라이브러리(~51KB)를 그때 내려받고 그 워커가 CDN 스크립트를 받으려다 CSP 에 막혀 메인 스레드로 물러남.
- **실측(폰 흉내 · CPU 4배, 잡음 많은 합성 문서 = 나쁜 쪽)**: 4000×3000 4.98MB → 0.61MB · 0.9초 / 1.88MB(종전엔 원본 그대로) → 0.61MB · 0.8초.
- **가독성**: 긴 변 2000px(2026-09-15 하한 그대로, 시험이 고정). 품질 0.8.
- **가드**: `doc-upload-fast-2026-11-11.test.ts` + 주입 4건.
- **롤백**: `compressForDocument` 의 빠른 길 한 줄 제거.
- **못 본 것**: 실제 폰·인앱 브라우저에서의 체감(로그인·사업자 화면이라 세션이 못 연다 — 대표 폰 확인 필요), 어드민이 읽기 좋은지.

## 후속 (같은 날) — 일반 사진·세 크기 올리기까지
- 대표 *"유사한 부분들로 최적화 할 것들 더 확인해봐"*. 올리는 자리 전수(24곳)를 보니 전부 `compressForUpload` 한 곳을 거친다.
- **`compressForUpload` 도 빠른 길(`encodeFast`) 먼저** — 되면 라이브러리 청크(~51KB)와 그 워커가 **부를 때마다 받는 외부 CDN(jsdelivr) 스크립트**를 건너뛴다. 결과가 목표 크기를 넘거나 실패하면 종전 길. GIF·SVG 는 빠른 길이 안 받는다(첫 장면만 남는다).
- **`uploadSizedImage`**: 세 크기를 차례로 올리던 것 → 첫 장(1280)으로 묶음 이름을 받고 나머지 둘은 동시에.
- 🩸 **정정**: 위에 "그 워커가 CDN 스크립트를 받으려다 CSP 에 막힌다" 고 적었는데 **틀렸다.** 라이브(`/faq` 에 묶음을 넣어 실행)에서 재 보니 막히지 않고 실제로 받아 온다(압축 2회에 요청 2번). 추측으로 적지 말 것.
- 실측(폰 흉내 · CPU 4배, 4MB 합성 사진): 새 길 0.5초(메인 스레드) vs 라이브러리 0.3초(워커) — **계산은 빨라지지 않는다.** 줄어드는 것은 내려받기(청크 + 외부 CDN 왕복)와 외부 의존이다.
- 잠긴 항목(`browser-image-compression` 함수 안 dynamic import)은 그대로다.
