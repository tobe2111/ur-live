## 0. 분류 기준 (이걸 먼저 고정한다)

**오픈 차단**은 "중요한 것"이 아니라 **아래 셋 중 하나에 해당하는 것**이다:

| | 기준 | 왜 |
|---|---|---|
| **A** | 없으면 **돈이 잘못 움직인다** | 되돌리는 비용이 파일럿 이득보다 크다 |
| **B** | 없으면 **되돌릴 수 없는 것이 남는다** | 배포로 못 지운다(색인·법적 고지·평문 저장) |
| **C** | 없으면 **경로를 완주할 수 없다** | 파일럿이 검증하려던 것 자체가 성립 안 함 |

**오픈 후 처리 가능**은 *"덜 중요하다"* 가 아니라 **"그 사이 손실이 축적되지 않거나 자가치유된다"** 는 뜻이다.
⇒ 각 항목의 근거 한 줄은 **A/B/C 중 무엇에 걸리는지 또는 왜 안 걸리는지**를 적는다.

> ⚠️ 파일럿 규모(매장 1~3, 주문 소량)를 전제로 한다. **규모가 커지면 아래 여러 항목이 오른쪽 →
> 왼쪽으로 이동한다**(특히 알림·문의·반품 입구). 규모 전제가 바뀌면 이 표를 다시 그릴 것.

## 3. 판정 ① — `INTERNAL_API_TOKEN`: **오픈 후 처리 가능** (조사 완료)

**결론: 무방비 엔드포인트는 0건이다. 반대로 잠겨 있다.**

전수 조사한 소비처 4곳이 **전부 동일한 fail-closed 패턴**이다:

```ts
if (!opsToken || opsToken !== reqToken) return c.json({ success:false, error:'Forbidden' }, 403)
//  ^^^^^^^^^ env 미설정이면 여기서 곧바로 403 — 열리는 게 아니라 닫힌다
```

| 엔드포인트 | 파일 | 미설정 시 |
|---|---|---|
| `POST /api/_internal/clear-rate-limit` | `internal-admin-tools.routes.ts:70` | 403 |
| `POST /api/_internal/reset-admin-password` | `internal-admin-tools.routes.ts:87` | 403 |
| `GET /api/moderation/stats` | `moderation.routes.ts:64` | 403(+ 상위 인증 401) |
| `POST /api/referral-tree/calculate-commission` | `referral-tree.routes.ts:613` | 403 |

**라이브 실측(2026-07-29 10:48 UTC)** — 토큰 없이 호출(가드가 DB 접근 앞이라 부수효과 0):
```
POST /api/_internal/clear-rate-limit  →  403 {"success":false,"error":"Forbidden"}
GET  /api/moderation/stats            →  401 (상위 인증에서 먼저 차단)
```

> ⚠️ **`env-readiness` 의 분류가 오해를 만든다.** 이 키는 `security` 그룹에 있고 그 그룹 설명이
> *"보안 — fail-open(동작하나 약화)"* 다. **이 키만은 fail-closed 다.** 제가 처음 감사에서
> *"미설정이면 fail-open"* 이라고 적은 것은 그 그룹 라벨을 그대로 읽은 것이고 **틀렸다.**
> ⇒ 후속 작업: `health.routes.ts` 의 이 항목 note 에 *"미설정 시 fail-closed(복구 경로 잠김)"* 로 정정.

**그래서 실제 리스크는 보안이 아니라 가용성이다**: 어드민 비밀번호 초기화·rate-limit 해제 같은
**복구 레버가 잠겨 있다.** 파일럿 중 대표가 어드민에서 잠기면 이 경로를 못 쓴다.
다만 ① 지금도 어드민 로그인은 정상 동작하고 ② 별도 `BOOTSTRAP_TOKEN` 경로가 있으며
③ 키 등록은 언제든 5분이면 된다 ⇒ **오픈을 막을 이유가 없다.**

> 💡 `DATA_ENCRYPTION_KEY`(B5) 와 **같은 작업**에서 함께 등록하면 비용이 사실상 0 이다.

## 4. 판정 ② — `0 18` 결측: **오픈 후 처리 가능** (단 관측 유지)

**결론: 결측은 지연이지 손실이 아니다.** 그 블록의 머니 작업이 전부 **누적·멱등** 술어를 쓴다.

| 작업 | 대상 선정 | 하루 걸러도 |
|---|---|---|
| `supplier-settlement-mature` | `status='pending' AND available_at <= now` | 다음 회차에 그대로 잡힘 |
| `auto-settlement` | `used_at < cutoff AND settlement_id IS NULL` | 같음 |
| `affiliate-mature` / `referral-mature` | hold 기간 경과분 전체 | 같음 |
| `expired-voucher-refund` | `status='unused' AND expires_at < now` | 같음(+CAS 로 이중환불 차단) |

**"어제 하루치만" 처리하는 작업이 없다.** 그래서 결측일의 대상은 다음 발화 때 함께 처리된다 — **누락이 아니라 24h 지연.**

**원인은 아직 미규명이고, 여기서 추측하지 않는다.** 확인된 사실만:
- 등록은 돼 있다(5일치 실행 흔적).
- 두 결측일(07-25·27)에 **다른 신호가 없다** — 그날 실패 기록도, 다른 블록 이상도 없다.
- 하트비트 저장은 07-29 배포라 **그 시점 관측 데이터가 존재하지 않는다.**

> ⇒ **관측이 먼저다.** 지금 원인을 파는 것은 데이터 없이 추측하는 일이고, 이 레포가 반복해 실패한 방식이다.
> 하트비트가 이제 매 실행을 기록하므로 **다음 결측이 나면 그때는 증거가 남는다.**

**단 두 가지는 오픈 후에도 계속 본다**:
1. **주 2회 이상 결측이면 격상** — 지연이 누적되면 정산 주기 약속(주간)이 깨진다.
2. **`payouts-generate`(주 1회)는 결측 비용이 다르다** — 하루가 아니라 **일주일** 밀린다.
   L3·L4 와 함께 **첫 지급 사이클 전**에 트리거 상태를 확정할 것.
