## 0. 먼저 — 내가 틀렸던 추정 하나

대표 질문에 처음 답할 때 나는 *"진짜 벽은 인증 축이다. 셀러 API 28개 모듈이 별도 JWT 를 요구하고
소비자 프로필은 세션 쿠키로 도니까, 그 28개를 다 고쳐야 한다"* 고 말했다. **측정해 보니 틀렸다.**

다리는 **이미 놓여 있고 라이브에서 돌고 있다**:

```
resolveActorUserId(c)            ← 소비자 세션 쿠키를 직접 읽는다 (seller-operators.routes.ts)
  → canOperateStore(DB, userId, sellerId)   ← owner(linked_user_id) 또는 operator(seller_operators)
    → POST /api/seller/stores/:sellerId/token  ← 그 좌석의 셀러 JWT 를 발급
GET /api/seller/my-stores        ← 소비자 세션만으로 내 좌석 목록
```

즉 **"소비자로 로그인한 사람이 자기 매장 좌석을 열 수 있는가"는 이미 해결돼 있다.**
남은 것은 인증이 아니라 **표면**이다 — 그 좌석으로 하는 일이 전부 별도 셸(`/seller/*`,
자체 레이아웃·자체 테마·자체 네비) 안에 있다는 것.

⚠️ **다음 세션은 이 절을 먼저 읽을 것.** "인증부터 고쳐야 한다" 로 시작하면 이미 있는 것을 다시 짓는다.

## 1. 실측 (2026-09-25)

### 1-1. 셀러 대시보드 전체

| | |
|---|---|
| `/seller/*` 라우트 | **68개** |
| 셀러 전용 코드 | **32,359줄** |
| `seller_token` 을 만지는 파일 | 138개 |
| `requireSeller()` 호출 지점 | 38곳 — **전부 `requireUserType('seller')` 한 함수로 수렴** |
| `getSellerIdFromToken()` 호출 지점 | 82곳 — **정의는 `lib/seller-shared.ts` 한 곳** |

### 1-2. 핵심 넷 (= 이미 확정된 다섯 대분류에서 '더보기' 를 뺀 것)

`seller-primary-nav.ts`(2026-09-14 대표 승인)가 이미 답을 갖고 있다 —
*"셀러가 하는 일은 넷뿐이다. 주문을 받고, 이용권을 만들어 팔고, 돈을 받는다(+ 그 셋이 모이는 홈)."*

| 탭 | 라우트 | 파일 | 줄 | API |
|---|---|---|---|---|
| 홈 | 1 | 1 | 107 | 0 (부품이 각자 호출) |
| 주문 | 5 | 13 | 2,222 | 16 |
| 이용권 | 9 | 20 | 3,656 | 21 |
| 정산 | 7 | 20 | 3,075 | 26 |
| **합** | **22** | **54** | **9,060** | **63** (그중 `/api/seller/*` 50) |

⇒ 핵심 넷은 셀러 코드의 **28%**. 나머지 72%(파트너·할인·매장·알림·도매·유어애즈 연동 등)는 이번 범위 밖.

### 1-3. 라이브 (D1 직접 조회)

```
sellers(도매 제외)     11곳 · 승인 9 · linked_user_id 있는 곳  1
seller_operators        9행 / 4명       ← 다중 매장이 이미 현실
                        user 35 = 5좌석 · user 3 = 2좌석
```

**두 가지가 여기서 결정된다:**
- **좌석 전환은 미룰 수 없다.** 4명 중 2명이 이미 여러 매장에 앉아 있다.
- **소유(`linked_user_id`)가 아니라 운영(`seller_operators`)이 실제 경로다.** 오늘 owner 로 연결된 건
  11곳 중 1곳뿐이고, `switch-to-seller` 는 `linked_user_id` 로만 찾는다 — 즉 **그 경로로는 4명의 9좌석이
  보이지 않는다.** 소비자 앱에서 좌석을 그릴 땐 반드시 `GET /my-stores`(= `canOperateStore` 기준)를 쓴다.

### 1-4. 테마

핵심 넷 파일에 `dark:` 가 **사실상 0개**다(orders 0 / group-buy 0 / analytics 0 / settlements 1).
셀러 대시보드는 라이트 고정이고 `check-dashboard-theme.sh` 가 `dark:` 추가를 **차단**한다.
소비자 앱은 다크를 지원한다. ⇒ **코드를 그대로 옮기면 그 순간 테마가 깨지거나 가드가 막는다.**

## 2. 결정 — 옮기는 게 아니라 다시 짓는다

9,060줄을 소비자 앱으로 **이식하지 않는다.** 세 가지 이유:

1. **치수가 다르다.** 셀러 화면은 PC 밀도 기준(사이드바 224px, 표, 다열 필터)으로 만들어졌고
   소비자 앱은 폰 우선 430px 액자다. 옮겨도 안 맞는다.
2. **테마가 다르다**(§1-4). 이식은 곧 9천 줄에 `dark:` 를 붙이는 일이고, 그건 가드가 막는 방향이다.
3. **필요 없다.** 사장님이 폰으로 하는 일과 앉아서 하는 일은 다르다.

### 경계 — 이 한 줄이 이 설계의 전부다

> **폰에서 한 손으로 하는 일 = 소비자 앱 / 앉아서 하는 일 = 셀러 대시보드.**

| 소비자 앱 안(신규) | 셀러 대시보드에 남김(무수정) |
|---|---|
| 오늘 주문 보기 · 상태 바꾸기 | 주문 표·기간 필터·대량 처리·엑셀 |
| 이용권 QR 사용처리 | 이용권 등록 위저드 전체 단계·사진 편집 |
| 이용권 켜기/끄기·재고 | 매출 분석 차트·promo 지출 표 |
| 정산 잔액·출금 신청 | 원장·회차별 명세·세금 |
| 할 일(승인 대기·후기 인증 N건) | 파트너·할인·매장·알림·도매·유어애즈 |

⚠️ **소비자 앱 화면에는 "전체 관리 도구 →" 가 항상 있다.** 막다른 골목을 만들지 않는다
(`linkshop-role-model.md` 의 "+ 담기가 항상 어딘가 노출돼야 한다" 와 같은 원칙).

## 3. 어디에 두나 — 마이(`/u/me` 계열)이지 유어샵이 아니다

대표가 말한 "프로필 페이지" 는 둘일 수 있다. **마이가 맞다.**

| | 유어샵 `/u/{handle}` | 마이 `/user/profile` |
|---|---|---|
| 누가 보나 | **손님** | **나만** |
| 성격 | 진열대 | 내 서랍 |
| 판매 관리를 두면 | 손님 화면과 섞인다 | 자연스럽다 |

그리고 §5.5 소유권 단일화(CI 가드)는 유어샵의 소유자 판정을 **"뷰/편집"** 만 가르도록 못 박아 뒀다.
거기에 주문·정산까지 얹으면 그 불변식이 흐려진다.
⇒ **유어샵은 "내 가게 보기" 한 줄 링크로만 등장한다.**

### 라우트

```
/user/profile          마이 (기존)
  └ 판매 카드          ← 좌석이 있으면 뜬다 (오늘 주문 N · 정산 예정 ₩N · 할 일 N)
/sell                  판매 홈        ← 신규, 소비자 셸 안
/sell/orders           주문
/sell/vouchers         이용권
/sell/money            정산
```

- `/seller/*` 는 **그대로 살려 둔다.** 301 하지 않는다 — 40여 개 운영 도구가 거기 있고,
  이미 공유·북마크된 URL 이다.
- `/sell/*` 에서 깊은 작업으로 갈 땐 `/seller/*` 로 넘긴다(같은 좌석 토큰이라 재로그인 없음).

## 4. 좌석 (다중 매장)

이미 API 가 있다. **화면만 만든다.**

```
진입      GET  /api/seller/my-stores        (소비자 세션만으로)
전환      POST /api/seller/stores/:id/token (canOperateStore 통과 시 그 좌석 JWT)
```

- 좌석이 **1개면 전환 UI 를 안 그린다**(기존 `StoreSwitcher` 규칙 승계). 2개 이상일 때만.
- 좌석 이름은 헤더에 **항상** 보인다 — 어느 매장으로 행동 중인지 모르는 순간이 없어야 한다.
  (지금 대시보드의 문제: 폰에서 전환 UI 가 헤더 구석 드롭다운이라 안 보인다 —
  `seller-dashboard-2nd-directions-2026-09.md` 가 이미 지적.)
- **승인 대기·반려 좌석도 들어간다**(2026-09-20 당근 규칙 `isSeatableStoreStatus`). 정지만 막는다.
  배너가 이유를 말한다.

### 🔴 좌석과 돈

좌석을 잘못 고르면 **남의 매장 정산을 본다.** 그래서:
- 좌석 판정은 `canOperateStore` **한 곳**만 쓴다. 화면이 `seller_id` 를 지어내지 않는다.
- 출금·정산 화면은 좌석 이름을 **그 화면 안에** 다시 표시한다(헤더만 믿지 않는다).
- 정산 실행(송금)은 이 범위 밖 — `payouts-generate` 의 기존 게이트 그대로.

## 5. 테마

소비자 앱 안이므로 **다크를 지원한다.** `light-island` 로 흰 섬을 만들지 않는다 —
그건 지도 타일·토스 위젯처럼 *우리가 색을 못 정하는* 자리에 쓰는 장치이고, 여기는 우리 화면이다.

신규 화면은 처음부터 코레일톡 디자인 시스템으로 짓는다(`ticket-completion-reference-2026-09.md`):

- 숫자가 주인공 · 아이콘은 `urdeal-icons`(선/면) · 이모지 0 · 색깔 정보상자 0
- `TicketCard` 재사용

## 8. 이 설계가 **하지 않는** 것

- 셀러 대시보드를 삭제하지 않는다. 40여 개 운영 도구는 거기 그대로다.
- 9,060줄을 이식하지 않는다(§2).
- `/seller/*` URL 을 바꾸지 않는다.
- 인증 축을 재작성하지 않는다 — 이미 있다(§0).
- **정산 송금 게이트를 건드리지 않는다.** `payouts-generate`·`isPayoutEligibleSellerStatus` 무접촉.
- 유어샵(`/u/{handle}`)의 소유권 모델을 건드리지 않는다.

## 9. 대표 확정 (2026-09-25)

> *"정산까지도 다 해주고, 주인 연결도 같이 가줘"*

둘 다 **범위 안**이다. 그리고 재 보니 **둘 다 이미 만들어져 있다** — 이 작업의 일은
기능을 짓는 게 아니라 **소비자 앱 안에 자리를 만드는 것**이다.

### 9-1. 정산 — 화면이 돈을 옮기지 않는다

| 이미 있는 것 | |
|---|---|
| `GET /api/seller/account/withdraw-check` | 출금 가능 여부·사유 |
| `POST /api/seller/account/withdraw` | 출금 신청(레이트리밋 5회/시간) |
| `payouts-generate` cron | **실제 송금** — `isPayoutEligibleSellerStatus`(승인된 매장만) |
| `payout_requires_voucher_use` | 사용 확인 게이트(대표가 켠다) |

**소비자 앱이 하는 일은 그 앞의 손잡이뿐이다**: 받을 돈을 보여 주고, 출금 신청을 부른다.
🔴 **금액을 화면이 계산하지 않는다** — 서버가 준 값을 그대로 그린다.
🔴 **정산 화면은 매장 이름을 카드 안에 한 번 더 적는다** — 헤더만 믿고 남의 매장 돈을 보면 안 된다.
🔴 게이트(`payouts-generate`·`isPayoutEligibleSellerStatus`·`payout_requires_voucher_use`)는 **무접촉**.
⚠️ 그래도 **머니 경로**다 — 단독 세션 + staging.

### 9-2. 주인 연결 — 문이 없는 게 문제였다

| 이미 있는 것 | |
|---|---|
| `store-codes.ts` (`kind='owner_claim'`) | 대행 등록 시 코드 발급. **사장님이** 입력한다(반대 방향이면 코드 유출 = 남의 매장 탈취) |
| `GET /stores/lookup-by-business` | 사업자번호로 찾기. **매장 공개 정보만** 준다(지금 주인이 누구인지는 안 알려준다) |
| `POST /store-claims` | 사업자등록증 첨부해 신청 — **항상 심사 대기** |
| `GET /store-claims/mine` · `/store-claims/lookup-by-code` | 내 신청 상태 · 코드 조회 |
| `/store/find` (`StoreOwnerClaimPage`) | 사장님 화면 |
| `AdminStoreOwnerPage` | 어드민 심사 |

**자동 승인은 없고 앞으로도 없다.** 사업자번호는 인터넷에 공개돼 있어 **번호 일치는 증명이 아니다**
(2026-08-26 에 번호만으로 자동 승인되던 경로를 이미 한 번 막았고, 그때 통과한 매장이 라이브에 남아 있다).

⇒ 이 작업이 더할 것: **마이/좌석 목록에서 `/store/find` 로 가는 길**과, 운영자로만 앉은 매장 행에
*"주인 없음 — 사장님께 코드 전달"* 을 띄우는 것. 기능은 안 짓는다.

### 9-3. 갱신된 단계

| 단계 | 내용 | 머니 경로 |
|---|---|---|
| **1** | 마이에 **판매 카드**(좌석 요약 + 딥링크) | 없음 |
| **2** | `/sell` **판매 홈** + 좌석 전환 + **주인 없음 배지 → `/store/find`** | 없음 |
| **3** | `/sell/orders` **주문** | 없음 |

주인 연결은 **단계 2에 얹는다** — 좌석 목록이 이미 `owner_claim_code` 를 내려주고 있어서,

## 10. 1차 시안을 그리다 잡은 결함 — 6자리 금액 × 3열은 430px 에 안 들어간다

판매 홈의 '이번 주' 를 처음엔 `[매출 | 수수료 | 받을 돈]` **3열 균등**으로 그렸다. 렌더해 보니
`1,240,00062,0001,178,000` 으로 **붙어 버렸다** — 6자리 금액 셋이 430px 안에서 각 130px 를 나눠 갖는데
23px 숫자로는 못 들어간다.

이 레포가 이미 같은 클래스를 겪었다: 2026-08-31 홈 카드에서 *"6자리 가격(숙소 119,000원)에서 할인 pill 이
다음 줄로 밀려 그 카드만 높이가 늘어나는"* 것. 그때의 처방과 같게 간다 — **한 줄에 욱여넣지 말고 줄로 나눈다.**

```
이번 주 받을 돈              정산 →
1,178,000원                        ← 26px, 하나만 크게
매출 1,240,000 − 수수료 62,000 (5%)  ← 12px 보조 줄
```

⚠️ **구현 규칙**: 판매 모드에서 **금액 3개를 한 행에 균등 배치하지 않는다.** 3열 grid 는
*개수*(주문 8 · 사용 5 · 판매중 2)에만 쓴다. 금액은 하나를 크게 + 나머지는 보조 줄로.
(오늘 사용 카드의 `5 / 31 / 2` 는 개수라 3열이 맞다 — 시안이 둘을 나란히 보여 준다.)

### 1차 시안에서 내가 어긴 것 (자기비판)

- **강조색 자리가 여덟이었다.** 규칙은 「강조색 하나, **자리 셋**」인데 밴드·버튼·배지·숫자·아이콘
  배경·체크·탭·칩까지 전부 파랬다. **파란 게 많으면 아무것도 안 강조된다.**
- **판매 홈에 주인공이 없었다.** 같은 무게의 카드 4장을 세로로 쌓아 시선이 어디에도 안 머문다.

- **소비자 앱 같지 않았다.** 유어딜 문법(티켓·브랜드 점)이 안 살고 작은 대시보드로 보인다.

### 세 방향 — 갈리는 축은 "무엇이 주인공인가"

| | 주인공 | 성격 | 대가 |
|---|---|---|---|
| **A 오늘 한 장** | **숫자** | 큰 금액 하나 + 테두리 없는 조용한 줄. 강조색은 밴드에만 | 할 일이 눈에 덜 띈다 |
| **B 티켓 지갑 뒤집기** | **파는 물건** | 손님 지갑의 티켓을 사장님 쪽에서 뒤집어 본다(절취선 왼쪽 = 오늘 몇 장). 새로 배울 그림 0 | 돈 숫자가 작아진다 |
| **C 할 일 큐** | **처리할 것** | 화면 전체가 대기 줄. 할 일 없으면 "오늘 할 일 없어요" 한 장 | 숫자 보러 온 사람에겐 한 단계 멀다 |

셋 다 구조(마이 → 판매 · 좌석 전환 · 전체 도구로 넘기기)와 §9 의 정산·주인 연결은 같다.
**화면이 무엇을 먼저 보여주는지**만 다르다.

### 🩸 3안 시안이 또 하나 잡았다 — 다크에서 안 보이는 라벨

`안 A/B/C` 태그를 `background: var(--ink); color: #fff` 로 그렸는데, 다크에서 `--ink` 는
`#F5F3F1`(거의 흰색)이라 **흰 면 위 흰 글자**가 됐다. `check-dark-contrast` 가드가 존재하는
바로 그 클래스다. ⇒ **면 색이 토큰이면 글자도 토큰으로**(`--pagefg` 면에는 `--page` 글자).
`#fff` 를 박는 순간 한쪽 테마가 깨진다.

## 13. ⭐ 추천안 — “보는 건 마이에서 다, 하는 건 들어가서” (2026-09-25)

### 형태 = 1, 단 **마이에서 보이는 양을 최대로**

마이의 판매 카드가 요약 한 줄이 아니라 **오늘 매출 + 확인할 주문 + 후기 인증 + 받을 돈**까지
전부 보여준다. 누르는 건 **손을 댈 때**뿐이다.

### 🔑 탭바를 바꾸지 않는다 — 이게 "별도 대시보드" 느낌을 없애는 핵심

판매 화면(`/sell/*`)에서도 하단은 **홈·교환권·이용권·유어샵·마이** 그대로이고 **마이가 켜져 있다.**
판매 안 이동(오늘·주문·이용권·정산)은 **상단 알약 세그먼트**가 맡는다.
⇒ 사용자는 "다른 앱에 갔다" 가 아니라 **"마이 안쪽에 있다"** 고 느낀다.
그리고 언제든 홈·교환권으로 한 번에 나갈 수 있다(막다른 골목 0).

⚠️ **셀러 전용 하단 탭(판매홈/주문/이용권/정산)을 만들지 말 것** — 1차·3안 시안이 그렇게 그렸고,
그 순간 소비자 앱이 아니라 축소된 대시보드가 된다.

### 문법 = 화면마다 그 화면의 주인공을 따른다

하나(A만·B만·C만)를 세 화면에 강제하는 게 애초에 무리였다.

| 화면 | 문법 | 왜 |
|---|---|---|
| 마이 판매 카드 | **A 숫자** | 바로 아래 `내 딜 잔액 10,300딜` 카드가 이미 A 문법이다. 이웃한 두 카드가 다른 문법이면 그 자리가 어긋나 보인다 |
| 판매 홈 · 주문 | **C 할 일** | 이 화면을 여는 이유는 처리할 게 있어서다. 매출은 맨 위 한 줄로 |
| 이용권 | **B 티켓** | 손님 지갑과 같은 그림을 사장님 쪽에서 뒤집어 본다. 새로 배울 게 없다 |
| 정산 | **A 숫자** | 받을 돈 하나를 보러 오는 화면 |

### 강조색 — 하나, 자리 셋

① 티켓 밴드 ② 지금 눌러야 하는 버튼 ③ 처리 대기 숫자. **그 외는 전부 회색.**
(1차 시안은 여덟 자리였다 — §11.)

### 주인 연결은 좌석 시트 안에서 보인다

운영자로만 앉은 가게 행에 **`사장님 미연결` + 줄 코드**가 그대로 뜬다
(`GET /my-stores` 가 이미 `owner_claim_code` 를 내려준다). 사장님은 `/store/find` 에서 그 코드를 넣고
사업자등록증을 올린다 — **자동 승인은 없다.**

### 조건부 렌더 (신규 UI 를 아무에게나 보이지 않는다)

- **셀러가 아니면** 마이에 판매 카드가 **없다** — 지금의 `내 가게 등록` 칩 그대로.
- **가게가 1곳이면** 좌석 줄·전환 시트를 **안 그린다**.
- **승인 대기·반려**도 들어간다(2026-09-20 당근 규칙). 정지만 막는다.

## 15. 착수 전에 박아 두는 세 가지 (2026-09-25 — 저장 모델 실측 + 결함 2건)

대표 *"지금 형태가 가장 이상적인 형태야?"* → 실측으로 답하다 나온 것들이다.
**접근 모델(권한)은 이상적이고, 저장 모델은 아니다.** 그리고 단계 1 이 반드시 막아야 할
결함이 둘 드러났다. 셋 다 여기 적어 둔다 — 다음 세션이 같은 자리를 다시 파지 않게.

### 15-1. 저장 모델 — 이상적이지 않다. 그래도 **지금 고칠 일은 아니다**

라이브 실측(2026-09-25):

| | 값 | 뜻 |
|---|---|---|
| `sellers` 컬럼 수 | **100 / 100** | D1 결과셋 한도에 **정확히 닿았다**. 새 컬럼 0칸 |
| `sellers` 행 | 11 중 **10이 매장** | 이 표는 이미 "사람"이 아니라 "가게" 표다 |
| 그중 가짜 이메일 | **9** | 사람이 없는 행에 `email` 이 NOT NULL·UNIQUE 라 만들어 넣는다 |
| `seller_meta` | 키 21종 · **111행** | 컬럼을 더 못 만들어 옆으로 밀어낸 것들 |

**이 어긋남이 실제로 두 번 터졌다**:
- 2026-09-02 — `sellers.email` UNIQUE 때문에 **두 번째 매장 등록이 100% 실패**했다.
- 2026-09-20 — 사업자등록증이 `seller_meta` 에만 들어가 **어드민이 못 봤다**(승인 화면이 컬럼만 읽었다).

이상적인 모양은 `stores`(가게) / `sellers`(사람·정산 주체) 분리다. **하지만 지금 하지 않는다** —
`seller_id` 가 주문·원장·정산·커미션·payout·토큰 **모든 머니 경로**에 박혀 있어서, 쪼개는 순간
그 전부가 동시에 움직인다. 등급 C 를 여러 개 한 번에 여는 일이고, 이 작업(화면)과 섞을 수 없다.

⇒ **지금 하는 판단**: 저장 모델은 **건드리지 않는다.** 대신 아래 두 가지만 고친다(싸고, 지금 아프다).

### 15-2. `linked_user_id` ↔ `seller_operators` — 길이 둘이라 9좌석이 안 보인다

좌석을 판정하는 길이 **둘**이다:

| 길 | 판정 | 한계 |
|---|---|---|
| `POST /switch-to-seller` | `sellers.linked_user_id = 내 user_id` **한 행** | `linked_user_id` 는 **UNIQUE(1인 1행)** |
| `GET /my-stores` | `canOperateStore` = 소유(link) **∪** 위임(`seller_operators`) | 전부 본다 |

그런데 `POST /store/new` 는 설계상 **`linked_user_id` 를 비워 두고** 권한을 `seller_operators`
로만 준다(1인 1행 제약 때문). ⇒ **`switch-to-seller` 는 그렇게 만들어진 좌석을 한 개도 못 본다.**
라이브에 그런 좌석이 **9개** 있다. 화면이 옛 길을 쓰면 사장님은 자기 가게가 없다고 듣는다.

🔴 **규칙 — 단계 1 이후 판매 화면의 좌석 출처는 `GET /my-stores` 하나다.**
`switch-to-seller` 는 *옛 단일 좌석용 호환 경로*로만 남긴다(새 화면에서 호출 금지).
`SellerSwitchInline` 의 `handleSwitch` 도 이번에 `/my-stores` → `POST /stores/:id/token` 으로 옮긴다.

### 15-3. 🔴 좌석 토큰 ↔ 인라인 작업 충돌 — **단계 1 에서 반드시 막는다**

좌석 토큰은 **JWT 안에 `seller_id` 가 박혀 있다**(`payload.seller_id`). 즉 **가게를 바꾸면
토큰이 통째로 바뀐다.** §14 는 작업을 마이 안에서 인라인으로 하기로 했으므로 이런 순간이 생긴다:

```
가게 A 의 주문 목록을 펼쳐 둔 채  →  [가게 전환] 으로 B 선택(토큰 교체)
                                →  아직 화면에 남아 있는 A 의 주문 행에서 [확인]
                                →  B 의 토큰으로 A 의 주문 id 를 보낸다
```

서버는 토큰의 `seller_id` 로 스코프하므로 **남의 주문을 확정하진 않는다**(그건 막힌다).
문제는 그 반대다 — **사장님이 A 를 처리했다고 믿는데 아무 일도 안 일어나거나**, 더 나쁘게는
id 가 겹치는 자원에서 **B 의 무언가가 움직인다.** 지금까지는 가게를 바꾸면 페이지가 통째로
갈아엎여서(대시보드 이동) 이 틈이 없었다. 인라인으로 옮기는 순간 생긴다.

🔴 **단계 1 에서 세우는 규칙 세 줄**:
1. **가게를 바꾸면 열린 시트를 전부 닫고 목록을 다시 불러온다.** 예외 없다.
2. **모든 판매 요청은 자기가 어느 `seller_id` 로 보내는지 안다** — 화면이 들고 있던
   `seller_id` 와 지금 토큰의 `seller_id` 가 다르면 **보내지 않고** 다시 불러온다.
3. **판매 화면은 `seller_id` 를 URL·localStorage 에서 읽어 API 로 넘기지 않는다.**
   권한 근거는 토큰 하나다(경로의 sellerId 는 '요청'일 뿐 — `stores/:id/token` 주석과 같은 규약).

가드 계획: 단계 1 에 `seller-inline-seat-*.test.ts` — ① 전환 핸들러가 열린 시트를 닫고 재조회하는가
② 판매 요청 경로에 화면 보유 `seller_id` 를 실어 보내는 자리가 없는가. 되돌려-검증 필수.
