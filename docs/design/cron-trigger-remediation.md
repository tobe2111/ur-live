## 3. Plan B — 트리거 수 제한에 걸릴 때

플랜 한도로 10개를 다 못 걸면, **트리거를 늘리지 말고 코드에서 시각 분기**한다.

### 핵심: **`*/5` + `0 * * * *` 두 개면 전부 커버된다**

매시 트리거는 03·09·18·19시에도, 일요일 20시에도, 월요일 00시에도 **반드시 발화**한다.
따라서 일간·주간 블록을 **매시 블록 안에서 UTC 시각/요일로 디스패치**하면 트리거가 2개면 족하다.

**이 레포에 이미 같은 패턴이 있다** — `ops-daily-digest` 가 매시 블록 안에서
`isOpsDigestHour()` 로 UTC 22시에만 실행한다(`scheduled.ts` 하위). 새 발명이 아니다.

### 우선순위 — 한도가 N개일 때 살릴 순서

| 순위 | 트리거 | 왜 이 자리인가 |
|---|---|---|
| 1 | `0 0 * * 1` **또는** 매시 디스패치 | **`payouts-generate`** — 이게 없으면 운영자·셀러에게 **돈이 안 나간다**(O8 차단) |
| 2 | `0 20 * * 0` | **`d1-backup`** — ~~유일한 축~~ **정정(07-31)**: CI 경로(`d1-backup.yml`, 수 20:00Z)가 살아 있어 이중화의 한쪽 |
| 3 | `0 18 * * *` | 정산 성숙·만료 환불·원장 정합 — 지급의 **전제**(성숙 안 되면 1번이 뽑을 게 없다) |
| 4 | `0 * * * *` | 환불 재시도 · webhook drain · 원장 자가복구 · **cron 감시자 자신** |
| 5 | `*/5 * * * *` | 이미 등록됨(유지) |
| 6 | 나머지(`*/2`·`0 3`·`0 9`·`0 0`·`0 19`) | 리마인더·정리·수집 — 지연이 돈으로 직결되지 않음 |

> 💡 **정산·백업 1순위**(대표 동의). 1~3 이 곧 "돈이 나가고, 잃어도 복구된다"의 최소 집합이다.

### Plan B 는 머니 경로다

`scheduled.ts` 의 정산 작업 **실행 시점**을 바꾸는 변경이다. ⇒ **단독 세션 + 멱등 재확인.**
바꾸는 것은 *디스패치 조건*뿐이고 정산 로직은 무접촉이지만, 시점 변경은 이중 실행 위험을 만든다:

- 각 일간 작업이 **같은 날 두 번 불려도 안전한가**(대부분 CAS/멱등이지만 **작업별로 확인**할 것)
- 매시 디스패처가 **UTC 기준**인지(KST 로 착각하면 9시간 어긋난다 — 이 레포의 반복 사고 클래스)
- 되돌리기: 디스패치 조건 제거 → `cron === '...'` 분기로 환원

## 4. 어느 플랜이든 — **첫 발화 때 밀린 일이 한꺼번에 돈다**

몇 달간 안 돌았다면 첫 실행에서 대량 배치가 터진다. 특히:

| 작업 | 첫 실행에 벌어지는 일 | 대비 |
|---|---|---|
| `payouts-generate` | 누적 미지급분이 **한 번에 payout 생성** | 생성만 하고 **지급 승인은 사람이** 한다 — 어드민에서 금액 검토 후 승인 |
| `expired-voucher-refund` | 만료 이용권 **일괄 환불** | 대상 건수를 먼저 보고 실행할 것 |
| `auto-settlement` / `*-mature` | 성숙 대량 전이 | 멱등이라 안전하나 **로그로 건수 확인** |
| `d1-backup` | 백업 1회 | 무해 |
| `retry-*` / `webhook-failed-drain` | 밀린 재시도 폭주 | 배치 상한이 있는지 확인 |

> ⚠️ **켜는 순서 권장**: 백업(2순위) → 정합/성숙(3순위) → 지급(1순위).
> **지급을 맨 마지막에** 켜야 잘못된 성숙 상태로 돈이 나가지 않는다.
> (우선순위 = "중요도", 켜는 순서 = "안전"이라 둘이 다르다.)

## 5. 감시 사각지대 — 이게 왜 안 보였나

`cron-stale-watch` 와 `GET /api/_healthcheck/cron` 은 **"한 번이라도 뛴 작업이 멈췄는가"**만 본다.
**한 번도 안 뛴 작업은 하트비트 목록에 아예 없어** `missing: []` 로 나온다(실측 확인).

⇒ *"기대 목록 vs 실제 기록"* 대조가 없으면 **미등록 트리거는 영원히 안 보인다.**

**환원 제안(다음 세션)**: `scheduled.ts` 가 분기하는 cron 식을 **상수로 export** 하고,
헬스체크가 *"기대 식 중 하트비트가 단 한 건도 없는 것"*을 `never_fired` 로 보고한다.
읽기 전용이라 위험이 낮고, 오늘의 이 발견을 **자동으로** 재현한다.

> ⚠️ 이 가드도 못 보는 것: 대시보드의 **실제 트리거 목록**(레포가 못 읽는다). 그래서 판정은
> *"코드가 기대하는 식 중 한 번도 안 뛴 것"* 까지이고, 원인 확정은 여전히 사람이 대시보드를 봐야 한다.
