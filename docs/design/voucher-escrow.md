# 이용권 에스크로 & 정산 안전판 설계 (티몬 붕괴 회피)

> 2026-07-03 — 티켓몬스터 초기모델 비교 진단 후속. 대표 승인 "모두 이상적으로".
> **이 문서는 코드만으로 끝나지 않는 결정(신탁·PG·회계·머천트 정책)을 정리한 것.**
> 코드로 안전하게 처리한 부분은 PR #430 에서 완료. 이 문서는 **대표 결정이 필요한 잔여 항목**.

---

## 0. 한 줄 요약

유어딜은 **"QR 사용 확인 후에만 정산"**(`auto-settlement.ts` — `status='used'` 게이트)으로
티몬을 죽인 *시간 기반 선정산*을 이미 구조적으로 극복했다. **그러나** 구매~사용 사이 고객 돈을
**진짜 에스크로(신탁)로 분리 보관하지는 않는다**(`self-redeem` 핸들러 주석: `돈 이동 X (에스크로는 Phase 2)`).
티몬 붕괴의 **법적 핵심은 "받은 돈을 운영자금과 섞어 쓴 것(commingling)"** 이므로, 규모가 커지기 전에
이 신탁 분리를 채우는 것이 1순위 리스크 대응이다.

## 1. 현행 돈 흐름 (as-is)

```
[소비자 결제]                [플랫폼 보관]              [매장 QR 사용]           [주간 정산]
Toss 결제 ──────────────▶ 플랫폼 계좌(단일) ──────────▶ vouchers.status='used' ──▶ 매장에 송금
  즉시 캡처                 운영자금과 미분리 ⚠️          used_at 기록             (월~일 → 차주 목)
                                                        ledger credit 기록        net = credit-fee-debit
```

- **정산 트리거**: `auto-settlement.ts:48` — `status='used' AND used_at < cutoff AND settlement_id IS NULL AND NOT IN(open disputes)`. ✅ 이행(사용) 후에만.
- **미사용 만료분**: 소비자에게 **환불**(breakage 가 매장 아닌 구매자 귀속). ✅
- **분쟁**: open dispute 있으면 정산 보류. ✅
- **정산 주기**: 월~일 사용분 → 차주 목요일 payout (`settlement-schedule.ts`), net(credit − fee − debit) ≥ 10,000원, 어드민 승인.

### ⚠️ 갭: 진짜 에스크로(신탁)가 없음
- 결제 캡처된 고객 돈이 **플랫폼 단일 계좌**에 들어가 운영자금과 **회계상 분리되지 않는다**.
- "사용 후 정산"이라 *논리적으로는* 매장 몫이 보호되지만, **자금이 물리적으로 분리 보관되지 않으면**
  플랫폼 현금흐름 악화 시 그 돈이 다른 데 쓰일 수 있다 = **티몬-위메프 2024 붕괴의 정확한 재현 경로.**

## 2. 이상적 목표 (to-be) — 3단계

### Phase 2a — 회계적 분리 (코드 + 회계, PG 무관: 가장 먼저)
- `escrow_ledger` 도입: 결제 시 `held`(고객예치) → 사용 시 `releasable`(매장 정산 대상) → payout 시 `released`.
- 대시보드에 **"미사용 예치 잔액(= 고객에게 갚아야 할 돈)"** 상시 노출 → 이 금액은 **운영자금으로 인식 금지**(회계 분리).
- 미사용 만료 시 `refunded`(고객 환불) 로 전이. **이 잔액을 절대 매출로 잡지 않는다.**
- ✅ 이건 우리가 코드로 구현 가능(신탁계좌 없이도 회계 규율부터).

### Phase 2b — 물리적 신탁 (은행/PG 결정 필요)
- **결제대금 예치(에스크로) / 지급보증 / 채무지급보증보험** 중 택1 — **전자상거래법상 통신판매 에스크로 의무**와 정합.
- 옵션:
  - (A) **PG 에스크로 서비스**(Toss/PG 사 제공) — 결제대금을 PG 가 예치, 구매확정(=QR 사용) 시 매장에 지급.
  - (B) **은행 신탁계좌 분리** — 고객예치금 전용 계좌, 정산분만 운영계좌로 이체.
  - (C) **소비자피해보상보험/채무지급보증** — 예치 대신 보험으로 커버.
- ⚠️ **코드만으로 불가** — 대표가 PG/은행과 계약 + 회계법인 자문 필요.

### Phase 2c — 자동 대사(reconciliation)
- 매일 `escrow_ledger held 잔액` vs `신탁계좌 실잔액` 대사 → 불일치 알림.

## 4. ② 기본 redemption 모드 결정 (부정 셀프사용 방어)

### 현황
- 3모드: `scan_only`(직원 QR) / `store_code`(카운터 4자리 셀프) / `self_free`(자유 셀프, **기본값**).
- `self_free` = 손님이 **매장 밖에서도 "사용완료"를 누를 수 있음**(GPS 증거만, 게이트 X). 60초 취소 + 사장님 알림이 크로스체크지만 **차단은 아님**.

### PR #430 에서 코드로 막은 것
- ✅ 소비자 셀프 경로(`self-redeem`)는 이미 모드 서버강제(scan_only 차단 / store_code 일치).
- ✅ 무인증 `/:code/use`(카운터 코드입력)의 **strict 모드 + PIN 미설정** 상품 코드-단독 소각 갭 차단(매장코드 일치 필수). scan_only·store_code 둘 다.

### 남은 결정 (대표 몫 — 라이브 머천트 동작 변경이라 임의 변경 금지)
- **기본값을 `self_free` 로 둘지, 더 엄격하게 바꿀지.**
  - `self_free` 유지 = 느슨한 카운터 편의(현행). 부정 셀프사용 여지 존재.
  - 기본을 `store_code` 로 = 모든 매장이 카운터 코드 필요 → 부정 차단 강하지만 **기존 매장 UX 변경**(온보딩 마찰 ↑).
- **권장(점진)**: 기본은 `self_free` 유지하되, ① 신규 매장 온보딩에서 **모드 선택을 명시 스텝**으로 승격(디폴트 노출), ② 셀프사용 이상징후(속도/위치 이격) 시 **사장님 알림 강조 + 정산 보류 플래그**(하드 차단 아님) — 스푸핑 오탐 없이 방어 신뢰도만 ↑.
