## 0. 왜 이 감사가 따로 필요한가

이 레포의 사고는 *"코드가 틀렸다"* 보다 **"코드는 맞는데 실행되지 않는다"** 쪽이 압도적으로 많다.
후자는 **에러가 안 난다.** 배포는 초록불이고, 테스트는 통과하고, 화면은 정상이다. 그래서 안 보인다.

**감사 질문은 "이 기능이 있는가"가 아니라 "이 기능이 **실제로 돈 증거**가 있는가"** 다.

| | 흔한 감사 | 실행증거 감사 |
|---|---|---|
| 묻는 것 | 코드가 있나 · 조건이 맞나 | **마지막으로 실행된 증거가 있나** |
| 통과 신호 | 심볼 존재 · 테스트 green | 하트비트 · 로그 · DB 행 · 실제 왕복 |
| 놓치는 것 | **실행 자체가 안 되는 경우** | (느리지만 안 놓침) |

## 클래스 A — 가드는 있는데 **안 돈다**

**정의**: 검사 스크립트가 레포에 존재하지만 어떤 실행 경로(CI·훅·audit-gate)에도 등록되지 않았거나,
등록됐어도 판정이 늘 참이라 통과만 한다.

**실사례**(2026-07-29): `check-input-text-color.mjs` 는 정상 코드를 오탐해 **어디에도 등록되지 못한 채**
2개월 방치됐다 — 파일이 있으니 보호받는 것처럼 보였다. `check-bundle-size` 의 gzip 예산은 존재하지 않는
`.gz` 사이드카를 읽어 측정값이 **항상 0** 이었고, `0 > 1.5` 는 영원히 거짓이라 몇 달간 통과만 했다.

**증거**: `check-guard-registry.mjs`(등록 여부) + 각 가드가 스스로 선언하는 **"측정 대상 0건이면 통과가 아니라 실패"**.

## 클래스 B — 코드는 있는데 **트리거가 없다**

**정의**: 실행 주체(cron 트리거·웹훅 구독·이벤트 바인딩)가 인프라 쪽에 등록되지 않아 코드가 한 번도 안 불린다.
레포는 인프라 설정을 못 보므로 **CI 로는 절대 안 잡힌다.**

**실사례**(2026-07-29): `scheduled.ts` 가 10개 cron 식으로 분기하는데 하트비트상 발화가 확인된 건 `*/5` 하나뿐.
`*/2` 는 ~140회 기회에 0건이었다. 사실이면 **`payouts-generate`(주간 정산 지급)·`d1-backup`(주간 백업)·
`auto-settlement` 이 전부 안 돈다.** → [cron-trigger-remediation.md](./cron-trigger-remediation.md)

**왜 안 보였나**: 감시자(`cron-stale-watch`·`_healthcheck/cron`)가 *"뛴 적 있는 게 멈췄나"*만 본다.
**한 번도 안 뛴 것은 목록에 없어** `missing: []` 로 나온다.

**증거**: *기대 목록 vs 실제 기록* 대조. 기대 목록은 코드에서 뽑고(정적), 실제는 하트비트에서 뽑는다(런타임).
**둘 다 있어야** 판정된다.

## 클래스 C — 심볼은 있는데 **그 기능의 경로가 아니다**

**정의**: 어떤 심볼의 호출처가 0건인 것을 보고 "기능이 없다"고 단정하는데, 실제 기능은 **다른 경로**로 구현돼
정상 동작 중인 경우. **거짓 양성** 클래스 — 없는 버그를 쫓느라 시간을 쓰고, 고치려다 멀쩡한 걸 깨뜨린다.

**실사례**(2026-07-29): `cart.store.ts:89 clearCart` 의 호출처가 0건이라 *"결제 성공 후 장바구니가 안 비워진다"*
로 보고했는데 **틀렸다.** 실제 장바구니는 **서버측**(`/api/cart`·`cart_items`)이고
`PaymentSuccessPage.tsx:126·271` 이 `order_number` 와 함께 clear 를 호출해 **그 주문 상품만** 지운다.
`cart.store.ts` 는 헤더 뱃지 카운트 전용 잔존 스토어였다.

**증거**: 심볼이 아니라 **기능의 실제 경로**를 따라갈 것 — 화면 → 호출 → 엔드포인트 → 테이블.
"호출처 0건"은 *가설의 시작*이지 결론이 아니다.

## 클래스 D — **배송 전제가 박힌 화면·상태 흐름** 〔대표 추가 2026-07-29〕

**정의**: P0 가 **픽업 전용**으로 확정됐는데, 기존 소비자 화면·상태 흐름은 **배송을 전제로** 만들어져 있다.
조건이 배송 상태(`DELIVERED`·`SHIPPING`·송장·배송비·주소)에 묶여 있으면 **픽업 주문엔 그 기능이 아예 안 붙는다.**
에러가 나지 않고 **버튼이 안 보일 뿐**이라 클래스 B 처럼 조용하다.

**촉발 사례**: 소비자 **반품 신청 입구**의 게이트가 `DELIVERED` + 7일이다(`ReturnRequestModal.tsx:4`, 서버 스펙 동일).
**픽업 주문은 `DELIVERED` 에 도달하지 않으므로 소비자가 반품을 올릴 입구가 없다.**

### 전수 대상 — 아래를 조건으로 쓰는 곳 전부

| 축 | 찾을 것 |
|---|---|
| 주문 상태 | `DELIVERED` · `SHIPPING` · `PREPARING` 을 **가시성/가능여부 조건**으로 쓰는 화면 |
| 배송 데이터 | `tracking_number` · 배송비(`shipping_fee`·`base_shipping_fee`) · 배송지(주소·우편번호) 유무로 갈리는 분기 |
| 상태 흐름 | 주문 진행 단계 표시(상품준비→배송중→배송완료) — 픽업에선 **단계 이름부터 틀리다** |
| 알림 | 배송 관련 알림 템플릿이 픽업 주문에 발송되는가 |
| 정산·환불 | 환불/반품 기한 계산이 **배송완료 시점** 기준인가(픽업엔 그 시점이 없다) |

### 판정 형식 (각 항목마다)

1. 이 화면/조건이 **픽업 주문에서 어떻게 보이는가** — 안 보임 / 잘못 보임 / 정상
2. **안 보임**이면 픽업용 대체 조건은 무엇인가(픽업 확인 전/후 · 픽업 마감 경과)
3. 세션 ④(픽업 공구) 범위인가, 별건인가

> ⚠️ **이 클래스는 "고칠 목록"이 아니라 "볼 목록"이다.** 픽업에서 안 보이는 게 **정답인 경우도 있다**
> (예: 송장 입력). 전부 고치려 들면 P0 가 배송 기능을 역수입하게 된다 — **P0 는 픽업 전용**이 상위 규칙이다.

**증거**: 픽업 주문 1건으로 소비자 여정 전 화면을 실제로 왕복(👤 대표 실계정 완주가 최종 판정).
정적으로는 위 축들의 grep 목록 + 각 건의 판정 기록.

## 감사 실행 순서

**B → A → D → C** 순으로 본다.

- **B 먼저**: 안 도는 걸 고치는 게 잘못 도는 걸 고치는 것보다 앞선다. 지금 B 하나가 정산 전체를 막고 있다.
- **A 다음**: 가드가 죽어 있으면 이후 감사 결과를 지킬 수단이 없다.
- **D**: P0 범위가 픽업으로 좁혀진 직후라 지금이 적기(넓히기 전에 봐야 한다).
- **C 는 상시**: 별도 패스가 아니라 **A·B·D 를 하면서 지켜야 할 규율**이다 —
  "호출처 0건"·"파일 없음"으로 결론 내기 전에 실제 경로를 확인한다.
