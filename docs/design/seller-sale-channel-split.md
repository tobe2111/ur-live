# 판매 방식 분리 — 상시딜 / 공구딜 (상태형 gb_mode · 셀러 폼 + 메인 피드)

> ⏳ **착수 시점: 지금 아님.** 8월 promo(커미션 예산 아비터 활성) 배치와 **한 세션**에서 구현.
> 콜드스타트 구간엔 공구딜도 메인 노출 유지. 게이트 OFF 기본. (대표 확정 2026-07-06)
>
> 📐 **구현 방식 = 상태형(gb_mode) — 대표 확정 2026-07-06.** "상품을 상시/공구로 나누는 채널 플래그"가
> **아니라**, **공구를 이용권에 얹는 상태(`gb_mode`)** 로 간다. 한 이용권은 **한 순간에 상시 아니면 공구
> 하나** 이므로 A(배타)가 **구조적으로 보장**됨(별도 배타 강제 불필요). 상세 완결 스펙 = **`개발요청_공구엔진_상태형양방향`**
> (SSOT — 이 문서는 그 상태형 스펙에 정합된 요약·위치 매핑. 세부 상태전이/양방향은 그 문서 우선).
> ⚠️ 그 스펙 문서가 아직 레포 미커밋이면 8월 세션 착수 전 `docs/design/` 에 커밋해 이 문서와 나란히 둘 것.

## 배경
사업자 유저가 이용권을 **두 상태** 중 하나로 판매(같은 이용권에 얹는 gb_mode):
- **상시(기본)** = 평소 영업(앱 메인·검색·지도로 상시 노출·유입).
- **공구(gb_mode ON)** = 기획전(인플루언서 링크·기간 한정, 더 큰 할인 + 소개비(promo%)로 홍보).

지금은 구분 없이 전부 메인 노출(콜드스타트). 8월 promo 켜질 때 "공구 상태 이용권은 메인에서 빼고 인플루언서 링크로" flip.

## 확정된 UI 구조 (대표 2026-07-06)
1. **"판매 방식" 라디오 = 셀러 폼 최상단.** 이용권 정보 블록 위가 아니라 **폼의 가장 처음**.
   - 이유: 상시딜/공구딜에 따라 아래 필드 구성이 통째로 갈림(공구딜만 기간·목표인원·promo%).
     매장이 다른 걸 입력하기 전에 채널부터 선택 → 그에 맞는 폼 전개. 중간에 만나면 이미 입력분이 무의미해짐.
2. **라벨은 사장님 언어로**(“메인 노출”·“어트리뷰션” 금지 — 오프라인 영업에 대응):
   - 상시딜 → **"평소 판매 — 앱에서 늘 팔아요 (검색·지도로 손님이 찾아옴)"**
   - 공구딜 → **"기획전 — 인플루언서와 기간 한정으로 팔아요 (더 크게 할인, 소개비로 홍보)"**
   - 프레임: 상시딜 = 정상 영업 / 공구딜 = 이벤트. 온보딩에서 "이걸 왜 나눠?" 질문을 없앰.
3. **메인 피드 flip**: promo 켜질 때 공구딜을 **완전 숨김이 아니라 "오픈 예정" 배지로 유지**.
   - 이미 있는 prelaunch 메커니즘(`product_supply_meta.prelaunch='1'` + FcfsBadge + 상세 CTA) 재사용.
   - 이유: 메인에서 "○○식당 공구 곧 열림"을 본 유저가 인플루언서 링크를 기다림 → 기대감↑.
     완전 숨기면 그 홍보 효과 소멸. (상품 공구의 "오픈 예정 알림받기"와 같은 원리.)

## 타이밍/세션 규칙 (강한 합의)
- ① **지금 당장 안 지음** — 콜드스타트엔 상시 노출 유지.
- ② **지을 땐 promo(#1)와 한 세션·한 배치** — promo% 필드가 공구딜 폼 안에 들어가므로 따로 하면 충돌.
  채널 플래그 + promo% + 검증을 **반드시 한 세션에서**(병렬 세션 충돌 방지 = 서비스 격리 원칙의 실전).
- ③ **전부 게이트 OFF 기본.**

## ⚖️ 정책 결정 — ✅ **A(배타) 확정 (대표 2026-07-06)**
"같은 이용권을 상시딜+공구딜 동시 가능?" → **A) 배타로 확정.** 단 구현은 **상태형(gb_mode)** 이라
배타가 **구조적으로 보장**됨 — 한 이용권은 한 순간 상시 아니면 공구 하나(별도 배타 강제 규칙 불필요).
- (기각) **B) 동시 허용** — 상품 2행·재고/기간 관리 복잡·같은 매장 2리스팅 피드 혼동. 매장이 능숙해진 뒤 재검토.

### ⚠️ #3(공구가<상시가 검증) — "제외" 아님, **단순화되어 살아있음**
- 초기 채널-플래그 가정에선 "같은 상품이 양쪽에 없으니 가격 교차검증 불필요"였으나, **상태형에서도
  공구 특가가 상시가보다 낮은지는 반드시 검증**해야 함(안 그러면 공구가 더 비싼 이상한 상황).
- 다만 이건 **"두 상품 간 교차검증"이 아니라 "한 이용권 안에서 공구 특가 < 상시가" 단일 규칙** →
  훨씬 가벼움. **`개발요청_공구엔진_상태형양방향` §1 에 이미 포함** — 별도 #3 작업 불필요, 그 검증에 흡수.

## 구현 스케치 (8월 세션용 — 상태형 기준, 착수 전 `개발요청_공구엔진_상태형양방향` 재확인)
- **상태 저장**: 이용권에 `gb_mode`(공구 상태 ON/OFF) — 상세는 상태형 스펙 SSOT. products 컬럼 예산제라
  신규 저장은 사이드테이블(`product_supply_meta`)/상태 필드는 스펙 정의 따름.
- **공구 상태 전용 필드**: 공구 특가(< 상시가, 단일 검증) · 기간(fcfs_deadline) · 목표인원 ·
  promo%(커미션 예산 아비터 `commission_budget_enabled` + `seller_promo_field_enabled` 연동 — §1 promo 와 한 배치).
- **피드 게이트**: `groupbuy_hidden_from_main` 플래그 OFF(콜드) → ON(flip) 시 공구 상태 이용권을
  **완전 숨김이 아니라 prelaunch("오픈 예정") 배지 노출**로 전환(기존 메커니즘 재사용).
- **배타**: 상태형이라 폼/데이터에서 구조적 — 별도 상품간 가격 교차검증 없음, 상태 내 공구특가<상시가 단일검증만.
