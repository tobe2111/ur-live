### D1. 냉장·냉동(`cold`) 미수령 — 환불액을 얼마로 할 것인가

| 안 | 소비자 | 운영자 | 비고 |
|---|---|---|---|
| **(a) 환불 0** | 못 받음 | 전액 정산 | 상품이 실제로 폐기됨. 다만 **소비자 반발이 가장 크다** |
| (b) 부분 환불 | 일부 | 나머지 정산 | 비율을 정해야 함 |
| (c) 현행 유지(전액) | 전액 | 0 | 운영자가 폐기 손실을 전부 떠안음 |

⚠️ **법무 X4c 와 묶여 있다** — 미수령 시 청약철회 제한 고지가 유효해야 (a)·(b)가 성립한다.
법무 회신 전에는 **(c) 현행 유지**가 안전하다(지금 상태 그대로).

### D2. 실온(`room`) 미수령 — 보관 기간과 환불 비율

- 픽업일로부터 **며칠**까지 보관하는가
- 그 후 환불 비율은 **몇 %** 인가(나머지는 운영자 보관·폐기 비용)

> 두 값 모두 **어드민 조정 대상**(`platform_settings`)으로 두고 코드엔 **기본값만** 박는다
> — CLAUDE.md 룰: *"수치(%·기간·금액)만의 변경은 문서 갱신 불필요."*

## 3. 구현 형태 (결정 후)

### 3.1 게이트
`platform_settings.pickup_unclaimed_policy_enabled`(기본 **OFF**). OFF 면 **현행 전액 환불 그대로.**
⇒ 머지해도 **라이브 동작 변화 0**. #844 와 같은 방식이다.

### 3.2 분기 위치
`handleExpiredVoucherRefunds` 의 **환불액 계산 한 곳**. CAS·멱등·원장 기록은 **byte-불변**으로 둔다.

```
refundAmount = policyEnabled
  ? unclaimedRefundAmount(applied_price, storage, daysSincePickup)   // 신규 순수함수
  : (기존 계산)
```

### 3.3 🔴 `storage` 가 `null` 이면 **현행 유지**(전액 환불)
④-a 가 낯선 값을 `null` 로 떨구도록 만든 이유가 이것이다.
**모르는 상태에서 소비자 돈을 덜 주지 않는다** — 그게 fail-safe 방향이다.

### 3.4 운영자 쪽 대칭
환불을 줄이면 그만큼 **운영자에게 정산**돼야 한다. 원장 기록이 없으면 **돈이 공중에 뜬다.**
⇒ 적립-역전 대칭(CLAUDE.md 머니 룰 #2)을 같은 커밋에서 배선한다.

## 4. 검증 절차 (실결제)

staging 이 없으므로 **#844 방식**(프로덕션 최저가 테스트 상품 + 즉시 환불)을 따른다.

| # | 확인 | 판정 |
|---|---|---|
| 1 | `storage=room` 상품 구매 → 픽업일 경과 → cron | 환불액 = 설정 비율 · 원장 대칭 |
| 2 | `storage=cold` 상품 동일 | D1 결정대로 |
| 3 | **`storage` 미설정** 상품 동일 | **전액 환불(현행)** — 3.3 불변식 |
| 4 | 게이트 OFF 로 되돌림 | 전액 환불로 즉시 복귀 |
| 5 | cron 2회 실행 | **이중 환불 0**(CAS 멱등) |
| 6 | 유어딜 5% | `floor(결제액×5%)` **불변** |

⚠️ **6번이 핵심이다.** 미수령 처리는 소비자↔운영자 사이의 분배이지 **플랫폼 몫을 건드리지 않는다**
(CLAUDE.md 커미션 재원 원칙 — *"유어딜 5% 는 불변, 깨지면 버그"*).
