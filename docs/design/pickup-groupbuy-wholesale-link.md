# §A. 대표 원문 (2026-07-29)

## 0. 배경
- 유어딜에 픽업 공구를 **이용권 레일 하위종**(`etc_voucher` 하위 플래그)으로 신설하기로 판정됨
- 기존 도매몰(구 "유통스타트", 3인 공동사업 파기로 사용자 귀속)을 유휴 자산이 아니라 **공급 측 백엔드**로 재활용
- 두 코드베이스는 합치지 않는다. 역할을 나누고 좁은 인터페이스로만 잇는다

## 1. 대원칙 3
- **P1. 돈은 유어딜에서만 흐른다.** 도매몰의 결제·PG·정산 기능은 전부 OFF. 근거: 유어딜 순수취 == 정확히 5% 불변식과 머니 가드·감사 이력(#479 / #496 / #514)이 유어딜 안에서만 성립한다. 돈길이 둘이면 대사가 불가능해지고 지금까지의 감사가 무효가 된다.
- **P2. 상품·재고의 SSOT는 도매몰.** 유어딜은 읽기 전용 미러 + 재고 차감 콜백만 갖는다. 유어딜에서 상품을 신규 생성하지 않는다.
- **P3. 사업자는 재고를 지지 않는다.** 공급사 → 매장 직배송. 유어딜도 도매몰도 어느 단계에서도 재화의 소유권을 갖지 않는다. 창고·물류 인력 0. 이 원칙이 깨지는 순간 이 사업은 유통업이 되고, 1인 운영이 불가능해진다.

## 2. 역할 분담

| 기능 | 도매몰 | 유어딜 |
|---|---|---|
| 공급사 관리·계약 | O | X |
| 상품 원장 · 매입가 | O | X |
| 재고 | O (원장) | 미러 |
| 소비자 노출 · 공구 집결 | X | O |
| 결제 | X (영구 OFF) | O |
| 픽업 확인 | X | O (`voucher_visits`) |
| 커미션 분배 | X | O (promo 레일) |
| 매장 발주서 | O | X |
| 정산 리포트 | 매입 기준 | 판매 기준 |

## 3. 세 가지 운영 모드

### 모드 A — 매장 자체 상품 (방배에서 검증)
매장이 공급자 겸 픽업 거점. 도매몰은 상품 등록 창구 역할만 한다.
```
매장이 도매몰에 상품 등록
  → 유어딜에 픽업 공구로 노출
  → 소비자 결제 (유어딜)
  → 픽업일에 매장 방문 · QR 사용확인
  → 정산 (판매 5% + promo 커미션)
```
물류 0 · 재고 리스크 0 · 소싱 협상 불필요. **첫 검증은 반드시 여기서.**

### 모드 B — 외부 공급사 중개 (방배 이후 판단)
도매몰 본래 기능이 여기서 살아난다.
```
공급사 입점 (도매몰) → 상품 등록 → 유어딜에서 공구 집결
  → 공구 성사 → 도매몰이 매장 단위 발주서 생성
  → 공급사가 매장으로 직배송 → 소비자 픽업 · QR
  → 정산 (판매=유어딜 / 매입=도매몰, 분리)
```
매장은 선주문 확정분만 입고하므로 재고 리스크가 없다. → 다이클로 대비 결정적 우위. 저쪽 가맹점은 점포·재고·보증금을 전부 진다.

### 모드 C — 상권 공동몰 (B2G 납품)
도매몰을 상인회 단위 멀티테넌트로 복제해 지원사업 산출물로 납품. 시장경영패키지의 "상점가 단위 온라인 쇼핑몰 운영 지원" 항목에 대응. 상인회 홈페이지 SaaS와 번들. 유어딜 연동 없이 단독 납품 가능하고 신규 개발이 거의 없다.

## 4. 연결 방식
단방향 push + 좁은 콜백. 양방향 동기화 금지.
- **도매몰 → 유어딜 (push)**: 상품ID · 상품명 · 판매가 · 재고 · 픽업정책 · 매장ID · 보관구분(냉장/냉동/실온)
- **유어딜 → 도매몰 (콜백 2종만)**: ① 재고 차감·복원 ② 공구 성사 이벤트
- 매입가·공급사 정보는 유어딜로 넘기지 않는다. 유출 시 매장이 마진 구조를 알게 된다
- 인증은 서버 간 시크릿. 재고 차감은 주문ID 멱등키 필수 — **중복 차감이 이 구조 최대의 사고 지점**
- 도매몰 장애 시 유어딜은 미러 데이터로 계속 판매 가능해야 한다 (공구 신규 개시만 차단)

## 5. 정산
- 판매가 · 5% · promo 커미션 = **유어딜**. 기존 레일 그대로, 새 요율 로직 금지
- 매입가 · 공급사 지급 = **도매몰**. 유어딜 머니 경로 무접촉
- 두 원장은 **공구ID로만 조인**. 금액은 서로 넘나들지 않는다
- 모드 B에서 공급사 대금 지급 주체는 **매장**. 유어딜도 도매몰도 대금을 쥐지 않는다 → 전금법 트리거 회피. 법무 결론 나오기 전까지 필수 조건

## 6. 미수령 · 환불

| 보관구분 | 정책 |
|---|---|
| 냉장 · 냉동 | 픽업 마감 후 환불 불가 |
| 실온 | 유예 3일 후 부분 환불(매장 원가 보전분 차감) |

- 정책값은 상수가 아니라 **설정**. 법무 확인 후 바뀔 수 있다
- 상품 등록 시 매장·공급사가 선택 → 소비자 결제 화면에 명시(청약철회 제한의 고지 요건)
- `auto-settlement.ts:222` 의 만료 100% 자동환불은 **무형 이용권 전용으로 조건 분기**
- 모드 B는 이미 배송이 끝난 재화라 미수령 손실이 매장에 남는다 → 매장 발주 시점에 고지·동의 절차 필요

## 7. 순서

| 시점 | 할 일 |
|---|---|
| 방배 전 | ① **gb 가격 소비자 결제 경로 배선(선행 필수)** → ② 픽업 공구 모드 A 선구현, 게이트 OFF |
| 방배 중 | 모드 A 실측 — 매장 몇 곳이 실제로 켜는가 · 픽업 노쇼율 · 매장 재구성 의사 |
| 방배 후 | 모드 A 데이터로 모드 B 착수 여부 판단. 모드 C는 다음 B2G 견적서에 항목으로 삽입 |

## 8. 이번에 하지 않는 것
- 도매몰 결제 · PG 연동 (영구 OFF)
- 유어딜에서의 택배 배송 (픽업만)
- 자체 창고 · 물류 · 재고 보유
- 도매몰 코드의 유어딜 병합
- 소비자에게 도매몰 직접 노출

## 9. 아직 열려 있는 판단
- **브랜드명** — "유어몰" 보류. 사입 성격이 드러나는 이름 권장
- **모드 B 수수료율** — 모드 A 실측 후 결정. 지금 정하지 않는다
- **도매몰 결제 기능** — 영구 제거 vs 게이트 보존
- **법무 묶음 추가 항목** — 청약철회 제한 고지 문구, 모드 B 대금 흐름의 전금법 해당 여부

# §B. 코드 대조 검증

원문의 전제를 이 레포 실제 구조와 하나씩 맞춰봤다. **방향은 전부 맞다.** 다만 §4(연결 방식)와 §1-P1(결제 OFF)의 **전제가 실제 아키텍처와 다르고**, 그 차이가 작업량과 사고 위험을 크게 바꾼다.

## B.0 검증 요약

| 항목 | 판정 | 한 줄 |
|---|---|---|
| §0 "두 코드베이스" | ❌ **사실 아님** | 같은 레포·**같은 D1**. worker 번들만 빌드타임에 갈린다 |
| §4 push + 서버간 시크릿 + 콜백 | ❌ **불필요·역효과** | 같은 DB 라 HTTP 를 끼우면 걱정한 중복차감을 **스스로 만든다** |
| §1-P1 "돈은 유어딜에서만" | ✅ **이미 그렇다** | 공급자 정산 엔진이 이미 소비자 worker 에 산다 |
| §1-P1 "도매몰 PG OFF" | 🟡 **PG 는 이미 없음. 진짜 돈길은 예치금** | "OFF" = 예치금 폐지를 뜻함(no-op 아님) |
| §1-P2 읽기전용 미러 | ✅ **기존 메커니즘 있음** | `supply_source_id` 재판매 복제 — 새로 만들 것 없음 |
| §2 역할 분담표 | ✅ 정합 | 1건 주석 필요(정산 엔진 위치) |
| §3 모드 A | ✅ 성립 | 가장 짧은 경로 |
| §3 모드 C "신규 개발 거의 없다" | ✅ **사실** | `wholesale_malls` 멀티테넌트 + 메디스타트 선례 |
| §5 "어느 쪽도 대금을 쥐지 않는다" | 🟡 **모드 B 한정으로 좁혀야 정확** | 유어딜은 `platform:escrow`, 도매몰은 예치금을 이미 쥔다 |
| §6 보관구분 | ✅ 가능 | 단 products ALTER 금지 → K-V |
| §7 순서 ① | ✅ **정확** | 선행 필수 판단이 코드와 일치 |

## B.1 🔴 가장 중요 — §4 연결 방식은 만들지 말 것

원문은 두 시스템이 **별개 코드베이스·별개 DB**라고 전제하고 HTTP push + 서버간 시크릿 + 재고 콜백을 설계했다. 실제는 다르다.

`docs/design/wholesale-separate-deploy.md` §0 이 사실을 못박아 두었다:

> **C.** 두 서비스가 **같은 D1** 의 같은 테이블(`products`·`sellers`·`supplier_settlements`·`order_items`)을 공유. 플래그(`is_supply_product`·`is_distributor`)로만 격리 → **DB 분리 불가/불필요** — 별도 worker 도 같은 D1 바인딩. 데이터 마이그레이션 0, 이중쓰기 0, reconcile 0

별도 배포(commit `93c0989`)가 가르는 것은 **worker 번들뿐**이다 — `WHOLESALE_BUNDLE=1` 이면 도매 라우트를 포함하고, 아니면 DCE 로 뺀다(`mount-wholesale.ts`). **데이터는 한 곳이다.**

그래서 원문이 *"재고 차감은 주문ID 멱등키 필수 — 중복 차감이 이 구조 최대의 사고 지점"* 이라고 정확히 짚은 그 위험은, **HTTP 콜백을 도입할 때만 생긴다.** 안 만들면 애초에 없다.

**이미 있는 것으로 충분하다:**

| 원문이 만들려는 것 | 이미 있는 것 |
|---|---|
| 도매몰 → 유어딜 상품 push | `supply.routes.ts:333` — 도매 원본을 셀러의 소비자 상품으로 **복제 INSERT**(`supply_source_id`=원본 id). 중복 등록은 `(seller_id, supply_source_id)` 조회로 409 |
| 재고 차감 콜백 + 멱등키 | `products.stock` **원자 CAS** — `UPDATE ... WHERE id=? AND stock >= ?` (`group-buy.routes.ts:259`). 같은 DB 라 콜백 자체가 불필요 |
| 재고 복원 콜백 | 조기 return·셀프취소 복원이 이미 대칭 (`group-buy-voucher.routes.ts:497`) |
| 매입가 비노출 | 소비자 SELECT 가 **명시 컬럼 목록**(`productDetailColsHealed`)이라 `supply_price` 를 안 실으면 안 나간다 |
| 도매몰 장애 시 계속 판매 | 같은 DB 라 **장애 개념이 없다**(도매 worker 가 죽어도 소비자 판매 무관) |

> ⚠️ **단, 매입가에 대한 정정 1건**: 원문은 *"매입가·공급사 정보는 유어딜로 넘기지 않는다"* 고 했으나, 현재 복제 INSERT 는 `supply_price` 를 **복제본 행에 함께 저장**한다(`supply.routes.ts:333~344`). 격리는 *행의 부재*가 아니라 **SELECT 컬럼 선택**으로 이뤄진다. 실질 보호는 되지만 원문의 표현과 메커니즘이 다르므로, 노출면 추가 시 컬럼 목록 점검이 필요하다.

**최소 변경(권장)**: §4 를 통째로 삭제하고 *"도매↔유어딜은 같은 D1 의 공유 테이블 + 플래그 격리. 연계는 기존 `supply_source_id` 복제 경로를 픽업 공구용으로 확장한다"* 로 대체.

## B.2 §1-P1 "도매몰 결제·PG OFF" — PG 는 이미 없다. 진짜 돈길은 예치금

`wholesale-plus.routes.ts:4` 가 명시한다:

> ⚠️ 도매몰은 **PG(Toss) 미사용** — 결제는 예치금(계좌이체로 충전된 잔액)에서 차감.

즉 **"PG 연동 OFF"는 이미 참이고 할 일이 없다.** 그런데 도매몰에는 다른 돈길이 살아 있다:

- **예치금**(`wholesale-deposit.routes.ts`) — 판매사 무통장입금 → 어드민 확인 → **잔액 적립** → 주문 시 차감. 즉 도매몰이 **선불 잔액을 보유**한다.
- **공급자 정산·출금**(`supplier-withdrawal.routes.ts`, `supplier_settlements`)
- **미수금/여신**(`outstanding_balance`)

⇒ *"결제 기능 전부 OFF"* 는 **no-op 이 아니라 예치금 모델 폐지**를 뜻한다. §9 의 "영구 제거 vs 게이트 보존" 판단이 바로 이것이고, 그래서 그 판단은 생각보다 무겁다.

> 🔴 **§5 와의 충돌**: 원문은 전금법 트리거를 **모드 B 공급사 대금**에서 걱정한다. 그런데 **선불충전 잔액 보유(예치금)가 전금법상 더 직접적인 노출**이고, 그건 모드 B 가 아니라 **오늘 이미 있다.** 법무 묶음(§9)에 "예치금 = 선불전자지급수단 해당 여부"를 **모드 B 대금흐름보다 먼저** 넣을 것을 권한다.

## B.3 §1-P1 "돈은 유어딜에서만" — 이미 그렇다 (새로 만들 것 아님)

`wholesale-separate-deploy.md` §0-B:

> 소비자 worker 가 `supply-settlement.ts` 를 호출 — 주문확정 `order-commissions.ts:128` `creditSupplierOnOrder`, 환불 `order-refund.ts:77` `reverseSupplierOnRefund`, cron `scheduled.ts` `matureSupplierSettlements` → **정산 엔진은 소비자 worker 에 남아야 함**

즉 소비자 주문이 확정되면 **유어딜 worker 가 공급자 적립까지 실행**한다. 원칙 P1 은 새로 세울 규칙이 아니라 **이미 구현된 사실**이다.

§2 표의 *"커미션 분배: 도매몰 X / 유어딜 O"* 는 맞다. 다만 표에 **"공급자 정산 실행 = 유어딜 worker(엔진), 리포트 = 도매몰"** 이라는 주석을 붙여야 다음 세션이 "도매몰이 정산을 돌린다"고 오해하지 않는다.

> 🔴 **모드 B 착수 시 주의**: `wholesale-separate-deploy.md` 가 *"ur-wholesale 에 **cron trigger 절대 금지** — 정산 이중성숙 방지"* 를 명시했다. 모드 B 의 "공구 성사 → 발주서 자동 생성"을 cron 으로 만들 때 **반드시 소비자 worker 쪽 cron** 에 붙여야 한다.

## B.4 §1-P2 읽기전용 미러 — 기존 메커니즘이 이미 그 모양

`supply.routes.ts:333` 의 재판매 등록이 P2 가 원하는 것을 이미 한다: 도매 원본(`is_supply_product=1, supply_source_id IS NULL`)을 셀러가 **자기 소비자 상품으로 복제**(`seller_id`=본인, `supply_source_id`=원본, 자기 판매가). 마진 가드(`판매가 >= 공급가`)도 있다.

그리고 소비자 카탈로그 격리가 이미 이 모델에 맞춰져 있다 — 2026-06-26 fix 가 **도매 원본만** 제외하고 **복제본은 통과**시킨다(`ProductRepository.ts:109`, `group-buy-public.routes.ts:519`, `cart.routes.ts:88`):

```
AND NOT (COALESCE(is_supply_product,0)=1 AND supply_source_id IS NULL)
```

⇒ P2("유어딜에서 상품을 신규 생성하지 않는다")는 **기존 격리 설계와 정합**하다. 새 파이프라인 불필요.

> ⚠️ **픽업 공구용 갭 1건**: 복제본은 **카테고리를 원본에서 상속**한다. 픽업 공구는 `etc_voucher` 여야 하는데(선행 판정 §3.2) 도매 원본은 도매 카테고리(식품·의료기기 등)다. **복제 시 카테고리 매핑**이 필요하고, 그게 없으면 §B.1 의 "이미 있다"가 픽업에는 그대로 적용되지 않는다. 모드 A 는 매장이 직접 등록하므로 이 갭을 피해 간다 — **모드 A 를 먼저 하라는 §7 순서가 이 점에서도 옳다.**

## B.5 §3 모드 C — "신규 개발 거의 없다" 사실 확인 ✅

`wholesale_malls` 멀티테넌트가 이미 완성돼 있고 **두 번째 몰(메디스타트)이 실제로 돌고 있다**:

| 상인회별 푸터/사업자정보 | `company_json` (푸터·고객센터·약관·개인정보방침 반영) |

## B.6 §5 "어느 쪽도 대금을 쥐지 않는다" — 범위를 좁혀야 정확

**유어딜은 이미 대금을 쥔다.** 원장에 `platform:escrow` 계정이 있고(`ledger.ts:168,178,188`), 이용권은 결제 시점에 escrow 로 잡혔다가 **사용 시점**에 `merchant:{id}` 로 풀린다. 픽업 공구도 같은 레일을 타면 **픽업 전까지 유어딜이 대금을 보유**하는 구조다.

**도매몰도 이미 쥔다** — 예치금 선불 잔액(§B.2).

⇒ §5 의 문장은 **"모드 B 의 *공급사 매입대금* 은 매장이 공급사에 직접 지급하며, 유어딜·도매몰 어느 쪽도 그 대금을 경유하지 않는다"** 로 좁혀야 사실과 맞다. 지금 표현대로 법무에 제시하면 escrow·예치금이 드러났을 때 신뢰를 잃는다.

## B.7 §6 보관구분 — 가능. 단 컬럼 예산

`products` 는 **97/100**, `sellers` 는 **100/100(한도 도달)** 이라 ALTER 가 CI 차단 대상이다(`check-products-column-budget`). 보관구분·픽업정책은 **`product_supply_meta` K-V** 로 (선행 판정의 `pickup_*` K-V 와 같은 자리).

`auto-settlement.ts:222` 조건 분기 지적은 선행 판정 §5d 와 **정확히 일치**한다. 다만 그 분기는 **머니 경로**라 단독 세션 + staging 실결제가 필요하다(CLAUDE.md 룰).

## B.8 §7 순서 — ①이 맞다 ✅

*"gb 가격 소비자 결제 경로 배선(선행 필수)"* 는 선행 판정 §3.0 과 일치한다. `resolveGbPricing` 은 마켓플레이스 표시·어드민 조종석·셀러 저장 3곳에만 있고 **소비자 구매 경로엔 없다.** 이걸 먼저 안 하면 픽업 공구를 만들어도 공구가가 결제에 안 붙는다.

## B.10 열린 판단에 대한 의견 (§9)

- **도매몰 결제 기능**: **게이트 보존** 권장. 영구 제거는 예치금 원장·미수금·출금 경로를 함께 걷어내야 해서 되돌리기 어렵고, 모드 B 가 살아나면 다시 필요해질 수 있다. 게이트는 되돌릴 수 있다.
- **모드 B 수수료율**: "지금 정하지 않는다"에 동의. 다만 **정할 때 `fee-resolver` 를 건드리지 않아도 된다** — 매입 축은 도매몰 원장이고 유어딜 5% 와 무관하다(선행 판정 §6).
- **브랜드명**: 판단 근거를 갖고 있지 않아 의견 없음.

## 이 문서가 정정한 것 (다음 세션이 원문만 읽고 오판하지 말 것)

- ❌ *"두 코드베이스 / 별개 DB / HTTP 로 잇는다"* → **같은 레포·같은 D1.** worker 번들만 빌드타임에 갈린다. HTTP 연계를 만들면 원문이 스스로 경고한 "최대 사고 지점"을 없던 데서 만들어낸다.

- ✅ *"모드 C 는 신규 개발이 거의 없다"* → **사실.** 메디스타트가 3커밋 선례.
