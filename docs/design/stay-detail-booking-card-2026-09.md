## 1. 진단 — 높이는 증상이었다

대표가 지목한 건 버튼 높이였는데, 그 박스를 코드로 재 보니 넷이 겹쳐 있었다.

| | 잰 값 | 어긋난 규칙 |
|---|---|---|
| ① 테두리가 세 겹 (바깥 카드 + 트리거 2개) | `border` ×3 | 표면 규칙 ① **카드 테두리 0** |
| ② 고른 값인데 라벨 없이 가운데 정렬 | `h-12`(48px), `justify-center` | 값이 '누를 버튼'으로 읽힌다 |
| ③ 체크인·체크아웃·박수가 한 줄 한 굵기 | 14px 1줄 | 표면 규칙 ③ **숫자가 주인공** |
| ④ "1박"을 박스 안·밖에서 두 번 | 중복 1건 | 나중에 한쪽만 고쳐진다 |

## 2. 안 B — 분할 카드형

```
┌──────────────────────────────────────┐   테두리 0 · shadow-lift · rounded-2xl
│ 체크인          ⟨1박⟩         체크아웃 │   행 min-h 66
│ 09.14 월                    09.15 화 │   17px extrabold tabular-nums
├──────────────────────────────────────┤   border-rule (투명 잉크)
│ 인원                              ⌄  │   행 min-h 58
│ 성인 2                               │   15px bold
├──────────────────────────────────────┤
│ 체크인 15:00 · 체크아웃 11:00          │   12px 회색 각주
└──────────────────────────────────────┘
```

🔑 **가운데 배지가 두 날짜의 관계를 말한다.** 그래서 박수를 다른 줄에서 또 말할 필요가 없고,
④ 중복이 구조적으로 사라진다. 탭 영역은 48 → **66 / 58** 로 커졌다.

⚠️ **펼쳐지는 달력·인원 패널은 무접촉.** 2026-08-19 대표가 야놀자 기준으로 확정한 것이고,
이번 지적은 *닫혀 있을 때의 모습*이다.

**왜 안 A(티켓형)가 아닌가**: 밴드가 브랜드 색 '면'이라 화면에 파란 면이 하나 더 생기는데,
이 페이지엔 이미 하단 구매 버튼이 그 자리를 쓰고 있어 강조가 둘로 갈린다.

## 3. 두 상세가 같은 부품 — 뿌리는 토큰이 둘이었던 것

`.gbd`(공구 상세)가 **자기만의 토큰 세트**를 갖고 있었다. 라이트는 우연히 거의 같았는데
**다크가 갈라져** 있어서, 다크에서 공구 상세만 다른 앱처럼 보였다.

| | `.gbd` | 티켓 체계 |
|---|---|---|
| 다크 배경 | `#070809` | `#11141C` |
| 다크 카드 | `#141517` | `#1D1F29` |
| 다크 구분선 | `#2A2D31` | `#2C2F35` |
| 라이트 전반 | (거의 동일) | — |

**처방 둘**
1. **토큰**: `.gbd` 가 값을 체계에서 받아 온다(`var(--bg)` · `var(--surface)` …).
   마크업은 한 글자도 안 바뀐다 — 변수 155곳 그대로. 색을 바꾸려면 이제 한 곳만 고친다.
2. **부품**: `components/ticket/FieldCard`(`FieldCard`/`FieldSplit`/`FieldRow`/`FieldNote`).
   숙소의 '인원' 행과 공구 상세의 '수량' 행이 **같은 `FieldRow`** 다.

🩸 **같이 드러난 것**: `--gbd-line` 과 `--gbd-accent-soft` 는 **정의된 적이 없었다.**
`FcfsApplyBlock` 이 `border: 1px solid var(--gbd-line)` 을 쓰는데, 값이 없으면 그 선언이 통째로
무효가 되어 테두리가 `currentColor`(글자색)로 그려진다. 헤어라인이어야 할 자리가 진한 선이었다.

체계에 없던 두 단계도 토큰으로 올렸다 — `--ink2`(잉크와 보조 사이) · `--wash`(카드 안 옅은 면,
마크업이 이미 `bg-gray-100 dark:bg-white/[0.06]` 로 손으로 쓰던 값).

⚠️ **`--gbd-danger` 는 일부러 안 옮겼다.** 이쪽은 *빨간 면 위 흰 글자*라 대비 기준이 다르다
(경위: `discount-is-sale-red.test.ts`).

## 4. 주소 — 한 번 더 말하던 것이 아니라 틀린 주소였다

대표 스크린샷의 그 줄: `경북 경주시 · 경북 경주시 손곡3길 37-14`.

라이브 50건 전수 실측:

| | 건수 |
|---|---|
| 주소가 자체 지역을 갖고 있다 | **50 / 50** |
| 그중 시·군·구가 그대로 겹친다 | 38 |
| **지역 항목과 주소가 서로 다르다** | **12 (24%)** |
| 지역 없는 맨 주소 | **0** |

24% 는 중복이 아니라 **오표기**다. `region=강원 속초시` ↔ `address=강원특별자치도 양양군` 을
이어 붙이면 속초에 있지도 않은 숙소가 된다. ⇒ **주소 항목이 이긴다**(`shared/stay-address.ts`).
지역 항목은 검색·필터용으로 남긴다.

## 5. 숙소 소개 문구 — 치유가 절반만 되어 있었다

대표 화면: `경주의 펜션 — 독채형 펜션 — 바비큐 테라스와 프라이빗한 휴식.`

2026-08-31 에 이 조립문을 고치는 치유(`heal-stay-descriptions`)를 넣었는데 **읽히지 않는 칸만**
고치고 있었다. id 2764 실측:

```
products.description                → '테라스에서 바비큐를 …'    ✅ 고쳐져 있었다
product_stay_info.description_full  → '경주의 펜션 — 독채형 …'   ❌ 그대로였다   ← 화면이 읽는 칸
```

더 나쁜 것: 대상 선택이 `p.description LIKE '%—%'` 하나여서, description 이 고쳐진 순간
그 행은 **영영 다시 선택되지 않는다**. ⇒ 선택은 두 칸 중 하나라도 줄표가 있으면, 갱신은 두 칸 모두.
