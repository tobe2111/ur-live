## 0. 한 줄 결론

**막는 것은 결제가 아니다.** 예상과 달리 항목 3(소비자 결제)은 최대 갭이 아니었다 —
*"몰 주문을 도매 레일에 태우려 하면"* 막히지만, **소비자 레일에 태우면 구조적 장애가 없다.**

진짜 갭은 **항목 2(운영자 자체 상품 등록)** 다. 판매사에게는 **자기 상품을 만드는 경로가 아예 없다**
(재판매 복제만 존재). 사업설계가 *"상품은 그들이 갖고 온다"* 를 전제하는데, 그 입구가 없다.

## 1. 셀프 개설 — 🟡 최소 변경

### 지금 몰 하나를 여는 데 실제로 필요한 것 = **데이터 행 1개**

`POST /api/admin/wholesale-malls` (`wholesale-malls-admin.routes.ts:112`) 가 이미 존재한다.
`INSERT INTO wholesale_malls (slug, name, host, brand_name, brand_color, logo_url, deposit_account,
commission_rate, categories_json, requires_license, license_label, features_json, company_json, active)`
— **코드 커밋 불필요.**

> ⚠️ **"메디스타트 3커밋" 의 실체 정정**: 커밋 메시지로 3커밋을 찾지 못했다(`git log --grep` 0건).
> 실제로 레포에 남아 있는 것은 **`repair-schema.routes.ts:1997` 의 시드 행 1개**
> (`INSERT OR IGNORE INTO wholesale_malls … (2,'medi','메디스타트' …)`) + 위 어드민 CRUD API 다.
> ⇒ 선행 문서의 *"모드 C 는 신규 개발이 거의 없다"* 결론은 **유지되지만**, 근거는 "3커밋 선례"가 아니라
> **"몰은 데이터 행이고 CRUD API 가 이미 있다"** 로 바꿔 말해야 정확하다.

### 남은 것 — 운영자가 신청 즉시 갖게 하려면

| 갭 | 현행 | 필요 |
|---|---|---|
| 권한 | `requireSuperAdmin()` + adminApp(IP 화이트리스트 + audit) | 운영자-대면 **신청** 엔드포인트 + 승인 시 내부 호출 |
| 신청 큐 | 없음 | 신청 테이블(상태: pending/approved/rejected) |
| 운영자 귀속 | `sellers.mall_id` 컬럼 존재(`sellerMallIdOf`) | 승인 시 운영자 seller 행을 새 mall_id 에 귀속 |
| 도메인 | `host` 없으면 `?mall={slug}` 로 접근 | 자체 도메인은 **별건**(DNS·CF 설정 — 코드 밖) |

**최소 변경**: 신청 테이블 + 승인 훅에서 **기존 몰 생성 로직 재사용**(새 생성 경로를 또 만들지 말 것).
`requires_license`·`categories_json` 같은 몰 옵션은 기본값으로 두고 운영자가 나중에 편집.

> ✅ **즉시 개설의 실질 장벽은 낮다.** 다만 "신청 즉시"를 무승인으로 하면 아무나 몰을 열 수 있으므로
> 초기엔 **승인 게이트 유지**를 권한다(P0 파일럿 1~3명은 어차피 수동이 더 빠르다).

## 2. 운영자 자체 상품 등록 — 🔴 안 된다(현행) / 최소 변경은 레일 교체

### 확인된 사실

| 주체 | 자체 상품 생성 | 근거 |
|---|---|---|
| 제조사(supplier) | **있음** | `supplier-dashboard.routes.ts:441·553·1435` — `requireSupplier()` |
| **판매사(distributor)** | **없음** | `wholesale.routes.ts` 에 `POST /products` 부재. 유일 경로는 **재판매 복제**(`supply.routes.ts:333`) |
| 소비자 셀러 | **있음** | `products.routes.ts:91·98`, `seller-*` |

⇒ 사업설계의 *"자기 거래처 상품을 직접 등록 (우리는 소싱 0)"* 은 **현재 도매 레일에 입구가 없다.**
운영자를 판매사로 두면 남의 상품을 복제하는 것밖에 못 한다.

### 최소 변경 — **도매에 새 등록 경로를 만들지 말고, 소비자 셀러 레일을 재사용**

운영자를 **`sellers` 행(소비자 셀러)** 으로 두고 기존 소비자 상품 등록 경로를 쓰되, 저장 시
**`products.mall_id` 를 운영자의 몰로 스탬프**한다.

이 선택의 이유는 등록 편의가 아니라 **뒤따르는 레일 전부가 공짜로 붙기 때문**이다 —
소비자 결제(§3)·공구 엔진(§4)·픽업 확인(§5)·5% 정산(§6)이 전부 `products.seller_id` 기준으로 이미 동작한다.
도매 레일에 등록 경로를 새로 파면 그 넷을 **전부 다시 이어야 한다.**

**3분 등록(사진·가격·마감일·픽업일)**:
- 사진·가격 = `products` 기존 컬럼
- 마감일·픽업일 = **`product_supply_meta` K-V**(`gb_deadline` / `pickup_*`)
  🛡️ `products` 97/100 · `sellers` 100/100(한도 도달) → **ALTER 금지**(CI 차단). K-V 가 유일한 자리.

> ⚠️ **불변식 ④(매입가 컬럼 누수)가 여기서 더 중요해진다.** 운영자 몰은 노출면을 늘린다.
> 몰 상품 조회 라우트를 새로 만들면 `consumer-wholesale-separation.test.ts` ④의 파일 목록에
> **같은 커밋에서 추가**할 것(그 테스트는 열거된 파일만 본다 — 새 라우트는 자동으로 안 잡힌다).

## 3. 소비자 결제 — 🟢 된다 (단, 레일 선택이 전부다)

### 예상과 달랐던 점

지시서는 이 항목을 최대 갭으로 예상했으나, **조사 결과 최대 갭이 아니다.** 다만 *"도매몰 주문을
유어딜 결제 엔진에 태운다"* 라는 문장 그대로 구현하면 막힌다. 무엇이 막는지부터.

### 왜 도매 레일로는 안 되는가

도매에도 Toss 경로가 **있다** — `wholesale.routes.ts:1775 POST /orders/confirm` 이
`confirmTossPayment` 를 호출한다(CLAUDE.md 의 *"도매몰은 PG 미사용"* 은 `wholesale-plus` 기준 서술이라
**전면 참이 아니다**). 그러나 그 경로는:

- `sellerIdFrom(Authorization)` → **`seller_token` 필수**. 소비자에겐 없다
- `WHERE toss_order_id = ? AND distributor_seller_id = ?` → **판매사 스코프**
- 대상 테이블이 `wholesale_orders` (B2B 발주) — 소비자 주문 개념(배송/이용권/환불/리뷰)이 없다

⇒ **소비자는 구조적으로 이 경로를 못 탄다.** 태우려면 인증·스코프·테이블을 전부 뜯어야 하고,
그건 잠긴 결제 경로를 건드리는 대공사가 된다.

### 되는 방법 — 몰 주문을 **소비자 `orders`** 로 생성

운영자 상품이 `products`(`seller_id`=운영자, `mall_id`=몰)이면, 소비자 구매는 **기존 소비자 주문/결제
경로 그대로**다. `payment.routes.ts /confirm`(잠금 파일) **무수정**.

**몰 귀속은 컬럼 추가 없이 해석된다**: `orders` 에는 `mall_id` 가 없지만(확인함), 주문 라인의
`product_id → products.mall_id` 조인으로 몰이 나온다. ⇒ **`orders` ALTER 불필요**(컬럼 예산 회피).

### 진짜 선행 결함 — gb 가격이 결제에 안 붙는다

`resolveGbPricing`(`shared/gb-session.ts:141`) 소비처는 **`gb-marketplace.routes.ts` 2곳뿐**이다
(표시용). 소비자 구매 경로에 없다 ⇒ **공구가로 결제되지 않는다.**
이건 이 설계의 갭이 아니라 **이미 확정된 선행 작업**이며, 구현 착수 조건 그 자체다.

### 애매한 것

- **몰 브랜딩된 체크아웃**(운영자 이름으로 보이는 결제 화면) — 결제 엔진과 무관한 **UI 문제**.
  Toss 위젯 자체는 잠금 파일이므로 브랜딩은 주변 화면에서만.
- **몰별 수수료율**(`wholesale_malls.commission_rate`) 이 소비자 5% 와 어떻게 만나는지 — §6 참조.
  현재 그 컬럼은 **도매 마진 계산용**이고 소비자 정산과 연결돼 있지 않다. 연결하면 5% 불변식과
  충돌하므로 **연결하지 말 것**(§6).

## 4. 공구 엔진 `gb_mode` — 🟢 된다 (몰과 직교)

`gb_mode` 는 테이블 컬럼이 아니라 **`product_supply_meta` 의 K-V**(`shared/gb-session.ts:39`,
키 `gb_mode`/`gb_price`/`gb_deadline`/`gb_promo_pct`/`gb_link_only`). 어드민 조종석
(`AdminGbCockpitPage` → `gb-cockpit.routes.ts`)에서 **상품별로** 설정한다.

⇒ **유어딜 전용도, 도매 전용도 아니다.** 상품에 얹는 상태라 몰 컨텍스트와 직교한다.

**단서**: 소비자 노출은 `gb-marketplace.routes.ts` 가 `product_supply_meta` 를 조회해 만든다.
몰 스코프 목록이 필요하면 그 쿼리에 `products.mall_id` 조건만 추가하면 된다(구조 변경 아님).

## 6. 정산 — 🟢 운영자 = **merchant**. 새 요율 로직 불필요

### 이용권 원장의 역할 정의 (`worker/utils/ledger.ts:114 recordVoucherUsedLedger`)

| 파라미터 | 의미(코드 주석) | 새 모델에서 |
|---|---|---|
| `merchant_id` | **store_owner seller_id** — 이행 주체 | **공구 운영자** |
| `seller_id` | **인플루언서(위탁 판매 시)** — 소개자 | 인플루언서 레일 그대로 |
| platform | `platform_fee_pct`(기본 5%) | **유어딜 5% 불변** |

계산식: `merchantRate = 1 − platformRate − sellerRate`, `platformAmount = floor(order_amount × platformRate)`.

⇒ 운영자는 상품을 갖고 와 이행하는 주체이므로 **merchant** 다. `seller` 자리는 인플루언서용으로 비워둔다
(사업설계 §6의 인플루언서 레일이 **그대로 성립**한다 — 새 자리를 만들 필요가 없다).

### 5% 불변식

`유어딜 순수취 == 정확히 5%` 는 **그대로 성립한다.** platform 분은 고정 비율로 먼저 떼고 나머지를
merchant/seller 가 나누는 구조라, 운영자 몫이 커지든 인플루언서 몫이 커지든 **platform 분은 불변**이다.
대표 확정 원칙(*"성장 커미션은 5% 밖 매장 promo 재원"*)과도 일치한다 — 운영자=merchant 면
promo 재원이 **운영자 마진에서** 나온다.

> 🔴 **하지 말 것**: `wholesale_malls.commission_rate`(도매 마진용)를 소비자 정산에 연결하는 것.
> 몰별로 플랫폼 요율이 달라지면 5% 불변식이 깨지고 `[INV-CB]` 가드와 충돌한다.
> 몰별 차등이 필요하면 **merchant 몫 안에서** 처리할 것(플랫폼 분 무접촉).

## 7. 예치금 제거 후 성립 여부 — 🟢 성립. 동결과 충돌 없음

### 예치금의 현재 용도 (2곳)

| 용도 | 코드 | 새 용도에서 필요? |
|---|---|---|
| B2B 발주 결제 | `deductDepositForOrder`(`wholesale.routes.ts:1689`) | **불필요** — 운영자가 자기 거래처에서 직접 조달(우리는 소싱 0) |
| 프로 멤버십 연구독 차감 | `wholesale/plus` | **걸림** — §8 참조(초기 무료 전략과도 충돌) |

### 대체 수단

- **소비자 → 운영자**: Toss 카드결제(소비자 레일, §3)
- **운영자 정산**: 원장(`ledger_entries`) → 기존 payout. **새 수단 불필요**

⇒ 새 용도는 **예치금을 아예 안 쓴다.** 결제 수단이 예치금뿐이라는 전제 자체가 B2B 발주 모델의 것이고,
운영자 모델에는 B2B 발주가 없다.

### 동결 판단과의 충돌 — **없다. 오히려 정합**

동결(신규 충전 차단 → pending 처리 → 잔액 소진·환급 → 기능 OFF)은 **기존 판매사 잔액을 정리하는 작업**이고,
새 용도는 그 수단을 안 쓴다 ⇒ **동결이 새 사업의 장애가 아니다.**

> ⚠️ **단 1건 걸림**: `wholesale/plus`(프로 멤버십)가 예치금 차감이라, 동결하면 그 결제 수단이 막힌다.
> 새 용도에서 plus 는 제거 후보(§8)이므로 실질 문제는 아니나, **동결 순서 3단계(잔액 소진·환급) 전에
> plus 갱신 처리 방침을 정해야 한다**(기존 구독자가 있으면).
> ⇒ 예치금 숫자 확보 시 `wholesale_deposits` 뿐 아니라 **활성 plus 구독 건수**도 같이 볼 것.

## 8-B. `mall_id` 격리 축 판정 〔2026-07-29 대표 추가 지시〕

운영자 상품이 소비자 `products` 에 살면 격리 축이 **소비자↔도매 하나에서 셋으로** 늘어난다.
기존 불변식 ①~③은 **소비자↔도매만** 본다(`NOT (is_supply_product=1 AND supply_source_id=0)`).

### 🔴 먼저 — 지시서의 전제 하나가 성립하지 않는다

> *"(a) 본진 노출 경로에서 `mall_id IS NULL` 누락 시"*

**`mall_id IS NULL` 인 행은 사실상 없다.** `ALTER TABLE products ADD COLUMN mall_id INTEGER **DEFAULT 1**`
(`repair-schema:949`, `sellers` 도 :947 동일) — SQLite 는 non-NULL 기본값을 주면 **기존 행을 전부 그 값으로 채운다.**
⇒ **유어딜 본진 소비자 상품이 이미 전부 `mall_id=1`** 이고, **몰 1 = '유통스타트'** 다(`repair-schema:1995`).

즉 `mall_id` 는 지금 "본진이냐 몰이냐"를 **구분하지 못한다.** 판별자로 `IS NULL` 을 쓰면 아무것도 안 걸러진다.

> 💡 **더 중요한 구조적 사실**: 오늘 본진과 도매가 안 섞이는 이유는 `mall_id` 가 아니라
> **`is_supply_product`** 다(불변식 ①). 운영자 몰 상품은 `is_supply_product=0`(소비자 셀러 상품)이므로
> **그 보호막 밖으로 나온다.** 새 축이 위험한 근본 이유가 이것이다.

### (a) 본진 노출 경로에서 몰 조건 누락 → **운영자 상품이 유어딜 본진으로 샌다**

운영자 몰 상품은 `is_supply_product=0` 이라 기존 ① 필터를 **그냥 통과한다.** 누수 지점:

| 표면 | 결과 |
|---|---|
| 홈 피드 · `/browse` · `/vouchers` | 남의 몰 상품이 유어딜 본진 카탈로그에 섞임 |
| 검색 · 자동완성 | 동일 |
| **`sitemap.xml`** | **유어딜 도메인으로 운영자 상품이 SEO 색인됨** — 되돌리기 가장 어려움 |
| 링크샵 추천 피드 · 공구 피드 cron 캐시 | 캐시에 구워져 TTL 동안 잔존 |

⇒ 본진 큐레이션·정체성 붕괴 + 몰별 브랜딩이 무의미해진다.
(운영자에겐 본진 노출이 이득처럼 보이지만, 그건 **정책 결정**이지 기본값이면 안 된다.)

> 🔴 **sitemap 은 별도 순위다 〔2026-07-29 대표 지시〕.** 위 표의 다른 경로는 **배포 한 번으로 되돌아간다** —
> 조건을 고치면 다음 요청부터 안 나온다(캐시는 TTL 로 빠진다). **sitemap 은 안 그렇다.**
> 색인은 우리 배포와 무관하게 **검색엔진 쪽에 남고**, 회수는 재크롤링·삭제요청에 달려 있어 **시간과 통제권이
> 우리에게 없다.** 잘못 나간 URL 이 검색 결과에 뜨는 동안 운영자 상품이 유어딜 도메인 자산처럼 보인다.
>
> ⇒ **순서 고정: `sitemap` 몰 가드가 첫 운영자 몰 개설보다 먼저 들어가야 한다.**
> 몰을 먼저 열고 가드를 나중에 붙이면, 그 사이에 색인된 것은 코드로 못 되돌린다.
> 대상: `src/worker/routes/sitemap.routes.ts`(불변식 ① 이 이미 2회 검사 중인 파일 — 몰 조건을 같은 자리에 추가).

### (b) 몰 조회에서 `mall_id` 누락 → **몰에 유어딜 본진 카탈로그가 통째로 뜬다**

기본값이 1이라 **기존 소비자 상품 전부가 `mall_id=1`**. 몰 조회가 조건을 빠뜨리면 그 몰 화면에
유어딜 전체 카탈로그가 노출된다. "자기 이름의 판"이라는 제품 약속이 첫 화면에서 깨진다.

> 현재 유통스타트/메디스타트 몰이 이 사고를 안 겪는 이유는 도매 쿼리가 **`is_supply_product=1` 로
> 자체 필터**하기 때문이지 `mall_id` 때문이 아니다. 운영자 몰은 그 필터를 못 쓴다(=0 이므로).

### 판별자 — ✅ **확정(2026-07-29 대표 채택)**

| 축 | 조건 | 비고 |
|---|---|---|
| 본진 노출 | 기존 ① 조건 **AND `COALESCE(mall_id,1) = 1`** | 유통스타트(=1)는 ①이 이미 제외 |
| 몰 조회 | **`mall_id = :mallId`** | 신규 운영자 몰은 **id ≥ 3** 보장(1=유통스타트, 2=메디스타트) |

- ❌ `mall_id IS NULL` 을 판별자로 쓰지 말 것(위 이유)
- ⚠️ `mall_id` 컬럼은 `repair-schema` best-effort ALTER 라 **미적용 환경 가능성**이 있다 →
  소비자 경로는 `dominant_color`/`referral_commission_rate` 선례처럼 **컬럼 부재 내성**(1회 감지 후 제외) 필요

### (c) 행위 테스트로 환원 — 🟡 **부분 가능. 단 ④의 열거식은 반복하지 말 것**

**문제 규모(실측)**: 소비자 디렉터리에서 `FROM products` 를 읽는 파일이 **37개**인데,
불변식 ①~③이 검사하는 파일은 **6개**다. 나머지 31개는 무방비이고, **새 파일은 자동으로 안 잡힌다.**
불변식 ④도 같은 열거식이라 같은 약점을 갖는다.

환원 설계 — 두 축을 나눠야 한다:

| 축 | 방법 | 자동 커버 |
|---|---|---|
| **정확성**(조건이 실제로 SQL 에 실리는가) | **행위 테스트** — fake D1 로 발행 SQL 캡처(`supply_price` 가드에서 검증된 기법). 텍스트 매칭이 아니라 실제 방출 SQL | 지정 진입점만 |
| **커버리지**(빠뜨린 파일이 없는가) | **래칫** — 소비자 디렉터리에서 `FROM products` 를 읽는 파일 목록을 baseline JSON 으로 동결. **새 파일이 나타나면 실패**, 고치는 법은 ①스코프 헬퍼 사용 ②검토 후 예외 등록 | **새 파일 자동** |

레포에 이미 같은 래칫 선례가 있다(`file-size-baseline.json` · `utc-date-baseline.json`).

**권장 구조 — 초크포인트**: 소비자 상품 노출 WHERE 를 **단일 헬퍼**(예: `consumerVisibleProductsWhere()`)로
모으고, 행위 테스트는 그 헬퍼가 두 조건(도매 원본 제외 + 몰 격리)을 모두 내는지 확인,
래칫은 "헬퍼를 안 쓰면서 `FROM products` 하는 새 파일"을 잡는다.

> ⚠️ **완전 자동은 아니다**(정직하게): 진입점 지정과 예외 등록은 사람이 한다.
> 래칫이 보장하는 것은 **"새로 생긴 것이 조용히 빠지지 않는다"** 이지 "모든 경로가 옳다"가 아니다.
> ⇒ 이 한계를 테스트 주석에 명시할 것(CLAUDE.md "못 막는 범위 명시" 룰).

**착수 시 같은 커밋에서 할 일**: 위 **몰 격리 래칫 신설**.

> ✅ **불변식 ④ 는 2026-07-29 에 래칫으로 승격 완료**(대표 승인) — 더 이상 파일 열거식이 아니다.
> 소비자 디렉터리(`features/products`·`features/group-buy`·`worker/routes`·`worker/cron`)를 glob 으로 훑고
> `scripts/consumer-cost-column-baseline.json` 에 등록된 파일만 예외로 둔다. **새 몰 라우트는 자동 검출**된다.
> ⇒ 착수 시 ④ 목록을 손으로 갱신할 필요가 **없어졌다**(이전 지시 무효).
> 되돌려-검증 3종 완료: 새 파일 매입가 노출 / 스캔 경로 헛돎 / baseline 죽은 예외 — 전부 빨강 확인.

## 8-C. 열린 항목 — 몰 1 의 의미 겸용 (지금 결정하지 않는다)

**현상**: `mall_id = 1` 이 지금 **두 가지를 동시에** 뜻한다.
1. **유어딜 본진** — 모든 기존 소비자 상품(`DEFAULT 1` 로 채워진 값)
2. **유통스타트 몰** — `wholesale_malls` id=1 의 실제 몰

§8-B 의 판별자(`본진 = ① AND COALESCE(mall_id,1)=1`)는 **이 겸용 상태를 전제로 성립한다** —
유통스타트 상품은 `is_supply_product=1` 이라 ①이 이미 걸러주기 때문에 지금은 안 부딪힌다.
즉 **오늘은 동작하지만, 두 의미가 우연히 안 겹치는 덕분**이다.

**장기 위험**: 유통스타트 몰에 소비자 상품(`is_supply_product=0`)이 하나라도 생기면 그 순간
본진과 구분이 사라진다. 운영자 몰이 늘어날수록 "1 = 본진"이라는 암묵 가정이 코드 여기저기에 스며든다.

**선택지(판단 보류)**

| 안 | 내용 | 비용 |
|---|---|---|
| A. 현행 유지 | 겸용 그대로 + ① 의존 | 0. 단 위 가정이 깨지는 날 조용히 샌다 |
| B. 본진에 전용 값 부여 | 본진 = `NULL` 또는 `0`, 몰 = 1..N | **라이브 데이터 마이그레이션**(전 상품 UPDATE) + 전 쿼리 동시 수정 |
| C. 유통스타트를 새 id 로 이전 | 1 = 본진 예약, 유통스타트 → id≥3 | 도매 데이터 이전 + host 매핑 변경 |

> 🔴 **지금 결정하지 않는다 〔2026-07-29 대표 지시〕. 착수 전 라이브 스키마 변경도 하지 않는다.**
> 이 절은 **항목으로만** 남긴다 — 결정 시점은 운영자 몰이 실제로 늘어나 겸용이 부담이 될 때다.
> 그때까지는 §8-B 판별자로 충분하며, **신규 몰에 id 1·2 를 절대 재사용하지 않는 것**(id ≥ 3)이 유일한 전제다.
