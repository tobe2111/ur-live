# 런북 — 인플루언서 유입 관통 필드테스트 (실기기·실결제)

> 목적: "인플루언서 링크를 처음 타고 온 신규 사용자"의 전 여정을 **실기기에서 한 번에 관통**시켜 어디서 끊기는지 본다.
> 왜 필요한가: 코드가 있다는 것과 실기기에서 돈다는 건 다르다. 자동화 환경(샌드박스)은 프록시 TLS 제약으로 브라우저 부팅·실결제·카톡 인앱을 못 돌린다 → **이 문서는 대표/팀이 실기기로 직접 실행**한다.
> 실행 조건: 스테이징(또는 프로덕션 소액) 실결제 1회 + **iOS 카톡 인앱 1회 + Android 카톡 인앱 1회**.

각 단계: **정상 / 깨짐 / 느림** 판정 + 📸 스크린샷. 특히 **A-2(링크샵 홉) · A-3(미충전 신규자) · A-4(인앱 OAuth)** 세 곳이 전환 병목이므로 집중 관찰.

---

## 준비물
- 인플루언서 역할 계정 1개(A), 신규 방문자용 **새 카카오 계정**(B, 한 번도 로그인 안 한 기기/계정).
- 소액 결제 수단(딜 충전용) + 매장 사장님 계정(C, QR 사용 처리용) 또는 매장 PIN.
- 어드민 콘솔 접근(원장·정산 확인, 게이트 토글).
- 기록지: 아래 표를 인쇄하거나 메모앱에.

## 시나리오 A — 신규 방문자 구매 관통 (가장 중요)

| A-1 | 인플루언서 링크 수신 | A 계정으로 딜 상세에서 공유 → 나온 `?ref=` 링크를 **카톡으로 B에게 전송** → B가 **카톡 인앱 브라우저에서 열기** | 링크샵(`/u/핸들`) 또는 딜 상세가 뜸 | 링크샵 첫 화면 | 정상 / 깨짐 |

> A-4 참고(코드 사양): 카톡 인앱은 UA 감지 후 iOS는 `kakaotalk://web/openExternal`, Android는 `intent://…chrome` 으로 외부 브라우저 유도(무한루프 sessionStorage 가드). iOS 세션은 same-origin 200 응답으로 `ur_session` 쿠키 영속. **복귀 시 pending_pin/returnUrl 보존 여부가 관건.**

### A-3 이탈 기록 양식 (서초 실측용 — 카드 직결제 도입 판단 근거)
> 카드 직결제(이용권 토스 직결) 도입 여부는 **지금 판단하지 말고 이 데이터로.** 인플루언서 유입 = 첫방문 = 미충전이 대부분이라 여기 이탈률이 크면 "이용권도 토스 카드 직결제 허용"이 필요.

| 일자 | 유입 인플루언서 | 링크 클릭(명) | 상세 도달(명) | 구매 시도(명) | **충전 화면서 이탈(명)** | 충전 완료·결제(명) | A-3 이탈률(%) | 메모(왜 이탈?) |
|---|---|---|---|---|---|---|---|---|
| | | | | | | | | |
| | | | | | | | | |

- **A-3 이탈률 = 충전 화면서 이탈 ÷ 구매 시도.**
- **판단 기준(제안)**: 3개 상권/2주 누적 **A-3 이탈률 ≥ 40%** 면 카드 직결제 도입 착수. < 25% 면 현행 딜 유지. 25~40% 면 "충전 UX 단축(원터치 충전+즉시결제)" 먼저.
- 정성 메모 필수: "충전 금액 입력이 번거로움" / "카드로 바로 사고 싶었음" / "딜이 뭔지 몰라 이탈" 등.

## 시나리오 B — 소개비(promo) 재원 확인 (원장)

### B-6 (현행 기본) — 소개비가 **어디서** 나가는지
1. 어드민에서 `promo_funding_source` 확인 → **미설정/`platform` = 플랫폼 부담(현행)**.
2. A 관통에서 발생한 그 주문의 정산 원장을 어드민에서 조회.
3. **확인**: 어필리에이트 2%가 **플랫폼 5% 안에서** 나갔는가(매장 정산액은 판매가−5% 그대로, 어필리에이트는 그 5%에서 빠짐)? → **현재 코드상 사실. 이게 리졸버 전환의 이유.**
   - 판정: ☐ 플랫폼 부담 확인 ☐ 예상과 다름(사유 기록)

### B-7 (매장 promo% 필드 활성 후) — 매장 promo% 건 딜
> 선행(순서 중요 — 자산 누수 방지): ① 먼저 **`promo_funding_source = owner`**(재원을 매장 부담으로) staging 검증 → ② 그 다음 **`seller_promo_field_enabled = true`**(셀러 폼에 소개비% 필드 저장 = `products.referral_commission_rate`) + 클라 플래그 `SELLER_PROMO_FIELD_ENABLED` 배포. ⚠️ **owner-funding 을 먼저 켜지 않고 필드만 켜면 매장 소개비를 플랫폼이 부담(누수)** — 어드민 힌트 그대로.
1. 매장(사장님/어드민)이 이용권 등록 시 **"추천 소개비 %"** 를 예: 20% 로 설정(게이트 ON 이라 폼에 필드 + 실수령 마진 계산기 노출). → `products.referral_commission_rate=0.20, referral_enabled=1` 저장.
2. 그 이용권을 **추천 링크(`?ref=`) 경유**로 신규자가 구매 → 매장에서 사용(QR/PIN).
3. 어드민 원장 확인:
   - ☐ 추천인(A) 딜 적립 = **20%**(referral_commission_rate override 적용 — resolveCommissionRate)
   - ☐ **매장(`merchant:{id}`) 원장에 promo debit 1행** = 그 적립액(owner-funding, `debitOwnerPromoForOrder`)
   - ☐ **플랫폼 revenue 는 5% 온전**(promo 가 5%를 안 깎음)
   - ☐ **환불 시** promo debit 역전(매장 receivable 복원) + 어필리에이트 clawback
4. 통과하면 프로덕션 flip 검토. 실패하면 두 게이트 OFF 로 즉시 원복(라이브 무영향 — 둘 다 기본 OFF).

> ⚠️ **알아둘 한계(현재 owner-funding 은 전역 스위치)**: `promo_funding_source=owner` 는 **모든** 어필리에이트를 매장 부담으로 돌린다 — promo% 를 안 건 상품(기본 2%)까지 그 매장이 부담. 상품별로 "promo 건 것만 매장 부담"으로 좁히는 per-product funding 은 설계 문서의 미래 개선(§3-D 주석) 참조. 초기(소수 매장·전부 promo 설정)엔 전역 스위치로 충분.
